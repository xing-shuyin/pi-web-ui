# AGENTS.md — pi-web-ui 项目指南

> 本文件是给 AI 编码助手（pi / Claude Code / Cursor 等）看的高层项目说明书。
> 详细文档按主题分拆在 `docs/` 目录下。
> 修改本文件后，在 pi 中运行 `/reload` 生效。

## 1. 项目是什么

pi-web-ui 是 pi 编码智能体（`@earendil-works/pi-coding-agent` SDK）的 Web 聊天界面：
浏览器里对话、查看文件树、附加文件、内置终端（xterm.js + node-pty）、模型管理、
声音提醒、中英文切换。一条命令可跑（`pi-web-ui`），可 Docker / systemd / launchd /
Windows 计划任务部署。
另有 **Electron 桌面壳**（`desktop/`）：随机空闲口起同一个 server + BrowserWindow，网页版零改动；
Windows 安装包随 GitHub Release 发布（CI 出包，当前未签名，见 `desktop/README.md`）。

- 仓库（公开）：`git@github.com:xing-shuyin/pi-web-ui.git`
- npm 包：`pi-web-ui`（发布者 npm 账号 `xingshuyin`）
- Node 要求：**>= 22.19.0**（pi SDK 的 dist 使用了 `import … with { type: "json" }` 语法）
- 版本：`package.json` 与 `package-lock.json` 两处同步维护

## 2. 技术栈

| 层     | 技术                                                                          |
| ------ | ----------------------------------------------------------------------------- |
| 后端   | Node + Express（静态 + `/api/health`）+ `ws`（`/ws` WebSocket 协议）          |
| 前端   | React 19 + Vite 8 + react-markdown + highlight.js + xterm.js                  |
| 智能体 | `@earendil-works/pi-coding-agent` SDK（进程内，读 `~/.pi/agent` 配置）        |
| 终端   | node-pty（服务端 PTY）+ `@xterm/xterm`（浏览器渲染，经 terminal bridge 转发） |
| 样式   | 单文件 `web/src/styles.css`（CSS 变量主题，深色）                             |

## 5. 开发工作流

> 详细文档见 `docs/development.md`

```bash
npm run dev          # 并行：node --watch 后端(:8788) + vite 前端(:5173)
npm run typecheck    # 双端 tsc --noEmit（提交前必跑）
npm run format       # prettier 全仓库格式化（提交前必跑；只检查用 format:check）
npm run lint         # oxlint（未使用变量/危险模式；提交前必跑；自动修用 lint:fix）
npm run build        # build:web (vite) + build:server (tsc)
npm start            # 跑编译产物 dist/server/index.js（生产）
npm test             # vitest 纯函数单测
npm run test:smoke   # 零 token 协议冒烟聚合跑器
npm run desktop:dev  # Electron 桌面壳指到本地 sidecar（:随机口，需先 npm run build）
npm run build:extension  # 打包 page-picker 浏览器扩展（esbuild → plugins/page-picker/extension/dist/）
npm run pack:extension   # 打浏览器扩展 zip → release/（打 tag 时 CI 自动出包并挂 Release）
npm run desktop:dist # 本地打桌面安装包 → release/（gitignore；CI 也跑同一条）
```

**关键约定**：缩进用 Tab；i18n 走 `useT()`（核心只含 `zh`/`en`，其余语言是 `locales/*.json` 可下载语言包、不进 npm，缺 key 自动回落英文；新 key 加 zh+en 即可，`tests/unit/locales.test.ts` 锁 key 对齐；8 个语言包也要同步加 key 且顺序与 zh 一致）；服务端多语言（issue #91）：`server/i18n.ts` 中英内联 + 翻译表（v2）。`resolveServerLang` 只做归一（zh-CN→zh、pt-BR→pt，空→en）；`pick(lang,zh,en,key?)` 第 4 参数是全局唯一翻译 key（`<模块>.<slug>`，如 `subagents.list.empty`），zh 走内联中文、其他语言查表、缺表/缺 key 回落英文；多行块用 `getServerBlock`（表里存 `\n` 拼接的一行）；tool definition 用 `bilingual(en,zh)` 静态双语（无 key，模型看英文无碍）；模板内容/用户覆盖保持 zh/en 字段（配置品，不进表）。第三语言的表放在语言包的 `serverStrings` 节（与 `strings` 同文件、一次下载全带走，`validatePack` 校验；缺 key 自动回英文所以部分翻译可安全上线）；服务端启动 + 包安装/删除时经 `loadServerStrings`/`unloadServerStrings` 注册。浏览器经 `hello.locale`/`set_locale` 上报 UI 语言（`client-state.json` 的 `locale` 持久化，切换经 settings reload 通道自动应用）；maker 统一收可选 `lang?: () => ServerLang`，推 UI 的 notice 走 `text`+`textEn` 双字段（前端按 locale 自选）；样式全部在 `styles.css`；新增协议消息只改 `protocol.ts` 再两端 switch 加分支；**前端新增服务端 URL（`/ws`、`/api/*`、`/plugins/*`、`/themes/*`）一律用 `web/src/base-url.ts` 的 `appUrl()` 包一层**（nginx 子路径反代依赖应用根前缀，裸写根路径会在子路径部署下 404）。

**测试规范**：端口隔离（≥8900）；data-dir 隔离（`mkdtempSync`）；精确清理自己进程；不允许 `pkill -f` 杀全局。

## 9. 常见坑

- **服务活着时跑 `npm run build` 会黑屏**：vite 先清空 `web/dist` 再写新文件，构建窗口内打开页面，`index.html` 与 hash 产物对不上；旧版里缺失的产物会穿透 `express.static` 落进 SPA catch-all 回 200 的 HTML，浏览器当 JS 执行失败，且 SW 会把它按 200 缓进 STATIC_CACHE（之后服务恢复了也好不了，必须 Unregister SW）。正确姿势：先停服务 → build → 启动 → 黑页标签 Unregister SW 后重载。服务端已加 `/assets/*` 等缺失 404（不再回 HTML）、SW 只缓存 content-type 对得上的资源。

- **改了 `protocol.ts` 后忘了在两端 dispatch/onmessage switch 加分支** → 前端收到未知消息类型被 switch 静默丢弃，表现为"没反应"。先跑 `npm run typecheck`。

- **toolResult 的 `details` 现在会下发浏览器**（`server/serialize.ts`，JSON ≤64KB 才带、超限**整丢**；随会话文件持久化，重放后还在）：`present_files` 的卡片数据、`ask_user_question` 的答案、`todo_list` 都走它，前端不必为了一点元数据再打一次 HTTP。两个坑：**新增自定义工具时别把大块内容塞进 details**（bash 的 details 里带整份 output，小输出会因此翻倍进快照；工具作者要自己封顶，见 `present-files-tool.ts` 的摘录预算）；**前端要有「拿不到 details 也能渲染」的兑底**（present_files 卡片就是「工具参数解析 + 可选 details 增强」，见 `web/src/present-items.ts`）。

- **新增可开关的 Agent 工具要动两处**：① `server/tool-manager.ts` 的 `AGENT_TOOL_CATALOG` 加一项（开关的唯一事实源；「其他」组同时给 `descKey`/`offHintKey` 文案 key，顺序即设置页渲染顺序；`todo_list` 例外固定 markers 分区）② `server/agent-service.ts` 的 customTools 注册（DSH 除外，它无 customTool 注册面）＋ `tests/unit/tool-registration.test.ts` 的 FACTORY_TOOLS 给工厂登记产出（逼着当场决定入目录还是内核）。设置页「其他」组按目录循环渲染（`OTHER_AGENT_TOOLS`），不再手写行。历史教训：`skill` 与 `present_files` 都曾只有目录、设置里找不到开关；`claim_files` 更惨——连目录都没进。两道静态守卫：注册→目录（tool-registration，含 bash/read 永不入目录）＋目录→设置行（settings-tool-rows），否则 CI 直接报红。工具名字符串只在 tool-manager 定义，工具模块 import＋re-export（present-files/skill/conversation_read/claim_files/delegate_task 模式）。
- **nginx 子路径部署（页面在 /pi/ 下）插件/WS/API 加载失败** → 大概率是新增的请求路径没走 `appUrl()`（见关键约定），请求落在网站根绕过了 `location /pi/` 的剥离转发；排查时先看浏览器 Network 的请求带没带 `/pi` 前缀。
- **快照 60ms 节流**：调试时 `get_state` 可立即推一次（`cs.flushSnapshot()`）。
- **snapshot 发送背压**：`send()` 在序列化之前检查 `ws.bufferedAmount`，超过阈值时丢弃 snapshot（全量幂等且稍后必有更新）；丢弃时安排 250ms 重试 timer。
- **`hello` 前/会话未就绪时的命令**：`server/index.ts` 的 `pending` 队列会缓存并在 attach 后重放。
- **clientId 每标签页独立**（issue #10）：前端 `getClientId()` 存 sessionStorage（非 localStorage），同源多标签页是多个独立客户端。回归：`multi-tab-test.mjs`。关浏览器重开 = 新 clientId，旧 ClientSession 变残留：**无其他在线浏览器时 attach 自动认领**最近断开的有内容残留（只换 map 键、不搬 runtime；首帧推送前必须按新 id 重接 `wireClient`，否则把自己当“另一处”），有在线标签时不认领（跑着的照常走 elsewhere 只读 + 双写拦截）。回归：`tests/orphan-adopt-test.mjs` + `tests/unit/orphan-adopt.test.ts`。**手动过户**：右键 elsewhere 行 → `take_over_conversation` 把整段对话（含子代理后代、等答复问卷/页调用、看门狗剩余计时）搬到本页并切过去（搬 runtime 本体，单 writer 不变；id 撞车时搬入方改名；源 active 自动修好，双方通知；源页旧对话框经 question_retracted 同步收起）。elsewhere 口径 = 运行中 + 源会话仍持有的已结束空闲对话（`isStreaming:false` + `sessionFile`，结束后仍可过户查看；空白对话不入列）。**新标签/切项目不再自动恢复别处持有的会话**：最近文件被其他在线客户端持有（跑着或空闲）时空白落地 + 提示去向（之前只拦 running，空闲照样恢复出第二个 writer，两边轮流发送分叉历史）。回归：`tests/takeover-test.mjs` + `tests/idle-takeover-test.mjs`（结束后过户 + 空白落地）。**过户搬不动工具闭包**：`ask_user_question` / `browser_page` 是建 runtime 时把当时的 ClientSession + conversationId 闭包进去的，过户只搬对话 —— 所以这两条桥接在**调用瞬间**按 runtime 身份解析「现在谁持有它」（`ClientSession.bridgeTarget` + `findConversationHome`，锚点是稳定的 `created.session` 对象而不是会改名的 conv id）；否则过户后新提问的 question_pending / page_request 会推给**过户前那台设备**（持有方收不到、老设备上那张问卷还不进快照 → 刷新即丢，pi 引擎问卷不超时 ⇒ run 永远挂住）。**跨页作答**：点 elsewhere 行的 `?` 经 `peek_elsewhere_question` 把问卷原文拉到本页弹框，`question_answer` 带 `owner` 由持有方 resolve（本页只展示/关闭，id 对方作用域、不进 answered 集合；问卷消失则明确通知）。别处列表靠运行签名驱动其他页重推（覆盖空闲行：流式→空闲、空闲行出现/消失都重推；问卷态已计入签名，挂起/解决不改变流式集合，不带它已打开的页看不到 `?`）。回归：`tests/remote-answer-test.mjs`。回归：`tests/takeover-test.mjs`。
- **`host.schedule` 的超长延迟会溢出成 1ms（死循环）**：宿主用 `setTimeout(next - now)` 引爆，而 Node 的 setTimeout 延迟超过 2^31-1ms（≈24.8 天）会被**静默截断成 1ms**（打一条 `TimeoutOverflowWarning`）；旧版 `nextCronFire` 在「一年内找不到」时还会回一个 366 天后的哨兵值。两者相遇 = 「1ms 后再触发 → 插件回调写盘/广播 → 再排下一次」的死循环（`{monthly, dom:31}`、`0 9 1 1 *` 都是合法且常见的触发档位）。现在 `armDelay()` 把延迟切成 ≤6 小时的分片、醒来重算，`nextCronFire` 找不到回 `null`（后台面板显示「不再触发」）。插件侧也有一条硬规则：**别把远期 cron 交给 `host.schedule`**（notes 插件只挂一条 `* * * * *` 巡检，每条提醒自带 `nextDue` 落库）。回归：`tests/plugin-cron-overflow-test.mjs`（5 秒内 0 次触发才算过）。
- **socket 半开**：服务端每 2s 发送一次心跳并携带主机资源指标；客户端 30s 无消息主动断开重连（指数退避 1s→10s）。
- **预览与附件行号**：`countLines` 不算尾随换行；前端 `split("\n")` 后也要 pop 掉末尾空串。
- **Windows 老中文文件乱码**：预览/内联附件/行附件统一走 `decodeText`（严格 UTF-8 失败 → GBK → latin1）。
- **Windows 窗口最小化后收不到桌面通知**（Win11 + Edge/Chrome 实测，2026-09）：最小化后 `document.hasFocus()` 仍为 `true`、`visibilityState` 仍为 `"visible"`，连 `blur`/`visibilitychange` 都不发 —— 只有原生窗口矩形会变（`screenX/screenY` 变成 -21334（Edge）/-32000（Chrome）、`outerWidth/Height` 塌成标题栏 108×20 / 160×28）。判定全在 `web/src/notify.ts`（`isCollapsedWindow` + `shouldSuppressNotify`，纯函数 + 单测）；Windows 上还额外要求「最近 2 分钟内有页面交互」才肯吞掉通知（焦点/可见性本来就在骗人，宁可多提醒也不静默）。**另一个坑：通知不能带 `tag`** —— Windows 把同 tag 的新通知当成「替掉旧条目」而且静默（没横幅、没提示音），只要通知中心里还留着一条 pi-web-ui 通知，后面每条都会被无声替换（`showNotification` 仍然 resolve，页面上看不出问题；`renotify: true` 实测救不回来）。排查入口：顶栏声音下拉 → 通知块底部的「发送测试通知」按钮（`NotifyToggle.tsx` 的 `SHOW_NOTIFY_TEST_PANEL` 常量，默认关闭，排障时改成 `true`），它显示实际通道（sw/page）、浏览器是否真的持有这条通知（`getNotifications()` 计数）与判定依据（焦点/可见性/最小化/空闲）。
- **模型列表刷新 = 官方目录整表替换（非并集）**：内置服务商（opencode-go 等）的模型目录来自 pi.dev（`https://pi.dev/api/models/providers/<id>`），`server/patch-remote-catalog.ts` 在启动时幂等改写 SDK 的 `remote-catalog-provider.js`，使 `getModels` 在远程数据存在时**整表返回官方目录**（无内置旧模型残留、无“新增 N 个”合并）；`listModels()` 先 `mr.refresh({ allowNetwork: true })` 与官方接口校验（SDK 4h 窗口内走 304）。注意：改 `node_modules` 的补丁在 `npm install`/SDK 升级后会失效，服务重启时自动重打；SDK 源码结构变化时自动跳过（回落 SDK 默认并集语义，不崩溃）。验证：`tests/scratch/verify-patch.mjs`。
- **PI_WEB_TOKEN 改口令后旧 cookie 卡死**（issue #71）：有效 token 请求会刷新 `pi_web_token` cookie 为当前值，401 且带失效 cookie 时自动 Expire——用户改了口令后**一次正确的 `?token=` 进入即永久恢复，无需清缓存**；别再实现「仅在无 cookie 时才下发」的旧逻辑（那是卡死根因）。回归：`tests/token-auth-test.mjs`。
- **`pi_web_token` cookie 存的是 `encodeURIComponent` 后的值**（issue #261）：cookie-value 只允许 ASCII，所以 `=` / `+` / 空格 / 非 ASCII 口令必须转义才能下发——**读取时一律先解码再和 `AUTH_TOKEN` 比**（`server/auth-cookie.ts` 的 `decodeCookieToken`，脏值解不开就原样返回）。反例（曾经的真 bug）：拿 `encodeURIComponent(AUTH_TOKEN)` 去比，于是 base64 口令尾巴上的 `=` 被存成 `%3D`，带 cookie 的请求全 401——表现为「`?token=` 那一次 200，之后每个资源都 401」。手写/旧客户端的明文 cookie 也要继续接受（`requestTokens` 两种候选都试）。
- **CSS 变量引用必须先有定义**：`var(--ghost)` 引用一个全仓没有 `--ghost:` 声明的变量按规范是 guaranteed-invalid —— 整条声明在计算值阶段失效（`background` 直接没背景、`box-shadow` 连投影与聚焦光环一起丢），带 fallback 的则静默用硬编码值（浅色主题下必是深色块）。`--bg-elev1`（正确名 `--bg-elev`）全史未定义还被 10 处引用，goalbar 因此一直没填充。回归靠 `tests/unit/css-tokens.test.ts`（静态体检，CI 必跑）；新增豁免（运行时注入的变量、刻意的中性兜底）要在该测试的豁免表里写上理由。
- **插件 UI 扩展点的 slot 必须两端同口径**：manifest `ui` 与运行时 `host.ui.register()` 走的是**同一套**别名映射 + 枚举校验（`UI_SLOT_ALIASES` / `UI_SLOTS`，见 `server/plugins.ts`），只改一边就会变成“注册了但界面上没有”—— 前端 `buildUiSlots` 遇到不认识的 slot 是**静默丢弃**，最难排。条目全局 id 是 `<pluginId>:<itemId>`、内置条目是 `host:<name>`；合并优先级固定为「宿主默认 < 插件贡献 < 插件 arrange < 用户偏好」，**用户偏好永远最后说话**。
- **新增「可隐藏 / 可排序」的宿主入口必须在渲染组件里接上 slot**：布局页的勾选框与 ↑↓ 只对**真按 slot 列表渲染**的东西生效。顶栏整条与底栏整条由 `TopBar.tsx` / `FooterBar.tsx` 里的 `hostNodes` 节点工厂 + `uiPrimary`/`bottombarItems` 顺序驱动（顶栏是**单一扁直流**：slot 顺序直排、align 只决定落两个 spacer 划出的哪一段，无任何按种类包裹的容器、无贴边例外；放不下/被隐藏的入口落进「⋯」溢出菜单：菜单型整块搬组件、动作类走 `dispatchHostOverflow`），消息工具条由 `Message.tsx` 跳 `hidden`，右栏 tab 由 `RightPanel.tsx` 按 `uiRightPanelTabs` 顺序渲染，输入框/文件预览/目标条/SCM/终端/左栏分区同理（各组件的 `*HostNodes` + `renderMergedToolbar`，见 `web/src/slot-toolbar.tsx`）。**加新入口忘了这一处 = 一个点了没反应的勾选框**（历史上就这么退化过）。另外：slot 数据没传时要退化成「按内置默认顺序全画」，别把整条顶栏/底栏清空。回归：`tests/ui-layout-ui-test.mjs`（真 Chrome，不入 run-smoke；含 #162 的 elementFromPoint 可见可点断言）。
- **顶栏平铺化（方案 A）的两条硬规则**：① 渲染层不得再加按种类分组的容器（`.brand` / `.view-switch` / `.topbar-desktop` 已全部删除）—— 跨类调序会把组撕成两截，而且手机端会退化成「一整组被 CSS 藏掉」；条目外观一律挂在条目自己身上（`.chip` / `.tb-tab` / `.plugin-topbar-item` / `.panel-toggle`）。②「放不下」与「被隐藏」必须走**同一个**「⋯」菜单、且由**实测宽度**决定（`web/src/topbar-fit.ts` 纯函数 + `TopBar` 的 ResizeObserver：宽度按 id 缓存，被丢进菜单的条目量不到宽度，缓存才能让它在窗口变宽时回来；宽度为 0 的条目（桌面端 CSS 藏起的 ☰/📁）不占位也不进菜单；测不到宽度时全保留）。手机端不再有第二套硬编码「⋯」面板，桌面与手机共用一份 slot 数据。单测：`tests/unit/topbar-fit.test.ts` + `tests/unit/topbar-panel-toggle.test.ts`（结构锁 + 实测溢出接线）。
- **往下展开的菜单不许挂在横滑/圆角裁剪容器里**（issue #162）：顶栏「⋯」溢出菜单曾用 `position:absolute` 挂在 `.view-switch{overflow:hidden}`（桌面）/ `.topbar-flow{overflow-x:auto}`（窄屏；扁平化之前叫 `.topbar-actions`）里，往下展开的部分全被祖先裁掉 —— `z-index` 救不了 overflow 裁剪，`overflow-x:auto + overflow-y:visible` 写了也白写（浏览器把可见轴算成 auto）。解法与 `ContextMenu.tsx` 同路：portal 到 body + `position:fixed` + 按触发按钮实测锚定钳制。另：这类菜单的关闭回调若是内联箭头，effect 每 render 解绑/重绑全套 document 监听，离散按键可能落在空窗里丢键 —— 关闭走 ref，监听在菜单开着期间只装一次。
- **菜单/下拉面板类浮层严禁因页面滚动而关闭**：浮层（如顶栏「⋯」菜单、插件面板 `PluginMenu`、各类按钮下拉等）统一接入 `web/src/use-floating-panel.ts` 的 `useFloatingPanel` Hook。**严禁在 `scroll` 事件中关闭浮层**——`addEventListener("scroll", ..., true)` 处于捕获期，页面内任何子元素滚动（如 AI 流式生成触发消息流自动吸底、侧边栏滚动）都会触发事件，导致弹窗被秒关。正解是 `scroll`/`resize` 时只重算锚点坐标保持贴合（`measure`），只有点击外部（`mousedown`）或按 `Escape` 才关闭。
- **新对话必须自动聚焦输入框**：新建对话（点击顶栏/左栏/预设条的新对话按钮、或进入/切换到空白新会话）必须通过 `web/src/composer-bridge.ts` 的 `focusComposer()` 与 `ChatInput` 的空白会话自动聚焦机制聚焦输入框（触屏设备 `IS_TOUCH` 豁免以防软键盘遮挡）；在非 `chat` 视图（如 terminal/scm）点击新对话必须同步切回 `chat` 视图，避免界面停在旧视图且无法打字。
- **`set_workspace_roots` 是按项目（cwd）存的**：同一客户端在不同项目下各有一份额外根（`client-state.json` 的 `workspaceRoots[cwd]`），切项目不会把 A 项目的根带到 B。安全含义：**额外根 = 工作区内** —— `isInsideWorkspace()` 算进去后，插件 `host.fs.*` 读那些目录不再需要单独授权（工作区外才要走确认框），用户加根前得知道这一点（右栏文案已提示）。
- **Playwright 脚本**：Chrome 路径由 `tests/lib/chrome.mjs` 逐平台探测（`PI_WEB_CHROME` 可覆盖），不再写死本机路径；脚本里取仓库根一律用 `fileURLToPath(new URL("..", import.meta.url))`——`URL.pathname` 在 Windows 上得到 `/E:/...`，`spawn` 会直接 ENOENT；服务端进程清理在 win32 走 `tests/lib/port-utils.mjs` 的 `freePort`（负数 PID 的进程组在 Windows 上不存在）。
- **DSH shipped 预设在 launcher boot 下不可直接 mount**：composition 的裸包名按 agent scope 的 baseUrl（= cordis.yml 目录）解析，官方靠 PluginPackages resolution 走安装锚点、pi-web-ui 没装那套。解法是 `server/dsh/preset-clones.ts` 的 file: 克隆（裸名→运行时树入口文件 URL，注意 `file:` 必须指到**文件**，目录 URL 恒判 broken；含子路径的包按 exports map 解析），roster 以 clone 目录为唯一 system 根并关 `includeShippedRoot`（同名早根优先，否则 shipped 的 broken 条目遮住 clone）。回归：`tests/unit/preset-clones.test.ts` + `tests/dsh-smoke-test.mjs` 的 2.5 节。
- **DSH 的 agent-scoped 事件 host 收不到**：`user-questions/request` 与 `agent/pre-step` 只在 agent scope 递送，host 注册的观察者永远看不见（且新版 `UserQuestionService` 已删 `registerProvider`，旧写法直接让整个运行时 boot 崩溃）。问卷 answerer 与技能目录过滤钩子必须在每次会话创建的 `setup()` 里挂到 agent scope（见 `goal-rpc.mjs` 的 `agentSetup`）。
- **`web/src/i18n.tsx` 的文案 value 只许是字符串字面量（含 `+` 续行），不许用变量/模板表达式/函数调用**：`npm run changelog:i18n`（`scripts/i18n-diff.mjs`）是手写解析器，只认引号字面量 + `+` 拼接（0.87.0 的 `filesHelp` 长文案曾用 `+` 续行把脚本搞崩过一次，修完才支持）。改完文案必跑一次该脚本验证；新增豁免先修解析器再合。
- **DSH 底栏统计（上下文占用 / 缓存命中 / 回复速率）吃的是「直播帧 + usage」事件面**：新版运行时不发持久 `assistant/chunk` 了（改成 agent scope 的 `agent/assistant-stream` 直播帧 → **host 侧同样收不到**，见上一条），usage 只在结束时随持久 `assistant/message.usage` 落一次。所以 wrapper（`goal-rpc.mjs`）构造器用 `{ global: true }` 订阅直播帧并转 `assistant.stream` 通知；服务端两条路共用 `applyStreamChunk`，`conv.liveChunks` 标记互斥（过渡期两边都在也不会喂两遍），纯映射在 `server/dsh/dsh-usage.ts`（单测 + `tests/dsh-stats-test.mjs` 假 runtime 回归，零 key / 零子进程）。**漏了这条路 = 没有 streamingMessage / 没有速率 / 底栏上下文永远是 `—`。**
