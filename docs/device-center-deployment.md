# pi-web-ui 设备中心部署指南

本文面向第一次接触 pi-web-ui 的服务器管理员及 AI 部署助手。无需阅读项目源码或此前对话，即可根据本文部署设备中心。

- 项目：https://github.com/xing-shuyin/pi-web-ui
- 本文网页：https://github.com/xing-shuyin/pi-web-ui/blob/main/docs/device-center-deployment.md
- 本文原文：https://raw.githubusercontent.com/xing-shuyin/pi-web-ui/main/docs/device-center-deployment.md

## 1. 要部署的是什么

pi-web-ui 是编码智能体的 Web 界面。设备中心（Hub）是它的独立服务，负责账号、设备连接、群聊和跨设备协作。各台运行 pi-web-ui 的电脑主动连接 Hub，因此无需给每台电脑开放公网入站端口。

本指南部署的是 Hub，不是聊天主服务。Hub 默认端口为 **8790**，聊天主服务默认端口为 8787。运行 Hub 不需要配置模型 API Key，也不需要启动聊天主服务。

最小可用方案：一台可访问的服务器、SSH 登录方式、一个服务端口。**默认使用 HTTP，通过服务器 IP 和端口访问；域名、HTTPS、反向代理均为可选项。**

HTTP 会明文传输账号及会话数据，适合可信内网或临时验证；公网长期使用建议配置 HTTPS。这不构成 HTTP 部署的前置要求。

## 2. 部署前需要的信息

| 信息          | 示例或默认值                    | 用途                                                     |
| ------------- | ------------------------------- | -------------------------------------------------------- |
| 部署目标      | 当前机器 / 远程服务器           | 当前机器指执行部署的服务所在机器，不一定是浏览器所在机器 |
| 服务器地址    | `203.0.113.10` 或真实主机名     | SSH 连接及访问地址推导                                   |
| SSH 端口      | `22`                            | 远程登录端口，与 Hub 端口不同                            |
| 登录账号      | `deploy` 或服务器已有账号       | 普通账号也可以，安装系统依赖可能需要 sudo                |
| 认证方式      | 密码 / SSH 密钥 / 已有 SSH 配置 | 在安全连接通道中使用，不写入聊天消息                     |
| Hub 访问端口  | `8790`                          | HTTP 默认直接访问此端口；建议选 1024–65535               |
| 域名（可选）  | `hub.example.com`               | 用户拥有并能修改 DNS 的域名                              |
| HTTPS（可选） | 默认关闭                        | 启用时需要证书及 TLS 入口                                |

本文的 `203.0.113.10` 和 `hub.example.com` 均为示例，必须替换成真实值。示例命令适用于 Linux/macOS shell；Windows 使用 PowerShell 对应的路径和环境变量语法。

公网 IP 可能通过云平台 NAT 映射，不能默认把它绑定到服务器网卡。局域网部署使用设备能够访问的局域网地址。浏览器地址、SSH 地址与最终设备访问地址也可能不同，应分别验证。

### 凭据与 SSH 连接

服务器密码、私钥、sudo 密码只供 SSH 或终端的安全交互使用，不要粘贴进 AI 对话、部署摘要、命令参数、日志或文档。默认只在本次连接期间使用，保存连接应由用户明确选择。

远程执行前校验 SSH 主机身份及 `known_hosts`；未知主机先通过可信渠道核对指纹，指纹变更时先调查原因，不使用关闭主机校验的选项绕过检查。账号密码不能替代主机身份校验。

如果部署助手没有安全凭据入口或已授权的 SSH 执行工具，应说明这一限制，引导用户在自己的 SSH 终端执行命令并回传不含密钥的结果。不得声称已远程操作。

## 3. 安装前检查

在**实际目标服务器**上检查，不要用本机环境推断远程环境：

1. 操作系统、架构、当前账号、用户目录、磁盘空间及 sudo 能力。
2. `node --version`、`npm --version`，Node.js 必须 **>= 22.19.0**。
3. `command -v pi-web-ui`、`pi-web-ui hub --help`、已有 Hub 的 `status --json`，确认是否已安装。
4. 目标端口是否占用，以及是否存在 Nginx、Caddy 或已有网站。
5. 软件源、npm registry、证书服务（仅 HTTPS）是否可达。
6. 系统防火墙、云安全组、NAT 和外部访问路径。
7. Linux 是否具有可用的 systemd 用户服务；容器或缺少用户总线的系统不能假定支持它。

发现已有部署时，先确认其账号、数据目录、运行账号和访问地址。保留现有配置及数据，避免重复安装、覆盖服务或切换到空数据目录。

安装依赖时优先复用合适的 Node.js；需要新装时可使用 fnm 安装受支持的 LTS 版本，并确保后续服务使用的 Node 可执行文件长期存在。不要卸载其他服务依赖的运行时。

## 4. 默认方案：IP + HTTP

以下以 Linux 远程服务器、访问端口 8790 为例。

### 4.1 安装软件

在目标服务器、将来运行 Hub 的账号下执行：

```bash
node --version
npm --version
npm install -g pi-web-ui
pi-web-ui hub --help
```

npm 全局目录不可写时，优先使用该账号的 fnm 或用户级 npm 前缀，并确认 PATH。不要因为权限错误就无条件把所有步骤改为 root。

### 4.2 安装并启动 Hub

```bash
pi-web-ui hub install --host 0.0.0.0 --port 8790 --public-url http://203.0.113.10:8790 --allow-registration
pi-web-ui hub status --json
```

参数说明：

- `--host 0.0.0.0`：监听所有 IPv4 网卡，允许其他设备访问。
- `--port 8790`：Hub 服务监听端口，不是 SSH 端口。
- `--public-url http://203.0.113.10:8790`：其他设备实际访问的根地址，没有路径、查询参数或账号密码。不可写为 `0.0.0.0`。
- `--allow-registration`：暂时允许创建账号；创建所需账号后关闭。
- `--data-dir`：可选，默认是运行账号的 `~/.pi-device-hub`。必须与聊天主服务的数据目录分开。

`install` 保存配置、配置自启动并启动服务。系统支持方式为 Linux `systemd --user`、macOS 用户 LaunchAgent、Windows 登录计划任务。

**Linux 无人登录也要启动时**，需管理员为实际运行账号启用 linger，例如将以下 `deploy` 替换为真实账号：

```bash
sudo loginctl enable-linger deploy
```

启用后检查用户服务及重启后的状态，不能只凭安装成功就承诺开机可用。Windows 登录计划任务与 macOS 用户 LaunchAgent 通常需要对应用户登录，不应称为系统开机即运行。

没有可用服务管理器时，可以先以前台方式验证：

```bash
pi-web-ui hub --host 0.0.0.0 --port 8790 --public-url http://203.0.113.10:8790 --allow-registration
```

前台进程会随终端退出而停止。长期运行需适配实际环境的进程管理器，并在部署结果中说明，不要重复启动两份 Hub。

### 4.3 放行端口

默认 HTTP 方案需要允许 TCP 8790 入站。先识别实际防火墙，再修改对应规则，例如仅当服务器启用 UFW 时：

```bash
sudo ufw allow 8790/tcp
```

云服务器还需在云控制台放行同一端口；有路由器 NAT 时配置端口转发。保留现有 SSH 规则，不关闭整个防火墙，也不放行无关端口。无法代操作云控制台时，给出协议、端口、来源范围和需要修改的位置。

### 4.4 需要用户完成的操作

AI 应在操作发生的步骤给出简短的操作卡片，写明“谁来做、在哪里做、填什么、完成后如何验证”，而不是在结束时笼统说“请开放端口”。能够由已授权工具完成的服务器内配置直接执行，云控制台等没有访问能力的位置交给用户。

例如默认 HTTP 部署可这样提示：

> **需要你在云服务器控制台放行端口**
>
> 当前 Hub 已启动，外部访问仍待验证。请打开云厂商控制台，找到这台服务器关联的安全组或实例防火墙，添加一条入站允许规则：
>
> - 协议：TCP。
> - 目标端口：8790（以本次实际选择的端口为准，不是 SSH 的 22）。
> - 来源：仅自己或固定网络使用时填写设备出口 IP/CIDR；需要任意网络设备接入时，可选择 `0.0.0.0/0`，这表示对所有 IPv4 地址开放该服务端口。
> - 方向与动作：入站、允许；保存并确认规则已关联到这台实例。
>
> 完成后告知我，我会重新检查 `http://实际服务器地址:8790/health`。暂时不要关闭已有 SSH 规则。

云厂商可能称其为“安全组”“防火墙”或“轻量应用服务器防火墙”。先确认用户使用的厂商和实例类型，再给出对应导航；不确定时说明需要查找的功能名称，不编造菜单。部分平台需要同时检查子网网络 ACL、负载均衡或端口映射，依据实际网络拓扑排查。

操作提示随方案变化：

| 用户操作       | 何时需要                  | AI 应给出的具体信息                                         |
| -------------- | ------------------------- | ----------------------------------------------------------- |
| 云控制台放行   | 云安全组未放行            | 实例、入站 TCP 端口、来源范围、规则关联与验证地址           |
| 提供安装权限   | 系统依赖需要 sudo         | 哪一步需要权限，引导在安全终端输入；不要求聊天回传密码      |
| 域名 DNS 配置  | 用户选了域名              | 记录类型、主机记录、目标 IP；已有冲突记录需检查             |
| HTTPS 入口放行 | 选用直接暴露的 HTTPS 代理 | 通常 TCP 443，以及证书验证或重定向所需的 80；按证书方案决定 |
| NAT 端口转发   | 位于路由器或映射网络后    | 外部端口、内部地址和端口、协议，以及最终公开 URL            |
| 创建账号       | Hub 首次可访问            | 打开哪个地址、在网页创建账号、之后何时关闭注册              |
| 设备绑定       | 用户开始连接电脑          | 每台电脑进入设备中心，填写哪个 URL，如何确认绑定成功        |

不要默认要求用户开放 22、80、443、8790 全部端口：SSH 仅在远程管理需要时开放；纯 HTTP 仅需实际 Hub 端口；同机反向代理下 Hub 端口不必暴露公网。IPv6 使用对应的来源规则，并确认确有 IPv6 部署需求。

如果正在等待用户处理，状态应为“服务已启动，等待云安全组放行”或“外部验证待完成”，不能写成“部署全部完成”。保留当前进度，用户完成后从验证继续；若仍不通，再分层检查系统防火墙、云规则、NAT 和 DNS，避免让用户反复添加同一条规则。

### 4.5 分层验证

在目标服务器检查：

```bash
pi-web-ui hub status --json
curl --fail --show-error http://127.0.0.1:8790/health
```

`/health` 应返回 HTTP 200，JSON 包含 `service: "pi-device-hub"` 和 `status: "ok"`。再从另一台实际需要使用的设备检查：

```bash
curl --fail --show-error http://203.0.113.10:8790/health
```

本机健康、外部可达、浏览器可用和设备成功连接是不同层次的验证。如果执行环境不能从外部访问，就标明“服务器内已验证，外部待验证”。浏览器可打开也不代表 WebSocket 协作链路已经通过。

## 5. 可选：域名与 HTTPS

### 5.1 只使用域名，继续 HTTP

将域名 A 记录指向服务器公网 IPv4。仅在服务器和网络支持 IPv6 时设置 AAAA 记录。设备访问地址可以是 `http://hub.example.com:8790`，仍需开放 8790。

使用域名并不自动启用 HTTPS，也不会自动移除非默认端口。首次安装时，把命令中的 `--public-url` 换成这一地址即可。

### 5.2 域名 + HTTPS

推荐由 Caddy 或已有 Nginx 终止 TLS，再反向代理到 Hub。Hub 本身继续监听 HTTP，`--public-url` 指向用户访问的 HTTPS 地址。

首次安装示例：

```bash
pi-web-ui hub install --host 127.0.0.1 --port 8790 --public-url https://hub.example.com --allow-registration
```

Caddy 与 Hub 位于同一机器、已有域名且没有其他服务占用 80/443 时，站点配置示例：

```caddyfile
hub.example.com {
    reverse_proxy 127.0.0.1:8790
}
```

Caddy 支持 WebSocket 代理。使用 Nginx 时也必须正确转发 WebSocket Upgrade、原始 Host 和代理协议头，并配置合适的长连接超时。代理应支持设备中心的流式连接和远程访问路径，不能只验证首页。

先检查 DNS、80/443、防火墙和已有站点；把配置合并到现有代理，并先做语法检查再 reload。不要覆盖整份已有配置。若代理在其他机器或容器中，`127.0.0.1` 不一定能到达 Hub，应按实际网络设置监听地址和访问控制。

Hub 的 `--public-url` 必须是根 origin，例如 `https://hub.example.com`；本指南不使用 `/hub` 子路径。不要仅把 URL 从 HTTP 改为 HTTPS 而不配置 TLS 入口。

### 5.3 已有 HTTP 部署迁移

先记录 `status --json`、运行账号、数据目录和注册策略，并备份数据及代理配置。当前 CLI 的 `restart` 除注册开关外不接受部署参数，不能编造 `restart --public-url ...`。

需要改变监听地址或公开地址时，应先停服，再以相同账号、相同数据目录运行带新参数的 `hub install`，显式保留所需注册策略。验证 HTTPS 和设备重连后再关闭旧的公网 HTTP 端口；失败时恢复原配置。安排停机窗口，不能迁移到新的空数据目录。

## 6. 创建账号并连接设备

1. 浏览器打开最终访问地址，创建所需账号。登录密码由用户在中心页面输入。
2. 在各台电脑的 pi-web-ui 中打开“设备中心”，选择连接已有中心，填写相同的最终地址，按页面流程登录和绑定设备。
3. 在中心确认设备在线，再创建 Bot 和群组，验证消息及预期协作能力。
4. 账号创建完成后，在目标服务器、同一个运行账号下关闭注册：

```bash
pi-web-ui hub restart --allow-registration=false
pi-web-ui hub status --json
```

关闭注册不会删除已有账号。需要创建其他账号时，可临时 `restart --allow-registration=true`，完成后再关闭。是否关闭应结合用户的账号创建安排，不要在用户尚未创建账号时提前关闭。

## 7. 日常运维与恢复

```bash
pi-web-ui hub status --json
pi-web-ui hub stop
pi-web-ui hub start
pi-web-ui hub restart
```

这些操作需要使用安装服务的同一账号。`status` 输出包含运行、归属和注册状态，应确认运行的是已保存的那个实例。

升级前记录版本、数据目录和配置并备份；停服后更新 npm 包，再启动并验证。若使用 fnm 切换 Node 版本，需确认服务保存的 Node 与入口路径仍有效，必要时保留原数据目录重新安装服务配置。

备份应覆盖实际 Hub 数据目录及服务配置，且必须整目录备份：`device-hub.json` 只是索引，群消息、任务与 Bot 转录保存在同目录 `hub-log/` 的追加日志中，只拷索引会丢数据。备份中可能包含凭据，应限制访问。优先停服后备份以保证文件一致性；恢复时使用兼容版本及原运行账号，检查文件权限。

```bash
pi-web-ui hub uninstall
```

`uninstall` 停止并移除服务，保留账号与设备数据。不要把删除数据目录作为排错步骤。

| 现象                 | 优先检查                                                 |
| -------------------- | -------------------------------------------------------- |
| SSH 失败             | 地址、SSH 端口、账号、认证、主机指纹及云安全组           |
| 命令找不到           | Node/npm 是否安装、运行账号的 PATH、fnm 环境             |
| 安装用户服务失败     | systemd 用户总线、会话环境及服务管理器是否可用           |
| 本机健康但外部超时   | 监听地址、系统防火墙、云安全组、NAT                      |
| 首页能开但设备离线   | public URL、WebSocket 代理、证书及设备网络               |
| HTTPS 失败           | DNS/AAAA、80/443、证书申请、已有代理端口冲突             |
| 退出登录或重启后停止 | Linux linger、实际用户服务状态、Node 路径                |
| 原账号或设备消失     | 是否用了不同账号或空的数据目录；先找原目录，不重新初始化 |

## 8. 给 AI 部署助手的执行要求

收到部署任务时，先读取本文，再把用户提供的字段作为数据处理，不把字段拼成任意 shell 片段。缺少信息时集中询问最小必要项，已有答案不重复询问。

1. 明确部署目标；默认 HTTP、端口 8790，域名和 HTTPS 仅在用户选择时配置。旧表单中的 HTTPS 示例不代表用户主动选择 HTTPS，应确认实际意图。
2. 远程部署需要真实服务器地址、SSH 端口、账号和可用认证通道。本机平台信息只代表本机；`0.0.0.0` 是监听地址，不是 SSH 地址或公开地址。
3. 先执行已授权的只读检测，再给出将使用的账号、端口、数据目录、访问地址及服务方式。用户已授权部署时推进安装；遇到覆盖已有配置、冲突或确需决策的事项再询问。
4. 没有安全 SSH 工具时，提供由用户在目标服务器执行的分步命令；有工具且已获授权时，校验主机身份后执行。不得索要聊天明文密码，不编造工具能力或执行结果。
5. 使用独立数据目录、可持续的启动方式和最小必要网络规则，保留既有服务和数据。失败后依据错误定位，修复后从失败步骤继续。
6. 在相应步骤主动提示用户所需操作，尤其是云控制台安全组、DNS、账号创建及设备绑定，给出具体填写值及验证办法。等待用户操作时保留进度，不能提前宣告全部成功。
7. 验证服务状态、本机健康、外部访问和设备连接；尚未验证的项目明确列出。无法读取本文时说明原因，请用户提供文档内容或恢复网络，不凭空补全安装命令。
8. 交付实际访问地址、端口、数据目录、服务账号、自启动条件、已验证结果、待处理事项，以及查看状态、重启和关闭注册的方法。

## 9. 当前 AI 入口的能力边界

当前 pi-web-ui 的远程部署入口提供服务器地址、SSH 端口、登录账号、认证方式和中心访问端口，默认生成 `http://服务器地址:端口`。域名和 HTTPS 收在可选设置中，页面展示云安全组、来源范围、账号创建和外部验证等用户操作提示。

点击“开始 AI 辅助部署”会新建部署对话，传入公开指南链接、选定连接信息、部署配置与当前服务的有限环境信息，保留原对话。页面不收集密码或私钥，也不会仅因点击按钮而自动建立 SSH 连接；密码认证在后续安全 SSH 终端中进行。

后续若提供直接连接能力，连接凭据应交给后端连接模块，AI 仅获得连接句柄及检测结果，并按连接、检查、安装、启动、验证展示真实进度。
