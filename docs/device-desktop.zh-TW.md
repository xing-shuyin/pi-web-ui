# 已授權裝置的原生遠端桌面

裝置中心參考 [krd](https://github.com/zzjcool/krd) 的原生捕獲與輸入方式，複用裝置訪問票據和聯結器，在瀏覽器 canvas 顯示 JPEG。從本機裝置中心開啟時，與「開啟裝置」的完整對話介面共用[區域網優先訪問](device-center.zh-TW.md#區域網優先訪問)：優先使用經過 TLS PSK 驗證的私網通道，不可達時嘗試裝置間 P2P，失敗使用原 Hub WebSocket 中繼。無需 VNC 服務、noVNC 或固定桌面埠。畫面不進入聊天快照或模型上下文。

Windows 支援 H.264 硬體編碼通道（見下文「H.264 硬體編碼通道」），瀏覽器支援 WebCodecs 時自動啟用，否則保持 JPEG。

## 聊天頁預覽與放大操作

從裝置通道進入遠端聊天頁後，右欄自動顯示該頁所屬裝置的桌面。當前裝置身份取自已授權的 portal capability 路徑，預覽、即時畫面與輸入均複用該路徑，不再由被控機向自己申請 LAN/P2P/Hub 票據。關閉預覽後可點「顯示此裝置的桌面」恢復；選擇裝置列表中的當前裝置也走同一入口。連線標記顯示「複用當前連線」，不猜測底層是 LAN 還是 P2P。獨立標籤由可信外層代為開啟，不放寬遠端沙箱許可權。

桌面工具欄按連線、檢視選項和輔助面板分組，跟隨聊天頁的主題顏色。`desktop-theme.ts` 定義允許同步的顏色令牌，父頁通過受來源視窗約束的訊息轉發到桌面沙箱，桌面僅接受顏色值，不載入任意樣式或 URL；主題切換不會重建 iframe 或 WebSocket。獨立頁面預設跟隨系統明暗，窄屏保留橫向工具條與單獨狀態行，設定、文字輸入、連線資訊互斥展開，支援 Escape 和外部點選收起。Hub 中繼的主題轉發需要 Hub 更新到同一版本。

從本機裝置中心或群成員開啟遠端桌面時，聊天頁右欄上方顯示一臺選中裝置的預覽，檔案與外掛區域保留在下方。預覽可收起、調整高度、切換裝置或關閉。“選擇裝置”在按鈕旁直接開啟裝置列表，顯示當前裝置和線上狀態，點選線上裝置即切換預覽，不跳轉裝置中心；關閉列表會取消未完成的讀取。點選“放大並操作”建立即時桌面視窗，視窗與全屏之間只改變佈局，不重新建立 iframe 或申請票據。放大視窗的 × 和“返回預覽”均保留選中裝置、恢復右欄預覽；右欄預覽自身的 × 才關閉整個桌面。返回預覽釋放即時連線和按住的鍵鼠，再申請新的預覽票據。切換聊天會話保留選中裝置；切換裝置、關閉桌面時清理舊頁面。手機瀏覽器放大後預設全屏；原生手機 App 仍使用自身裝置介面卡。

`web/src/device-access.ts` 管理裝置選擇和 preview/live 狀態，`use-desktop-target.ts` 在頁面掛載時申請一次性票據；非同步響應受 AbortSignal 和裝置選擇代次約束。裝置列表遇到臨時 502/503/504 時在同一 15 秒期限內最多自動重試兩次，關閉列表會取消請求和等待，不重建已有預覽。`desktop-preview.tsx` 只在預覽可見時通知沙箱頁面啟動請求。摺疊、隱藏右欄或瀏覽器進入後臺會取消請求和輪詢。視窗沿用 `RemoteDesktopWindow.tsx`，使用統一浮層層號。兩種模式均顯示實際 LAN/P2P/Hub 路徑，LAN 回退後更新標記。

`/desktop-preview` 提供獨立只讀頁面，通過現有授權通道請求 `/api/device-desktop/preview`，收到畫面後間隔 3 秒再請求，最多一個請求在途；圖片長邊目標 640 畫素。採集端使用 preview 模式，Windows/macOS 每輪等待 3 秒，Linux X11 使用 1/3 FPS。僅降低瀏覽器顯示頻率不算輕量採集。

`desktop-preview.ts` 合併同裝置併發請求，複用最近 2.5 秒內的幀，最多等待 8 個請求；沒有請求後 6.5 秒關閉預覽助手。即時桌面啟動時停止專用預覽助手，預覽請求複用即時採集的最新幀（此時尺寸沿用即時畫面）；即時桌面退出且仍有預覽請求時恢復低頻助手。預覽始終只讀，不請求 macOS 控制授權。停用桌面、退出服務、請求取消和遲到的採集回撥均有獨立清理。

裝置端、本機服務和 Hub 都需要支援新的預覽入口。舊裝置不支援時顯示預覽不可用，可繼續開啟原有即時桌面；不自動用全速桌面流偽裝輕量預覽。直接訪問 Hub 的瀏覽器通過 WebRTC 選擇區域網或跨網直連，失敗使用 Hub 中轉；控制端不需要安裝 pi-web-ui，詳見 [瀏覽器直連](device-center.zh-TW.md#純瀏覽器訪問-hub-的直連通道)。

### 預覽驗證

開啟獨立標籤頁或桌面殼獨立視窗成功後，主頁面保留裝置選擇並回到小預覽；關閉獨立視窗後仍可直接檢視預覽。瀏覽器阻止彈窗或桌面殼開啟失敗時保留原操作視窗，不清除選擇。新視窗沒有 opener，關閉通知不跨來源傳遞；主頁面可見時，預覽在服務端複用獨立視窗的即時幀，視窗關閉後恢復低頻採集。

數字小鍵盤的 `Numpad0`–`Numpad9`、加減乘除、小數點、回車及 NumLock 按獨立物理鍵傳遞，不能當作未知鍵丟棄。Windows 小鍵盤迴車和除號保留擴充套件鍵標誌，回車與主鍵區回車分別記錄並釋放；macOS 使用系統 Carbon 鍵碼，Linux 使用 X11 keypad keysyms。NumLock 的數字/導航狀態取決於被控系統。`tests/device-desktop-windows-keys-test.mjs` 編譯實際 C# 助手、驗證 22 種按鍵描述及釋放標誌，不向使用者桌面注入測試按鍵；瀏覽器測試覆蓋真實鍵盤事件到 WebSocket 的傳遞。

`tests/device-current-desktop-test.mjs` 在 8996 埠用真實 Chromium 驗證 Hub/LAN 路徑下的巢狀沙箱、持續預覽、直接控制、中文輸入、返回與重新開啟，確認沒有「再次開啟自己」的請求；檢查 one-dark、white、nord 主題即時同步且不重連，以及手機寬度。使用模擬採集幀，不代表跨機器幀率。

`tests/unit/device-desktop-preview.test.ts` 驗證快取、併發複用、取消和即時採集切換；原生/Linux 用例檢查低頻引數和只讀約束。`node --import tsx tests/device-desktop-window-test.mjs` 使用 8997 埠和真實 Chrome，驗證巢狀沙箱中的連續預覽、摺疊暫停、右欄隱藏暫停、放大操作、全屏不過載、返回預覽、手機寬度及關閉清理，截圖位於 `artifacts/device-center/`。該介面測試使用模擬桌面，不代表跨機器效能實測。

### 版本升級

控制端、被控端和 Hub 需更新並重啟實際執行程序，才能使用對應的新能力。只更新 npm 包後重新整理頁面不會替換仍在執行的舊後端。已安裝服務可執行 `pi-web-ui server restart`，有自定義名稱時附加 `--name <原服務名>`；前臺執行按原工作目錄、埠和資料目錄引數重啟。Hub 服務按原安裝方式執行 `pi-web-ui hub update` / `hub restart`，再用 `pi-web-ui hub status --json` 檢查實際版本。保留原資料目錄、鑑權和裝置繫結。

Windows 已安裝系統桌面服務時，還需執行 `pi-web-ui desktop service install` 更新受保護的採集程式。Mac 需要螢幕錄製及輔助功能許可權。舊裝置缺少能力時保留中繼或提示升級，不自動安裝系統元件。

從 Hub 開啟遠端聊天頁後，如果剪貼簿入口消失，或切換裝置時預覽內出現整張聊天頁，先核對 Hub `/health` 返回的實際版本。舊 Hub 可能將不認識的 `__desktop_target` 地址轉發到裝置的聊天首頁；更新被控端 npm 包不能替換 Hub 的包裝頁和轉發邏輯。更新 Hub 服務後，需要從裝置列表重新開啟入口，不能沿用升級前的短期訪問地址。

先驗證雙機預覽持續更新、放大操作、返回預覽和隱藏暫停，再驗證區域網和跨網通路。測試釋出與實機驗證範圍見對應 PR；原生平臺、顯示器重新整理率和不同 NAT 環境需分別驗證。

## 群組成員桌面

進入群聊後，右欄顯示“群組遠端桌面”：預設按電腦排列預覽卡片，下方“全部成員”及成員按鈕可切換為單個成員畫面；點選畫面開啟原即時控制視窗，關閉放大視窗返回群組預覽。群成員是 Bot，`GroupDetail.room.botIds` 限定成員範圍，只有 Bot 的明確 `deviceId` 可對映為桌面目標；不會把 Bot ID 當作裝置 ID。多個 Bot 共用同一臺電腦時，保留各自的成員按鈕，共用一張預覽。卡片同時顯示成員名及裝置的“備註 · 計算機名”。離線電腦保留狀態卡片，缺失裝置關聯的成員按鈕不可操作。

`group-active-context.ts` 提供當前群狀態，`group-desktop.ts` 派生裝置對映，`GroupDesktopPreview.tsx` 管成員選擇及可見性，`DesktopPreviewFrame.tsx` 與普通桌面共用預覽、主題及狀態處理。裝置目錄僅在面板可見時重新整理；可見卡片才申請桌面入口，滾出網格、摺疊面板、切換頁面或選擇其他成員後停止對應預覽。正在放大的電腦暫停其預覽。切群/離群及成員移除會釋放該群的控制視窗。原左欄成員的遠端按鈕也會定位到群組中的對應預覽，不影響 `@` 引用和任務派發。

桌面仍通過既有裝置訪問鑑權與 LAN/P2P/Hub 選擇開啟；裝置目錄返回的本機 ID 直接複用當前 Web 連線，不繞 Hub 連線自己。介面展示群成員不擴張訪問許可權，也不會自動啟用被控機桌面。本批無需改變 Hub 協議；檢視群組的 Web 頁面需更新，已執行相容桌面服務的成員端可沿用原版。

## 動態畫質與傳輸解析度

工具欄「畫質」提供自動 / 流暢 / 均衡 / 清晰，傳輸畫面長邊上限（跟隨視窗、960、1280、1920、2560 px）及 10 / 15 / 30 / 60 / 120 / 240 FPS 目標，預設 60。解析度保持螢幕比例且不放大源畫面；不修改作業系統顯示設定。鍵鼠繼續使用歸一化座標。設定在當前連線內生效，包括只讀連線。連線資訊分別顯示目標及實際採集、傳送、顯示幀率；靜止桌面可只發送低頻保活幀，不能用它衡量最高幀率。

- 自動模式以容器尺寸及最高 2 倍畫素密度為解析度上限，不因網路往返延遲縮小畫面。JPEG 與 H.264 共用 `desktop-video-flow.ts` 的確認反饋：最低實測往返時間作為基線，持續增加的排隊延遲才降低質量，然後降低採集幀率，恢復時逐步提高。穩定的高延遲不會單獨觸發降清晰度。手動畫質固定對應質量與幀率，傳輸視窗和佇列仍有上限。
- 擁塞判斷覆蓋一秒內全部有效反饋：超過一半反饋有超過 80 ms 的額外排隊或解碼佇列大於 3，連續兩個視窗後降檔；超過一半反饋額外排隊超過 250 ms 或解碼佇列大於 8，當個視窗即降檔。降檔不受五秒冷卻限制，單個及時 ACK 也不能掩蓋多數幀延遲；少量延遲反饋不會單獨觸發降檔。升檔仍需連續三十個健康視窗（每視窗至少 90% 反饋額外排隊低於 30 ms、解碼佇列小於 2），避免短暫好轉後立即升檔再降檔。編碼流重建時清空取樣桶，避免把單幀啟動延遲當成穩定擁塞。手動設定仍立即生效，在途幀、位元組及斷線檢測上限不變。驗收須測輸入到畫面響應和畫面年齡，不能只用 FPS 或停頓次數證明低延遲。
- `desktop-quality.ts` 負責配置校驗及使用者請求的基礎引數。`ready.dynamicQuality` 宣告能力；舊採集端不接收新配置。畫質訊息獨立於鍵鼠授權，數字有範圍限制，不能觸發本機安裝、顯示設定或其他命令。
- Windows 服務通過保護目錄中的 `profile-v2` 校驗值與已安裝二進位制繫結，防止回滾後錯誤宣告能力。全域性 npm 安裝/升級通過安裝指令碼自動更新系統服務；指令碼被停用時，終端中的首次啟動會補裝，取消後可用 `pi-web-ui desktop service install` 手動重試。會話切換恢復時保留畫質，仍不重放鍵鼠。
- Windows 優先使用 DXGI Desktop Duplication，複用 GPU staging texture 及 Bitmap；不可用時回退 GDI，鎖屏和會話恢復仍走現有系統服務。Mac 使用持續 SCStream、複用 CIContext，只保留最新待編碼幀。JPEG 客戶端通過 `jpegFeedback=1` 請求協商，僅在 `ready.jpegFeedback=1` 時傳送累計 `jpeg_ack.id`；序號按有序 WebSocket 的 JPEG 幀計數。視窗從兩幀起步，結合實際確認位元組速率及最低確認時間計算在途位元組預算，額外排隊預算 100 ms；不能將一張大圖片的傳輸耗時乘以目標 FPS 當成鏈路容量。最多 64 幀且未確認資料不超過 4 MiB，另保留一幀最新待發送畫面；客戶端跳過待繪製舊幀後，累計確認可釋放對應視窗。JPEG 看門狗檢測連續 15 秒無有效確認進展；重複或偽造序號不延長計時，持續收到確認時不因舊幀年齡誤斷開。舊客戶端或舊服務維持兩幀視窗及逐幀 `ack`。Linux X11 調節時替換 ffmpeg 採集程序，保留 WebSocket 和輸入狀態，舊採集幀不會進入新流；調整期間可能短暫等待首幀。
- 預覽仍使用低頻、低解析度只讀採集；後臺不可見卡片不佔持續採集。只有本機固定 `/desktop` / `/desktop-preview` 內建頁保留同源，遠端票據頁始終保持 opaque sandbox，訊息同時校驗來源視窗與 origin。

## H.264 硬體編碼通道

JPEG 在 1920×1080@60 實測約 100 Mbps、2560×1440@60 約 162 Mbps（單幀 200–330 KB，GDI+ 軟體編碼 10–15 ms），中繼和大多數跨網鏈路都喂不起，幀率選項形同虛設。Windows 因此增加 H.264 通道：優先用 `ffmpeg` 的 `ddagrab`（DXGI 零複製）採集，NVENC 硬編碼為 Annex-B，Node 切成訪問單元逐幀下發，瀏覽器用 WebCodecs `VideoDecoder` 硬解。

- 實測（RTX 4060 Laptop，2560×1440）：@60 穩定 55 fps / 12.6 Mbps；@120 穩定 111 fps / 17.7 Mbps。首幀約 310–350 ms（ffmpeg 啟動 + NVENC 初始化）。同畫質下頻寬約為 JPEG 的 1/10，編碼不佔 CPU。
- 啟用條件：瀏覽器支援 WebCodecs（HTTPS 或 localhost）並在 `desktop-ws?video=1` 協商影片。未安裝系統桌面服務時沿用 ddagrab/NVENC 通道；服務具有與二進位制雜湊繫結的 `video-v1` 能力時，走下面的內建原生採集編碼通道。只有 `raw-v1` 的舊服務仍可使用上一版 Node 編碼橋；更舊服務和不支援 WebCodecs 的瀏覽器繼續使用 JPEG。
- 編碼引數：`-preset p1 -tune ll -rc cbr -g <fps> -bf 0`，位元速率由 `desktop-video.ts` 的 `videoBitrate()` 按解析度/畫質/幀率推導（1080p 約 5–9 Mbps，1440p 約 9–14 Mbps，120 fps ×1.4）。改畫質或幀率會重啟 ffmpeg（重開 IDR），瀏覽器在下一個關鍵幀重新同步。
- FFmpeg 通道的 VBV 緩衝預算為目標位元速率的 100 ms，限制週期關鍵幀的突發大小，避免單張關鍵幀阻塞有序跨網通道數百毫秒；保留平均位元速率、目標幀率和一秒關鍵幀間隔。VBV 是編碼器約束，不是對每幀位元組數或網路延遲的硬保證。
- 分包與丟幀：`createH264Splitter` 按 Annex-B 起始碼與 VCL 首片（`first_mb_in_slice==0`）切出訪問單元，引數集隨關鍵幀下發，比 JPEG 多一幀延遲。H.264 幀不能像 JPEG 那樣用新的覆蓋舊的，積壓超閾值時丟棄直到下一個關鍵幀。
- 採顯分離：ffmpeg 只負責畫面；鍵鼠仍由 Windows 原生助手 `input` 模式注入（無採集執行緒），保證控制可用。
- 分發：釋出包自帶 `bin/ffmpeg/<platform>-<arch>/ffmpeg.exe`（`npm run build:ffmpeg` 下載，`PI_DESKTOP_FFMPEG` 可覆蓋，見 [環境變數](env-vars.zh-TW.md)）。缺失時不影響 JPEG 通道。
- 不改變輸入許可權、只讀連線、剪貼簿和顯示選擇：影片模式只替換畫面編碼，控制與授權校驗仍由服務端強制。

### 隨 pi-web-ui 內建的服務影片通道

DXGI 採集源必須放在 FFmpeg 的 `-filter_complex` 中，與 `-filter_hw_device` 繫結到所選顯示器的顯示卡。`-f lavfi -i ddagrab` 會建立獨立的預設裝置，不能保證多顯示卡選擇生效。NVIDIA 原生解析度優先直接提交 BGRA 紋理，避免不必要的縮放與顏色轉換；調整為較低解析度後重新選擇縮放路徑。GPU 影片處理器不可用時，保留 DXGI 採集，回讀縮放後上傳 NV12 紋理再交給硬體編碼器；不能向 D3D11 NVENC 會話提交普通 CPU 幀，也不能因縮放失敗就立即改用 GDI。Intel 紋理經同一顯示卡派生的 QSV 上下文對映。所有 DXGI 路徑失敗後才嘗試 GDI，輸出仍使用 passthrough，不靠補幀提高統計數字。

參考 RustDesk 的[影片採集/編碼迴圈](https://github.com/rustdesk/rustdesk/blob/master/src/server/video_service.rs)設計，獨立實現採集、編碼與瀏覽器顯示的分層。此實現沒有啟動 RustDesk 應用，也未移植其完整引擎或協議。使用者只安裝 pi-web-ui；Windows 首次啟用鎖屏控制仍須授予本應用桌面服務管理員許可權。

`PiWebDesktop` 繼續負責當前桌面、鎖屏桌面及鍵鼠輸入。`video-view` / `video-control` 在選定 Windows 會話、實際輸入桌面內啟動受保護的原生編碼元件；FFmpeg 在同一程序裡完成採集、縮放和 H.264 編碼，原始畫素不經過 C# 管道或 Node。按顯示器實際邊界匹配 DXGI 介面卡及輸出，支援多顯示卡，不能把 `DISPLAY2` 當成某個介面卡的第二個輸出。編碼選擇對應 RustDesk `video_service.rs::get_encoder_cfg` 的 VRAM → HWRAM → 軟體順序：先 GPU 紋理直接硬體編碼，再嘗試 DXGI 讀回或 GDI 採集搭配硬體編碼器，所有硬體路徑失敗才用 libx264。NVENC/AMF 紋理路徑使用 D3D11 縮放，QSV 使用硬體幀對映。顯示卡列舉獨立於顯示輸出，RDP/鎖屏缺少 DXGI 輸出時仍檢查硬體編碼能力。旋轉或不支援的輸出走 GDI。連線資訊顯示實際採集、編碼、解碼後端，並通過詳情提示保留有界回退原因。

編碼元件只允許來自 `Program Files\pi-web-ui-desktop\ffmpeg.exe`，安裝時檢查包內構建清單 SHA-256，複製到管理員保護目錄，啟動時再次比對保護目錄內的雜湊；SYSTEM 採集器不使用 PATH、`PI_DESKTOP_FFMPEG`、呼叫者提供的路徑或指令碼。輸入桌面來自本機 `OpenInputDesktop`，連線不能指定任意會話或桌面。編碼程序納入 kill-on-close Job；客戶端關閉、服務退出或更換桌面後清理。

畫質、幀率、畫面尺寸或輸入桌面變化會重開編碼器。每段新流通過復位標記清空舊分幀狀態，重新發送引數集和 IDR；SPS 決定 codec，瀏覽器在流復位時重建解碼器，即使 codec 字串相同也不沿用上一編碼會話的參考幀。解碼選擇參考 RustDesk `codec.rs::Decoder::new`：先用實際 codec 檢查 `prefer-hardware`，支援即明確啟用硬體；僅能力檢查不支援或執行初始化失敗才使用 `prefer-software`。非同步探測和流切換丟棄舊代回撥，恢復時等待關鍵幀；等待解碼的輸入最多 32 幀/16 MiB，避免延遲積累。協議為最多 64 KiB 的編碼塊，H.264 組幀上限 16 MiB、單幀上限 4 MiB；管道、錯誤日誌和啟動/停滯等待均有界。採集頻率由採集器控制，輸入和編碼時間基準明確，輸出停用 CFR 自動補幀，不能用補出的重複影像充當效能提升。

僅有 `raw-v1` 的已安裝舊服務繼續由 `desktop-video-encoder.ts` 在普通使用者程序探測/執行編碼器；保留原始幀 32 MiB 限額和消費確認。JPEG 預覽仍復用 GDI DIB surface 或 DXGI 採集，不受影片元件啟動影響。

預設 Windows FFmpeg 可由 `npm run build:ffmpeg -- --platform=win32-x64` 在 Windows、macOS 或 Linux 上準備；相容編碼器與原生元件必須先在 Windows x64 構建機執行 `npm run build:desktop-codec`，或將該機的構建產物複製到打包環境。`scripts/ffmpeg-build.json` 固定預設構建 URL 和 SHA-256；包內包含執行檔、許可證和構建來源。`pack:p2p` 與 npm 釋出前步驟會校驗這些元件，使用者無需另外下載 FFmpeg 或 RustDesk。舊桌面服務未能自動更新時，可執行 `pi-web-ui desktop service install` 重試。

`node --import tsx tests/device-desktop-video-test.mjs` 用真實編碼器和 Chrome 驗證 60/120/240 配置及同一視窗內的解析度變化；輸入是合成畫素，不是實際桌面 FPS。Windows 本機已驗證服務影片到瀏覽器與動態解析度；當前控制台的 GDI/libx264 靜態畫面約 30 FPS，上一版 raw 管道同條件約 18 FPS。該資料不是動態桌面或高刷顯示器驗收。GPU 路徑、不同顯示卡、鎖屏→登入和跨網高刷仍需在目標機器實測；目標幀率是上限，不能把歷史 ddagrab/NVENC 結果套用到新服務路徑。

連線資訊中的 `libx264` 表示被控端正在軟體編碼，即使同一行顯示瀏覽器硬體解碼，也不代表採集與編碼已經使用顯示卡。實際服務測試會記錄 `fallback` 原因；Windows 上同時檢查顯示介面卡的 `ConfigManagerErrorCode`。裝置管理器 Code 31/43、獨立硬體編碼探測失敗屬於顯示卡或驅動異常，調高 FPS 上限不能修復；應先恢復顯示卡，再重新連線測試硬體後端和實際幀率。

## 多顯示器

## 剪貼簿同步

瀏覽器直接訪問 Hub 時，可信外層提供「剪貼簿 · 瀏覽器文本傳遞」：手動貼上併發送、讀取遠端當前文本、複製到本機，單次最多 16 KiB。HTTP 頁面可使用選中文本後 Ctrl/Cmd+C，安全上下文下可點選複製按鈕；不自動讀取控制端剪貼簿。圖片、檔案和後臺自動同步仍需從控制端本機 localhost 客戶端開啟裝置。只讀連線允許讀取，拒絕寫入；關閉面板或斷開立即停止本次傳遞。手動連線不註冊剪貼簿監聽器。

本機直連、遠端會話內和獨立標籤頁統一在桌面工具欄左上方「連線／斷開」旁顯示「剪貼簿」入口，使用同一套 dialog 面板。點選通過 `desktop-clipboard-show` 沿已驗證的 iframe 鏈通知最外層控制頁面；該訊息僅開啟 UI，不攜帶同步方向，也不能啟用本機剪貼簿。本機的原生同步方向也在面板內選擇，關閉面板保留已選的自動同步方向。播放器通過 `desktop-clipboard-available.toolbar` 宣告內建入口，外層不再重複顯示按鈕；舊版被控端僅保留外層頂部左側的相容入口。切換裝置或斷開會停止傳遞並清空舊文本。獨立桌面頁也提供手動文本面板。

可信外層工具欄提供關閉 / 我方到對方 / 對方到我方 / 雙向同步，預設關閉，只同步開啟後的複製操作。兩端更新後，從控制端本機 localhost 的 pi-web-ui 開啟遠端裝置；純瀏覽器直連 Hub 尚不提供系統剪貼簿自動同步。原生依賴 `@crosscopy/clipboard` 可用於 Windows x64、Mac x64/arm64、Linux x64，平臺或許可權不支援時只停止剪貼簿功能。只讀桌面禁止向被控端寫剪貼簿。

支援文本（1 MiB）、PNG 圖片（16 MiB、最大 32M 畫素）、最多 32 個普通檔案。新版兩端協商流式能力後，一批檔案總大小最多 16 GiB；舊端仍限制 32 MiB，不支援資料夾或符號連結。檔案從已驗證的原始檔案控制代碼分塊讀取，接收端分塊寫入自己的臨時目錄，校驗完成後才設定系統檔案剪貼簿。接收前檢查可用磁碟空間；每個程序同時傳輸的保留配額為 32 GiB，完成的檔案最多保留 16 批、32 GiB，當前批次不會因舊的 128 MiB 限制被立即刪除。斷開清理未完成檔案；原檔案不修改。文本和圖片不儲存歷史；已完成的臨時檔案不保證跨程序自動清理。

`desktop-clipboard-protocol.ts` 定義限額與訊息，`desktop-clipboard-native.ts` 封裝原生讀寫、回聲抑制及檔案暫存，`desktop-clipboard-transfer.ts` 負責有界檔案讀寫與 SHA-256，`desktop-clipboard-connection.ts` 處理方向、分塊和確認視窗，`desktop-clipboard.ts` 處理端點鑑權。獨立 WebSocket 避免檔案內容佔用桌面幀佇列；新版最多 32 個 24 KiB 分塊等待確認，舊端仍逐塊確認。超時、磁碟不足和原始檔變化只取消本次傳輸並保留同步方向，可重新複製；協議或完整性異常仍斷開連線。瀏覽器顯示傳輸進度。瀏覽器橋只接受使用者選定方向和對應視窗的訊息，遠端頁面不能主動開啟我方剪貼簿。本機 viewer 端點位於禁止遠端中繼的 `/api/device-desktop/local/` 下，遠端端點沿用桌面鑑權。opaque iframe 的本地網路許可權僅用於已有能力入口，不改變來源隔離。

`desktop-preferences.ts` 按裝置身份儲存畫質、解析度上限、幀率、適應視窗、只讀和使用者明確選擇的剪貼簿方向。可信外層負責持久化，opaque 頁面通過驗證來源的訊息橋讀寫畫面偏好，不能寫剪貼簿方向。票據更新不會清空偏好；獨立標籤、縮放返回和重連會恢復配置。只讀連線臨時限制同步方向，保留原選擇；恢復監聽不會發送開啟前已有的剪貼簿內容。

## 平臺與啟用

Windows 未安裝桌面後臺服務時，採集依賴 pi-web-ui 所在的互動使用者會話。該會話變為 Disconnected 或切到鎖屏桌面時，LAN/P2P/Hub 通道正常也不能使普通使用者採集器繼續工作。已安裝下述服務時，採集跟隨當前可用的使用者/控制台會話，可進入 Windows 鎖屏登入桌面；登入仍由 Windows 處理。服務採集程序在登入或會話切換時退出，Node 會在 30 秒恢復視窗內按 250 毫秒至 2 秒退避重建採集，保留當前瀏覽器連線，丟棄切換期間輸入；收到新畫面後恢復。超出恢復窗口才向頁面報告可重試錯誤，前臺每 10 秒重試。手動斷開、關閉視窗會取消採集重建；前臺重試在後臺頁面暫停。預覽採集錯誤不會誤觸發 LAN/P2P 回退。

### Windows 鎖屏桌面服務

Windows x64 全域性安裝 npm 包時自動安裝或更新內建桌面服務，只需確認 Windows 管理員授權。npm 停用 lifecycle 指令碼時，在終端啟動 pi-web-ui 或執行原有的 `server install/start/restart` 會自動補裝，不再要求單獨執行桌面安裝命令。後臺啟動、CI、Linux 和 macOS 不彈出 Windows 授權。

安裝器按原生原始檔和編碼器清單指紋判斷是否需要更新；同一指紋取消或失敗後不反覆彈窗。手動解除安裝會關閉自動補裝，`PI_DESKTOP_SERVICE_AUTO=0` 也可停用。需要主動重試或檢查時才使用以下維護命令（install 會自行申請管理員授權）：

```powershell
pi-web-ui desktop service install
pi-web-ui desktop service status
```

安裝器使用 Windows 的 .NET Framework 編譯器生成固定的採集程式，放在管理員/SYSTEM 可寫、繫結賬戶只讀的 `Program Files\pi-web-ui-desktop` 下，註冊自動啟動的 `PiWebDesktop` 服務。提權前記錄原始賬戶 SID，使用其他管理員憑據授權也不會誤繫結到管理員。服務編譯失敗不替換已有程式，啟動失敗嘗試恢復上版。解除安裝用 `pi-web-ui desktop service uninstall`，移除服務啟用標記並恢復普通使用者採集器選擇，保留受保護安裝檔案。自動安裝不改變遠端桌面的啟用偏好或已有訪問鑑權。

Windows 影片路徑按顯示器實際 DXGI 介面卡選擇 NVENC（NVIDIA）、AMF（AMD）、QSV（Intel，包括核顯），首先嚐試 GPU 紋理編碼，再嘗試記憶體畫面硬體編碼，最後才使用 libx264。Media Foundation 只在強制硬體模式下作為系統相容後端。實際啟動併產生影片才算成功，失敗會切換候選後端，診斷顯示後端與失敗原因。

預設 FFmpeg 與桌面硬體相容編碼器隨 npm 包分發。相容構建保留 NVENC 12.1 ABI，並包含 AMF、QSV/oneVPL、Media Foundation；優先試用相容構建的硬體路徑，失敗後保留預設構建和軟體回退。NVIDIA 仍先檢查驅動實際支援的 API。兩個程式均校驗 SHA-256 後複製到受保護目錄，服務只接受固定列舉選擇，不接受外部可執行路徑。受保護檔案沿用 `ffmpeg-nvenc-compat.exe` 名稱以相容舊安裝。構建來源與許可證隨包提供；相容構建入口為 `scripts/build-ffmpeg-compat.mjs`，釋出端用 `scripts/fetch-ffmpeg.mjs` 準備兩套二進位制，終端使用者不另裝 FFmpeg 或 RustDesk。

`scripts/patch-ffmpeg-desktop.mjs` 儲存固定 FFmpeg 原始碼補丁（`desktop-timing-v2`）：Windows 高精度 waitable timer、DXGI 非阻塞取幀、無更新時的有界休眠、落後時重置取樣時鐘，以及 D3D11 影片處理器的紋理與色彩轉換相容。高精度計時不可用時保留原有休眠回退，不全域性調整系統時鐘、不忙迴圈。GPU BGRA→NV12 使用 BT.709 limited，並在原生編碼命令的 H.264 VUI 中寫入匹配的色彩矩陣/範圍；原始 BGRA、CPU 轉換和預設編碼器不套用此標記。修改這些補丁後必須重建二進位制、更新歸檔與二進位制摘要，並提供匹配原始碼和第三方許可證。

資訊面板的輸出/傳送 FPS 是影片幀計數，包含 `ddagrab` 為固定輸出頻率複製的幀，不是顯示器重新整理率或獨立畫面更新率。60 Hz 顯示器不能用此計數驗證真實 120/240 Hz。服務端統計附帶單調時鐘 `elapsedMs`，前端用它計算輸出/傳送 FPS，避免把中轉統計訊息的到達抖動當成採集掉幀；本地繪製率仍按瀏覽器時鐘計算。H.264 沒有 JPEG 的逐幀 ACK，確認等待顯示 `—`，不得將預設的 0 當作零延遲證據。診斷時可用相容 FFmpeg 的 debug 日誌 `Desktop update`、`Duplicated output frame` 區分桌面更新與重複幀（關閉日誌合併：`-loglevel repeat+debug`）。

未安裝系統服務時，普通使用者採集也會探測全部廠商和系統硬編碼，相容 NVIDIA 驅動；能力快取一分鐘且失敗失效。該路徑仍不提供安全桌面能力。60/120/240 是採集目標上限，實際受顯示輸出、驅動、編碼能力、網路和瀏覽器影響。瀏覽器 H.264 WebCodecs 需要安全上下文（HTTPS 或 localhost）；公網 HTTP Hub 會使用 JPEG，不能把編碼器測試幀率當作該入口的顯示幀率。

Web 後端通過同一使用者的本機命名管道呼叫服務；管道拒絕網路登入賬戶，服務檢查客戶端賬戶，客戶端檢查管道服務程序與 SCM 登記的 PID 一致。服務不接受指令碼、可執行路徑、任意會話號或外部命令，只接受預覽、只讀、控制及對應的原始畫素/壓縮影片模式和有界桌面輸入。控制端已有的 HTTP/WS 鑑權、裝置歸屬校驗和只讀限制繼續生效。

服務在呼叫賬戶的活動會話或當前控制台啟動獨立的 SYSTEM 採集程序，通過 `OpenInputDesktop`/`SetThreadDesktop` 跟隨普通桌面與登入桌面；遇到其他已登入賬戶的桌面時拒絕訪問。採集程序通過 SYSTEM 專用隨機管道傳輸，並用 Windows Job 保證斷連和服務退出後終止。輸入驗證和只讀限制在 Node、服務及採集器分別執行。視窗控制代碼/影像/輸入不經過聊天或模型；沒有新增監聽埠，不儲存登入密碼，不配置自動登入、不自動解鎖。

該服務只負責桌面採集與輸入。Web/裝置聯結器必須仍在執行；不會把現有聊天服務改成 SYSTEM，也不承諾重啟未登入時裝置聯結器自動上線。物理顯示輸出、系統電源狀態及要求 Ctrl+Alt+Del 的登入策略仍可能影響操作，未增加虛擬顯示驅動或修改登入策略。

遠端裝置標籤頁顯示「備註 · 計算機名 · pi-web-ui」，無備註時只顯示計算機名，只有舊 Hub 未提供名稱時才回退裝置 ID。Hub 和本機 LAN/P2P 入口共用名稱規則，圖示從當前授權通道載入應用原有 favicon，不額外開放裝置資源。更新後重新開啟遠端標籤頁生效。

遠端聊天頁面內也可以點選桌面的“獨立標籤頁”。遠端 iframe 只發送帶請求 ID 的訊息；可信外層驗證訊息來源後申請同一裝置的新一次性票據並開啟視窗。新視窗與原預覽各有獨立入口，不開放 iframe 的 popup/same-origin 許可權，也不接受遠端頁面指定跳轉 URL。需要更新控制端、被控端和 Hub，重新開啟舊標籤。

遠端頁面內選擇另一臺電腦時，通過當前能力根下的 `__desktop_target?device=<id>` 請求獨立桌面入口。Hub 同時驗證來源裝置與目標裝置歸屬，生成目標裝置自己的 capability；LAN 入口由本機聯結器向已繫結 Hub 申請目標票據。普通遠端頁面不能呼叫本機 `devices/:id/open` 管理介面。巢狀預覽、即時桌面和獨立標籤使用明確目標 ID，剪貼簿訊息沿對應桌面視窗傳遞，不讀寫中間那臺電腦的剪貼簿。巢狀跨裝置桌面目前走 Hub 中繼。

僅持有桌面票據的 wrapper 允許 opaque 祖先（不設定 `frame-ancestors`，因為 `http: https:` 也無法匹配 opaque origin）；普通裝置入口仍限制同源祖先。所有遠端內容仍在不含 `allow-same-origin` 的沙箱內，`frame-src` 限於該裝置能力路徑，訊息校驗來源視窗和 origin。`tests/device-nested-desktop-test.mjs` 使用真實 Hub、兩個聯結器及 Chrome 驗證切換目標、剪貼簿歸屬、預覽恢復和獨立標籤；畫面與剪貼簿使用測試後端。

### Windows：關閉 RDP 後繼續使用當前桌面

有本機控制台的 Windows 可以嘗試把當前活動 RDP 會話交還控制台。在該 Windows 上執行 `pi-web-ui desktop console --check`，只檢查會話、許可權及是否有其他控制台使用者，不修改登入狀態。

確認物理螢幕允許保持已登入後，在**同一 Windows 賬戶的管理員終端**執行：

```powershell
pi-web-ui desktop console --confirm
```

這會呼叫系統 `tscon`，立即斷開當前 RDP，把會話交還本機控制台。小預覽會自動重試採集。命令只接受當前程序所屬、同一使用者的活動 RDP 會話；存在其他已登入控制台使用者時拒絕執行，不接受指定會話 ID，不儲存密碼，不配置自動登入。未確認、未提權、鎖屏或已斷開的會話均不自動切換。切換失敗會報告錯誤，不能把命令成功等同於畫面驗收；需繼續檢查即時畫面。

這是保留已登入控制台的方式，不提供鎖屏、UAC 安全桌面、登出後或重啟未登入時的無人值守控制；無顯示輸出的雲主機還可能需要虛擬顯示裝置。後續重新登入 RDP 又會改變會話狀態。

預設關閉，在桌面頁面點選啟用；偏好原子儲存至 `<dataDir>/desktop-settings.json`。`PI_DEVICE_DESKTOP=1` 強制啟用，頁面不能覆蓋環境變數。執行時支援不代表已經獲得系統授權，捕獲啟動失敗會在頁面顯示原因。

| 平臺          | 實現                                                                      | 條件                                                                           |
| ------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Windows       | 使用者會話助手或 Windows 後臺服務，GDI 捕獲與 SendInput                   | 普通模式依賴活動使用者桌面；鎖屏採集需安裝後臺服務                             |
| macOS 14+     | Swift 助手，ScreenCaptureKit SCScreenshotManager 捕獲與 CoreGraphics 輸入 | Xcode 或 Command Line Tools 提供 Swift；螢幕錄製許可權；控制還需輔助功能許可權 |
| Linux X11     | ffmpeg x11grab 採集，xdotool 輸入                                         | DISPLAY/XAUTHORITY，ffmpeg，xdpyinfo 或 xrandr；僅檢視可不安裝 xdotool         |
| Linux Wayland | 暫不支援                                                                  | 後續需接入 Portal/PipeWire，不能把 XWayland 當完整桌面                         |

舊 `PI_DEVICE_VNC_*` 配置不再讀取。macOS 許可權申請由被控 Mac 本機的「裝置中心 → 本機遠端桌面」發起：點選“授予螢幕錄製許可權”或“授予遠端控制權限”，再在 macOS 彈窗或設定中確認。僅檢視需要螢幕錄製，控制還需輔助功能。遠端連線僅檢查許可權，不請求授權或開啟系統設定。本機申請會嘗試開啟未獲授權的對應設定頁；系統可能不重複彈窗，授權物件以 macOS 識別的實際宿主為準。請勿在“＋”檔案選擇器中猜選程式。系統要求重啟時，重啟實際服務再連線。當前 Windows 已實機驗證，macOS/Linux 尚需目標機器實機驗證。

macOS 採集和授權統一使用 `~/Library/Application Support/pi-web-ui/native-desktop/PiWebDesktop`。首次使用由 Apple `swiftc` 非同步編譯，原始碼不變時跨連線、重啟和 Node 升級複用同一二進位制，避免每次臨時解釋 Swift。升級導致元件改變仍可能需要重新授權，固定路徑不繞過 macOS TCC，也不保證簽名變化後保留許可權。預覽與操作視窗統一解釋許可權錯誤，許可權或服務恢復後定時重連；真實 TCC 授權與 Swift 編譯仍須在 Mac 實機驗證。

## 宿主接入和許可權

`server/device-center/desktop.ts` 匯出 `createDeviceDesktop({app,dataDir,authorize})`。在 SPA fallback 前註冊路由，在已有 HTTP upgrade 分發中先呼叫 `desktop.handleUpgrade(req,socket,head)`；未知路徑返回 false。服務關閉時呼叫 `desktop.close()`。

HTTP/WS 獨立檢查物理迴環來源、迴環 Host、本機鑑權與存在時的精確 Origin。設定寫入另要求 Origin；聯結器重寫固定的本機 Host/Origin 並注入本機憑據，Hub 校驗賬號和裝置歸屬。公網建議使用 HTTPS/WSS。

| 路徑                                       | 用途                                 |
| ------------------------------------------ | ------------------------------------ |
| GET /desktop                               | 自包含瀏覽器頁面                     |
| GET /desktop-preview                       | 只讀低頻預覽頁面                     |
| GET /api/device-desktop/preview            | 授權後的預覽 JPEG，禁止快取          |
| GET /api/device-desktop/status             | 平臺支援、啟用狀態和診斷原因         |
| GET /api/device-desktop/setup/status       | 相容狀態入口                         |
| GET /api/device-desktop/local/status       | 僅裝置本機設定頁的狀態               |
| POST /api/device-desktop/local/permissions | 僅本機請求 screen/control 系統許可權 |
| POST /api/device-desktop/local/enable      | 僅本機啟用或關閉遠端桌面             |
| POST /api/device-desktop/setup/enable      | 持久設定 `{enabled:boolean}`         |
| POST /api/device-desktop/setup/install     | 相容入口，報告無需安裝元件           |
| WS /desktop-ws?viewOnly=1                  | 預設只讀；顯式 viewOnly=0 開啟控制   |

只讀由服務端和原生助手按連線強制；有裝置訪問許可權的使用者可顯式建立控制連線，因此它不是賬號級只讀授權。切換隻讀會重新連線。狀態 `available` 只表示已啟用且執行時可用；系統許可權和圖形會話仍需捕獲啟動驗證。

頁面 URL 全部相對 document.baseURI 構造，支援 `/device/<id>/` 和其他反代字首。頁面錯誤使用 textContent。舊 noVNC 資源路由不再提供。

## 傳輸與清理

輸出為最大 4 MiB 的二進位制 JPEG，文本幀報告 ready/error/stats。瀏覽器完成繪製後回覆 `{type:"ack"}`，每連線僅有一幀等待確認；等待期間只保留最新一張候選幀，ACK 到達且上次傳送完成後立即發出，避免舊幀排隊。15 秒未確認會報告錯誤並關閉採集，使用者可重新連線。傳輸佇列上限 4 MiB，另有最多 4 MiB 的最新候選幀。輸入為最大 16 KiB 的 JSON，校驗 normalized pointer、wheel、物理 key code、text 和 release。

即時頁的“連線資訊”展示累計採集/傳送/替換幀數、確認等待、傳送佇列，以及瀏覽器測得的顯示 FPS 和解碼繪製時間。確認等待包含網路、解碼與瀏覽器排程，不等同於純網路 RTT；此輪保留原即時採集頻率，並未升級為 30 FPS 影片編碼。

每裝置最多四個桌面連線；啟動超時 60 秒，30 秒 ping/pong，30 分鐘無使用者輸入釋放。斷開、關閉、停用或錯誤清理捕獲並釋放按住的鍵鼠。原生程序輸入佇列、幀大小和錯誤日誌均有界，取消先請求退出再終止特定子程序。捕獲器本身不監聽額外 TCP 埠；裝置聯結器按需提供共享的加密區域網埠，桌面與完整裝置網頁共用該通道。本機服務入口由服務持有 TLS-PSK；純瀏覽器 Hub 入口持有裝置限定的短期 WebRTC 閘道器金鑰，PSK 與裝置憑據仍留在服務端。不保存錄像；接收的剪貼簿檔案按上述限額暫存。

## 驗證

### 原生 GPU 編碼通道預覽

Windows x64 新通道由本專案獨立實現 D3D11 / FFmpeg 硬體編碼適配，參考 GPU 優先架構，不包含 RustDesk `hwcodec` 原始碼，詳情和固定依賴版本見
[`native/desktop-codec/README.md`](../native/desktop-codec/README.md)。它按真實桌面更新發送完整 H.264 幀，
靜止時傳送獨立心跳；瀏覽器繪製後反饋幀編號，採集端按未確認視窗暫停獲取下一幀，避免持續積壓。
自動模式依據相對最低確認時間的增長和解碼佇列，先降位元速率，再降幀率；手動畫質仍保持使用者選項。
幀率和位元速率通過原生介面動態更新；本版 FFmpeg 的 AMF 需在引數變化時重建編碼器，仍保留瀏覽器連線。
解析度、顯示器或 Windows 桌面切換同樣重建編碼器。
DXGI 無首幀或無法建立複製時，普通已登入桌面優先嚐試 WGC GPU 採集，直接將紋理交給原生硬體編碼器；
安裝器在支援的 Windows 上用系統自帶 WinRT 後設資料編譯此適配，不另裝程式或驅動。
部分 Windows 無法在 SYSTEM 程序中啟用 WGC（可能返回 `E_OUTOFMEMORY`）。此時由受保護服務啟動
同一執行檔的只讀使用者採集程序，驗證登入使用者 SID、管道對端 PID 和有限影片包；輸入繼續由 SYSTEM
處理。進入鎖屏等安全桌面時關閉使用者採集，恢復系統採集。子程序隨連線退出，由 Job 統一回收。
不支援 WGC 的系統或安全桌面仍可回退為複用 GDI 畫素緩衝，再上傳 GPU，繼續使用硬體編碼；
相同畫素不會重複傳送。此路徑保留 GPU 縮放、顏色轉換和編碼，但不能消除 GDI 採集本身的耗時。

新二進位制協議通過 `video-flow-v1` 能力指紋和獨立服務模式協商，舊客戶端繼續使用原通道。
`PIV1` 瀏覽器幀頭只在 URL 顯式協商後傳送，裝置中繼仍透傳 WebSocket。
預覽包的實際執行時標識為 `native-d3d11`。尚未完成 Intel、其他驅動以及 120/240 Hz 顯示器實機驗收；
瀏覽器統計中的低靜態 FPS 是正常按需採集行為，不能用重複靜止畫面作為高刷驗收。

正式打包前，在 Windows x64 構建機執行 `npm run build:desktop-codec`，再執行 `npm run pack:p2p`；
CI 的 Windows 安裝包流程執行相同的構建與校驗。原始碼、補丁、許可說明和可重連結庫隨原生元件打包，
缺少原生元件或重連結材料時釋出會失敗並給出構建命令，不會靜默生成缺少硬體編碼能力的包。
如從其他系統釋出 npm 包，需先從 Windows 構建機複製對應的原生元件和相容編碼器輸出；
維護者還應核對自身發行渠道的許可證要求。詳見 [`native/desktop-codec/README.md`](../native/desktop-codec/README.md)。

相關測試在 `tests/unit/device-center-desktop*.test.ts`、`device-desktop-native.test.ts`、`device-desktop-linux.test.ts`、`device-desktop-relay.test.ts` 和 `device-lan*.test.ts`。LAN 測試使用真實 TLS PSK、HTTP/WS 和 Chrome 巢狀沙箱，驗證聊天與畫面直連、授權隔離、路徑字首及斷線回退。覆蓋許可權、啟用持久化、原生程序清理、輸入邊界、只讀、幀確認以及真實 Hub/connector 中繼。可用 Chrome 時驗證代理字首下的畫布解碼、控制模式滑鼠移動與輸入長度；瀏覽器模擬畫面測試不等於各平臺實機驗證。

## 顯式檔案傳輸

遠端桌面工具欄的“檔案傳輸”開啟雙欄檔案管理器：左側是控制者本機，右側是當前被控裝置。兩側支援路徑輸入、主目錄/磁碟快捷訪問、上一級、重新整理、新建目錄、多選；雙擊目錄進入，選好接收目錄後按“傳送 →”或“← 接收”。下方任務列表分別顯示名稱、方向、狀態、進度、傳送路徑及接收路徑，可暫停、繼續、取消和清除已完成記錄。收起不取消傳輸；關閉桌面或切換裝置會取消未完成任務。

檔案傳輸獨立於系統剪貼簿。分塊為 1 MiB，單任務上限 16 GiB / 10000 項；原生接收端先寫選定目錄內的臨時目錄，檢查位元組數和增量 CRC32 後釋出檔案，遇到同名檔案/目錄自動新增編號，保留原檔案。舊客戶端不提供目的目錄時仍使用 `~/Downloads/pi-web-ui-Received/<日期-任務ID>`。CRC32 用於檢測傳輸損壞，不承擔身份認證；請求沿用桌面授權。重複原生分塊按偏移和 SHA-256 判重，同窗口可繼續傳輸，暫停超過 30 分鐘可能過期，需重新選擇。釋出過程中磁碟失敗可能留下部分已釋出檔案；重試複用已釋出項，不覆蓋其他檔案。

壓縮包按原位元組傳輸，不二次壓縮；原生雙向傳輸保留目錄層級和空目錄。原生路徑限定在本機磁碟或 POSIX 根目錄內、受當前服務使用者系統許可權限制，拒絕 UNC、符號連結、裝置路徑及路徑穿越。單目錄列表最多展示 2000 項；匯出目錄會遍歷完整目錄並檢查總數/大小。原始檔修改會中止該任務，防止把不同版本混為一個檔案。

檔案管理器執行在最外層控制者文件。遠端頁面只能請求開啟介面，或響應控制者發起的遠端檔案請求；不能發起本機磁碟操作。`/api/device-desktop/local/files` 要求 loopback、宿主認證、同源校驗及自定義請求頭，且被 Hub/LAN 轉發器明確禁止。它不需要開啟控制者的桌面共享。巢狀裝置頁面只轉發經過視窗身份校驗的訊息，不會把中間裝置當作“本機”。

遠端檔案操作繫結到當前已認證的桌面 WebSocket；斷開後能力立即失效。只讀連線可以檢視和下載檔案，但服務端拒絕傳送檔案和新建遠端目錄；切回可控制模式後方可寫入。

瀏覽器直接開啟 Hub 時無法任意訪問本機磁碟：支援目錄授權的安全上下文可用“選擇本機目錄”授予讀寫許可權；其他瀏覽器可選擇檔案/資料夾傳送，接收通過瀏覽器下載管理器儲存，目錄為 `.tar`。`webkitdirectory` 回退不含空目錄；瀏覽器目錄寫入取消後可能留下已完成的部分檔案。瀏覽器下載由瀏覽器管理進度，任務列表只顯示已交給瀏覽器，不宣稱校驗完成。要使用完整的雙側磁碟瀏覽，請從本機 `pi-web-ui` 開啟遠端裝置。下載響應的大檔案額度只針對 `/api/device-desktop/files/download/<任務ID>`，其他 HTTP/WS 限額保持原值。控制端、被控端和 Hub 均需更新。

影像回退通道在同一次 animation frame 中調整畫布大小並繪製，避免先清空畫布再等待重新整理產生短暫黑幀；斷開連線、鎖屏等安全狀態的清理行為保持原樣。

剪貼簿檔案同步在準備、傳輸、完成或失敗時向桌面頁面展示狀態。失敗不會清除使用者原有剪貼簿；資料夾被明確提示改用檔案傳輸。系統檔案事件之外增加活動同步期間的檔案清單檢查，防止漏掉複製事件。大檔案完成提示出現前貼上仍可能得到原來的檔案。

巢狀遠端桌面的裝置選擇器從當前訪問授權所屬賬號獲取列表（`__desktop_devices`），不讀取被開啟裝置自己的配對賬號；切換仍逐裝置校驗訪問許可權。預覽和放大視窗均可選裝置，切換保持當前模式。自動開啟當前桌面的延遲響應不能覆蓋使用者已經選擇的新目標。
