# Device Center and cross-platform collaboration (beta)

The mobile native client can list, connect to and switch between multiple devices with a Hub account and receive device notifications in one place; native login, capability, relay boundaries and build acceptance: [`mobile.md`](mobile.en.md).

Device Center is a standalone service for accounts, device connections and group chat. Each pi-web-ui connects to the hub outbound, so no computer needs a public address. Device Center is self-hosted; the repository does not provide a live official public entry. Windows, macOS and Linux use the same connection protocol, but real platform testing still has to run on the corresponding machine.

The main app's **device connections and cross-platform collaboration** is the single entry point, split into **Devices and connections / Groups and tickets / External channels**. The devices section keeps pairing, bots, remote desktop and execution permission; the groups section creates or manages groups and directly configures an independent AI Router, views tickets and retries failed runs; external channels embed the bundled Superagent for configuring GitHub / Feishu credentials and group mappings, with no separate install or top-bar entry. Actual chat still uses the group main conversation flow on the left.

Standalone deployment steps: [Device Center Deployment Guide](device-center-deployment.en.md) — from server connection and default IP + HTTP through opening ports, optional domain and HTTPS, verification and failure recovery, with no project context needed.

Once Device Center is bound, the brand icon in the top left opens a device quick list that jumps straight to devices of the same account or opens remote desktop. The quick list reuses Device Center's device catalog and binding authorization entry, supports online status, manual refresh and narrow-screen display, and closes on an outside click or Escape. Until a binding exists, the plain brand display stays; a temporary connection failure does not revoke a known binding entry.

## First use and install guidance

With no hub bound, bots and groups can be created locally without connecting another device, registering an account or installing a standalone Hub. The group entry starts an in-process private loopback Hub on demand, reusing the existing bot, group chat, task and file protocols; data lives in `<pi-web-ui data-dir>/local-device-hub/`, and credentials are used server-side only and rotate on restart. Local tasks may execute, still limited by the bot capability allowlist and local approvals; execution permission for an external Hub stays off by default. Local bots use the existing unpaired scope, and groups and messages survive restarts; binding an external Hub switches to its separate scope and unbinding restores local data, so the old runtime must stop before switching. While an external Hub is offline its binding and known groups are kept, and local data is not switched in automatically.

The Device Center overview always offers bot and group management. When cross-device collaboration is needed, choose “Connect to an existing hub” (「连接已有中心」) or “Create my hub” (「创建我的中心」); creating can use the current machine hosting the pi-web-ui service or deploy to an existing server. With no server yet, start on the current machine to try it out — a server purchase is not a prerequisite. “Current machine” here means the machine running the pi-web-ui service, not the device with the browser open.

One-click local install is reachable only through localhost/127.0.0.1 by default; a reverse-proxied deployment can declare its domain with `PI_WEB_ALLOW_HOSTS`, which then becomes reachable too (behavior is unchanged when undeclared). Write requests must be same-origin. The page first shows the platform, Node version, separate data directory and install plan; clicking install runs the Hub CLI of the current package in a separate child process with fixed arguments, never through a shell. It listens on `127.0.0.1:8790` by default and stores data in `<pi-web-ui data-dir>/device-hub/`, separate from client config. The page can change the listen IP, port and public origin; for other devices to connect, use an address those devices can reach and configure the matching network access.

A successful install means the service is installed and passed the start check — not that anyone is logged in or paired. Check the installed service with `pi-web-ui hub status --json` and disable registration with `pi-web-ui hub restart --allow-registration=false`. Then open the hub, create an account and return to the pairing flow; create bots and groups after binding. Installation explicitly opens account registration, so disable open registration with the service management command once the account exists. A bound hub that is temporarily offline or whose list request failed must not be treated as unconfigured; the group entry and the already loaded list stay.

“Let AI deploy for me” (「让 AI 帮我部署」) opens a separate conversation carrying the chosen deployment target, listen address, public address and available local environment information. The AI checks the environment first, then deploys and verifies through the same CLI set; remote deployment needs an explicit target and an existing trusted connection method from the user, and the remote plan must not be run against the current machine by default. Passwords, private keys and pairing credentials must not enter the deployment prompt. The prompt carries the public raw text of the standalone deployment guide plus a web fallback link and requires reading it first; default IP + HTTP, with domain and HTTPS optional. The AI must distinguish the system firewall from the cloud security group and state the actual TCP port, source range and the place to open it; when it cannot operate the cloud console, mark it as awaiting the user and re-verify external reachability afterwards. This entry does not buy a server or complete account login automatically.

`GET /api/device-center/setup` returns the local deployment plan plus the existing installation, ownership and health state queried via the CLI `hub status --json`; a failed read must not be treated as not installed. After a refresh or leaving the page, the actual install address can be restored and pairing continued; leaving the page does not undo an already submitted system service install. `POST /api/device-center/setup` accepts `host`, `port`, `publicUrl` and an explicit `allowRegistration: true`. Install requests are mutually exclusive and a duplicate returns 409; validation failure returns 400 and install failure returns 500. Shutting down the Device Center runtime cancels and waits for the install child process to exit, so an old operation cannot keep publishing success.

## Usage flow

1. Follow the first-run guidance in Device Center to connect an existing hub, or deploy your own with one-click local install, AI assistance or the CLI below. HTTP with a public IP works directly; device web pages and remote desktop share the Hub port by default, entered at `/device/<device ID>/`, with no extra device port to open.
2. Start pi-web-ui on each computer and switch the top bar to the “Device Center” in-app tab; the UI follows the current theme and language and opens no separate browser page. Device binding management still requires localhost/127.0.0.1 by default (a domain declared in `PI_WEB_ALLOW_HOSTS` works too, for reverse-proxied deployments). The old `/devices` address redirects to the device tab of the main app.
3. Enter the hub address and a name for this machine to get a pairing code valid for ten minutes.
4. Log in to your account on the hub and confirm the pairing code. The local page polls for the device credential, which is stored only in the local data directory and never shown to the browser.
5. In Device Center on the hosting device create a bot: enter a name and identity prompt, browse the fixed working directory through the global path component and pick a model with the common model selector or inherit the machine default. Tools, Skills and MCP use a searchable checklist; when a new bot first loads its catalog, items default to the currently saved tool switches, later catalog refreshes or project switches do not override manual choices, and editing an existing bot keeps its grants; built-in tools are shown in full, high-privilege and platform-unsupported tools are only flagged rather than hidden or rejected through a bot-specific blocklist, and execution grants follow the bot's explicit tool allowlist (platform availability and the tools' own checks still apply); switching the project directory refreshes that project's capability catalog, and grants that exist but are currently unavailable stay visible and can be removed. One device can host multiple bots. Click ＋ in “Groups” (「群组」) on the left and pick a bot of this account to create a group. Clicking the group name reuses the main conversation flow; type `@`, search and select a bot, then send the task. A candidate inserts an explicit target marker carrying the stable bot ID; typing `@name` alone dispatches nothing. The Hub website can also create groups and chat.
6. On a computer that must run tasks and receive files, explicitly enable execution permission on its local binding page. Off by default. It lets the agent modify files, run commands and apply explicitly submitted file-sync requests, still subject to local approvals.

Group members are only bots; devices just host them, keep an online connection and grant execution. One bot can join multiple groups; devices, bots and groups are isolated between accounts. Every device's pi-web-ui can create groups from the collapsible “Groups” (「群组」) section on the left and open group chat, and can rename, manage members or delete a group from the context menu; the Device Center tab keeps group management while actual chat always enters the existing main conversation flow. The Hub alone handles accounts, device connections, group and message store-and-forward, task routing and file relay, so device users need not open the Hub website to operate. The Hub website keeps its own separate entry. Cross-account invitations and team member management are not supported yet.

Local user actions and AI relay use different credentials: a new pairing generates a device execution credential and a local interaction credential separately, the latter held only by the restricted local HTTP interface and never handed to the browser or a model. A local human can start a new task chain; an AI credential still needs a trusted parent task. Old bindings without an interaction credential must be re-paired. Deleting a group or removing a member is refused while related unfinished tasks exist, so execution ownership is not lost.

## Top-left device overlay (desktop popover / phone drawer)

The brand button at the top-left of the topbar (`BrandDeviceMenu`) turns into the device entry point once there is an external binding: on desktop it is a popover hugging the button, and on narrow screens or coarse pointers (`(max-width: 640px), (pointer: coarse)`) it becomes a drawer rising from the bottom. Both share the same content body `DevicePanel` and only swap the container and the sizing tokens.

- **One row per device = one clickable area**: clicking the whole row opens that device directly (the most frequent action, zero menu levels); the row end always shows the two actions `远程桌面` (Remote desktop) and `⋯`, and `⋯` only holds low-frequency items (set note / copy device ID). Remote desktop is the second most frequent action and does not go into the menu — otherwise it costs one more click. After opening any device the popover/drawer collapses immediately.
- **The local row only identifies**: no whole-row link, no `远程桌面` (opening yourself is a duplicate window, and remote-controlling yourself is meaningless), only the 「本机」 (This device) label and `⋯` (note / copy ID).
- **Sizes**: the desktop popover is 264px wide with 30px rows and 24px icons; the touch layout uses 56px rows and 44×44 touch blocks (a 1px divider between the two, read as a 「分体按钮」 / split button), shows the device ID as a second line inside the row and hides the chevron.
- **Notes**: on desktop the note is edited inline in the row (`Enter` saves, `Esc` cancels, row height unchanged); on phone it is 「长按整行」 (long-press the whole row) or `⋯ → 设置备注` (set note), which opens an edit bar at the bottom of the drawer (`保存` / Save finishes it in one tap).
- **Gestures**: the drawer pulls to refresh when the list is scrolled to the top (zero clicks), pulls down on the top grabber to close, closes on backdrop tap, and closes with the `Esc` key. Touch feedback uses `:active` and does not depend on `:hover`.
- **Overlay contract**: the `⋯` menu portals into `body` + `fixed` (otherwise `.dp-scroll` / the popover's `overflow` clips it), and stacking goes through `useOverlayZIndex()`; the drawer container uses an overlay stack level, `max-height: 62dvh` + `overscroll-behavior: contain` + `env(safe-area-inset-bottom)`.
- **Single source for the breakpoint**: `COARSE_POINTER_QUERY` in `web/src/use-coarse-pointer.ts` and the `.dp-*` media queries in `styles.css` must be changed together, otherwise the component and the styles run two different layouts.
- **Sources of truth**: `web/src/components/DeviceDirectory.tsx` (fetching / note write-back / the page-style cards) · `web/src/components/DevicePanel.tsx`★ (the popover and drawer content body) · `web/src/components/BrandDeviceMenu.tsx` (popover / drawer container) · `web/src/use-coarse-pointer.ts` · `web/src/styles.css` (`.dp-*`). Unit tests: `tests/unit/device-panel.test.ts`, `tests/unit/brand-device-menu.test.ts`.

## Deploying the hub

With the npm package installed the service can be managed directly; a source checkout needs the server built first:

```sh
npm run build:server
```

Prefer the dedicated service management commands to install and configure logon autostart:

```sh
pi-web-ui hub install --host 127.0.0.1 --port 8790 --public-url http://127.0.0.1:8790 --allow-registration
pi-web-ui hub status --json
pi-web-ui hub restart --allow-registration=false
pi-web-ui hub stop
pi-web-ui hub start
pi-web-ui hub uninstall
```

`install` saves the config and starts the service; `start/stop/restart/status/uninstall` use the saved config, and `restart --allow-registration=false` changes only the registration setting while keeping the rest. `uninstall` removes the autostart config and keeps account, device and group data. Installation refuses to overwrite a service that already exists or whose ownership cannot be confirmed; a taken port, insufficient privileges or a failed health check report explicit errors. After an interrupted install, check with `status --json` first and recover with `start` or `restart`; do not delete the data directory to retry.

Linux uses `systemd --user`, macOS a launchd user service, Windows a logon scheduled task. When no native service manager is available or privileges are insufficient, installation reports failure; booting Linux without a logged-in user needs an administrator to enable linger for that user. Locks in the CLI config are reclaimed only after the holding process is confirmed gone; an unknown or still-live holder is never overwritten.

### Automatic public HTTPS deployment

Public Linux installs configure trusted HTTPS by default. Replace the address below with your own public IPv4 or a domain already resolving to the server; nothing depends on a particular computer, a fixed IP or another app's config:

```sh
pi-web-ui hub install --public-url https://YOUR_PUBLIC_IP_OR_DOMAIN --allow-registration
```

Debian/Ubuntu prepares Certbot automatically (at least 5.4), requests a short-lived Let's Encrypt certificate for a public IPv4 and a domain certificate for a domain, and installs a Node HTTPS/WebSocket gateway plus a renewal timer that checks every six hours. A matching existing Certbot certificate is reused with its original renewal hooks untouched; the gateway loads renewed certificates automatically. Administrator privileges are used only for certificates, ports 80/443 and the systemd system service; the Hub keeps its original user service and data directory. Other Linux distributions must install Certbot 5.4+ beforehand; automatic IPv6 certificate deployment is not supported yet.

Public TCP 80 (certificate validation) and 443 (HTTPS) must be open in the cloud security group and firewall. The automatic installer does not take ports from other apps: if 80/443 are already taken and no reusable certificate exists, use the existing reverse proxy and pass `--https=external`; an intranet HTTP or debugging deployment can pass `--https=off`. An HTTP `--public-url` becomes the default HTTPS address of the same host once automatic deployment succeeds, and the internal Hub port stays 8790. A failed HTTPS check restores the previous Hub config and the command does not report success.

After updating an existing Hub to a build with HTTPS support, run `pi-web-ui hub https` once. Use `--public-url https://YOUR_DOMAIN` to set the new address. The original HTTP address keeps only authenticated device connections and the browser entry redirects to HTTPS; existing accounts, groups and device bindings are kept. Devices can switch to the HTTPS Hub address later, and the old HTTP port can be closed once everything has migrated. `PI_DEVICE_HUB_LEGACY_ORIGINS` is that compatibility allowlist (at most eight HTTP origins) and does not relax Origin checks on the browser management API. `PI_DEVICE_HUB_HTTPS=off|external` means the same as the corresponding install flags.

HTTPS provides the browser secure context needed for WebCodecs, the clipboard and similar APIs; whether P2P can be established still depends on both sides' versions and on NAT/firewalls. HTTPS alone does not turn a relay into a direct connection. Uninstalling only the Hub user service does not remove the shared certificate or the HTTPS system service; when retiring the whole deployment, also stop the matching `pi-device-hub[-name]-https.service` and the renewal timer.

`pi-web-ui hub` without a subcommand keeps the foreground mode and honours the following environment variables; a source checkout can also run `node bin/pi-device-hub.mjs`.

| Environment variable               | Description                                                                                                             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `PI_DEVICE_HUB_PUBLIC_URL`         | The hub's HTTP or HTTPS origin, e.g. `http://203.0.113.10:50001`, with no path                                          |
| `PI_DEVICE_HUB_PATH_ACCESS`        | On by default; `0` restores the legacy separate domain/port mode                                                        |
| `PI_DEVICE_HUB_DEVICE_DOMAIN`      | Compatible with legacy separate device domain config; by default devices are reached through the hub's single-port path |
| `PI_DEVICE_HUB_HOST`               | Defaults to `127.0.0.1`                                                                                                 |
| `PI_DEVICE_HUB_PORT`               | Defaults to `8790`                                                                                                      |
| `PI_DEVICE_HUB_DATA_DIR`           | Defaults to `~/.pi-device-hub`; must be separate from the client data directory                                         |
| `PI_DEVICE_HUB_ALLOW_REGISTRATION` | `1` opens registration, off by default; enable it for the first account, then restart to disable                        |

### Hub online upgrade

The standalone Hub's “One-click upgrade” (「一键升级」) and `pi-web-ui hub update` install the npm `latest` package into `releases/<random ID>/` under the service config directory, then switch the service entry and restart. If install or the build check fails, the old service keeps running; if the new version fails to start, the old service definition saved in `service.previous` is restored and restarted. Data directory, instance ID, accounts, device credentials and groups stay in place. A rollback restores the running program, not the business data; published versions must keep data backward compatible. Once a previous managed version is confirmed, a successful upgrade keeps the current and previous running versions and cleans up older managed directories; when directory ownership cannot be proven, the directory is kept for manual diagnosis.

The Hub's first account is the deployment owner, and only that account can upgrade or query upgrade tasks. Web cookie operations still check same-origin; the device-side human entry uses a separate `uiCredential` and requests `/api/device-user/system/upgrade`, while an execution credential cannot call system maintenance. Old devices without a human credential must be re-paired. A foreground or embedded Hub does not support automatic service upgrades and reports an explicit error.

An upgrade request returns HTTP 202 with a persistent task ID; acceptance is not success. `<Hub data directory>/hub-upgrade.json` records `queued/running/succeeded/failed`, phase, version, boot identity and failure reason; `hub-upgrade.log` holds that run's npm/preflight logs. The page queries the result by task ID and shows success only when the target version matches the health-check version, the instance and registration config match and the boot identity changed. A still-healthy old process, an upgrade API error or a query timeout never count as success. Tasks and lifecycle use separate cross-process locks that stop the web UI and the command line from submitting or running upgrades at the same time.

The executor is started by an independent service manager task: Linux uses `systemd-run --user`, macOS a one-off launchd job in the GUI domain, Windows a separate temporary scheduled task, so stopping the Hub does not kill its own upgrade process. The upgrade task reuses the config location validated when the service was installed and re-checks the instance and data directory instead of having a background process re-infer HOME or APPDATA; config paths are not exposed through the upgrade API. Windows waits for the scheduled task and its instance to stop and confirms the TCP resource of the configured listen address has been released before starting the new service, allowing up to four minutes for the release check. If the port is still held at the deadline, or the resource state cannot be verified, the upgrade fails explicitly and does not kill whoever holds the port. macOS confirms the old launchd job was removed before starting the new service. npm must sit next to Node. Upgrade dependency installs disable lifecycle scripts and optional dependencies, and a standalone Hub loads neither the Agent SDK nor the local terminal module. At install time a trusted environment variable `PI_DEVICE_HUB_UPDATE_SOURCE` can store an internal registry package reference or a local candidate `.tgz`; HTTP requests cannot choose the package source. `PI_DEVICE_HUB_SERVICE_NAME=pi-device-hub-<name>` installs an isolated named instance, and the default name stays compatible with existing deployments.

When an old public version has no versioned health information, install the new global CLI and run `pi-web-ui hub update` for the first bootstrap; afterwards operate directly in the Hub web UI. Pre-release verification against real services, candidate package checks and the cross-platform matrix: [Hub release package upgrade acceptance](hub-upgrade-release-testing.en.md).

### Plain HTTP with a public IP

```sh
PI_DEVICE_HUB_PUBLIC_URL=http://203.0.113.10:50001 \
PI_DEVICE_HUB_HOST=0.0.0.0 \
PI_DEVICE_HUB_PORT=50001 \
PI_DEVICE_HUB_ALLOW_REGISTRATION=1 \
pi-web-ui hub
```

Open the matching TCP port in the security group, then open the hub address in a browser and enter the same address on each device to bind. This mode needs no domain, certificate or reverse proxy and uses HTTP and WebSocket; accounts, device credentials, messages and files all travel in plaintext. Disable open registration after the accounts are created. Device web pages use the `/device/<device ID>/` path on the same port and need no extra port, domain or certificate. The entry first verifies account ownership or redeems a one-time ticket issued by the local interaction credential, then loads the device page in an isolated frame. Device pages get no same-origin access to the Hub; resources, APIs and WebSockets all go through the bound device's random capability path. The group bar and device menu use the read-only `/api/device-center/chat-status` to query `hubUrl` and `deviceId`; the Hub capability entry serves that minimal binding information directly and returns the same two fields for the old device UI's `/status` query, while the `/status` and settings APIs used for local administration still refuse to be forwarded to a device. Error responses such as policy rejections and offline states after the capability check also carry sandbox CORS headers so the page can read the actual error state.

### Single-port path and legacy separate-origin compatibility

The default device entry shares the Hub port, e.g. `http://203.0.113.10:50001/device/<device ID>/`; custom aliases still point at the same entry. Devices no longer consume extra ports. The Hub enforces a CSP sandbox on device pages and never enables `allow-same-origin`. A random capability path reaches only its own device and cannot be used as a Hub account credential; revoking a device voids its access. When browser storage is unavailable in the isolated page an in-page memory fallback is used; when the same cause makes `navigator.serviceWorker` unreadable inside the sandbox it degrades to `undefined`, notifications switch to in-page `Notification` and first paint is not blocked. The theme choice (`pi-theme`) is stored in the browser storage of the Hub entry page through a restricted message bridge, isolated per account and device and restored before first paint; refresh, reopen or capability credential rotation does not reset the theme. The bridge accepts theme reads and writes only for the current isolated iframe, cannot address other storage keys and never persists device page tokens. The theme still belongs to the current browser and does not sync across browsers or devices; other local preferences still reset on page refresh. When an older Hub does not provide the bridge, the page waits at most 500ms and then continues starting.

The legacy separate-origin compatibility config follows:

The hub domain and the device domain must not be parent and child, e.g. use `console.example.com` with `devices.example.net`. Configure wildcard DNS and a wildcard certificate for the device domain, forward HTTP and WebSocket traffic for both domains to the same hub port and preserve the original Host and Origin. The proxy should not buffer SSE. HTTP or HTTPS both work; HTTPS encrypts transport, and HTTP pages show a plaintext-transfer notice.

Both the hub account cookie and the device access cookie are host-only. Device access verifies account ownership on the hub first, then issues a short-lived one-time ticket that is exchanged for an access cookie after entering the separate device domain. Revoking a device closes existing relay connections and clears device access credentials.

The current relay decrypts traffic it forwards; there is no end-to-end encryption. Model keys and project files stay on each computer, while served pages, terminal streams, file-sync bundles and task reports pass through the hub. Deploy only to a trusted server. One process owns one data-dir; multiple instances sharing write access to the same directory are unsupported.

The group menu offers “Clear messages” (「清空消息」): after confirmation it deletes all messages, task history and message receipts of the group, keeping the group name and bot members, and it cannot be undone. Clearing is refused while tasks are queued, running or stopping; wait for them to finish. The operation is checked per account and persisted atomically in the Hub; local groups and bound devices follow the same API rules.

## Bot identity and execution boundaries

A bot's stable ID is separate from the device hosting it. Groups use `botIds`, and the optional `primaryBotId` must point at a group member; the primary bot can be set or cleared when creating a group and when managing members. A human message with no target goes to the primary bot and continues its most recent open group conversation with a valid config; an explicit target and a continued conversation take precedence. Public bot messages never trigger default dispatch; removing the primary bot or revoking its device clears the setting without picking a replacement. With no primary bot set, the original @ dispatch behavior stays. The dispatch context freezes the primary bot ID at that moment, and the executor injects coordination duties only into the primary bot that is in the same group and whose identity matches: answer ordinary questions directly, look up member capabilities and delegate work the user asks to run, query persistent conversations before continuing an explicitly matched task, and ask the user when it is ambiguous. The coordinator role expands no tool or approval permissions and never dispatches on its own from message history; delegation results reuse the existing related-request reply and auto-continue mechanisms, and completion still requires checking delivery evidence. Messages use `targetBotIds`; tasks record the target `botId`, internal routing `deviceId` and config version. Device-auth sync may update only its own bot, and group messages and task reports are checked against bot ownership. Hub storage uses the new structure and does not migrate group data from legacy device members.

Every group task captures the same shared context before dispatch: group name, bot members and recent public messages in time order, with a total JSON budget of 24 KiB. The current task body is passed separately; other members' past replies are reference data, not instructions or dispatch authorization, and the context for a batch of targets is frozen before any member runs. Plain chat context travels only with the task; an explicit contract task seals the actual input as an immutable ContextManifest persisted in the task record. A member's internal reasoning and local tool output never enter group history. A continued conversation keeps its original execution context and currently still carries a fresh bounded snapshot of group messages; group messages are not yet deduplicated incrementally across turns.

Members with a `device_collab` grant can use `read_history` (`roomId`, their own `sourceBotId`, optional `before` cursor) to read earlier raw text without waking other members. Each page is capped at 24 KiB JSON, overlong messages are split by `textStart` / `textEnd`, and `nextBefore` walks backwards to the full text; cursors use stable message IDs, appends do not disturb pagination, and clearing or message eviction invalidates old cursors explicitly. The Hub re-verifies account, device, enabled state and group membership. Each group keeps at most 500 public messages and anything outside the retained range cannot be read back; there is no promise of unlimited history and no extra model call to generate a summary that might lose facts. Without the tool grant, recent context is still included but earlier content cannot be read back.

The group composer picks targets uniformly through the `@` menu: each bot offers a “New conversation” (「新对话」) entry and a named “Continue conversation” (「继续对话」) entry, the composer keeps the meaning of the choice and no longer shows a separate task-target dropdown. A mention binds stable bot/conversation IDs, is converted to a bot marker on send and routed to the chosen conversation; editing or deleting the mention clears its reference. A single message continues one existing conversation, and mixing in other new or continued targets rejects the send; a new conversation still supports @-mentioning several bots at once. A failed list update is reported only in the @ menu and blocks continuing an old conversation. If the chosen conversation was deleted, closed or its config became invalid, it reports an explicit error and never quietly becomes a new task.\n\nPlain chat tasks support both new and continued runs: a new task creates a shared standard persistent conversation (`independent: false`); a continued run restores the bot's original transcript by its stable Hub conversation ID, with the working directory and identity taken from the bot's startup config; an unspecified model captures the local pi default model instead of inheriting the UI's current session model; tools, Skills and MCP use an explicit allowlist applied at the execution entry. MCP uses a task-specific Bridge that starts only allowlisted servers, and their tools must also match the tool allowlist. Skills grant no extra tool permissions. The working directory is the default operating location, and strictly confining access outside it still needs sandbox isolation. Device execution permission and approvals remain outer constraints. One device runs at most 4 concurrent tasks with up to 32 waiting; workspaces of the same bot or with overlapping real paths stay serial, the scheduler picks the currently runnable item in queue order, and an independent workspace can skip a conflicting waiting item. Directory aliases are unified through realpath, and a bot/directory stopped without confirmation stays isolated; cancelling a wait frees its queue slot immediately, and over-capacity requests are refused explicitly. A continuation does not interrupt a running tool but resumes the same transcript after the current turn ends. Bot conversations can be viewed and interacted with locally without takeover; viewing migrates no execution ownership and does not affect group task runs. Bot transcripts still cannot be resumed through the ordinary history-resume entry to create a second execution instance; resuming allows only the exact path persistently registered on the device and verifies Hub, device, group, bot config version and working directory. Credential rotation does not change conversation identity, while a directory or bot version change refuses continuation instead of quietly creating a new one. A transcript survives an execution failure for recovery and local inspection.

Conversation capacity counts “unstopped conversations”: stopped conversations go into a bounded archive (200 plain entries are kept per group, entries without contract/delivery/review/integration records are evictable), and the archive does not consume new-conversation slots; `POST /api/rooms/:id/conversations/:conversationId/delete` allows only conversations with no in-flight tasks and no contract/delivery/review/integration records, to free capacity — clearing the whole group is not a substitute. Revoking the device that hosts a bot closes its conversations and marks them `closedReason=device_revoked`; after a bot version, device or membership change, conversations return as `stale`, the UI blocks continuation and prompts for a new one. Group messages support `replyToMessageId` (which must point at a message in the same group) as a reply anchor and project it to bots with the group context and `read_history`. When a human message omits `targetBotIds`, the Hub parses `@Name` / `@Name(<id>)` from the body: same-name multi-member cases are not guessed, non-members are not dispatched to, and a body mention no longer silently falls back to the primary bot because the client did not resolve it. Idempotent receipts are decoupled from message retention (2000 messages per group, 7 days), so message eviction no longer weakens replay protection.

Explicit code delivery submits `executionMode: "code"` plus a versioned contract through the existing task creation API or `device_collab`; ordinary UI messages stay in chat mode. Code creates a fresh isolated execution session per turn, runs against a fixed repository baseline and a sealed Manifest, and captures an immutable artifact carrying the patch and Git Tree after a confirmed stop; execution end and artifact creation are recorded separately and neither constitutes verification or acceptance automatically. Contract tasks and their conversations are retained until an explicit clear or group deletion, so history trimming cannot rewrite version authority. Artifacts are read by digest and byte range through `task_evidence evidenceKind=artifact`. Request budget, permissions and current limits: [versioned contracts and code tasks](device-collaboration.en.md#21-versioned-contracts-and-code-tasks).

Hub state persists in two layers: `device-hub.json` remains the single **index** (`version: 2`, same schema, holding accounts/devices/bots/groups/conversations/deliveries/receipts, with `messages`, `tasks` and `conversationMessages` fixed as empty arrays), while large collections land in append-only logs under `hub-log/`: `hub-log/messages/<roomId>.jsonl`, `hub-log/tasks/<roomId>.jsonl` and `hub-log/conversation-messages/<conversationId>.jsonl`. Each line is `{"v":1,"op":"upsert","value":…}` or `{"v":1,"op":"del","ids":[…]}`; a collaboration transaction uses `hub-wal.jsonl` as its single commit point: the index and the three collections' add/remove deltas, an increasing sequence number and a checksum are written and fsynced before the commit is acknowledged; logs and index are then updated as recoverable projections, and the index finally saves `checkpointSeq`. A failed projection keeps the already committed in-memory state and the WAL, the next write or the replay after restart fills the checkpoint, and the same sequence number may never overwrite an old transaction or be reported as an ordinary commit failure. The WAL is cleared only after the projection completes. Deletes append tombstones; when tombstones reach 200 or lines exceed twice the retention limit the file is rewritten from live rows (temp file + fsync + rename); loading keeps 500 plain history entries per group, additionally keeps unsettled tasks and contract evidence, and repairs a half line left by a crash (truncate to the last newline). The `messages`/`tasks`/`conversationMessages` inlined by older versions are written to the logs and then cleared from the index on `open()` (rerunnable, losing no rows); `readPersistedHub(dataDir)` lets tools and tests replay the WAL in memory and rebuild the full state without triggering interruption markers, creating directories or modifying files. **Compatibility boundary**: both the index schema and old data files load, but an old Hub version that reads `device-hub.json` directly sees only empty collections, so the full state must be exported before falling back to an older version.

The device scheduler's room fairness history (last dispatch time and count) persists in `task-scheduler-state.json` in the data directory with a 250ms debounce and atomic writes, and is restored after a restart; a corrupt or missing state starts neutral fairness and never blocks dispatch.

“Stop selected conversation” (「停止所选会话」) first persistently closes admission of new messages, then asks the device to cancel that conversation's running and queued turns; success requires the stop confirmation. Without confirmation it shows pending and keeps blocking group clear/delete; a failure or disconnect event never substitutes for the stop confirmation. Stop applies only to the selected conversation and does not auto-stop other members' tasks it already dispatched; a closed originating conversation is not woken again by subtask results. Users can stop group conversations of the same account, while a bot can stop only its own.\n\n## Group task progress and human interaction

Group chat receives task progress over an SSE stream bound to the account and group; the executor reports only a restricted slice of assistant body text, the phase and tool names, and internal reasoning, tool arguments and raw tool results never enter public progress. The Hub verifies bot, task, attempt and the increasing sequence number, keeps progress in memory only and announces a refresh of persistent task state after a transaction succeeds. Fixed polling is off while the connection is healthy, falls back on failure and re-fetches authoritative state on reconnect. Hiding the page and switching groups close the old connection, and a slow consumer is disconnected and resynchronized.

Native `ask_user_question` and tool approvals surface in the group through a separate interaction bridge; replies bind to the current task and attempt, approvals only allow a one-time approve or deny, and remote modification of persistent authorization rules is not allowed. The group-only `conversation_attention` can accept human answers while the current task still runs; the answer is persisted first and later turns wait for the original execution to end before entering the same conversation, avoiding concurrent transcript writes.

Execution timeout uses a 20-minute window with no real activity and pauses while waiting on a human. Real model output and tool activity renew it; status queries and network heartbeats do not represent progress. A network drop keeps leased local execution, and reconnect claims it with task/attempt/lease; an old generation or a revoked permission cannot resume. A Hub restart provides a bounded claim window; when a device process restart cannot prove the old execution still exists, the interruption is recorded and an explicit continue is required, without auto-replaying side effects. The active lease and terminal results are both written to the local `task-recovery-state.json`, which saves the result and removes the lease in one atomic replacement; the two old recovery files are cleaned up after a successful migration. The Hub accepts immutable results by attempt and lease generation, and an ACK clears the device outbox only after it carries the matching committed digest; a permanent terminal conflict or an invalidated attempt uses a rejection receipt bound to the original result and atomically moves the full result into a persistent quarantine instead of looping reconnects. Recovery state is written as version 2 (version 1 still reads), the quarantine holds at most 128 entries / 2 MiB with an 8 MiB total file cap; migration and rollback: [`device-collaboration.md`](device-collaboration.en.md#21-versioned-contracts-and-code-tasks); full reports have their own outbox, so a terminal confirmation never deletes a report that has not been uploaded. Older versions cannot read the new unified recovery file, so back up and convert the recovery state before rolling back — never just delete the new file.

In-message reports keep a 16 KiB excerpt budget; the full text is persisted on the executing device and uploaded to the Hub in chunks, capped at 4 MiB per report, with anything over the limit explicitly marked rejected; the device report outbox has a 64 MiB total budget and at most 128 entries, and clears confirmed history within limits. Task details and `task_evidence` are read by shard, full digest and version, and an unfinished, missing or rejected upload never masquerades as a full report. Context summaries keep constraint sources, decisions and evidence references, and any truncation explicitly points to reading the full record.

## Bot execution context and prompt layering

The fixed execution rules for group tasks are bound to the local execution capability and supplied as SDK session system instructions; the primary bot's coordination duties come from the member identity frozen at dispatch time and never restore permissions from message history. A bot's custom identity instructions and execution rules stay in effect across the default prompt, composed templates and resumed sessions. Each user turn carries only task data and local measurement information instead of appending the full fixed rules again. The system layer still provides necessary context with the underlying model request; this change removes duplicated rules from the transcript and promises nothing about provider token billing or cache hit rates.

`device_collab` binds the source bot, group and parent task automatically from the current SDK session and refuses when an explicit argument conflicts with the binding. `current_task` queries the current association; `conversation_attention` and `conversation_deliver` may omit their own conversation ID. An execution turn that received `kind=request` replies with `reply_to_request`, and the server binds the reply target and request ID from the current request, so it cannot be used to pick another destination. Plain local conversations have none of these default bindings and still must supply the fields the original API requires and pass the existing authorization checks. Continuing another work conversation still needs an explicit target, so a task association is never mistaken for dispatch authorization.

Group history is delivered as a separate `device-group-context` custom message: a bounded snapshot the first time, increments for continued conversations. Delivery happens after SDK automatic compaction and is based on the actual context of the active branch: only segments that are still visible with identical content, sender and text range are omitted; edited or re-ranged segments are provided again. When the history join point is not visible, it falls back to the current bounded snapshot and marks `gap=true`. Custom messages persist with the SDK transcript and coverage is recomputed after a session resumes, without relying on in-process “already sent” cursors; text removed by compaction or a context edit can be provided again. Similar markers inside ordinary messages, tool output and compaction summaries are not evidence of deduplication. Every model request also re-checks coverage against the final request context; if compaction happens again during execution, missing segments are temporarily backfilled so increments never reference removed text. Temporary backfill never pretends to be a persisted delivery record. The current task body is always kept in full.

Before each atomic transaction commits, the Hub projects structured task state and events uniformly from existing tasks, messages, pending decisions and delivery records. The state keeps the conversation's initial goal, current execution phase, pending questions, most recent result, human decision evidence and delivery references; follow-up questions and work bot results never overwrite the initial goal. Events record an ordered increasing sequence, capped at 100 entries and 64 KiB total; this is a current snapshot plus a bounded event window and is not a promise of full replay from sequence zero. Old data gets an initial snapshot with no invented historical events, and interruptions after a restart are recorded as real transitions.

`device_collab task_state` reads the current state and retained events; `task_update` lets only the bot currently running in this conversation report progress, constraints, blockers and next steps, and requires `expectedRevision`, with a re-read after a version conflict. Reports carry a `bot_reported` source and cannot change the server-side goal, execution phase or human decisions. Dispatch carries a task state snapshot and `current_task` also returns values observed at dispatch time; use `task_state` for live state. None of these reads dispatch or retry tasks automatically.

The task state reference snapshot handed to the model uses a 12 KiB UTF-8 JSON budget by default, including the selection metadata itself; the initial goal, current task, phase and pending questions are kept, and human decisions outrank bot reports and historical results. Optional records are selected as whole entries, never truncating the current user task or handoff. Omitted counts and existing evidence truncation markers are surfaced explicitly; read `task_state` before relying on an omitted constraint or decision. When the minimum budget cannot fit essential state, essential fields are kept and marked overflow instead of claiming the budget was met. Group history keeps its separate 24 KiB bounded snapshot and increment mechanism, and this budget is not a token cap for the full provider request.

The fixed execution rules keep only long-lived principles such as permissions, workspace, history trust and result delivery. `device_collab execution_guide` reads the local fixed workflow by `coordination`, `delivery` and `review`, loaded on demand before the first delegation or a delivery/review request. Tool permissions still come from the existing allowlist and server checks; tools are not yet hidden or enabled dynamically per phase.

`device_collab context_metrics` reads context counters for the currently bound SDK session. The metrics separate source history text, added text, deduplicated text, injected JSON and temporary fix bytes; all bytes are UTF-8 and are not equivalent to tokens, cache hits or billing. The custom message details store the matching counts, and model body text carries no diagnostic metadata. In-process sampling covers at most 50 sessions with the latest 100 entries each; the tool returns the latest 10 plus the retained-window counts, and restart or eviction loses samples without affecting tasks or delivery evidence.

This phase has not implemented model-generated task summaries, per-phase tool switching or provider cost and cache statistics. Deduplication, identity verification and request association are the server's responsibility, and group message bodies and other bots' output continue to be handled as untrusted reference data.

## Windows → Mac → Linux relay

Group messages support explicit targets, task state and result reports. The task card's relay entry can carry the repository, commit, branch and pending verification items to the next device. Prefer committing to Git first, then have the target platform verify the commit and run real builds and tests.

The executor creates a shared, persistent standard local conversation for a new task and restores the original bot conversation for a continued task, without switching the conversation the user is using. Ordinary new conversations are independent by default (`independent: true`) and opening one across pages keeps the existing takeover flow; conversations created by groups and by WeChat, QQ and similar channels are shared by default, viewed directly and keep their original execution ownership. It calls the agent through the local existing WebSocket protocol, never auto-approves permissions and never answers questions for the user; questionnaires and approvals go to the existing global modal, the task keeps waiting, the execution timeout pauses while waiting on a human and continues after the answer. Results include the local OS, conversation identity and the actual assistant report. Whether tests passed still rests on command evidence.

The AI can call `device_collab` to list bots and groups. An execution conversation of a bot with a tool grant can also send messages, dispatch to a specific bot and transfer files. Persistent collaboration works through `conversation_create` / `conversation_list` / `conversation_read` / `conversation_send`; conversation creation saves the immutable delegation source `sourceBotId`, `sourceConversationId` and `parentTaskId`, lists and tool projections keep those fields, and later continuations never rewrite the original ownership. Both create and continue accept `kind: request` / `requestId`, and create does not allow `reply`; `kind: request` produces a related request, and the receiver replies to the original conversation with `kind: reply`, the same `requestId` and the request's `sourceConversationId`, never guessing a target from a bot name. The Hub persists the message and the execution turn before dispatching; a subtask's terminal report can create one continuation task in the originating conversation, a duplicate report does not wake it again, and replies or results never form a mutual wake-up loop. Every write operation names the local `sourceBotId` explicitly, and tasks and files also name a `targetBotId`; a plain conversation cannot impersonate a bot via the same working directory, and an execution conversation cannot impersonate another bot. Device dispatch needs a trusted current parent task and the context is injected by the executor; a single root task dispatches at most 16 tasks in total with relay depth at most 8. A running parent task may currently dispatch the next task, so relays can run in parallel; result wake-ups also count against the same automatic relay budget. New human input can open a new bounded task chain on the original conversation, while a bot's own continuation message cannot refresh the budget. With no group task currently receiving, a local AI cannot fabricate a parent task to start a bot task chain; the user can start one with an @ mention in the group.

### Development delivery and acceptance

A group conversation records execution state and development delivery separately: an execution marked `completed` only means the turn ended, not that code was delivered or accepted. A bot appends a delivery record to its own stable conversation with `device_collab conversation_deliver`: the legacy commit form supplies the repository, baseline and full commit SHA; the code-artifact form has the currently running task reference an artifact the same author completed earlier via `artifactTaskId`, and the Hub derives the contract, Manifest, tree identity and acceptance criteria — a tree SHA is not a commit. The check source is fixed to `bot_reported`, so no command is run and no verification credential is generated from it. Ordinary discussion can still reply directly without a delivery record.

A human can accept in the collapsible delivery panel against the exact version; other bots submit `accepted` or `changes_requested` through `conversation_review` and cannot review their own work. The commit form binds the same commit SHA; artifact acceptance requires a genuinely successful Integration verification first and binds artifactDigest, integrationId and verificationDigest, recording results and evidence item by item against the sealed acceptanceCriteria. An old version, a different artifact or two missing commits cannot match the current delivery. Rework continues along the original group conversation and keeps history; acceptance itself never dispatches rework or runs a Git merge.

The protocol is defined in `server/protocol.ts`; the Hub verifies account, group membership, bot and running-task ownership inside the transaction and persists before returning. Transaction callbacks stay synchronous and external RPC runs outside the transaction; returned data is checked for clonability before the WAL commit and given an independent copy, so non-separable results such as functions never cause a “committed but failed” response, and an external alias during async work cannot rewrite the returned facts. Deliveries and reviews deduplicate by idempotency key, and the same key with different content is refused; history has a capacity budget and explicitly refuses appends once full. HTTP entries are `POST /rooms/:id/conversations/:conversationId/deliveries` and `/reviews`, following the local proxy, Agent and cross-device account boundaries.

Full development regression: `node tests/device-project-collaboration-test.mjs` (or through the smoke runner). The test starts a standalone Hub and two separate device services, uses a real Git repository and a local deterministic model, and covers delivery, cross-device pull, failed rework, re-acceptance and the integration check. Two services on one machine verify the inter-device protocol and flow but do not replace Windows/macOS on-device acceptance.

Before continuing a bot transcript, the server waits for old execution instances that were confirmed stopped and released their registration to finish cleanup, even if the old WebSocket's close event has not arrived. Holders still registered or still executing are not preempted and resuming fails explicitly; a warning during resume also ends the task, so a group never stays stuck showing running. Live-path regression: `node --import tsx tests/device-bot-live-integration-test.mjs` (build the server first): it starts the Hub, device service and a local HTTP model on a separate port and temporary data directory, verifies that three different messages land in the same transcript and checks that later SDK requests carry the prior text.

A new conversation's SDK transcript path may be allocated before the file exists: after ownership checks the runtime atomically registers the path, lets the first message create the file and verifies the file exists before the task ends successfully. A failed first turn keeps the registration for recovery; continuing still verifies that the registered file exists and never fakes a resumable transcript by creating an empty file.

Network blips and process crashes are handled separately: while a connector reconnects with backoff it keeps the local execution and conflict locks, and resumes progress and result reporting after a lease-claim confirmation for the current task; the Hub does not terminate a task that holds a lease just because the network closed. A Hub restart lets the original holder claim within the recovery window; after the timeout it settles the interruption, the parent result notification and the conversation queue uniformly. When a device process restart finds an orphan lease it only reports the interruption instead of blindly re-running, and the user can explicitly continue a registered transcript. Revoking a device or an explicit stop cancels the task, and an unconfirmed stop keeps the isolation. The protocol prevents the duplicate execution on reconnect that tests cover but promises no global exactly-once side effects at every crash instant.

## In-group native questionnaires and one-time tool approvals

`human-interaction.ts` maps native questionnaires and tool approvals from the current executor connection to short-lived random interaction IDs; the native request ID stays on the executing device. The projection binds task, attempt, group, bot and device, and the Hub re-checks account and group membership against the persistent task. At most 8 items and 24 KiB per task, answers capped at 16 KiB, and the Hub keeps in-memory projections for at most 128 tasks without persisting them. Each execution consumes at most 256 items, and beyond that limit handling continues locally on the executing device.

The group-side `GET/POST /api/rooms/:id/interactions` accepts only human user sessions (including the local UI authenticated by the existing device-user check); bot credentials cannot answer. Questionnaires support options, free text, dependent questions and cancel; approvals only approve this once or deny, the raw arguments and reason stay on the executing device, and the in-group prompt says to check the native request first. No answer can carry arbitrary WS frames, edit tool arguments or change trust or memory allow rules. After re-validating against the current local session and the pending items, the executor may send only `question_answer` or `tool_approval_response` (`scope: once`). Once the local bridge consumes the pending request it registers the complete reply frame under the current bot execution capability; the WebSocket control gate passes only that frame and consumes the grant immediately, refusing cross-task frames, a different request ID, tampered answers and widened approval scope, and clearing unconsumed grants when the capability is revoked.

The Hub removes an interaction only after the executor ACK from the WebSocket bound to the current device; a rejection or no confirmation within 5 seconds returns 409 and keeps the pending item. An answer cannot be replayed after a withdrawal, timeout, task end or lost connection. The UI refreshes on group SSE invalidates and falls back to 2-second polling on visible pages when the connection fails; switching groups and disabling cancel unfinished answer requests. The final tool execution result after a native WS write is still reported through task state; a successful HTTP forward is not a substitute.

## Scheduling, task details and group workspace

Device Center offers execution scheduling settings: concurrency defaults to 4 (1–16) and waiting defaults to 32 (0–128, 0 meaning no queueing). Settings are saved atomically before being applied; an invalid or corrupt setting never silently raises the resource limit. The scheduler picks fairly per group under the serial constraint for the same bot and truly overlapping workspaces, and a runnable task that waited too long comes first. The queue shows position and the controlled blocking reason, cancellation binds task and attempt, and an unconfirmed stop keeps occupying an isolation slot.

The group task bar opens details with persistent events, tool start/end state, reports, interactions and delivery references. Events use a bounded asynchronous segmented log, at most 20 segments of about 50 entries / 64 KiB each; eviction, corruption, write failure and expired cursors give explicit feedback. Tool arguments expose only a structured operation summary, and internal reasoning and sensitive arguments never enter public events. Log and report reads strictly verify account, group, task and execution generation.

The group composer supports plan-only. A planning task allows only read-only actions of authorized tools, and unknown tools and write/dispatch actions are hard-refused; once the real plan steps are persistently ready, a human clicks “Start implementation” (「开始实施」) to create the follow-up execution turn, and a bot cannot approve it itself. A group workspace can bind an existing canvas of the current device; the reference alone does not start it, and an explicit start reuses the original canvas service and verifies graphId and cwd. Bot presets read the real local config and save partially by allowlisted fields and revision; absent permissions are not cleared, and an in-flight bot usage blocks hot edits. Group extension slots use host registration and rendering; search explicitly covers group name, bot and task title/ID and does not claim a full-text log index.

## Delivery verification and integration pipeline

Commit delivery keeps the 「先审查再准备」(review first, then prepare) discipline: artifacts can be prepared and genuinely verified first and accepted separately afterwards; `completed` does not mean acceptance passed. A human picks the target bot and branch and reviews the diff in the isolated worktree, the verification commands are explicitly submitted once by the account owner and frozen, and final confirmation requires a genuinely successful credential plus the target branch being checked out in no worktree. Before publishing, the Hub first persists `publishIntent`, the device's publish log is written to disk before the CAS and the success receipt is saved before the conversation is cleaned up; startup and reconnect only re-check and never resend the CAS automatically.

**The full hard constraints take §2.1–§2.3 and §8 of [`device-collaboration.md`](device-collaboration.en.md) as their single source of truth** (WAL transactions, contract / Manifest, credential whitelist, CAS re-check, isolated worktree boundaries, delivery ≠ acceptance), in particular [`§2.3 Publish intents and the post-crash re-check`](device-collaboration.en.md#23-publish-intents-and-the-post-crash-re-check). This document keeps only operational details such as the local on-disk layout, capacity / budget caps and compatibility boundaries. Startup and reconnect only re-check the log, original repository identity and target ref and never resend the CAS automatically; a repeated confirmation of an existing intent also returns only the current record. The UI offers a manual re-check, and only the account owner can resume under the same intent after the device clearly proves the CAS never started, or was refused and stopped; a bot cannot self-approve a resume. A CAS that started without a receipt stays unknown, and even if the target returns to the old SHA that is no safe basis for a retry. ## Large file chunked transfer

Beyond small-package sync, a deterministic user transfer entry and chunking engine were added: at most 256 MiB and 2048 files per transfer, with a 512 MiB total staging budget on the receiver. The manifest pins file digest, size and chunk layout, and each chunk's index, offset, byte count and digest are verified before writing; a duplicate chunk allows only identical content, and a corrupt chunk can be retransmitted. A mismatched source file version must be refused; an old manifest is never mixed with new content.

In a group you can pick the source/target bot and path to start a transfer directly, without relying on a model to parse natural language. The Hub background task is bounded, persisted and shows progress, differences and errors; after a disconnect the same manifest is resumed explicitly, and confirmed chunks continue once the receiver and Hub registration are rebuilt. The staging directory binds the Hub, device, group, bot, revision and real workspace; stopping the service keeps unfinished staging, and changing the root or the bot cannot reuse an old package.

Import still requires a preview and revision-based confirmation, conflicting paths are explicitly overwritten item by item, and target files are never deleted. Cancel first stops sending and the target's in-flight work, and releases quota only after real I/O has finished and both sides confirm the fence; until the stop is confirmed, continue, import and conflict tasks are blocked. Links/junctions, sensitive paths and ignores follow the shared path rules. `sync_files` reuses the chunking path and keeps only a bounded summary in the tool receipt.

## AI file sync

The `device_collab` file flow:

1. `sync_files`: specify the group, local source bot, target bot and a relative project path; `recursive: true` selects directories recursively. The sender verifies files and builds a SHA-256 manifest, the hub forwards it, the target stages it, and a transferId plus a diff preview are returned. Ignored or sensitive paths found during recursion are skipped and reported through `exclusions` / `totalExcluded`, while explicitly selecting them is refused.
2. `transfer_preview`: re-fetch the target's current state and revision.
3. `transfer_apply`: carries the confirmed revision; differing existing files are refused by default and must be listed explicitly in overwritePaths.

Transfers and tasks use the target bot's fixed project root and no longer maintain a group-level device directory binding. Bot config is isolated per Hub address and device identity and persisted atomically; full prompts, model and capability config and absolute paths stay local, and the Hub syncs only public identity and config version. Modification or deletion is refused while a task or file operation holds the bot usage right; staged files bind the bot and workspace version, so after a switch an old file package cannot be imported into a new directory. Conversations with another cwd cannot borrow that bot's project permissions. Path traversal, symlinks/directory junctions, `.git`, `.env*`, common credential paths and `node_modules` are refused; directory recursion must be enabled explicitly and scans at most 4096 entries; target files are never deleted. One package is at most 8 MiB and 128 files, with a 32 MiB total target staging budget. The data directory must sit outside the project root.

The target baseline is re-checked before overwriting, and a write is refused when a change happened after the preview. A multi-file import is not a cross-file transaction and returns the actual applied, unchanged and rejected sets; a failure does not automatically retry a transfer already in the apply phase. Staged files live as long as the local service, may become invalid after reconnect or restart, and should be sent again. Sync never runs scripts, installs dependencies or restarts services automatically.

This transfer gives SFTP-like on-demand file/directory passing over the existing device connection, with no SSH/SFTP to configure; it is not continuous directory mirroring or delete sync. See [file transfer boundaries](device-file-sync.md). This round suits source code and small test assets; prefer Git LFS or dedicated artifact storage for large build outputs. Git repository passing and file package sync never apply another machine's absolute paths locally.

## Domain-free device web entry

By default, opening only the main Hub port is enough. Every device card has a fixed entry `/device/<device ID>/`; an optional alias (e.g. `mac`, `office`, `linux`) still checks login and device ownership first, then enters the same single-port access path, and the link may carry `#s=<conversation ID>`. ## LAN-first access

Choosing “Open device” (「打开设备」) or “Remote desktop” (「远程桌面」) on a local pi-web-ui device card uses the same LAN-first negotiation. The Hub first checks account and device ownership, then issues a short-lived device channel grant through the authenticated connector's `device_lan` RPC. The target device listens on a random TCP port on demand and publishes up to 16 RFC1918 IPv4 candidate addresses; the local service runs real TLS handshakes and health requests in parallel under an overall deadline and picks the first address that passes identity verification. Whether a connection is direct depends on actual reachability and key verification, never on an IP text prefix or a guess that a subnet matches.

Once the direct connection succeeds, page resources, the conversation WebSocket, uploads and desktop JPEG/input all travel over the LAN without detouring through the Hub and without relayed JSON/base64 chunks. The Hub still owns authorization. The channel uses TLS 1.2 PSK with a 32-byte random key per grant, and keys exist only in the Hub and the two service processes, never handed to the browser. The random listen port accepts only a valid PSK and reuses the connector's path allowlist, local Host/Origin rewriting and credential injection; local config and system permission request APIs remain unreachable from remote. The main web service does not need to listen on the LAN.

The browser opens a local one-time ticket wrapper page at `/device-lan/<device ID>/__open`, and remote content still runs in a sandbox without `allow-same-origin`, loaded through a random capability path; it reuses the Hub path entry's HTML rewriting, CORS, CSP and header sanitizing and supports a local reverse-proxy path prefix. Grants renew on demand at expiry, and a connector disconnect or unbinding revokes the related channels and connections; cancelling a single grant revokes only that key and leaves other connections alone. Separate browser tabs and separate Electron windows use the same selection logic.

When no private address is reachable or the port is blocked, the P2P path below is tried; if the peer does not support it or hole punching fails, the original Hub ticket is used. An already open page that disconnects re-negotiates the LAN path first, tries P2P if still unreachable, and only then requests a new Hub ticket and falls back. These TLS probes are started by the paired local service; a browser without the local service uses the separate WebRTC channel below. Sources of truth: `server/device-center/device-lan.ts` (device encrypted channel and parallel probing), `device-lan-access.ts` (local isolated entry) and `web/src/device-access.ts` (unified open entry).

## P2P device access

After LAN probing fails, the local service automatically tries device-to-device WebRTC P2P and falls back to the Hub relay only if that fails. “Open device” (「打开设备」) and “Remote desktop” (「远程桌面」) on group members share this flow. This native path requires pi-web-ui on both ends; the browser-only path is the next section. Persistent group records, ordering, approvals, task leases and device authorization stay with the Hub.

The Hub negotiates capabilities over the authenticated `device_lan` RPC (tolerating old responses) and forwards bounded SDP through the targeted `device_p2p` RPC. Native negotiation still accepts only the existing human device credential and verifies account and device ownership, never an ordinary browser cookie. Each session has its own ICE/DTLS identity and a short-lived TLS-PSK grant; on the native path the SDP, addresses and PSK never return to the browser. The target helper connects only to the fixed loopback gateway authorized for this session and accepts no arbitrary TCP target.

The Go/Pion helper is managed by Node over stdio and uses UDP IPv4/IPv6 ICE, STUN and a reliable DataChannel; one HTTP/TLS or WebSocket connection maps to one data channel. Send chunks are 16 KiB, per-stream high-water is 256 KiB and the SCTP receive limit is 1 MiB; there is no fake-data warm-up. Each helper holds at most 32 active and 32 pending streams, Node runs at most 16 helpers overall and each target connector has at most 8 sessions. The total negotiation deadline is 25 seconds: Hub signalling 10 seconds, target candidate gathering 8 seconds, encrypted tunnel verification 8 seconds, and every phase stays bounded by the total deadline and caller cancellation. ICE connected only means the underlying connection; P2P is announced as available only after the TLS-PSK handshake on the real DataChannel and an HTTP health request succeed. When the queue hits the high-water mark it waits to drain, keeps waiting while throughput is still falling, and closes the stream only after 30 seconds without progress; polling also covers a lost low-water notification. UDP uses a system-assigned ephemeral port so a narrow fixed port range does not collide. A binding generation change, connector disconnect, grant revocation, helper exit and page close all clean up the related connections.

The direct page keeps the isolated capability URL under `/device-lan/` and retains the existing CSP, path allowlist, Origin and credential sanitizing. The displayed path is decided by which connection actually succeeded: `lan` / `p2p` / `hub`. When the wrapper page unmounts it sends a release request guarded by the capability and distinguished by page generation, with a 2-second refresh grace so a reload does not revoke the new page by mistake; restoring a connection requests a new ticket and reports the new path. The transport never automatically replays unconfirmed uploads, keyboard/mouse input or task commands.

The complete npm P2P package ships Windows x64, macOS arm64/x64 and Linux arm64/x64 helpers plus a SHA-256 manifest verified at use; macOS/Linux run an executable copy in a private temporary directory so an npm package built on Windows does not lose exec permission. Users do not install Go; unsupported platforms, old Hubs/devices, a missing helper or failed hole punching all fall back to the Hub. The complete distribution entry for a source build is `npm run pack:p2p`, which needs Go ≥1.24; an ordinary web build does not require Go and does not guarantee the helper is included. Desktop installers are packaged by the three platform jobs in `.github/workflows/desktop-release.yml`, each running `npm run build:device-p2p -- --host` first (`bin/` is in the electron-builder allowlist), and `tests/unit/p2p-helper-release.test.ts` guards that chain. Running `npm start` directly in a source checkout requires `npm run build:device-p2p -- --host` once beforehand, otherwise there is no local helper, P2P always falls back to the Hub and the log says `helper-missing`.

Device-side settings: `PI_DEVICE_P2P=0` disables it; `PI_DEVICE_P2P_STUN` takes up to 4 comma-separated `stun:host:port` entries, defaulting to `stun:stun.l.google.com:19302,stun:stun.miwifi.com:3478,stun:stun.cloudflare.com:3478`, probed by the helper in parallel. The default lists several servers because with a single STUN entry, once that server is blocked or black-holed (timeouts for `stun.cloudflare.com:3478` were measured on networks in China) no srflx candidate is gathered, hole punching always fails and the UI shows only relaying. A failed attempt logs one line per phase (`helper-missing` / `ice-config` / `gather-failed` / `signal-rejected` / `ice-failed` / `tunnel-failed` / `cancelled`) prefixed `[DeviceCenter] Device <id> P2P failed: <reason>; using Hub relay`; when the target reports no capability it logs `target reports no helper`. The Hub browser entry uses the browser negotiation flow below. A self-hosted coturn STUN service can be used; when a direct connection is impossible, traffic goes through the original Hub.

### Direct channel for browser-only access to the Hub

The controller needs no pi-web-ui, RustDesk or browser extension — just a browser logged into the Hub; the controlled side runs a build with the P2P helper. The Hub wrapper page negotiates with the target helper through the browser's `RTCPeerConnection`, where ICE may choose a host path on the same LAN or a punched path across networks. **The first screen does not wait for negotiation**: the wrapper page attaches the Hub relay address to the subframe as soon as it opens (a page in about 2 seconds), direct connection keeps negotiating in the background, and once connected new requests go direct automatically while the page's long-lived connection is switched over by the app's own reconnect (one extra WebSocket reopen); if negotiation fails or the direct path breaks, it stays on — or returns to — the relay. The top status first shows “Server relay (trying direct in the background…)” (「服务器中转（后台尝试直连…）」) and, after switching, shows “LAN direct” (「局域网直连」), “P2P direct” (「P2P 直连」), “TURN relay” (「TURN 中转」) or “Server relay” (「服务器中转」) according to the candidate actually selected, and never substitutes ICE connected for a business health check. The browser's default STUN servers are Xiaomi and Cloudflare; device helpers keep using the device-side config. A selected TURN path is still a relay and must not be called direct.

Sources of truth: `browser-peer-client.ts` (fetch and WebSocket bridge in the wrapper page/sandbox), `browser-peer-gateway.ts` (device-side protocol and quotas), `device-p2p.ts` (helper and grant lifecycle), `relay.ts` (capability-path signalling). The Hub verifies the existing account ownership and the random capability path before allowing `__browser_p2p` to submit bounded SDP; signalling accepts only the Hub Origin or an opaque subframe holding a valid capability path. The browser receives only this device session's short-lived gateway key, never local credentials or the TLS-PSK. The target always forwards to the existing PSK-authorized gateway and reuses the admin path bans, header sanitizing and desktop input limits. A session lasts at most 30 minutes, and a device disconnect/rebind, helper exit or page close reclaims it; a late close request from an old page cannot revoke a new connection.

Static resources such as page HTML and scripts are still served by the Hub; the direct connection carries the conversation/desktop WebSocket and dynamic fetches (including chunked file upload and download). Hub management operations such as group authorization and task records still belong to the Hub. Native browser link downloads and requests that bypass fetch may still go through the Hub, so it cannot be claimed that all traffic bypasses the server. Switching to another device inside a remote session uses a separate capability wrapper page, and the current controlling browser still connects to the target device instead of using the first device as a controller.

When the connection fails, in-flight channels close and traffic switches back to the Hub; failed submissions, file chunks and keyboard/mouse input are not replayed automatically, avoiding duplicate execution. The app's existing reconnect rebuilds the WebSocket. Direct negotiation has a 20-second cap (a timeout only affects whether the upgrade happens, not whether the page is already usable); each opening negotiates once, and after direct access is closed the device entry must be opened again to retry it. Relaying is kept when the browser lacks WebRTC, an old device does not understand the signalling, the helper is missing or UDP/NAT forbids a direct connection. A plain HTTP Hub can still negotiate a DataChannel; clipboard permission, WebCodecs hardware decoding and local directory grants remain limited by the browser secure context, and HTTPS is required to obtain them.

Update the Hub and the controlled side, restart the actual services and reopen the device from the Hub to test; the controller only refreshes the browser. `node --import tsx tests/device-browser-p2p-test.mjs` uses real Chrome/Pion to verify direct HTTP/WS, upload/download, cancellation, nested devices, permissions and relay fallback; `--insecure-origin` uses an actual private-network HTTP address to check that a non-secure context can also establish the channel. These tests do not represent all public NAT combinations or 120/240 Hz desktop performance.

### TURN relay

Some symmetric NAT, CGNAT or UDP-restricted networks make direct connections fail. Both ends can set `PI_DEVICE_TURN` (up to three addresses), `PI_DEVICE_TURN_USERNAME` and `PI_DEVICE_TURN_CREDENTIAL`; the helper adds TURN as an extra ICE server and allocates relay candidates, and when the relay path is selected traffic is forwarded through your own coturn. If TURN is unavailable too, it still falls back to the Hub.

TURN addresses support `turn:host:3478?transport=udp`, `turn:host:3478?transport=tcp` and `turns:host:5349?transport=tcp`, with Node and the native helper applying the same protocol, IPv6, port and credential validation. `native/device-p2p/ice_tcp_test.go` verifies candidate gathering against a real local TURN service that listens on TCP only.

`pi-web-ui desktop diagnose --p2p` prints diagnostics without SDP, IPs or credentials: helper availability, TURN config state and host/srflx/relay candidate counts. It only verifies local candidate gathering, not peer reachability, and does not inspect the browser's own ICE candidates or connection. Negotiation timeouts are reported as `gather-timeout`, `signal-timeout`, `ice-timeout` and `tunnel-timeout`, and only caller cancellation reports `cancelled`.

A new target may return allowlisted failure codes such as `target-busy`, `target-helper-missing`, `target-unavailable` and `target-gather-timeout`; Hub RPC failures distinguish `signal-timeout` from `signal-failed`. No exception stack, credential or arbitrary error text is returned. An empty response from an old target is still recorded as `signal-rejected`. `node --import tsx tests/device-p2p-latency-test.mjs` injects two-way latency between the real DataChannel and the TLS handshake, covering a normal connection slower than the original 2-second verification window and rejection of a wrong key; build the platform P2P helper before running it.

- Relay candidates are allowed only when TURN is configured: without it, a helper that sees a relay pair fails immediately, so traffic never detours through a third party for no reason.
- When relaying is active the log writes one line `[DeviceCenter] Device <id> P2P is relayed through TURN`; the UI path still shows `p2p` (it is genuinely not the Hub relay, just forwarded through your own server).
- An address without credentials reports `ice-config` directly and never silently degrades to “no relay”.
- Bandwidth: the H.264 channel needs about 12 Mbps at 1440p60 and 18 Mbps at 1440p120, so coturn only needs bandwidth and a UDP port range (`min-port`/`max-port`) at that order of magnitude; TURN over TLS (`turns:`) needs extra certificates and adds latency, so prefer `turn:` + UDP.
- Deployment example: [Device Center deployment](device-center-deployment.en.md#turn-coturn). Upgrading only the Hub on a server is enough for signalling; no desktop environment is needed. `PI_DEVICE_P2P_HELPER` is an absolute-path override for trusted administrators and development testing that bypasses the bundled check; browsers and Hub signalling cannot set it.

`node --import tsx tests/device-p2p-test.mjs` uses a temporary data directory, two separate helper processes and the real Hub RPC / local access API to verify that P2P is chosen when the LAN is unreachable, concurrent HTTP/desktop/chat, keys never reaching the browser, concurrent sessions, fallback and revocation. Loopback verification on one machine does not represent cross-network hole punching or real desktop frame rates. Full on-device acceptance still needs Mac/Windows across different networks, UDP blocked, device reconnects and platform permission checks. P2P does not lift the frame-rate limits of desktop capture and encoding.

## Browser remote desktop

Device cards offer a separate “Remote desktop” (「远程桌面」) entry that reuses account ownership checks, the one-time ticket and the device access path. The implementation follows [krd](https://github.com/zzjcool/krd) for native capture and keyboard/mouse injection; screen and input reuse the LAN channel above when possible and use the existing WebSocket relay when unreachable, never entering the chat snapshot or model context. No noVNC or VNC service to install and no fixed desktop port.

Remote desktop is off by default; the local enable preference persists to `<dataDir>/desktop-settings.json` and runtime state updates only after a successful write. `PI_DEVICE_DESKTOP=1` forces it on, and a local disabled preference cannot override that environment variable. Read-only permission is enforced by the backend, and keyboard/mouse input on a read-only connection is never injected into the controlled computer. Opening the remote desktop page connects automatically in controllable mode to devices that are enabled and available; the user can switch to read-only at the top. The top uses a compact single-row toolbar with settings, the macOS permission guide and text input collapsed by default, the picture takes the remaining height, and fullscreen keeps the toolbar. When a device is not enabled or unavailable, settings expand, a successful enable connects automatically and a failed connection shows the specific reason. The Hub wrapper page that redeems the remote desktop ticket allows cross-origin embedding, while the inner capability page keeps the sandbox without `allow-same-origin` and the random capability path; ordinary device web wrapper pages still allow same-origin embedding only. Legacy separate-domain/port desktop tickets are exchanged for Hub path tickets before loading, so floating windows do not depend on third-party cookies.

In the chat web UI, the device catalog and group member remote desktop entries open in one App-wide shared floating window that supports dragging, bottom-right resizing, minimizing and fullscreen; clicking the chat area or switching views does not close the window, and minimizing keeps the connection. The iframe inside grants only scripts/forms/pointer-lock and forbids `allow-same-origin`, reusing the server-issued isolated capability URL and the existing authorization flow. Clicking “Separate tab” (「独立标签页」) requests a new one-time ticket and closes the floating window only after it opens successfully; a blocked popup or failed authorization keeps the window and shows the error. Electron opens a separate window with the existing `openHub` bridge and likewise closes the floating window only after the bridge reports success. The entry behavior on the Hub's standalone pages is unchanged.

| Platform      | Capture and input                                                                        | Requirements                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Windows       | GDI capture + SendInput keyboard/mouse injection                                         | An accessible local graphical desktop session                                                |
| macOS         | Swift native helper: ScreenCaptureKit `SCScreenshotManager` capture + CoreGraphics input | macOS 14+, Swift CLI; screen recording permission, plus accessibility permission for control |
| Linux X11     | ffmpeg capture + xdotool keyboard/mouse injection                                        | An accessible X11 session and ffmpeg; xdotool may be omitted for view-only                   |
| Linux Wayland | Not supported yet                                                                        | Would later need Desktop Portal screen sharing and remote control capabilities               |

The old `PI_DEVICE_VNC_*` environment variables are retired and no longer configure addresses, ports, passwords, paths or browser components.

## Verification and boundaries

The group chat delivery panel groups pending acceptance, review requests for changes, execution failures and interruptions under “Needs my attention” (「需要我处理」), shows only those by default and can switch to all conversations. Classification is derived by `web/src/group-attention.ts` from execution state and the latest review matching the exact delivery ID/commit SHA; without an explicit human question, running, closed and delivery-less plain Q&A produce no to-do, and report text is never parsed to guess a blocker. A bot can register `answer` / `decision` plus a question through `conversation_attention`, and must bind its own currently running task and the original conversation; the question is stored in the conversation and still shows after a refresh. Group members submit a human answer carrying `attentionId` through “Reply and continue” (「回复并继续」), and can only answer after the bot stops running; the answer, the continuation task and clearing the to-do commit in one transaction. A retry reuses the idempotency key, an old question ID is refused, and other bots cannot answer on someone's behalf or set another bot's question. Existing acceptance operations keep binding to the original delivery version.

`tests/device-bot-live-integration-test.mjs` uses a real Hub, device runtime, SDK and a local deterministic HTTP model to verify that the primary bot receives messages without an @, that tool delegation produces a related request, that the execution result returns to the original conversation and that follow-up messages continue the same executor conversation; it also verifies that SDK tool questions persist, that a human answer clears the to-do and restores the original conversation, that a duplicate request creates only one continuation task and that an old question is refused. It verifies the transport and execution chain, not a real model's task understanding or selection quality. Artifacts are prepared uniformly through `tests/lib/ensure-build.mjs`.

Related tests live in `tests/unit/device-center-*.test.ts` and cover account isolation, pairing, the real loopback HTTP/WS relay, task protocol, @ selection, file integrity and conflicts. Tests call no real model and cannot replace end-to-end acceptance on the three real platforms. Public operation also needs monitoring, backups, account recovery and service capacity verification; this code does not create a domain, buy a server or open public registration automatically.
