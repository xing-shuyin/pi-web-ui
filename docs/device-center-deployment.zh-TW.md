# pi-web-ui 裝置中心部署指南

本文面向第一次接觸 pi-web-ui 的伺服器管理員及 AI 部署助手。無需閱讀專案原始碼或此前對話，即可根據本文部署裝置中心。

- 專案：https://github.com/xing-shuyin/pi-web-ui
- 本文網頁：https://github.com/xing-shuyin/pi-web-ui/blob/main/docs/device-center-deployment.md
- 本文原文：https://raw.githubusercontent.com/xing-shuyin/pi-web-ui/main/docs/device-center-deployment.md

## 1. 要部署的是什麼

pi-web-ui 是編碼智慧體的 Web 介面。裝置中心（Hub）是它的獨立服務，負責賬號、裝置連線、群聊和跨裝置協作。各臺執行 pi-web-ui 的電腦主動連線 Hub，因此無需給每臺電腦開放公網入站埠。

本指南部署的是 Hub，不是聊天主服務。Hub 預設埠為 **8790**，聊天主服務預設埠為 8787。執行 Hub 不需要配置模型 API Key，也不需要啟動聊天主服務。

公網 Linux 預設使用自動 HTTPS，域名不是必需項，公網 IPv4 也可申請可信證書。新部署執行 `pi-web-ui hub install --public-url https://實際公網IPv4或域名 --allow-registration`；已有 Hub 更新後執行 `pi-web-ui hub https`。安裝器管理證書、HTTPS/WebSocket 閘道器及自動續期，不依賴固定伺服器。前置條件及相容遷移見 [公網 HTTPS 自動部署](device-center.zh-TW.md#公網-https-自動部署)。

HTTP 仍適用於可信內網或臨時驗證，顯式使用 `--https=off`；已有 TLS 代理使用 `--https=external`，安裝器不會覆蓋它。以下第 4 節保留顯式 HTTP 的完整排查步驟。

## 2. 部署前需要的資訊

| 資訊          | 示例或預設值                    | 用途                                                     |
| ------------- | ------------------------------- | -------------------------------------------------------- |
| 部署目標      | 當前機器 / 遠端伺服器           | 當前機器指執行部署的服務所在機器，不一定是瀏覽器所在機器 |
| 伺服器地址    | `203.0.113.10` 或真實主機名     | SSH 連線及訪問地址推導                                   |
| SSH 埠        | `22`                            | 遠端登入埠，與 Hub 埠不同                                |
| 登入賬號      | `deploy` 或伺服器已有賬號       | 普通賬號也可以，安裝系統依賴可能需要 sudo                |
| 認證方式      | 密碼 / SSH 金鑰 / 已有 SSH 配置 | 在安全連線通道中使用，不寫入聊天訊息                     |
| Hub 訪問埠    | `8790`                          | HTTP 預設直接訪問此埠；建議選 1024–65535                 |
| 域名（可選）  | `hub.example.com`               | 使用者擁有並能修改 DNS 的域名                            |
| HTTPS（可選） | 公網 Linux 預設開啟             | 自動申請並續期證書，需公網 TCP 80/443                    |

本文的 `203.0.113.10` 和 `hub.example.com` 均為示例，必須替換成真實值。示例命令適用於 Linux/macOS shell；Windows 使用 PowerShell 對應的路徑和環境變數語法。

公網 IP 可能通過雲平臺 NAT 對映，不能預設把它繫結到伺服器網絡卡。區域網部署使用裝置能夠訪問的區域網地址。瀏覽器地址、SSH 地址與最終裝置訪問地址也可能不同，應分別驗證。

### 憑據與 SSH 連線

伺服器密碼、私鑰、sudo 密碼只供 SSH 或終端的安全互動使用，不要貼上進 AI 對話、部署摘要、命令引數、日誌或文件。預設只在本次連線期間使用，儲存連線應由使用者明確選擇。

遠端執行前校驗 SSH 主機身份及 `known_hosts`；未知主機先通過可信渠道核對指紋，指紋變更時先調查原因，不使用關閉主機校驗的選項繞過檢查。賬號密碼不能替代主機身份校驗。

如果部署助手沒有安全憑據入口或已授權的 SSH 執行工具，應說明這一限制，引導使用者在自己的 SSH 終端執行命令並回傳不含金鑰的結果。不得聲稱已遠端操作。

## 3. 安裝前檢查

在**實際目標伺服器**上檢查，不要用本機環境推斷遠端環境：

1. 作業系統、架構、當前賬號、使用者目錄、磁碟空間及 sudo 能力。
2. `node --version`、`npm --version`，Node.js 必須 **>= 22.19.0**。
3. `command -v pi-web-ui`、`pi-web-ui hub --help`、已有 Hub 的 `status --json`，確認是否已安裝。
4. 目標埠是否佔用，以及是否存在 Nginx、Caddy 或已有網站。
5. 軟體源、npm registry、證書服務（僅 HTTPS）是否可達。
6. 系統防火牆、雲安全組、NAT 和外部訪問路徑。
7. Linux 是否具有可用的 systemd 使用者服務；容器或缺少使用者匯流排的系統不能假定支援它。

發現已有部署時，先確認其賬號、資料目錄、執行賬號和訪問地址。保留現有配置及資料，避免重複安裝、覆蓋服務或切換到空資料目錄。

安裝依賴時優先複用合適的 Node.js；需要新裝時可使用 fnm 安裝受支援的 LTS 版本，並確保後續服務使用的 Node 執行檔長期存在。不要解除安裝其他服務依賴的執行時。

## 4. 顯式 HTTP：內網或臨時驗證

以下以 Linux 遠端伺服器、訪問埠 8790 為例。

### 4.1 安裝軟體

在目標伺服器、將來執行 Hub 的賬號下執行：

```bash
node --version
npm --version
npm install -g pi-web-ui
pi-web-ui hub --help
```

npm 全域性目錄不可寫時，優先使用該賬號的 fnm 或使用者級 npm 字首，並確認 PATH。不要因為許可權錯誤就無條件把所有步驟改為 root。

### 4.2 安裝並啟動 Hub

```bash
pi-web-ui hub install --https=off --host 0.0.0.0 --port 8790 --public-url http://203.0.113.10:8790 --allow-registration
pi-web-ui hub status --json
```

引數說明：

- `--host 0.0.0.0`：監聽所有 IPv4 網絡卡，允許其他裝置訪問。
- `--port 8790`：Hub 服務監聽埠，不是 SSH 埠。
- `--public-url http://203.0.113.10:8790`：其他裝置實際訪問的根地址，沒有路徑、查詢引數或賬號密碼。不可寫為 `0.0.0.0`。
- `--allow-registration`：暫時允許建立賬號；建立所需賬號後關閉。
- `--data-dir`：可選，預設是執行賬號的 `~/.pi-device-hub`。必須與聊天主服務的資料目錄分開。

`install` 儲存配置、配置自啟動並啟動服務。系統支援方式為 Linux `systemd --user`、macOS 使用者 LaunchAgent、Windows 登入計劃任務。

**Linux 無人登入也要啟動時**，需管理員為實際執行賬號啟用 linger，例如將以下 `deploy` 替換為真實賬號：

```bash
sudo loginctl enable-linger deploy
```

啟用後檢查使用者服務及重啟後的狀態，不能只憑安裝成功就承諾開機可用。Windows 登入計劃任務與 macOS 使用者 LaunchAgent 通常需要對應使用者登入，不應稱為系統開機即執行。

沒有可用服務管理器時，可以先以前臺方式驗證：

```bash
pi-web-ui hub --host 0.0.0.0 --port 8790 --public-url http://203.0.113.10:8790 --allow-registration
```

前臺程序會隨終端退出而停止。長期執行需適配實際環境的程序管理器，並在部署結果中說明，不要重複啟動兩份 Hub。

### 4.3 放行埠

預設 HTTP 方案需要允許 TCP 8790 入站。先識別實際防火牆，再修改對應規則，例如僅當伺服器啟用 UFW 時：

```bash
sudo ufw allow 8790/tcp
```

雲伺服器還需在雲控制台放行同一埠；有路由器 NAT 時配置埠轉發。保留現有 SSH 規則，不關閉整個防火牆，也不放行無關埠。無法代操作雲控制台時，給出協議、埠、來源範圍和需要修改的位置。

### 4.4 需要使用者完成的操作

AI 應在操作發生的步驟給出簡短的操作卡片，寫明“誰來做、在哪裡做、填什麼、完成後如何驗證”，而不是在結束時籠統說“請開放埠”。能夠由已授權工具完成的伺服器內配置直接執行，雲控制台等沒有訪問能力的位置交給使用者。

例如預設 HTTP 部署可這樣提示：

> **需要你在雲伺服器控制台放行埠**
>
> 當前 Hub 已啟動，外部訪問仍待驗證。請開啟雲廠商控制台，找到這臺伺服器關聯的安全組或例項防火牆，新增一條入站允許規則：
>
> - 協議：TCP。
> - 目標埠：8790（以本次實際選擇的埠為準，不是 SSH 的 22）。
> - 來源：僅自己或固定網路使用時填寫裝置出口 IP/CIDR；需要任意網路裝置接入時，可選擇 `0.0.0.0/0`，這表示對所有 IPv4 地址開放該服務埠。
> - 方向與動作：入站、允許；儲存並確認規則已關聯到這臺例項。
>
> 完成後告知我，我會重新檢查 `http://實際伺服器地址:8790/health`。暫時不要關閉已有 SSH 規則。

雲廠商可能稱其為“安全組”“防火牆”或“輕量應用伺服器防火牆”。先確認使用者使用的廠商和例項型別，再給出對應導航；不確定時說明需要查詢的功能名稱，不編造選單。部分平臺需要同時檢查子網網路 ACL、負載均衡或埠對映，依據實際網路拓撲排查。

操作提示隨方案變化：

| 使用者操作     | 何時需要                  | AI 應給出的具體資訊                                         |
| -------------- | ------------------------- | ----------------------------------------------------------- |
| 雲控制台放行   | 雲安全組未放行            | 例項、入站 TCP 埠、來源範圍、規則關聯與驗證地址             |
| 提供安裝許可權 | 系統依賴需要 sudo         | 哪一步需要許可權，引導在安全終端輸入；不要求聊天回傳密碼    |
| 域名 DNS 配置  | 使用者選了域名            | 記錄型別、主機記錄、目標 IP；已有衝突記錄需檢查             |
| HTTPS 入口放行 | 選用直接暴露的 HTTPS 代理 | 通常 TCP 443，以及證書驗證或重定向所需的 80；按證書方案決定 |
| NAT 埠轉發     | 位於路由器或對映網路後    | 外部埠、內部地址和埠、協議，以及最終公開 URL                |
| 建立賬號       | Hub 首次可訪問            | 開啟哪個地址、在網頁建立賬號、之後何時關閉註冊              |
| 裝置繫結       | 使用者開始連線電腦        | 每臺電腦進入裝置中心，填寫哪個 URL，如何確認繫結成功        |

不要預設要求使用者開放 22、80、443、8790 全部埠：SSH 僅在遠端管理需要時開放；純 HTTP 僅需實際 Hub 埠；同機反向代理下 Hub 埠不必暴露公網。IPv6 使用對應的來源規則，並確認確有 IPv6 部署需求。

如果正在等待使用者處理，狀態應為“服務已啟動，等待雲安全組放行”或“外部驗證待完成”，不能寫成“部署全部完成”。保留當前進度，使用者完成後從驗證繼續；若仍不通，再分層檢查系統防火牆、雲規則、NAT 和 DNS，避免讓使用者反覆新增同一條規則。

### 4.5 分層驗證

在目標伺服器檢查：

```bash
pi-web-ui hub status --json
curl --fail --show-error http://127.0.0.1:8790/health
```

`/health` 應返回 HTTP 200，JSON 包含 `service: "pi-device-hub"` 和 `status: "ok"`。再從另一臺實際需要使用的裝置檢查：

```bash
curl --fail --show-error http://203.0.113.10:8790/health
```

本機健康、外部可達、瀏覽器可用和裝置成功連線是不同層次的驗證。如果執行環境不能從外部訪問，就標明“伺服器內已驗證，外部待驗證”。瀏覽器可開啟也不代表 WebSocket 協作鏈路已經通過。

## 5. 可選：域名與 HTTPS

### 5.1 只使用域名，繼續 HTTP

將域名 A 記錄指向伺服器公網 IPv4。僅在伺服器和網路支援 IPv6 時設定 AAAA 記錄。裝置訪問地址可以是 `http://hub.example.com:8790`，仍需開放 8790。

要顯式保留 HTTP，安裝時同時傳 `--https=off`；否則公網 Linux 安裝會自動啟用 HTTPS。

### 5.2 域名 + HTTPS

預設由安裝器配置內建 TLS 閘道器。已有 Caddy/Nginx 時使用 `--https=external`，保留現有代理；下面是外部代理方式。Hub 本身繼續監聽內部 HTTP。

首次安裝示例：

```bash
pi-web-ui hub install --https=external --host 127.0.0.1 --port 8790 --public-url https://hub.example.com --allow-registration
```

Caddy 與 Hub 位於同一機器、已有域名且沒有其他服務佔用 80/443 時，站點配置示例：

```caddyfile
hub.example.com {
    reverse_proxy 127.0.0.1:8790
}
```

Caddy 支援 WebSocket 代理。使用 Nginx 時也必須正確轉發 WebSocket Upgrade、原始 Host 和代理協議頭，並配置合適的長連線超時。代理應支援裝置中心的流式連線和遠端訪問路徑，不能只驗證首頁。

先檢查 DNS、80/443、防火牆和已有站點；把配置合併到現有代理，並先做語法檢查再 reload。不要覆蓋整份已有配置。若代理在其他機器或容器中，`127.0.0.1` 不一定能到達 Hub，應按實際網路設定監聽地址和訪問控制。

Hub 的 `--public-url` 必須是根 origin，例如 `https://hub.example.com`；本指南不使用 `/hub` 子路徑。不要僅把 URL 從 HTTP 改為 HTTPS 而不配置 TLS 入口。

### 5.3 已有 HTTP 部署遷移

先記錄 `status --json`、執行賬號、資料目錄和註冊策略，並備份資料及代理配置。當前 CLI 的 `restart` 除註冊開關外不接受部署引數，不能編造 `restart --public-url ...`。

更新到支援自動 HTTPS 的版本後，執行 `pi-web-ui hub https`，或用 `--public-url https://實際域名` 指定新地址。它會驗證 HTTPS 並保留舊裝置憑據連線；驗證失敗恢復原配置。不要解除安裝重灌或切換資料目錄。待全部裝置改用 HTTPS 地址後再關閉舊 HTTP 埠。

## 6. 建立賬號並連線裝置

1. 瀏覽器開啟最終訪問地址，建立所需賬號。登入密碼由使用者在中心頁面輸入。
2. 在各臺電腦的 pi-web-ui 中開啟“裝置中心”，選擇連線已有中心，填寫相同的最終地址，按頁面流程登入和繫結裝置。
3. 在中心確認裝置線上，再建立 Bot 和群組，驗證訊息及預期協作能力。
4. 賬號建立完成後，在目標伺服器、同一個執行賬號下關閉註冊：

```bash
pi-web-ui hub restart --allow-registration=false
pi-web-ui hub status --json
```

關閉註冊不會刪除已有賬號。需要建立其他賬號時，可臨時 `restart --allow-registration=true`，完成後再關閉。是否關閉應結合使用者的賬號建立安排，不要在使用者尚未建立賬號時提前關閉。

## 7. 日常運維與恢復

```bash
pi-web-ui hub status --json
pi-web-ui hub stop
pi-web-ui hub start
pi-web-ui hub restart
```

這些操作需要使用安裝服務的同一賬號。`status` 輸出包含執行、歸屬和註冊狀態，應確認執行的是已儲存的那個例項。

升級前記錄版本、資料目錄和配置並備份；停服後更新 npm 包，再啟動並驗證。若使用 fnm 切換 Node 版本，需確認服務儲存的 Node 與入口路徑仍有效，必要時保留原資料目錄重新安裝服務配置。

備份應覆蓋實際 Hub 資料目錄及服務配置，且必須整目錄備份：`device-hub.json` 只是索引，群訊息、任務與 Bot 轉錄儲存在同目錄 `hub-log/` 的追加日誌中，只拷索引會丟資料。備份中可能包含憑據，應限制訪問。優先停服後備份以保證檔案一致性；恢復時使用相容版本及原執行賬號，檢查檔案許可權。

```bash
pi-web-ui hub uninstall
```

`uninstall` 停止並移除服務，保留賬號與裝置資料。不要把刪除資料目錄作為排錯步驟。

| 現象                 | 優先檢查                                                 |
| -------------------- | -------------------------------------------------------- |
| SSH 失敗             | 地址、SSH 埠、賬號、認證、主機指紋及雲安全組             |
| 命令找不到           | Node/npm 是否安裝、執行賬號的 PATH、fnm 環境             |
| 安裝使用者服務失敗   | systemd 使用者匯流排、會話環境及服務管理器是否可用       |
| 本機健康但外部超時   | 監聽地址、系統防火牆、雲安全組、NAT                      |
| 首頁能開但裝置離線   | public URL、WebSocket 代理、證書及裝置網路               |
| HTTPS 失敗           | DNS/AAAA、80/443、證書申請、已有代理埠衝突               |
| 退出登入或重啟後停止 | Linux linger、實際使用者服務狀態、Node 路徑              |
| 原賬號或裝置消失     | 是否用了不同賬號或空的資料目錄；先找原目錄，不重新初始化 |

## 8. 給 AI 部署助手的執行要求

收到部署任務時，先讀取本文，再把使用者提供的欄位作為資料處理，不把欄位拼成任意 shell 片段。缺少資訊時集中詢問最小必要項，已有答案不重複詢問。

1. 明確部署目標；公網 Linux 預設自動 HTTPS，域名可選，內部埠 8790；使用者顯式選擇 HTTP 時使用 `--https=off`。
2. 遠端部署需要真實伺服器地址、SSH 埠、賬號和可用認證通道。本機平臺資訊只代表本機；`0.0.0.0` 是監聽地址，不是 SSH 地址或公開地址。
3. 先執行已授權的只讀檢測，再給出將使用的賬號、埠、資料目錄、訪問地址及服務方式。使用者已授權部署時推進安裝；遇到覆蓋已有配置、衝突或確需決策的事項再詢問。

## 9. 當前 AI 入口的能力邊界

當前 pi-web-ui 的遠端部署入口提供伺服器地址、SSH 埠、登入賬號、認證方式和中心內部埠，預設生成 `https://伺服器地址`，支援公網 IPv4 無域名部署。HTTPS 開關與可選域名在連線設定中，頁面展示雲安全組、來源範圍、賬號建立和外部驗證等使用者操作提示。

點選“開始 AI 輔助部署”會新建部署對話，傳入公開指南連結、選定連線資訊、部署配置與當前服務的有限環境資訊，保留原對話。頁面不收集密碼或私鑰，也不會僅因點選按鈕而自動建立 SSH 連線；密碼認證在後續安全 SSH 終端中進行。

後續若提供直接連線能力，連線憑據應交給後端連線模組，AI 僅獲得連線控制代碼及檢測結果，並按連線、檢查、安裝、啟動、驗證展示真實進度。

本文提供的公網連結需要文件合併到倉庫 `main` 後才能訪問。未釋出的工作區改動不會自動出現在 GitHub。已安裝軟體若需要嚴格對應某一版本，應改讀實際存在的版本 tag 下同路徑文件；新文件出現以前的歷史 tag 不包含此檔案。

## TURN（coturn）

對稱 NAT / CGNAT 下 UDP 打洞必然失敗，需要 TURN 中繼。Hub 只做信令，TURN 是另一份獨立服務（可與 Hub 同機）。最小可用配置（Ubuntu/Debian，安全組放行 3478/udp 與 relay 埠段）：

```bash
apt-get install -y coturn
cat >/etc/turnserver.conf <<"EOF"
listening-port=3478
fingerprint
lt-cred-mech
realm=pi-web-ui
external-ip=<伺服器公網 IP>
min-port=49160
max-port=49200
no-multicast-peers
no-cli
# 長期憑據：與裝置端 PI_DEVICE_TURN_USERNAME / PI_DEVICE_TURN_CREDENTIAL 一致
user=pi:<強密碼>
EOF
sed -i "s/^#TURNSERVER_ENABLED=1/TURNSERVER_ENABLED=1/" /etc/default/coturn
systemctl enable --now coturn
```

驗證：

```bash
# 應當返回 XOR-MAPPED-ADDRESS（同一埠打兩個 STUN 地址對映一致 = 錐形 NAT，可打洞）
turnutils_uclient -u pi -w <密碼> -p 3478 <伺服器IP>
```

裝置端（兩端都要）：

```bash
PI_DEVICE_TURN=turn:<伺服器IP>:3478 \nPI_DEVICE_TURN_USERNAME=pi \nPI_DEVICE_TURN_CREDENTIAL=<強密碼> \npi-web-ui server restart
```

要點：

- 只需要 `turn:` + UDP；`turns:`（TLS）要證書且延遲更高，非必需。
- `external-ip` 必須寫公網 IP，否則 coturn 會分配內網對映，客戶端拿到不可達候選。
- 頻寬按 H.264 通道估算：1440p60 約 12 Mbps、1080p60 約 6 Mbps、1440p120 約 18 Mbps/路。
- 只想驗證鏈路時先把 `min-port`/`max-port` 收窄到 40 個埠即可，正式使用再按併發數放寬。
- 中繼生效時服務端日誌出現 `P2P is relayed through TURN`；介面通路仍顯示 `p2p`。
