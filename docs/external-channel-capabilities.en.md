# External messaging channel capabilities and usage

Covers 11 channels: WeChat iLink, QQ, WeCom, Feishu, DingTalk, Telegram, Discord, Slack, Matrix, WhatsApp, and iMessage. Each platform's API permissions, account eligibility, and format limits still apply.

## Unified behavior

All 11 channels handle `/help`, `/new`, `/clear`, `/status`, `/stop` (alias `/abort`), `/model`, `/thinking`, `/cwd` (alias `/workspace`). An unknown command replies with help and does not reach the model. Discord/Slack commands are text commands inside ordinary messages; no platform-native slash-command endpoint is registered.

Sessions are isolated by sender and conversation space: Telegram chat/topic, Discord channel (including standalone thread channels), Slack channel/thread, Matrix room/thread. Whether the session mapping persists differs per channel; Telegram, Discord, Slack, and Matrix keep preferences and mappings in plugin memory and reset on restart. New/clear and directory switches change the peer account epoch, so the next host.chat uses a different accountId and the daemon does not reuse old context. History is kept. A model switch opens new context; see each plugin README for restrictions on switching mid-run.

All bridges consume the real conversationId and stable runId from the host.chat acknowledgement, and buffer assistant messages and end events that arrive before it. Events are claimed by runId, so a conversation takeover or rename cannot misroute them. Stop passes the stable runId first; a stop during download cancels subsequent model delivery. Dispatch, download, and model execution failures get channel feedback; send failures themselves are recorded in state/logs, and Discord/Slack/Matrix additionally use host notification capability when available.

PNG/JPEG/GIF/WebP are passed as `{path, imageData:base64, mimeType, name}` under the existing PromptAttachment contract, at most 8 per request, 10 MiB per image, 20 MiB of images total, and finally bounded by host validation and the model's vision capability. A Telegram or Matrix event usually carries only one media item. Non-images are input as `{path:absoluteDownloadedPath, mode:"reference", name}`; the model receives a real file reference, not a remote download link.

Media passed as base64 to Feishu/DingTalk maxes out at 10 MiB each and 20 MiB combined; WhatsApp inbound media maxes out at 10 MiB each. Outbound Feishu maxes out at 10 MiB, DingTalk/WhatsApp at 20 MiB, still bounded by each platform. Local path references do not consume the base64 byte budget.

Audio/video send and receive is not automatic understanding: the plugins bundle no speech transcription or video decoding. Received audio/video, unsupported image types, or unknown file types are stated explicitly, and the model needs a working transcription, decoding, or document-reading tool. When it cannot be understood the plugin must say so rather than silently dropping the attachment. See each plugin README for download locations and authorization requirements; workspace files need the host fs permission.

## Verification and deployment

This round's behavior tests use mock platform HTTP/API and host.chat, covering real attachment content, command interception, account epoch, group/thread isolation, stable runId and early end events, and races such as stopping during download. No production bot credentials were used for real end-to-end platform tests.

The local plugin directory actually inspected was `C:\Users\c\.pi-web\plugins`; the installed QQ and WeChat sources there were synced, and secrets/storage were verified unchanged; the other nine channels were not installed and were not installed automatically. Telegram/Matrix are at version 0.2.0, Discord/Slack at 0.1.7.

The public host now genuinely passes attachments through via `host.chat({text, attachments})`; at most 8, base64 attachments 10 MiB each and 20 MiB total, over-limit rejected explicitly rather than truncated; local path references go through the existing attachment permission chain. `host.abortRun(runId)` can find the real run after takeover by its stable `pr-` identifier, and returns failure for a stale identifier instead of stopping a same-named conversation by mistake.

This round's joint verification: 29 related test files, 404 tests passing, covering host media input, stop ownership, and each channel's behavior; plugin versions, tool prompts, and manifest permissions have separate guard tests. Prettier, all five project TypeScript checks, lint, and diff whitespace checks passed. Real end-to-end platform integration with production accounts still needs separate verification.
