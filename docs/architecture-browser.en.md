# Built-in browser and desktop Agent

The desktop app combines the browser and the existing pi-web-ui Agent in one window, supporting three modes: browser, agent, split. The startup mode is decided by the `defaultMode` setting; new users default to agent (the local Agent sidecar starts in parallel, and the shell shows a boot placeholder until it's ready); if the Agent fails, the placeholder offers a one-click switch to the browser. The npm / pure-Web service entry keeps using the existing path.

## Modules and boundaries

- `browser/contracts.ts`: public browser state and host interfaces; page request types are derived from `server/protocol.ts`.
- `browser/runtime/manager.ts`: the single source of tab state — manages WebContentsView, navigation, restore, persistent sessions, downloads, and teardown.
- `browser/storage/index.ts`: bookmark tree, history, settings, encrypted credentials, and legacy data import.
- `browser/renderer/`: the standalone browser shell, new tab page, bookmark/history/settings/download panels, document and media pages, built on the existing theme baseline.
- `browser/automation/executor.ts`: page operation executor, independent of the chat UI.
- `browser/preload.cts`: secure capability handshake; exposes only the interfaces matching a confirmed role.
- `desktop/browser-host.ts`: browser + Agent combined layout, IPC role verification, site permissions, and authorization for user-selected files.
- `desktop/browser-policy.ts`: trusted addresses and layout pure functions.
- `desktop/main.ts`: single app startup, sidecar, updates, and packaging entry.

The browser module doesn't import the Agent runtime, and the backend doesn't import Electron. Future work on the browser's address bar, tabs, navigation, storage, and performance can proceed inside browser independently. The Agent joins the layout through a dedicated native view provided by the host.

## Windows, modes, and lifecycle

BrowserWindow's webContents loads the local shell.html; tabs and the dedicated Agent use WebContentsView.

- **browser mode**: full-width complete browser, an 88px browser shell at the top (tab bar and address bar), the page view below; the top right switches back to Agent / split view;
  each tab's page icon follows the site: the main process listens for `page-favicon-updated` and accepts only http(s) and small `data:image` (`pickTabFavicon`; over-long data URLs and `javascript:`/`file:` are always dropped), clearing it when main-frame navigation starts; the shell renders `<img class="pb-tab-favicon">`, falling back to a globe icon when loading fails or there's no icon, while internal pages keep `π`.
- **agent mode**: the Agent occupies the whole viewport at full size and full height (starting at y: 0), no browser tabs or address bar shown, keeping the pure desktop experience and window controls/dragging identical to no integration, with a browser switch button in the top bar;
- **split mode**: left and right side by side, independent. The left side is the complete Agent view (y: 0 top to bottom), the right side an independent browser (a local browser shell at the top of the right side, the page view below) — the effect is like having an Agent window and a browser window tiled on the desktop.

Startup mode = `BrowserSettings.defaultMode` (`agent` default / `browser` / `split`). Two entry points write the same setting: browser settings → startup mode, and the app settings dialog → 「桌面应用」(desktop app) page (visible only in the desktop shell, going through host IPC via `pi-desktop:browser-get/set-startup-mode`). Switching at runtime changes only the current session and isn't written back to settings; the old `mode` (last-used mode) stored by older versions is migrated to `defaultMode` on first read, so existing users start up the same after upgrading. On agent / split startup, the Agent view isn't shown before the first frame is ready; instead the shell renders the `pb-boot` placeholder (with the failure reason and a 「切换到浏览器模式」(switch to browser mode) exit), handing over to the Agent view and focusing it once ready.

Switching modes reuses the same views and updates visibility, bounds, and focus without reloading pages. Hidden pages keep valid dimensions — they don't shrink to 1×1. Closing a tab closes the corresponding WebContents; quitting the app cleans up tabs, downloads, the Agent, and pending channels.

Native views can't be covered by an ordinary DOM z-index, so shell panels (bookmarks / history / downloads / settings / extensions) **no longer use a DOM overlay + hidden content area**: one panel = one `panel.html` view (`WebContentsView`), added to `contentView` after the page view so it covers it, and the host positions it, per the size the panel reports itself, as a rectangle below the toolbar and flush to the right edge of the window (`panelLayerBounds` in `desktop/browser-policy.ts`). The page and Agent split outside that rectangle stay visible and clickable — this is exactly what fixed "the page and chat all go black the moment the plugin list opens".

- Open/close goes through the `panel` action (`{ open, panel }`); clicking the same panel again collapses it (the toolbar button is itself a toggle, so the frontend needs no state). Sizes are reported by the panel page (`{ size }`); the panel measures itself and the host clamps it into the usable area, with a fallback timeout when it can't measure (`PANEL_LAYER_SHOW_DELAY`).
- Panels live in their own view, so `window` events don't cross over: bookmark / settings / extension changes go through `panel`'s `{ event }`, which the host forwards as `pi-browser:panel-event` (`onPanelEvent` in `browser/preload.cts`), and the shell and new tab page each refresh.
- Actions inside a panel must "do the work first, then close the panel" (navigation, opening the extension page): destroying the view takes the next IPC with it.
- Internal tabs (new tab page etc.) keep using page-local DOM for their own overlays: `dialog.show()` rather than `showModal()` — no `::backdrop` scrim, don't make the whole window inert, close on outside click or Esc (`handleOutsidePointer`/`handlePanelEscape` in `browser/renderer/panels.ts`).
- The `overlay` action now serves only the shell's search overlay: that's a DOM overlay covering the whole content area, so the content view has to yield — a different thing from panels.

The Agent can sync mode and tab state with the host via `piDesktop.browser`.

Window drag regions (`-webkit-app-region`) can't hang off layout artifacts that can disappear: the Agent top bar used to rely solely on `.tb-spacer` for dragging, and once a narrow split pane entered the mobile view, a media query collapsed the spacer to `display: contents` (no box = no drag region), so the whole header could no longer drag the window. Now `body.is-desktop .topbar-flow` declares `drag` itself and interactive items opt out one by one with `no-drag`, independent of whether the spacer exists; see `tests/unit/desktop-agent-input-regions.test.ts` for the regression guard.

## Local and remote Web Agent

The local address comes from the actual sidecar startup result and isn't fixed to 8787. The desktop's default service port follows `desktop/startup.ts`. A remote HTTP/HTTPS Agent address can be connected and remembered in browser settings.

When that trusted address is opened with the built-in browser:

```text
Agent service → existing page WebSocket → page_request
→ __piWebUiHost.pageCall → __piBrowser.pageCall
→ main-process authorization check → browser automation → target tab
→ page_response back the same way
```

`__piWebUiHost` is still maintained by the web app. The web frontend prefers detecting `__piBrowser` and keeps the existing page-picker path when native capability is absent. No hiding the Electron UA, no extra user plugins, no fixed 7801 anonymous HTTP API. In an ordinary system browser, pages keep the existing extension-based integration.

This mode requires the connection carrying the Agent page to be online; it doesn't provide unattended or cross-device execution by itself. Nor does it read system Chrome's tabs or login state automatically.

## Permissions and data

Every IPC checks mainFrame, the current URL and the role — not just at preload initialization:

- The shell and precisely allowlisted local internal pages may call browser UI, storage and file-picker capabilities.
- Trusted pages at the local/configured Agent origin may call the page-execution interface; ordinary websites can't operate other tabs.
- Websites never get browser bookmarks, credentials or any filesystem interface.
- Site permissions are handled by the session handler; sensitive permissions are explicitly granted and stored per origin.
- eval is off by default and can be explicitly enabled in settings. An explicit target that has gone away must not fall back to operating other tabs; multiple tabs on the same origin should use a stable tabId.
- "Which tab the user currently has open" is a protocol fact, not a client guess (the only native-side source of truth is `BrowserManager.getActiveTabId()`): `browser_page`'s `pages`/`status` mark the current tab `active: true` and return `activeTabId` (only operable pages are exposed; internal pages and the caller's own view don't count); with multiple tabs open an explicit `target` is still required, and the error text names the exact tab the user has open. Same for page-picker: among authorized pages only the active tab of the last focused window is marked `active`, along with `activeOrigin`; unauthorized pages aren't reported even when in the foreground (the extension doesn't request the `tabs` permission; only origins with granted host permissions are queried with `active: true, lastFocusedWindow: true`).
- Local files must be authorized by the system picker, read limit 32 MiB; text documents can be saved; binary Office documents are read-only previews, and writing text back into the original binary file is forbidden.
- **Password field values never leave the page**: both channels follow one rule — `read what=query` doesn't return `value` and blanks `text`, `read what=html` clones then strips the `value` attribute, and the `type` echo carries no value either. The native-side source of truth is `isPassword` in `browser/automation/page-operation.ts`; on the page-picker side it's `isPassword`/`outerHtmlMasked` in `plugins/page-picker/extension/src/content/bridge-page.ts`. Changing either side requires changing the other: password fields can still be filled with `type` as usual, they just aren't echoed back. Regression: `tests/unit/page-picker-password-mask.test.ts` and `tests/page-picker-bridge-test.mjs`.
- Extension installation ranks the same as 「加载已解压扩展」(load unpacked): only a user-selected directory or `.crx` file is accepted. For `.crx`, the main process strips the `Cr24` signature header before unpacking (entry count / size limits, no out-of-bounds paths or links, `manifest.json` must exist), and **doesn't verify the signature**; the unpack target is `userData/extensions/crx-<content hash>`, and reinstalling the same file keeps the same path. Installed directories are recorded in `userData/extensions/installed.json` (`{ path, enabled }[]`; the older plain string array is still readable), and on restart only the `enabled` ones are restored (Electron's `loadExtension` isn't persistent by itself).
- The extension panel is opened by the extension icon in the browser toolbar (the puzzle-piece button in `shell.ts`, badge = enabled count), with the same entry semantics as Chrome's extensions menu: **one row per extension, clicking the whole row opens its own page** (`default_popup`, falling back to the options page if absent), with the enable toggle at the row start and reload/options/remove at the row end `⋯` (the same native menu as right-click). The panel is a small overlay (`pb-dialog-compact`, 360px wide, height following the list), not a full-screen window. `extensions.list` merges "what's actually loaded in the session" (`session.extensions.getAllExtensions()`) with "what `installed.json` remembers"; for disabled entries the name/version is read back from the manifest on disk, and loaded entries carry `popup` (the `default_popup` of the manifest's `action`/`browser_action`/`page_action`, with the rule single-sourced in `browser/runtime/extension-state.ts`). `extensions.toggle` disables = `removeExtension`, enables = `loadExtension` again; `extensions.reload` unloads then loads the same directory (extension code changes need no app restart); `extensions.remove` only unloads + forgets it from the manifest, **without deleting the disk directory** (a directory the user unpacked shouldn't be deleted by the browser). The settings panel keeps only a single 「管理扩展」(manage extensions) entry, no longer re-listing extensions.
- The toolbar's extension icon is rendered by `electron-chrome-extensions`' `<browser-action-list>` (see "Extension capability boundary" below); clicking it opens Chrome-semantics `default_popup` / `onClicked`. Extension **panel** rows have the same semantics: clicking the whole row goes through `extensions.openPopup { path, anchor }`, loading `chrome-extension://<id>/<default_popup>` in **a separate frameless small window in the same session**, positioned **where the mouse went down** (the panel row records the `pointerdown` viewport coordinates → screen coordinates; keyboard activation or a click outside the row falls back to the row's bottom-right corner; clamped to the screen work area), the window is **square-cornered** (`roundedCorners: false`; macOS's default rounding clips a chunk off each corner of extension pages), and it closes on blur — only one window per extension page; the panel is collapsed before opening (so the overlay doesn't sit on the page that's about to open, and the page comes back with it), but collapsing the panel must not steal focus back to the shell — the action popup holds focus at that moment, and one steal makes it blur and close itself (measured on mac as "the popup flashes and vanishes"): `closePanelLayer()` doesn't restore focus when it sees a focused action popup, and a blur within 300ms of the popup appearing doesn't count as closing (`ACTION_POPUP_BLUR_GRACE_MS`); a disabled row instead hints to enable it first. The popup window **opens at the size the extension page itself asks for** (Chrome's popup is as big as its content, not a fixed 400×560, otherwise a narrow page leaves a big empty strip on both sides): the size is measured in the page before opening the window, taking the smaller of two measures: the content box (`body.scrollWidth/scrollHeight` — most accurate for fixed-width popups like Dark Reader's 285px one) and the bounding box of descendant boxes (when `body` is stretched to the viewport the real size is on the children; boxes as wide/tall as the viewport only count as stretched containers, taller than the viewport counts as a valid signal; the scrollbar only takes width when the content height exceeds Chrome's cap and a vertical scrollbar really appears). Taking the smaller is mandatory: absolutely positioned tooltips and animation-collapsed areas moved out of the viewport blow the bounding box far beyond the content, and trusting only the bounding box measures 550px wide with a black strip on the right; then clamp to Chrome's 800×600 cap, measure twice (text rewraps when the width changes), and fall back to a default size if measuring fails; the pure functions and measuring script are in `browser/runtime/extension-popup.ts` (unit test `tests/unit/extension-popup.test.ts`). Both paths share one rule: Chromium's preferred-size mode (`preferred-size-changed`) doesn't fire for `chrome-extension://` pages in practice, so the toolbar action icon path (the library's `PopupView`) is taken over too — the host listens for `browser-action-popup-created`, first gives the window a normal viewport, measures the content size with the same method, then calls the library's own `updatePosition()` (anchoring and alignment stay in the library) and `show()`; without the takeover the window sticks at 25×25 and stays hidden (clicking the icon does nothing). The options page goes through `extensions.openOptions { path, anchor }` (`options_ui.page` first, then legacy `options_page`): it opens a normal resizable window that doesn't close on blur — Chrome's two presentations (tab / embedded in chrome://extensions) unify into one normal window here, and `open_in_tab` doesn't participate in the model. Browser navigation policy is unchanged — only "pages declared by a loaded extension itself" can open; `extensionPageUrl` validates the id shape and rejects `..`/absolute paths/paths with a scheme, and arbitrary `chrome-extension://` addresses aren't accepted; external links inside extension pages go to the system browser (`setWindowOpenHandler` deny + `shell.openExternal`). Native regression: `tests/browser-desktop-smoke.mjs` (preload an unpacked extension → restore on startup → popup + options page → disable/enable/reload/remove).
- The extension row's `⋯` and right-click are **the same native menu** (`extensions.menu { items, anchor }`): item labels, check states and enabled states are composed by the renderer (following the UI language); the main process only does `Menu.popup` and passes back the selected item id, returning `null` when the menu is dismissed; unloaded extensions don't show "popup / options". No extra usage hint line — the menu button is the entry point.
- Dropping a `.crx` also goes through the same install path: internal pages get the path via preload's `webUtils.getPathForFile`, then call `extensions.installCrx { path }`; if dropped onto a web page, `BrowserManager`'s navigation guard intercepts the file:// navigation and hands it to `onFileDrop`, and the main process reports via a system dialog once installed.

### Extension capability boundary (Electron ≠ Chrome)

Electron 44's extension context only recognizes **15 namespaces** (`action alarms declarativeNetRequest dom extension i18n idle management offscreen proxy runtime scripting storage tabs webRequest`), `tabs` also lacks `create/remove/captureVisibleTab`, and `storage.sync` has no backend. The extension ecosystem assumes the full API set is there, so this is split into two layers:

**Layer one: `electron-chrome-extensions` (`desktop/browser-host.ts`) — the semantics layer, owning no windows.**
It adds `windows / contextMenus / notifications / cookies / webNavigation / permissions / commands / downloads / topSites / privacy` on the extension session, and routes tabs/windows write operations back to **our own model**: `createTab → BrowserManager.createTab`, `selectTab → activateTab`, `removeTab → closeTab`, `createWindow → standalone BrowserWindow` (the popup type gets a frameless small window, and `addTab` after creation makes it visible to `chrome.tabs.query`), `removeWindow → destroy` (refuses to close the main window), `requestPermissions → native confirmation dialog`. Tab lifecycle is reported by `BrowserManagerOptions.extensionHooks` at `createTab/activateTab`; the context menu goes through `webContents.on("context-menu") → getContextMenuItems()` to compose a native `Menu` (edit items → extension items → back/forward/reload).

Toolbar actions: the library's `<browser-action-list>` is injected by `injectBrowserAction()` in `desktop/preload.cts` (effective only for `shell.html`; the preload is bundled into a single file with esbuild — sandboxed preload can't do module resolution), `shell.ts` creates the element dynamically, `partition` takes `BROWSER_EXTENSION_PARTITION` from `browser/contracts.ts`, and the main process maps it back to the browser session from `session.fromPath()` with `setSessionPartitionResolver`; icons come from the `crx://` provided by `ElectronChromeExtensions.handleCRXProtocol(session.defaultSession)`. Clicking an icon is Chrome semantics: open `action.default_popup` or fire `chrome.action.onClicked`, with badge/title/icon all maintained by the library.

**Layer two: `browser/runtime/extension-compat.ts` — fills only the gaps layer one doesn't cover.**

- `chrome.tabs.captureVisibleTab / duplicate / move / highlight / discard` (not implemented by the library);
- `chrome.storage.sync` lands on `local` (the library already maps it once; this is the fallback when the library is absent);
- All three entry points are covered: MV3 `background.service_worker` is wrapped in `__pi-sw.js` (classic `importScripts`, `type: module` uses `import`), one line is prepended to MV2 `background.scripts`, and `content_scripts` are injected one by one (`world: "MAIN"` isn't injected), while declared popup/options pages get `<script src="/__pi-compat.js">` inserted in `<head>`.
- **No more faking success**: members that can't be reached call back `undefined` and log a `[pi] chrome.<api> is not implemented` warning, instead of returning `[]/true` to fool extensions.

Constraints and boundaries:

- The library's preload ends with `Object.freeze(chrome)`: **adding top-level namespaces is now impossible** (e.g. `fontSettings`); the compat layer can only add members to existing namespaces.
- It writes only to crx unpack directories (`userData/extensions/crx-<hash>`); a directory the user picked with 「加载已解压扩展」 isn't changed by a single byte. It's idempotent, backs up the original manifest as `manifest.original.json`, marks the version in `__pi-compat.json` (`COMPAT_VERSION`, 3+ coordinates with the semantics layer), and self-heals on upgrade at boot.
- **`declarativeNetRequest` static rules are actually enforced by us** (`browser/runtime/dnr.ts`): Electron's own DNR only stores, never blocks (confirmed by measurement), so the host reads the `declarative_net_request.rule_resources` JSON from loaded extensions' manifests and compiles it into `session.webRequest.onBeforeRequest` decisions — the only channel in Electron that really blocks requests. Supports `block`/`allow`, `urlFilter`/`regexFilter`, `resourceTypes`/`excludedResourceTypes`, `domains`/`requestDomains`/`initiatorDomains` and their exclusions, and priority (higher wins; on equal priority allow beats block); host permission gating follows Chrome semantics (`example.com` doesn't cover subdomains; write `*.example.com` for those). Literal prefiltering + regex size/backreference limits keep the cost and ReDoS in check; built-in pages (`file:`) and extension pages are never blocked. Extension load/disable/remove/reload coalesce into a single refresh.
- Still not doable: dynamic/session DNR rules (they live in the extension's LevelDB, unreadable by the main process), the `redirect` / `modifyHeaders` / `allowAllRequests` actions, `sidePanel` / `tabGroups` / `identity`, and namespaces the library doesn't provide and the freeze blocks, like `fontSettings`; MV2's `webRequest` blocking still works but Electron 44 marks it deprecated.
- `chrome.tabs.captureVisibleTab` has a real implementation: the host attaches a small bridge script (`browser/runtime/extension-bridge.ts`) to the browser session's frames / service worker, so `__piExtensionBridge` exists only in extension contexts (ordinary pages have `location.protocol !== "chrome-extension:"` and get nothing exposed); the main process then verifies the sender belongs to the same session and originates from `chrome-extension://`, captures the active tab with `capturePage()`, and supports `format: jpeg` + `quality`.
- The compat layer also fills two small library gaps: `windows.getAll({ populate: true })` fills each window's `tabs` from a real `tabs.query` (the library's dist has no populate implementation); `chrome.storage.sync` lands on local. The only remaining empty implementations are `tabs.duplicate / move / highlight / discard`.

The judgement basis is Chromium's log in the main-process stderr (`ExtensionLoadWarning` / `Extension Error` blocks). Native regression: `tests/browser-desktop-smoke.mjs`: toolbar renders action buttons → click opens `chrome-extension://<id>/popup.html`, `extensions.list` restore, panel popup/options page, disable/enable/reload/remove, and a `crx compat shim` case (hand-built crx → unpack → wrap manifest → SW using `chrome.windows` doesn't crash → options page gets the library namespaces and the compat layer's added `tabs` members → content scripts still inject). Pure functions and idempotency: `tests/unit/extension-compat.test.ts`.

Browser files and sessions live in Electron userData/browser; the Agent's existing data directory keeps using the original config. Credentials use Electron safeStorage; saving is refused when no secure encryption backend is available. The vault can fill the current site only on the user's explicit choice; both the main process and the page check the exact origin, and forms are never submitted automatically. Legacy AI Browser data can be imported from a user-chosen old directory; existing target files aren't overwritten; import errors are reported separately.

## Page script injection (Agent → page)

The Agent can inject scripts into web pages: the `browser_script` tool (`server/browser-script-tool.ts`) → `page_request` (`op: "script.list|status|create|update|remove|enable|disable|run"`) → `desktop/browser-host.ts` verifies the caller → `browser/automation/scripts.ts` → `BrowserManager`. The wire protocol gains no new fields (`op` is still a string); the actual injection happens only on the main-process side.

- **One record, two lifecycles**: `PageScript`'s (`browser/runtime/scripts.ts`) `persistent` decides whether it's written to `userData/browser/scripts.json` (still effective after restart) or lives only in memory (gone when the browser closes). Temporary scripts are re-injected after a page refresh, which is exactly the semantics "temporary" should have; a one-off change = create a temporary script → `run` → `remove` (which also runs cleanup).
- **Defaults to the user's current tab**: a script's default target shares the same source of truth as `browser_page`'s active semantics (`BrowserManager.getActiveTabId()`) — omitting `matches` makes a new script apply only to the target's site (target defaults to the current tab); `script.run` without a target hits only the current tab; `script.status` carries `activeTabId` and each tab's `active`. Only an explicit `[]` or `*` means the whole site.
- **Scripts have no capability limits**: no cap on code size, count, or match count, and no restriction on code content. Scripts run inside the target page and naturally can't reach the host bridge (`__piBrowser` / `__piWebUiHost` exist only in the Agent page), and the main process never executes script code either.
- **Injection timing**: `dom-ready` uses `executeJavaScript` (not subject to page CSP); `document-start` uses CDP `Page.addScriptToEvaluateOnNewDocument` (only it can grab the new document's first line), degrading to dom-ready and recording `lastError` when the debugger is already taken; `world: "isolated"` uses `executeJavaScriptInIsolatedWorld` / CDP `worldName` and gets no page JS handle. CSS goes through `insertCSS`/`removeInsertedCSS`, cleanly undoable in a way JS isn't.
- **Runs once per document**: `BrowserManager` resets the tab's runtime state on `did-start-navigation` (non same-document), and a per-document `WeakMap` token in the page dedupes further, so a repeated `dom-ready` or dual-channel injection can't run the same script twice in one document.
- **Revocable**: a top-level `return function () {...}` in the script is the cleanup hook, called before re-running/disabling/removing; the in-page registry `window.__piPageScripts` is directly inspectable in DevTools.
- **Observable**: `script.status` returns `{ injected, skipped: [{scriptId, reason}], errors }` per tab (`scripts-disabled` / `internal-page` / `not-matched:<url>`); injected code carries `//# sourceURL=pi-script://<id>/<name>.js`, so it can be breakpointed separately in DevTools.
- **Boundaries**: internal pages (shell/newtab/workspace/office) are never injected; with the `allowScripts` master switch off everything is skipped; ordinary websites can't manage scripts through any entry (`scripts.*` is opened only to shell internal pages). The settings panel's 「页面脚本」(page scripts) lists all scripts (temporary/permanent badge, source, `document-start`/`isolated` non-default badges) and allows disabling, viewing the code, and deleting.

## Credential vault (passwords + TOTP)

Toolbar key icon → `vault` panel (one member of `BROWSER_PANELS`, going through the same `panel.html` overlay views). Passwords and TOTP are the same thing in the user's eyes ("this site's credentials"), so they merge into one panel with two segment tabs sharing one set of interactions. The shell can specify which tab opens first with `panel { open, panel: "vault", tab: "totp" }` (the key icon always opens TOTP; 「打开凭据保险库」(open credential vault) in settings opens passwords).

### Shared interaction (design C: icon toolbar)

- **Actions live only in the top row**: the panel puts no buttons on entries; actions are collected into the title bar's action slot (`.pb-dialog-actions` in `panels.ts`). Buttons are icon-only (accessible names via `aria-label`), names come from `data-tip` CSS hover bubbles (`title` left empty to avoid stacked native tooltips); the two rightmost icons use `data-tip-end` for right alignment so the overlay's rounded corners don't clip them. The toolbar follows the tab: passwords get `添加 ｜ 填入 / 显示密码 / 编辑 / 删除` (add | fill / show password / edit / delete), TOTP gets `扫码 / 导入图片 / 添加 ｜ 填入 / 导出此条 / 导出全部 / 改名 / 上移 / 下移 / 删除` (scan QR / import image / add | fill / export this entry / export all / rename / move up / move down / delete).
- **Select first, then act**: click an entry or use ↑↓ to select; the toolbar acts on the selected one; with nothing selected the action icons are `disabled` (greyed out, the `::after` bubble suppressed) and the end move-up/move-down are greyed too. An entry matching the current tab is selected and moved to the top on open, so "open panel → click fill" is two clicks. `Enter` fills it into the page; on the TOTP tab `Shift+Enter` copies the code, on the password tab it shows/hides the password.
- The 「密码库」(password vault) section in the settings panel keeps only one line of description and one entry (`vaultSection`); all real add/edit/delete happens here, so two lists aren't maintained in two places.
- The panel overlay view (`panel.html`, `body.pb-panel-layer`) is a third root: it must be in the global `[hidden]` exemption list, otherwise rules like `.pb-form{display:flex}` draw `hidden=true` forms anyway (that's exactly where the "add form expanded by default" bug came from).

### Passwords

- **The list never sends plaintext**: `passwords.list` returns the projection `{ id, name, url, username, createdAt, hasPassword }` (`password` is stripped in the main process's `browser-host.ts`), the same rule as TOTP's "secret never leaves the main process". There are only two doors to plaintext: `passwords.reveal { id }` (fetched once when the user clicks "show password"; the UI covers it again after 10 seconds) and `passwords.fill` (fetched inside the main process and filled straight into the page; plaintext never passes through the renderer).
- **Writes go only through fine-grained actions**: `passwords.upsert { id?, name, url, username, password? }` (`id` present means update; empty `password` means keep the old one) and `passwords.remove { id }`. The renderer never holds the whole plaintext list, so it can't be allowed to `save` the full list — the old `passwords.save` is kept only for smoke tests/migration.
- **Fill checks same-origin**: `passwords.fill` → `fillCredential()`, requiring the current tab and the entry's `url` to have **exactly equal origins**, and exactly one visible password field on the page; after filling it only sends `input`/`change`, and the user clicks submit himself.
- Encryption still goes through `BrowserStorage`'s `enc:<safeStorage>`; when `passwords.available` (= `isEncryptionAvailable()`) is false, the panel shows the vault as locked.

### TOTP

- **Scanning = screenshot the current tab, no DOM reading** (`totp.scan` → `WebContents.capturePage()` → `browser/runtime/qr.ts`): a QR code on a page may be an `<img>`, a `<canvas>`, inline SVG, a CSS background, or drawn dynamically on canvas, and every capture method has to deal with CORS and cross-origin canvas tainting; a screenshot treats them all the same and needs no camera permission. The cost: **the QR code must be visible in the viewport**, otherwise it errors and asks the user to scroll. Decoding uses `jsqr` (pure JS, the only new runtime dependency); `NativeImage.toBitmap()` gives **BGRA**, so `bgraToRgba()` swaps the order before feeding it. Image import (`totp.importImage`) goes through `nativeImage.createFromDataURL()`, the same decode path.
- **Only `otpauth://totp` is accepted**: `parseOtpauth()` (`browser/runtime/totp.ts`) rejects ordinary-URL QR codes and `hotp`, erroring out instead of treating garbage as a secret; algorithm/digits/period all carry allowlists (SHA1/SHA256/SHA512, 6–8 digits, 1–3600s).
- **The secret never leaves the main process**: the renderer only gets `PublicTotpEntry` (the `publicTotp()` projection, no secret); to get a code it sends `totp.code { id }` for the main process to compute (`totpCode()`, RFC 6238). The only thing that brings a secret out is `totp.export` (otpauth URI), explicitly clicked by the user.
- **Encryption**: `BrowserStorage.listTotp/saveTotp` store the secret as `enc:<safeStorage>`, in `userData/browser/totp.json`; `totp.available` probes first.
- **Automatic site matching**: entries carry `origin` (the origin of the page at scan time; http/https only and exact equality only — `https://github.com` doesn't cover `https://gist.github.com`). When the current tab matches, the toolbar icon shows a small dot and the panel moves that entry to the top; matching happens in the renderer (`refreshTotpMatch` in `shell.ts`, data from `totp.list`), and changes feed back through the `pb-vault-changed` panel event.
- **Filling never auto-submits**: `totp.fill` → `fillTotpCode` in `browser/runtime/credentials.ts`; the target order is `autocomplete="one-time-code"` → a group of `maxlength=1` single-character boxes → a single field whose name/placeholder looks like a code → the currently focused field; after filling it only sends `input`/`change`.
- Reordering (`totp.reorder`), renaming/rebinding (`totp.update`) and deleting (`totp.remove`) are all in the toolbar, writing back the same encrypted file; list order is the `order` field, and entries not listed survive a reorder at the tail — no data loss.
- Pure logic (Base32/HOTP/TOTP RFC 6238 vectors, otpauth variants, projection, ordering, origin matching, QR bitmap decoding) all lives in `tests/unit/totp.test.ts`, with no dependency on Electron.

## Custom new tab page and theme override (user edits / Agent designs)

Built-in pages (shell / panel / newtab / office / workspace) are build artifacts — read-only and unwritable once packaged; user and Agent customizations always land in **Electron `userData/browser/custom/`**: `newtab.html` (new tab page, self-contained HTML) and `theme.css` (theme override). Single source in `browser/runtime/customize.ts` (`BrowserCustomization`: paths, size cap, atomic writes, status, fallback rules).

- **One kind, one file**: the new tab page is a complete HTML file (inline `<style>`/`<script>` as you like, no template syntax or multi-file project); the theme is one CSS file. Writing an empty body = restore the default (it won't leave you stuck on a blank page); over 512KB errors out instead of truncating (blocks "stuff a 20MB base64 image into the new tab page").
- **Who opens it**: `BrowserManager` maps `newtab` / empty address / the old custom address all to `customization.newTabUrl()` (`targetUrl()`), so Ctrl+T, the toolbar `+`, restoring the last tab, and "preview" in the panel all take the same path. With no custom file it falls back to `dist/browser/renderer/newtab.html`. A custom page still counts as `internal` in tab state: `browser_page` doesn't treat it as an operable page, page scripts aren't injected, and DNR and the navigation guard treat it as an internal page.
- **Same rights as built-in pages**: `isBrowserAssetUrl()` (`desktop/browser-policy.ts`) accepts one more host-composed path (`custom/newtab.html`), so a custom page can get the `piBrowserShell` bridge (`settings.get` / `bookmarks.list` / `tabs.create` / `navigate` …). This is a deliberate trade-off: it's still a local file, and only this way can an AI-designed page have a search box and bookmark pills that actually work. The cost: **whatever is written into this HTML gets local file and credential bridge capabilities**, so the tool prompt explicitly forbids stuffing remote scripts or untrusted markup into it.
- **Effective immediately on write**: write/delete the new tab page → every tab sitting on the new tab page reloads (built-in ↔ custom toggle each way); write/delete the theme → open internal page tabs drop the old key then `insertCSS`, **without a full page refresh** (unsaved edits in Office / workspace must not be wiped by a color change). The shell and panels aren't tabs; `DesktopBrowserHost.applyChromeTheme()` injects them at their own `dom-ready` and after writes.
- **Two entry points, one implementation**: the settings panel's 「新标签页 / 主题」(new tab page / theme) (`designEditor` in `browser/renderer/panels.ts`: body field + save / preview / restore default, showing the file's absolute path) and the Agent tool `browser_design` (`server/browser-design-tool.ts`) both only speak `design.status|get|save|reset`, landing on the same set of methods in `desktop/browser-host.ts`'s `call()` and `BrowserManager`.
- **Preview requires a visible page**: calling `capturePage()` on a hidden / unmounted `WebContentsView` in Electron returns an empty image or hangs (measured), so `design.preview` opens or activates a new-tab-page tab and switches the window to browser mode if needed, then captures (≤1280px, JPEG); if it can't, it honestly reports 「需要可见页面」(needs a visible page) instead of faking success.
- **No new fields on the automation wire**: the tool still goes through the existing `page_request`, with `op` as `design.status|get|save|reset|preview` (`BrowserDesignHost` in `browser/automation/design.ts`), handled in `createBrowserExecutor` before the "pick target tab" branch — so it works even when the browser has only internal pages left.
- **How to back out of a bad write**: the theme is arbitrary CSS and could in theory hide the shell entirely. There's exactly one recovery path and it must really work — delete `userData/browser/custom/theme.css` (or `newtab.html`) and restart, or have the Agent run `design.reset`; the settings panel also shows the absolute paths of both files directly, so an external editor can deal with them.
- Regression: `tests/unit/browser-customize.test.ts` (storage / size / atomic write / URL recognition), `browser-design-tool.test.ts` (tool contract, kind isomorphic with `browser/contracts.ts`, `get` truncation), `browser-design-ops.test.ts` (executor branch).
