A Full Diagnosis of the Systemic Design Defects in Today's Groups

Based on hands-on code experiments and a deep audit of the call chains, group collaboration has 6 core bottlenecks:

Fragmented topology model #FLAW-01

“Fork-and-Forget” Dispatch Creates Collaboration Islands

When a human @-mentions several Bots in one message, the Hub forks multiple independent Tasks concurrently through targets.map. Every Task is frozen against the current 24 KiB snapshot before it runs, so concurrent Bots cannot see each other's reasoning or intermediate artifacts, and there is no Pipeline / Join orchestration.

Root consequence: Dependent collaboration such as “Bot A writes the interface while Bot B writes the tests against it” is impossible; each Bot reinvents the wheel and the artifacts collide badly.
Two tracking models #FLAW-02

Public Group Message Stream vs. Point-to-Point Private Conversations

The backend maintains both RoomMessage (max 500) and HubConversation. Bot-to-bot send_task / reply calls live inside private conversations, so the group chat stream has to stitch in fake messages (group-task:${id}) to force status cards into view.

Root consequence: The main group view is flooded with mechanical “collaborating sub-agent queued/running” cards, and the human conversation is cut off from the multi-Bot business discussion.
Memory gap #FLAW-03

A Mechanical 24 KiB Hard Cap and the “Invisible Blackboard”

The task context groupTaskContext is hard-capped at 24 KiB, so any long log brutally truncates older history. The server does already ship GroupBlackboard (with versioned optimistic locking), but the web group drawer and the main chat view expose no way at all to view or edit the blackboard!

Root consequence: Long-lived business background and technical constraints are lost within a couple of turns; Bot consensus is guesswork, and humans cannot inspect or correct the blackboard from the UI at all.
Distributed consistency #FLAW-04

Resource Locks Are Memory-Only, Lost on Restart and Invisible to Humans

The single-machine scheduler relies on overlapping physical paths for mutual exclusion, but cross-device locking depends entirely on the Hub's HubLockManager. That manager is pure in-memory, so every lock is gone after a Hub restart; and the chat composer has no entry point for declaring a resource lock, so multi-machine Bots mutating the same remote Git repo are left with no protection.

Root consequence: Concurrent Git push force-overwrite conflicts and file corruption are easy to trigger, and after a network outage recovers there is no distributed transaction compensation.
Human-in-the-loop closure #FLAW-05

No In-Flight Steering

A normal single conversation accepts live Steering input to correct execution; in a group, queue: { steering: [], followUp: [] } is hard-coded empty. If a running Bot goes off course, the human can only watch it finish or bluntly call /stop to kill it; there is no way to step in and correct it mid-flight.

Root consequence: Long tasks have almost no fault tolerance; one wrong step collapses the whole collaboration chain, and human-machine collaboration lacks flexibility.
Hard-coded lock-in #FLAW-06

Core Configuration Is Not Decoupled; Hard-Coded Constants Bypass Settings

The code is littered with hard-coded constants such as const HISTORY = 500, GROUP_CONTEXT_BYTES = 24 * 1024, allowBotMentions: false and other hard-coded constants. Even after raising parameters in execution-settings.json, many Hub code paths still read the fixed constants, so the configuration never takes effect.

Root consequence: Even when compute and network would allow it, group performance and scale stay throttled by the hard-coded “thin pipe” at the bottom of the stack.

A Deep Comparison of the Three Architecture-Level Rewrites

Judged by engineering feasibility, system robustness and forward-looking design, here are three staged architecture options:

Plan A: Progressive enhancement — “Blackboard consensus hub + fully externalized parameters”

Keep the existing Hub-Device primary/replica topology and log model; focus on closing the critical gaps: a native blackboard UI, decoupled hard-coded constants, and opened-up in-group @ interaction with decision write-back.

Change risk
Low
Timeline
1.5 weeks

📌 1. Global and room-level config hub (Execution Settings 2.0)

Refactor every hard-coded constant into a three-level inheritance model. Room-level RoomSettings lets you drag-adjust group history and context size right in the frontend group settings.

📋 2. Native persistent blackboard panel (First-Class Blackboard)

Add a “group blackboard” interactive drawer to the top right of the main group view, with live Markdown editing and version history. Task context always packs the full blackboard, eradicating long-term memory loss.

💬 3. Guarded self-initiated collaboration (Safe Bot Mentions)

Turn on allowBotMentions: true and add a Hub-level rate-limit circuit breaker of at most 3 dispatches per turn; a Bot that @-mentions a peer in the group then triggers dispatch automatically.

🔔 4. Automatic decision bulletin (Attention Auto-Broadcast)

After a human answers a Bot questionnaire or approves a request, the system broadcasts a formatted bulletin into the public group stream and incrementally writes it back to the blackboard, removing the cognitive silos between Bots.

Plan B: Collaboration bus (recommended) — “One unified stream + declarative workflows + live steering”

Kill the dual message/conversation model outright; introduce topology orchestration (Pipeline / Fan-in / Fan-out) and a distributed Steering protocol to build an industrial-grade multi-agent collaboration pipeline.

Architecture completeness
Excellent (9.5/10)
Recommendation
★★★★★

🌿 1. Unified tree conversation model (Unified Tree Stream)

Abolish the dual-track model: every message is a node in the same tree stream. Bot-to-bot delegation becomes a child branch (Thread) under the main message, which the frontend collapses and drills into directly — no more card flooding.

🎯 2. Declarative collaboration workflows (Pipeline / Fan-in / Fan-out)

Humans can issue a workflow instruction right in the group (e.g. @BotA research this and hand it to @BotB to implement, then let @BotC summarize); the orchestrator then advances state along the topology graph, and each node's artifacts automatically become the exact input for the next node.

🕹️ 3. Live in-flight steering (In-flight Steering Protocol)

Open up the cross-device Steering protocol. While a Bot runs a long task, the human types corrections in the group and the Hub delivers them in real time into the target device Agent's execution queue, dynamically influencing later tool choices with no hard interrupt.

🔒 4. Persistent distributed locks and intent locks (Persistent Resource Locks)

HubLockManager moves to an append-only log (WAL) for persistence, with Shared Read / Exclusive Write intent lock tiers, and the group composer automatically derives resource locks from the project root paths implied by the @Bot mentions.

Plan C: Autonomous agent mesh — “Digital R&D studio + distributed knowledge base + sandbox rollback”

A forward-looking architecture that upgrades a group into a fully autonomous virtual team. It introduces vectorized semantic layered memory, fine-grained Capability permission decay and Git worktree snapshot rollback.

Forward-looking
Very high (Cutting-edge)
Timeline
4 - 6 weeks

🧠 1. Hierarchical memory matrix (Hierarchical Memory Matrix)

Break past every plain-text context limit: L1 blackboard consensus (global state) + L2 embedded vector knowledge base (semantic retrieval over 20,000+ group history entries, backfilled on demand) + L3 task snapshot evidence chain.

🛡️ 2. Physical Git worktree isolation and crash snapshot rollback (Worktree Sandbox)

Every multi-machine task dispatch pulls its own isolated temporary Git branch. On a network split, a crash or a human rejecting the delivery, one click rolls back the physical directory and leaves the main branch untouched.

👥 3. Multi-account cross-device federation (Multi-Tenant Group Collaboration)

Rework the single accountId architecture so different team members can bring their own machines and Bots into the same distributed project group, backed by a group membership identity chain signed with public/private keys.

📺 4. Multi-machine live streaming dashboard (Live Streaming Multiplexing)

The frontend natively fans out multiplexed real-time Token streams; while several Bots run concurrently, you can watch each Agent's reasoning and terminal execution side by side like a war room.
