當前群組系統性設計缺陷全景診斷

基於程式碼實測與深層呼叫鏈路審計，當前群組協同存在的 6 大核心瓶頸：

拓撲模型割裂 #FLAW-01

“多頭派發 (Fork-and-Forget)” 導致協同孤島

人類發訊息同時 @ 多個 Bot 時，Hub 直接通過 targets.map 併發派生多個獨立 Task。每個 Task 執行前被凍結在當前 24 KiB 快照中，併發執行的 Bot 互不可見對方思考與中間產物，缺乏流水線 (Pipeline) 與匯聚 (Join) 編排。

根本後果： 無法處理“Bot A 編寫介面，Bot B 同時根據介面編寫測試”的依賴協同，各自閉門造車導致產物嚴重衝突。
概念與儲存雙軌 #FLAW-02

群公開訊息流 vs 點對點私有會話脫節

底層同時維護 RoomMessage（最多 500 條）和 HubConversation。Bot 間呼叫 send_task / reply 被封裝在私有會話中，群聊天流不得不通過拼接偽假訊息（group-task:${id}）強塞狀態卡片。

根本後果： 群聊主檢視被機械的“協同子代理排隊中/執行中”卡片嚴重刷屏，人類對話與多 Bot 業務討論上下文斷層。
記憶斷層 #FLAW-03

24 KiB 機械硬上限與“隱形黑板”

任務上下文 groupTaskContext 硬上限僅 24 KiB，稍有長日誌即暴力截斷舊歷史；而服務端雖已設計了 GroupBlackboard（帶版本號樂觀鎖），但前端群組抽屜與聊天主介面完全沒有展示與編輯黑板的入口！

根本後果： 長期業務背景與技術約束幾輪即丟失；Bot 共識只能盲人摸象，人類完全無法在 UI 上檢視或糾偏黑板內容。
分散式一致性 #FLAW-04

資源鎖全記憶體態，重啟即失且對人隱形

單機排程器依靠物理路徑重疊互斥，但跨裝置完全依賴 Hub 的 HubLockManager。該管理器純記憶體儲存，Hub 重啟後鎖全丟；且前端聊天框無任何宣告資源鎖入口，多機 Bot 併發修改同一遠端 Git 倉庫時處於無保護狀態。

根本後果： 極易引發併發 Git push 強制覆蓋衝突與檔案破壞，斷網恢復後無分散式事務補償機制。
人機互動閉環 #FLAW-05

缺失執行中動態轉向 (In-flight Steering)

普通單會話支援即時輸入 Steering 糾偏執行；而在群組中，queue: { steering: [], followUp: [] } 被硬編碼置空。執行中的 Bot 若理解偏離，人類只能眼睜睜看其執行完或直接粗暴呼叫 /stop 終止，無法半途介入修正。

根本後果： 長任務容錯率極低，單點失誤導致整條協作鏈崩塌，人機協同缺乏靈活性。
硬編碼鎖死 #FLAW-06

核心配置未解耦，常量寫死繞過設定

程式碼中散落大量如 const HISTORY = 500、GROUP_CONTEXT_BYTES = 24 * 1024、allowBotMentions: false 等寫死常量。甚至在 execution-settings.json 調高參數後，Hub 程式碼多處仍然讀取固定常量，配置無法生效。

根本後果： 即使硬體算力與網路條件允許，群組效能與規模仍被底層寫死的“小水管”死死鎖死。

三大架構級重構方案深度對比

從工程可行性、系統健壯性與前瞻性出發，提供三套階梯式演進架構方案：

方案 A：漸進增強型 —— “黑板共識中樞 + 全引數動態外接”

保留現有 Hub-Device 主從拓撲與日誌模型，聚焦解決關鍵斷層：黑板 UI 原生化、解耦寫死常量、放開群內 @ 互動與決策回填。

改造風險
低 (Low)
研發週期
1.5 周

📌 1. 全域性與群級配置中樞 (Execution Settings 2.0)

將所有寫死常量重構為三級繼承模型。支援群級 RoomSettings，在前端群設定中即可隨意拖拽調整群歷史與上下文大小。

📋 2. 原生黑板常駐面板 (First-Class Blackboard)

在群聊主介面右上側增加“群組黑板”互動抽屜，支援即時 Markdown 編輯與版本歷史展示。任務上下文優先打包全量黑板，徹底根除長期記憶丟失。

💬 3. 受控自發協同 (Safe Bot Mentions)

開啟 allowBotMentions: true，並在 Hub 層引入每輪最多派發 3 次的限流熔斷計數，Bot 在群裡 @ 同伴即可自動觸發派發。

🔔 4. 決策自動公報 (Attention Auto-Broadcast)

人類回答 Bot 問卷或審批後，系統自動在公開群訊息流廣播格式化公報，同時增量回寫黑板，消除多 Bot 間的認知資訊孤島。

方案 B：協同匯流排型 (推薦) —— “全流歸一 + 宣告式工作流 + 即時轉向”

徹底解決訊息與會話雙軌制；引入拓撲編排（Pipeline / Fan-in / Fan-out）與分散式 Steering 協議，構建工業級多智慧體協同流水線。

架構完備度
優秀 (9.5/10)
推薦指數
★★★★★

🌿 1. 統一樹狀會話模型 (Unified Tree Stream)

廢除雙軌制，所有訊息均為同一樹狀流中的節點。Bot 間委派成為主訊息下的子分支 (Thread)，前端支援摺疊與直觀下鑽，徹底解決卡片刷屏。

🎯 2. 宣告式協同工作流 (Pipeline / Fan-in / Fan-out)

人類可在群內直接下發工作流指令（如 @BotA 調研 並轉交給 @BotB 實現，最後由 @BotC 彙總），編排器自動按拓撲圖推進狀態，上一節點的產物自動成為下一節點的精確輸入。

🕹️ 3. 飛行中即時轉向 (In-flight Steering Protocol)

打通跨裝置 Steering 協議。當 Bot 執行長任務時，人類在群內直接打字糾偏，Hub 即時投遞到目標裝置 Agent 的執行佇列中動態影響後續工具選擇，無需硬中斷。

🔒 4. 分散式鎖持久化與意圖鎖 (Persistent Resource Locks)

HubLockManager 改由追加日誌 (WAL) 持久化，支援 Shared Read / Exclusive Write 分級意圖鎖，群聊輸入框支援自動根據 @Bot 涉及的專案根路徑推導資源鎖。

方案 C：自治智慧體網格型 —— “數字研發室 + 分散式知識庫 + 沙盒回滾”

前瞻性架構，將群組升級為全自主執行的虛擬團隊。引入向量化語義分層記憶、細粒度 Capability 許可權衰減與 Git 工作樹快照回滾。

前瞻性
極高 (Cutting-edge)
研發週期
4 - 6 周

🧠 1. 分層記憶矩陣 (Hierarchical Memory Matrix)

突破所有純文本上下文上限：L1 黑板共識 (全域性狀態) + L2 嵌入式向量知識庫 (20,000+ 群歷史語義檢索按需回填) + L3 任務快照證據鏈。

🛡️ 2. Git 物理工作樹隔離與崩潰快照回滾 (Worktree Sandbox)

每個多機任務派發自動拉取獨立 Git 臨時分支。發生斷網腦裂、崩潰或人類拒絕交付時，自動一鍵回滾物理目錄，零汙染主分支程式碼。

👥 3. 多賬號跨裝置聯邦 (Multi-Tenant Group Collaboration)

重構單一 accountId 架構，支援不同團隊成員攜帶自己的電腦和 Bot 加入同一個分散式專案群組，建立基於公私鑰簽名的群成員身份鏈。

📺 4. 多機流式全景看板 (Live Streaming Multiplexing)

前端原生支援多通道即時 Token 流分發，多個 Bot 併發執行時，可像作戰指揮室一樣分屏即時檢視每一個 Agent 的思考與終端執行全貌。
