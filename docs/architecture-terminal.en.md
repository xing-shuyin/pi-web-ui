# Terminal architecture

> Covers PTY management, the native CLI workbench, key encoding, output coalescing, SCM git queries, liveness detection, terminal-backed bash, and more.

## Windows PTY and input-method positioning

On Windows, the local PTY uses the bundled ConPTY via `useConptyDll: true` on `node-pty`. The system's older built-in ConPTY redraws the screen while the cursor is hidden but discards the final cursor-positioning sequence the CLI emits; the input cursor drawn by the TUI then separates from xterm's actual cursor, and the Chinese IME candidate box lands on the status bar or at the bottom of the window. The bundled ConPTY keeps those sequences, so xterm's input textarea follows the CLI's real input position. The setting covers the local shell, the native CLI and terminal-backed bash; remote virtual PTYs are unaffected.

`tests/native-cli-smoke-test.mjs` verifies it against a real PTY: hide the cursor, draw the input row and the right-hand status bar, then move back to the input row — the final positioning sequence must reach the client. That regression shares the full pipeline with paste, reconnect, exit and restart.

## Native CLI workbench

- Inside a standard Pi `ClientSession` host, every CLI creation adds a separate `Conversation` that shares the host's `ConversationSummary` list, project list, file tree and previews with its normal chats; the type comes from the current conversation snapshot and is not stored as a client-global tab. The launch config can pick programs with a standalone CLI such as Pi, Claude Code, Codex and Antigravity (agy), which is distinct from the current chat host engine. Other chat hosts — DSH, Claude, Codex, Durable — are not yet adapted to `new_cli_chat`: the request returns an error notice and a failure acknowledgement, never auto-switches the user's engine, and does not aggregate a cross-engine list. The `terminal` toggle governs both CLI and plain terminals under `PI_WEB_TABS`, and the server rejects input once it is disabled.
- Sources of truth: `server/native-cli.ts` (launch config, type persistence, input and file preparation), `server/native-cli-model.ts` (runtime model connection resolution and subprocess auth adaptation), `server/native-cli-state.ts` (native session binding and event cursor), `server/native-cli-runtime.ts` (host/terminal adaptation contract), `server/native-cli-session.ts` / `native-cli-session-hooks.ts` (exact continuation and official events), `server/remote-cli-persistence.ts` (tmux keep-alive and instance control), `server/remote-native-cli.ts` (remote detection and secure launch data), `server/native-cli-routes.ts` (on-demand detection API), `server/native-cli-remote-files.ts` (remote references and attachment staging), `server/native-cli-remote-cleanup.ts` (offline cleanup retries), `server/remote-ssh-service.ts` (shared SSH channel and leases), `server/native-cli-references.ts` (materializing page, conversation and canvas reference content), `server/engine-catalog.ts` (single source for engines, package names and CLI capabilities), `server/engine-cli.ts` (shared launch resolution and version probes), `server/native-cli-discovery.ts` (local CLI path detection), `server/terminals.ts` (real PTY lifecycle), `server/dispatch-domain-handlers.ts` (create and paste routes), `web/src/components/NativeCliCreateModal.tsx` (create modal and expanding new-chat control), `web/src/components/NativeCliPanel.tsx` (embedded TermXterm), `web/src/native-cli-reference.ts` (reference plan and targets), `web/src/native-cli.css` (themed styles).
- When creating a CLI from another local or SSH project, switch the window's current directory to the target project after a successful launch, stop the old project's Git watcher, then refresh the workspace root, project list, sessions, file tree and commands; the page snapshot uses the target directory. On launch failure the original project and active conversation are preserved.
- The topbar 「＋」 new-conversation button keeps the icon plus the 「新对话」(New conversation) text; to its right sits a separate 「⌘ CLI」 pill button (icon `FiCommand`, distinct from the terminal view's `FiTerminal`) that opens the engine picker modal for the current directory on click — it does not expand on hover and uses no negative margin, so it never covers adjacent controls such as the logo on the left. A new CLI conversation is also reachable from the top-left 「＋」 menu and from left panel project rows, and all three entry points reuse the same modal and honor the `terminal` feature toggle. Left panel project rows have little room, so they keep the expanding control: on hover or focus the same control expands leftward into a CLI click zone showing only an icon, both zones are square at the original button height and share one background and outer outline, expand and collapse animate width and negative margin together without nudging adjacent actions, and when closed the CLI zone is hidden and not focusable.
- Presets and engine management share `ENGINE_CATALOG`, deriving directly launchable Pi, DSH (`dsh-tui`), Claude Code, Codex and Antigravity (`agy`) from `cliCommand`. agy is a standalone interactive CLI that launches its native TUI directly, bypassing IDE launchers, `--print` and ACP; [official install instructions](https://antigravity.google/docs/getting-started?tab=cli), native path `~/.local/bin/agy` on macOS/Linux, `%LOCALAPPDATA%\\agy\\bin\\agy.exe` on Windows, and it is detected even when the server has no PATH. The first run keeps the CLI's own theme, rendering, workspace trust and login flow. agy has no npm package and no SDK chat driver, so it stays out of the SDK engine install and upgrade catalogs; `NativeCliEngineId` and `BuiltinEngineId` describe CLI presets and SDK engines respectively.
- The DSH native CLI preset is based on the ecosystem interactive TUI package `@deepseek-harness-tui/dsh-tui` (command `dsh-tui` / alias `dst`, driven underneath by `@deepseek-ai/dsh`, install with `npm i -g @deepseek-ai/dsh @deepseek-harness-tui/dsh-tui`). DSH keeps its own profile config and env-var/model credentials, and CLI launch-model inheritance stays off (`cliModelArgs: null`). Pi Durable exposes only a library API with no npm bin, so the option is disabled with a note that it has no standalone CLI, and the server refuses to launch it too.
- Interactive CLIs launch directly and inherit the target host's environment and login config by default; with Claude/Codex model inheritance enabled, connection info reaches the subprocess per the rules below. No skip-permissions flags are added, and answers are not parsed into chat messages. Arguments are one per line, and input is never executed as a shell expression.
- Settings → Models & providers → 「CLI 启动模型」(CLI launch model) stores a separate inheritance toggle per CLI in `nativeCliInheritModel`, all off by default; it is a globally shared launch preference and does not enter the main agent preset. Supported capabilities are declared by the single source `ENGINE_CATALOG.cliModelArgs`: Pi passes `--provider` and `--model`, Claude Code / Codex / Antigravity pass `--model`, and custom commands never have their argument format guessed. When enabled, `newCliChat` captures the current conversation's model `{ provider, id }` before the first await, stores it in `NativeCliConfig.model` and persists it into the native CLI metadata; with no current model it keeps the CLI's default config. Existing CLIs, explicit restarts and history restores reuse the captured value and are unaffected by later model choices or toggle changes. An explicit user `--model` / `-m` (including `=value`) and Pi's `--provider` each take precedence, and text after `--` is not treated as options. On every create, restart and history restore, Claude Code / Codex re-resolve that provider's runtime API key, endpoint and request headers through the host SDK's `modelRuntime.getAuth`, supporting current keys and dynamic auth config; keys are never written into `NativeCliConfig`, session metadata, protocol snapshots or the CLI's global config. Claude connects through the subprocess's `ANTHROPIC_BASE_URL`, the official API-key or custom-endpoint token env vars, and clears OAuth/cloud env vars that conflict with that connection. Codex pins a temporary Responses provider via `-c` and references keys and header values only through env vars, so they never enter argv. The provider must still speak the corresponding CLI protocol (Anthropic Messages for Claude, Responses for Codex). Pi / Antigravity get only the model arguments; auth and endpoints come from each CLI's own config, and SDK subscription OAuth is not converted into an API key — the CLI still needs its own login. Closing the terminal or conversation during async auth cancels the pending launch request, so late credential resolution cannot spawn the process again.
- Presets launched locally detect the machine running pi-web-ui through `resolveEngineCliLaunch` on every launch: scan `PATH` in order first, then the user's native install directories (e.g. `~/.local/bin`), the current Node directory, the npm prefix, pnpm / Volta / Bun / Scoop directories and the fnm / nvm persisted-version directories. Multiple persisted versions are scanned in descending version order; if a launcher is still missing, reuse `global-loader.ts`'s global package detection and check the real entry of the matching `package.json.bin`. An installed package does not mean a usable CLI entry. It never scans the whole disk, path detection runs no shell or extra probe commands, and uninstalled results are not cached. On POSIX, candidates without execute permission are skipped; npm JavaScript entries launch through an adjacent Node or the server's current Node instead of the shell's `node`; an explicit custom path keeps priority, and detection failure prompts to install the CLI or configure a custom path. A remote browser uses the server machine's CLI and cannot detect installs on the browser's machine. When the create modal opens it calls the same detection API for the local workspace (`target: "local"`), greys out uninstalled presets and shows 「未安装」(not installed), takes the install command from `ENGINE_CATALOG.installCommand`, and one-click install reuses the host's existing `pi-web-ui:plugin-run-command` event to run it in a terminal tab (agy has no npm command, so it links to the official install instructions); if detection itself fails (e.g. the terminal feature is off) presets are not disabled — creation falls back to a direct create so probing cannot wedge it.
- The CLI version probe in engine management, the actual Claude/Codex driver launch and the native PTY workbench share `engine-cli.ts`; drivers no longer maintain their own PATH, version-manager or npm-entry lookup. The version probe only runs the shared resolution result plus `--version`; SDK or runtime availability for Pi/DSH/Durable is still judged by each engine's own contract, and library availability is never equated with a standalone CLI.
- On Windows, resolve the literal entry inside npm `.cmd` wrapper scripts: Node scripts launch through Node, native `.exe` / `.com` (e.g. Claude Code) launch directly. Arguments stay separate argv entries and are not expanded through `cmd.exe`; wrapper scripts that need variable expansion, extra arguments or commands are still rejected, and the user can point at the real executable.
- `new_cli_chat { config: NativeCliConfig, cwd?, requestId? }` creates and activates a standalone CLI; with `requestId` it reuses the `new_chat_result { requestId, ok, conversationId? }` acknowledgement. `UiState.nativeCli?` and `ConversationSummary.nativeCli?` are both `NativeCliConversation { config, terminalId, status? }`. The SDK runtime only hosts the existing Conversation — a plain `prompt()` refuses to send model messages to the CLI; the CLI does not take part in blank-chat reuse.
- A CLI uses an existing conversation-owned PTY; input, paste, attach, resize and kill carry `conversationId` plus `ownerKind: "conversation"` for exact routing. `TerminalInfo.nativeCli` keeps the launch config, and one PTY binds exactly one xterm writer. The launch directory is fixed to the project directory at creation time; switching projects never changes the process cwd.
- Switching to a normal chat or a different CLI, reconnecting and page reloads only attach to the existing PTY and replay its buffer; switching away and LRU auto-collapse never release the CLI. After the process exits, the descriptor and output are kept, and the user restarts explicitly with `terminal_create` (`ownerKind: "conversation"`, the owning `conversationId`, the descriptor's `terminalId`). Restart config and cwd are read from the conversation and ignore client overrides; a failed restart keeps the old output. Only an explicit conversation close releases the runtime and PTY wholesale.
- Prepare the SDK host and PTY before creating, then activate on success; an SSH launch waits for the remote directory, the executable and a no-echo bootstrap handshake confirmation. A failed create releases the new resources and keeps the original active conversation; concurrent creates on the same terminal share one launch, and closing or releasing the host cancels the pending request and immediately closes a late channel; pending instances also take part in terminal ownership queries so a close during the first launch still hits the original owner. Remote creates have a 90-second deadline and reject late activation after it expires; the frontend waits 120 seconds for the acknowledgement, so it never reports a timeout and then switches into the new CLI anyway. The session custom entry `webui/native-cli { version: 1, config }` stores the type and is written explicitly even with no chat messages; opening from history restores the CLI descriptor and allocates a terminalId for the current runtime; a keep-alive session attaches to the original process first and only starts a continuation process through the exact native binding once the process has exited. A failed history launch keeps the CLI type for an explicit retry; corrupt or unknown-version type metadata is refused rather than mistaken for a chat. The native chat transcript is still stored by the CLI itself; the separate `webui/native-cli-state` metadata stores the exact session binding and event cursor, and restore fills in the native continuation arguments automatically. A plain PTY restores neither process nor buffer across a server restart; with SSH tmux keep-alive enabled a still-live original process can be reattached.
- After creating a CLI, actively rebuild and push the owning project's `sessions` history list instead of relying on SDK message events or the user expanding the project again; if a directory scan from before the creation is still running, discard its stale cache and rescan once it ends. The history scanner extracts the config from the same `webui/native-cli` marker, and `SessionSummary.nativeCli?: NativeCliConfig` projects the history type (with no runtime `terminalId`); zero SDK messages still keep `messageCount: 0` rather than faking a normal chat message. Incremental scans, long config lines and renames all preserve the type metadata.
- `NativeCliPanel` only embeds `TermXterm` and has no separate composer. The user types directly into the native CLI; while that CLI is active, references are injected into the terminal through the shared `composer-bridge` target and the right panel's `App.attach`. References go through `terminal_cli_paste` and wait on `terminal_cli_paste_result` by `requestId`; the server strips control characters and writes one bracketed paste into the same PTY, **without appending Enter**, and never guesses from screen text whether the CLI is waiting for input.
- For an async read of a page, conversation or canvas, capture the target manager and PTY process instance first; after the await, paste only into that original instance. Switching conversations never redirects to a new CLI, and a process rebuilt under the same ID after exit refuses the old request. Materialization or paste failures, disconnects and ACK timeouts show a notice without auto-Enter and without auto-retry.
- Files and directories pass real paths and may carry line numbers; an explicitly picked absolute path follows the normal attachment policy and allows browsing from the right panel's machine plus extra roots. Relative paths and their symlinks must stay inside the CLI cwd; uploaded files and images are saved to the existing per-client uploads directory and their real path is passed, with uploadPath always validating current client ownership. Whether an image is readable is up to the CLI — this feature does not imply native multimodal injection. Short text references keep the original text; references beyond the PTY budget are written to disk; authorized pages read visible text, conversations read the real transcript, canvas exports real JSON, and the CLI receives the actual content file path. A read failure or empty content returns a failure acknowledgement and never degrades into metadata carrying only a URL/ID.
- SSH workspaces support POSIX (Linux/macOS) remote CLIs. They reuse saved SSH hosts, auth, known_hosts and the connection pool without adding a separate credential store; unknown or changed host keys are still confirmed through the existing SSH workspace flow. `cwd` stays the canonical `ssh://user@host:port/path`, the SDK host and history keep an on-disk cache via `resolveWorkspaceSessionDir`, and `.pi-remote-uri` preserves the real remote identity; launch, reopen and history restore always run in the corresponding remote directory. Remote Windows is not supported yet and never degrades to local execution.
- The create modal requests `appUrl('/api/native-cli/discovery?cwd=…')` on demand and shows available presets plus unavailable reasons (for SSH it also shows host, directory and keep-alive status); closing, retrying or switching projects cancels the old detection and ignores late results. The API sits behind existing auth and the terminal feature toggle. Remote detection and launch share the remote PATH, covering native, agy and npm/pnpm/Volta/fnm/nvm install directories; they never use the local Node, PATH or `.cmd`. A custom executable takes a remote command or path. SSH presets are clickable only after detection confirms them; local presets are disabled only when detection explicitly reports them missing.
- SSH uses `createCommandPty`'s exec + PTY channel. The non-interactive POSIX bootstrap first verifies the directory and executable permissions and disables echo, then passes bounded safe reference env vars over stdin after receiving a random handshake token; keys never enter the exec command, argv, shell history, config or logs. After restoring terminal mode it execs the native CLI without relying on remote Python/Node or on `AcceptEnv`. Inherited model endpoints must be reachable from the remote host, where `localhost` means the remote machine; no model proxy tunnel is created automatically. A pure POSIX bootstrap cannot confirm every execve failure mode — a bad interpreter that exits immediately still surfaces through the exit event.
- An active remote shell, CLI or exec holds a connection lease that prevents the original 30-minute idle reclaim from closing a running channel; completion, cancellation and disconnect all release it. Without keep-alive, an explicit close only closes the owned channel; with keep-alive it first confirms the owned tmux instance stopped. Both preserve other sessions on the shared connection and never treat `exit` as CLI input. After a disconnect the output and exit status are kept for an explicit reopen; native menus, tool permissions and login are handled by the CLI itself.
- Remote references use real POSIX paths and by default validate same host, workspace and realpath/symlink boundaries; an absolute path outside the workspace requires explicit server authorization. Local `uploadPath` validates per-client ownership against the resolved instance `dataDir` (including a `--data-dir` override), staying consistent with where materialized references are saved; images, uploads and page/conversation/canvas materialized files are written over SFTP into a random `/tmp/pi-native-cli-<UUID>` directory (0700) before the remote path is pasted; recursive directory upload is out of scope for now. A successful paste binds staging cleanup to the captured process instance; keep-alive sessions also persist directory ownership and clean up only after confirming the process exited or stopped. Failures, cancellations and late mkdir also clean up; an offline cleanup failure keeps the path and retries in the background with backoff while the service runs.
- Clicking the close control on a running CLI conversation in the left panel sends `dismiss_conversation`, then releases the runtime after confirming the process stopped while keeping history; a failed stop keeps the conversation for retry. Deleting a history record still needs a second confirmation: `delete_session` first confirms the owning process stopped and removes it from running conversations, then deletes the record, for both foreground and background CLIs. A conversation's own CLI terminal takes part in switch keep-alive (`countBlockingLive`) but is not counted among user terminals that block removal (`countUserBlockingLive`); interactive terminals the user opened separately and standalone CLI tabs still protect the scene. After a successful delete the latest history list for the record's project is pushed, with no page refresh needed across projects or SSH history; an old list scan started before the delete is invalidated and re-read, so it cannot resurrect the deleted record.

## Native bash lifecycle

`resolve-global-sdk.ts` registers `patch-bash-process.ts`'s Node module load hook when preloading, applying an in-memory compatibility patch (issue #794) before the SDK's native shell module first compiles, covering both the bundled and the followed SDK while continuing to reuse the SDK's shell config, environment and process-tree cleanup. No installed SDK file is rewritten. An unrecognized upstream structure emits a warning instead of silently assuming the fix applied. CLI, production, desktop and dev servers must all preload this module before their entry point; tests that import the SDK directly register no hook and produce no disk side effects. A second load hook, `patch-executable-lookup.ts` (issue #810), replaces the SDK's `which` / `<cmd> --version` subprocess probes with a PATH scan the same way (on by default for Android/Termux, see `docs/env-vars.md`); it too only rewrites ESM source in memory, and an unrecognized structure warns instead of assuming the fix applied.

The execution timeout only bounds the main process's run phase; on `exit` the real exit code is saved and the execution timer stops, after which it waits for output to close or for 100ms of silence. Output draining has its own 1-second cap that continuous output cannot extend; hitting it explicitly marks collection stopped and closes the local read end, so a background child holding inherited pipes cannot wait forever. A normal exit does not kill background jobs. Cancellation and a genuine execution timeout call the SDK's process-tree termination and wait at most 1 second for cleanup, settling even without `exit`/`close`. Every settle path releases listeners, output streams and timers.

`timeout` changes neither the native/PTY routing nor persistence; on Windows it still only uses a persistent terminal with an explicit `persist: true` and terminal takeover enabled, avoiding console exhaustion from one-shot terminals.

`abort_bash`'s optional `conversationId` pins the conversation held by the current client; when omitted only the current session is used and no other running command is looked up. The native, terminal and extension bash controllers all hang off the stable `Conversation` object, resolve ownership at execution time, and migrate with takeover and ID-collision renames. The target runtime is captured before cancellation and the stop notice is injected only into that runtime; no stop request is sent while the frontend is switching conversations.

### Native session continuation, remote keep-alive and state

- `webui/native-cli-state { version: 1, key, preset, cwd, nativeId?, processId?, lastEventId?, seenEventIds, stagingPaths? }` is server-owned binding metadata, kept separate from the client-fillable `NativeCliConfig`. `key` is a standalone UUID; history restore validates engine and workspace instead of guessing the native session from the project's 「最近一次」(most recent). Internal hook args, provider keys and script contents never enter public config or snapshots; the returned launch config serves the current process only.
- Pi uses a separate session directory and an exact `--session`; Claude uses `--session-id` / `--resume` with the same UUID; Codex, which supports official hooks, captures the exact thread ID from SessionStart and later runs `resume <ID>` without falling back to `--last`. agy supports `--settings`-based hook lifecycle events and first-ID capture (SessionStart / PreInvocation / PreToolUse / Stop), degrading to process state when the user passes `--disable-hooks`; dsh and Custom keep process state. Explicit user session arguments win; a lost bound session fails loudly instead of switching to someone else's history. A `native-id` under the same key may restore an ID or session switch the parent layer has not yet persisted, once the corresponding transcript is verified to exist; the project's latest is never read.
- Lifecycle comes from official events: Pi's interactive input, agent_settled and user-question events, plus Claude/Codex's SessionStart, UserPromptSubmit, Stop, PermissionRequest and friends. `working` is not equivalent to a user send; only the separate `submitted` projects as `native_cli_prompt_submitted` for sidebar ordering and fires no OS notification. Existing user hooks/settings keep priority and Codex defers per event (including legitimate quoted TOML keys); without reliable events it degrades to process state and never parses the screen to guess completion or approval. First-time trust for newly added hooks is handled by the CLI's own official UI, and permissions are never skipped.
- Native records live in local `<dataDir>/native-cli/<key>` or remote `~/.pi-web/native-cli/<key>`, private directories 0700, records/scripts 0600. Event files are bounded; restore continues consuming from the persisted cursor, and a history baseline without a cursor replays no submit or completion events. Derived identity events are deduplicated separately: only the original SessionStart cursor or later semantic events advance the cursor, so an interruption after identity is persisted cannot lose completion. A new process does not replay the old process's activity or questions, while attaching to a live process keeps catching up. Observer errors and synthetic process errors do not replace the native cursor. A natural exit calls `flush()` before stopping observation; a canceled done only updates idle state and sends no completion notification.
- `NativeCliConversation.status` exposes starting, running, working, waiting for input/approval, disconnected, exited and error info, plus last activity, native ID and continuation capability. A single-round error keeps the live PTY writable and only shows the error; an SSH disconnect is not treated as task completion. Reliable done/error/question/approval go through both the bounded dedup browser events and the unified `onNotificationEvent` mobile notification interface; navigation uses the host Web/SDK sessionId, the native ID is only for continuation and display, and notifications carry no body. Read-only shared views such as the mobile app show only status and native ID — they never attach a PTY, register a composer or expose process controls; native questions and permission actions must still be handled in a writable window that owns the CLI.
- The SSH create modal probes tmux on demand (requires ≥3.2) and keep-alive defaults to off. When checked it uses a UID-private socket directory via a fixed `TMUX_TMPDIR=/tmp` and `tmux -L pi-web-cli-<UUID>`, avoiding the Unix socket length limit with long HOMEs. Each actual new instance writes a random generation; atomic create, probe, attach and handle stop validate the instance, so an old handle never stops a new process under the same key. `remain-on-exit` preserves the exit status and the host probes periodically for the real exit code; network unreachability is never treated as finished.
- 「断开连接」(Disconnect) only closes the current attachment, keeping the remote process, observer and attachments still in use; 「重新连接」(Reconnect) prefers probe + strict attach-only, so an existing process depends neither on the old CLI path, the current model credentials nor the transcript file still existing — an upgraded CLI or changed provider can still be reattached. If the instance disappears during attach it reports a retry instead of launching a placeholder. Only when the process truly does not exist are the CLI and model resolved again for an exact continuation.
- 「停止」(Stop), an explicit conversation close or a history delete first confirm the remote stop; a failed confirmation keeps ownership/history for retry. Service shutdown, SSH loss and user detach never send stop; the shutdown path of a pending reconnect manager also uses `shutdown: true`. stop/create for the same terminalId are serialized, instances are validated across awaits, and the pending launch slot is not reused before cancellation cleanup finishes. When history has no live handle, stop can run independently against the verified binding without launching the CLI.
- Keep-alive sessions write SFTP staging directory ownership into the binding, so a disconnect or shutdown does not delete files a remote task may still read; cleanup happens after confirming exit/stop, and a lost-connection failure enters the existing backoff cleanup queue. This implementation does not guarantee notifications while the local service is stopped, and does not auto-install tmux or build a model network tunnel.

## Terminal management

- **User terminals and agent terminals are separate tiers**:
  - **Terminals the user creates directly** (UI plus-button create, run custom command, `agentBash !== true`): owned by the `ClientSession` (workspace level) and alive per client; **always shown** in the terminal list, no longer affected or filtered by a single conversation's switching, rollback, deletion or lifecycle; output streams straight through in real time; destroyed only when the user closes it manually or the process exits on its own.
  - **CLI session terminals**: owned by a single CLI `Conversation`, always kept across switches, reclaimed only when the conversation closes; they do not enter the client-owned global terminal tabs.
  - **Terminals taken over/invoked inside the agent** (`agentBash: true` or interactive terminals invoked by agent tools): owned by a single `Conversation` and follow that conversation's lifecycle and liveness detection (silence ≥15s injects a steer reminder).
- **Unified list push and routing**: the server's `pushTerminals()` merges user terminals with the current conversation's agent terminals; `handleTerminalMessage` matches the target terminal through the global `findTerminalManager` index for input (`terminal_input`), resize (`terminal_resize`), close (`terminal_kill`) and rename (`rename_terminal`), reaching across conversations seamlessly.
- **Every spawn path shares one admission gate**: `terminal_create` (browser/agent) and `run_command` (command list) both use `validateId` (letters/digits/.-_:/≤80 chars) + `ensureSpawnAllowed` (a new live PTY must stay under `MAX_TERMINALS`; restarting an already running terminal in place takes no new slot; **an exited terminal in history frees its slot** — with the cap full, re-running an exited terminal is rejected too, closing the "one ID generates unbounded PTYs" hole); failures all go through `fail()` (notice + red error inside the terminal + terminal_exit).

## terminal_key key encoding

`encodeTerminalKey(key, modifiers)` is a pure function (exported, byte-level assertions in terminal-smoke-test.mjs): named keys route by name, and Ctrl/Alt combos never fall back to "Ctrl + first letter" — Ctrl+ArrowUp=`ESC[1;5A` (not Ctrl+A), Ctrl+Enter=`ESC[13;5u` (not Ctrl+E); arrow keys/F1–F4/Home/End with modifiers use xterm modifier sequences `ESC[1;<m>X`, other named keys use CSI-u `ESC[<code>;<m>u`, and plain characters map Ctrl A–Z→0x01–0x1A, Shift uppercases, Alt prefixes ESC.

## Output coalescing

Output is pushed to the browser as `terminal_output` carrying a `conversationId`; an unmounted terminal keeps a 2MB output window replayed on switching back. A socket disconnect does not kill the PTY; switching/reconnecting keeps state, and PTYs are only all killed when the conversation is released or the service shuts down.

**Terminal output micro-batch coalescing** (`queueOut`/`flushPending` in `terminals.ts`, window `OUTPUT_FLUSH_MS=16ms`): every `pty.onData` chunk goes into the `pendingOut` buffer first and is flushed as one `terminal_output` — the WS frame storm of hundreds to thousands of small chunks per second during a build drops 10–50×; exit/kill/in-place restart flush first and then send the exit event, guaranteeing order.

## Terminal query replies must be one-for-one (`1;2c` showing up at the prompt)

Programs in the terminal query terminal capabilities with CSI/OSC, and the terminal (xterm.js / the ConPTY peer) **replies automatically**, with replies travelling over the PTY **input** channel. Windows' `useConptyDll` ConPTY sends `ESC [ c` (DA1) at startup and **blocks input** until it gets a reply, and **honors only the first one** — any extra reply has no query to pair with and lands directly on the shell prompt, where readline treats it as ordinary keystrokes: `ESC[?` is swallowed and `1;2c` is typed into the command line (`ESC[12;40R`, `ESC]11;rgb:…` likewise).

- **Single source**: `server/terminal-query.ts` defines "query requests", "reply shapes" and "the ConPTY DA1 answer" in one place. `TERMINAL_QUERY_RESPONSE_RE` / `isTerminalQueryResponse` are re-exported by `terminals.ts` (used to decide "this input was not typed by a human", so it does not count toward `used`).
- **Who answers ConPTY's DA1**: the server. `registerPty`'s `pty.onData` strips DA1 out of the output with `splitConptyDa1` while `conptyHandshake === false` (including half prefixes split across two chunks) and immediately writes `pty.write("\x1b[?1;2c")` once, matching xterm.js's answer. That query is never sent down to any UI: it does not depend on whether a browser currently has xterm attached, and "replay + live stream each replying once" cannot produce an extra one. Only local ConPTY is affected (remote virtual PTYs / POSIX have no such handshake).
- **History replay only paints**: `TerminalManager.attach()` / `replay()` send `stripTerminalQueryRequests(entry.output)`, and the reset frame in `web/src/terminal-bridge.ts` also strips before writing. The live stream stays untouched — queries must reach the terminal or nobody replies. `server/bash-tool`'s `read()` still returns the raw history (the agent sees the real output).
- **Regression tests**: `tests/unit/terminal-query.test.ts` (stripping/chunk splits/replay and attach frames), `tests/unit/terminal-bridge.test.ts` (live passes through unchanged, reset strips).

## node-pty × Node `--watch` compatibility self-heal

`server/patch-node-pty.ts` (must be imported before node-pty): the dev script uses `node --watch`, and watch mode pushes `watch:require`/`watch:import` messages into node-pty's ConPTY worker / console-list agent IPC channel — node-pty 1.1.0 does not recognize them, so ① each one `console.warn('Unexpected ConoutWorkerMessage')`-spams the console; ② the kill path treats a watch message as an agent reply and crashes calling `.forEach` on `message.consoleProcessList`, which is undefined. At startup the patch module idempotently rewrites the installed copy (following the spawn-helper chmod precedent); `terminals.ts` adds a second layer filtering console.warn as a fallback. Production (no `--watch`) is unaffected.

## SCM source control

`SCMPanel` (view `git`) runs its read-only git queries through the server's `server/scm.ts`, using `execFile("git", …)` directly (no shell — no prompt/echo/ANSI/zsh differences), parsed into structured JSON.

### Protocol

The client sends `scm_status` (status+branches (incl. remotes, for-each-ref)+numstat) / `scm_history` (commit graph, lazy — queried only when switching to the 「提交树」(commit tree) tab) / `scm_filediff` (single-file staged+worktree diff) / `scm_commit` (git show after hash whitelist validation), and the server must answer exactly one `scm_data` (echoing reqId + kind, ok/error/notRepo); the frontend matches pending slots by reqId — every request has exactly one response, so the UI can never hang on loading; sendScm occupies no slot and sets no busy while the socket is down (no spinning deadlock). Path validation: filediff's path must still resolve inside the workspace; a non-git repository returns ok:true + notRepo:true (the panel shows a hint instead of an error). 15s timeout, maxBuffer 16MB.

### Resizable left column width (issue #139)

The changed-files / commit-history column defaults to 300px; drag the divider to its right (`.scm-divider`, double-click resets to default): the width is written to the inline CSS variable `--scm-sidebar-w` on `.scm-body`, dragging keeps a minimum width for the diff area based on container width, and `localStorage` is written only on release (key `pi-web-ui:scm-sidebar-width`). Clamping and stored-value parsing are pure functions (`clampScmSidebarWidth` / `parseScmSidebarWidth` in `web/src/scm-sidebar.ts`, unit test `tests/unit/scm-sidebar.test.ts`; browser regression `tests/scm-test.mjs`: drag +120px → survives reload → double-click back to 300). The CSS side adds a `max-width: calc(100% - 220px)` backstop so a narrowing window cannot squeeze the diff area away.

### git directory watcher

On the first scm_status, `git rev-parse --absolute-git-dir` locates .git and fs.watch is armed (non-recursive — HEAD/index/packed-refs are all top-level, covering commit/stage/checkout); events are debounced 600ms and push `scm_changed` → the frontend refreshes silently (external CLI/IDE changes show up live); setCwd/dispose/notRepo unwatch; a watch failure degrades silently to a visible 30s poll.

### Auto-refresh triggers

All go through silent refresh without flashing a spinner: scm_changed / git write commands generated by SCM in a terminal tab going running→exit (title `/^git /`) / view activation / cwd change / 30s polling.

### Write operations

Still through a visible terminal tab (reusing TerminalPanel's tab logic) and switching to the terminal view: commit/push/pull/switch branch (remote branch `origin/x` → `git checkout -b x origin/x || git checkout x`) / stage a single file (`git add -- <path>`, + button on row hover) / unstage (`git reset HEAD -- <path>`, − button), with paths escaped through single quotes. The branch dropdown groups local/remote (optgroup, i18n scmRemoteBranches).

### Historical lesson (abandoned old implementation)

Once used a hidden PTY plus shell-variable-assembled sentinels to split text, and hit three landmines: the xterm writer overriding the parser, a zsh prompt with no trailing newline gluing lines and swallowing the `## main` status header, and the global queue being blocked by slow queries during streaming.

## Terminal liveness detection (liveness watchdog)

`noteAgentActivity` / `armIdleWatch` in `terminals.ts` plus agent-service's `notifyTerminalIdle`: the agent tool path's terminal(action=create/input/key) arms a "silence epoch" — when that terminal produces no output for `PI_WEB_TERMINAL_IDLE_MS` (default 15s) **and the conversation is streaming**, an onAgentIdle callback has the host `sendUserMessage` inject a steer reminder that wakes the AI to check (waiting for input / suspended).

Anti-noise design: ① terminals the user opened by hand never participate (only the tool wrapper layer calls noteAgentActivity, never the browser path); ② one-shot — after firing it disarms and only re-arms when the agent touches it again; ③ any output/input during the epoch resets the countdown; ④ exit/close tears the clock down. The reminder text is itself a self-contained steer message (terminal id, recent output, suggested read/input/key/close actions), so it already tells the model what to do; the global terminal guidance paragraph is gone and no longer occupies system prompt space. Regression: `tests/terminal-idle-test.mjs` (instantiates TerminalManager directly + small threshold, zero tokens, no server; win32 unverified).

## Terminal-backed bash

The bash tool always overrides the SDK's built-in bash and, per the `terminalBash` setting toggle (off by default), **routes dynamically** between two implementations (agent-service's `makeAdaptiveBashTool`):

- **Off (default)**: `makeKillableBashTool` — uses the SDK's native `createBashToolDefinition` (plain process spawn, **no terminal**), i.e. the pre-override behavior; `persist` has no effect on this path, and `head`/`tail` post-process the returned lines.
- **On**: `makeTerminalBashTool` — the command is written into the visible terminal (every script is escaped with `$'...'` into a single physical line for eval, then the outer layer captures `$?` and prints a sentinel, so an interactive program cannot read the next line's sentinel as input); the sentinel carries a per-invocation random 12-hex nonce and only that one is honored (a real `[pi-exit:42]` in the output is not taken as a genuine exit code); after the sentinel line yields the **real exit code** it returns the full output (`stripAnsi` cleanup; echo and redraw lines removed by injection position without swallowing real output). On this path `persist` decides the terminal **lifetime** and `head`/`tail` decide the number of returned lines.

The native bash wrapper must pass `execute`'s 5th argument (`ctx`) through to the SDK definition: the SDK uses it to inject `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL` into every command, and subshells inherit those values. Without `ctx`, the SDK still **clears** inherited session variables but cannot write current values (subshells then read missing or stale values). This applies only to native bash; the terminal path does not go through the SDK's session environment injection. Also, when embedded as an SDK runtime, the SDK does not set the CLI-only `AI_AGENT` / `PI_CODING_AGENT` markers automatically.

> Note: `persist`/`head`/`tail` always appear in the bash tool's parameter schema (shared by both implementations); with the setting off `persist` is ignored while `head`/`tail` still apply.
>
> **Prompt single source**: description / promptSnippet / promptGuidelines / parameter descriptions are not written once per path — the single source of truth is `server/tool-prompts.ts`, consumed by `makeKillableBashTool` (which also hosts the parameter schema), `makeTerminalBashTool` and `makeAdaptiveBashTool`. `makeAdaptiveBashTool` only overrides `execute` (routing). Historically it also overrode description, so the terminal copy was hard-coded yet never sent — a dead copy that kept drifting ("prefer head/tail over piping" lived only there).

### `persist` semantics with the setting on

- **`persist=false` (default, one-shot)**: every call creates a new terminal `ai-bash-<n>` (`agentBash=true`), the shell exits via `exit` when the command finishes (process ends), and the terminal with its output stays in history for review; it blocks until the command ends with no idle unblocking (close to plain bash semantics). **Windows adaptation (issue #269)**: on Windows, MSYS2 has a hard-coded global console cap of 128 (`MAX_CONS 128` in `\cygwin.shared`), and every `CreatePseudoConsole` starts a persistent `conhost.exe`; high-frequency one-shot terminals are not only extremely slow (~1.3s each) but exhaust MSYS2 console allocation completely and deadlock after 128 allocations. So on Windows, one-shot commands (`persist !== true`) route automatically to native SDK bash (pure process over pipes, ~20ms, zero console device allocation); only an explicit need for persistent interaction (`persist === true`) uses the always-on visible terminal `ai-bash` (a single reused terminal, occupying 1 slot).
- **`persist=true`**: reuses the persistent terminal `ai-bash` — shell state (cd/venv) survives across calls, and after idle unblocking `terminal(action="wait"/"read"/"input"/"key")` observes and interacts. While a command is unfinished, injecting bash again is refused; interactive programs can only be driven by input/key; nested shell/SSH state is decided by its own process, and the outer command must not be assumed finished.

### Windows ConPTY exit and MSYS2 console release (issue #215 / #269)

Pseudo-terminal teardown on Windows has two major architectural traps:

1. **ConPTY shutdown deadlock (issue #215)**: if a process exits and `pty.kill()` is called directly (underneath, `ClosePseudoConsole`) while the pipe still holds undrained data, a kernel-level synchronous deadlock freezes the event loop.
2. **MSYS2 console slot leak (issue #269)**: calling Node's `process.kill(pid)` blindly (Win32 `TerminateProcess`) skips MSYS2's DLL destructors and console cleanup hooks, permanently leaking console device slots (cap 128) in the global named shared memory `\cygwin.shared`; once exhausted it triggers `fatal error - console device allocation failure - too many consoles in use, max consoles is 128`.

`killNative` and the terminal lifecycle in `terminals.ts` split these cases carefully:

- **Process already exited naturally (`entry.exited === true`)**: never call `process.kill(pid)` (avoiding a mistaken kill of a new process after PID reuse); call `entry.pty.kill()` directly to release the HPCON, socket and worker handles, because the process is dead and the pipe sees EOF, so `ClosePseudoConsole` can never deadlock. This safe cleanup runs on a natural terminal `exit`, on eviction of the oldest entry by `this.history` (beyond 32), when the user closes a history tab in the UI, and in `killAll`.
- **Process still running (`!entry.exited`)**: first write `\x03exit\r` to the PTY so the shell exits cleanly and runs MSYS2 cleanup hooks; only if it still has not exited, fall back to `process.kill(pid)`, then call `pty.kill()` to release handles (on shutdown `shutdown=true` skip `pty.kill()` and let the OS reclaim).
- **`conpty_console_list_agent` fault tolerance (`patch-node-pty.ts`)**: add try-catch to node-pty's console-list agent so a failed `AttachConsole` on a dead process no longer throws an uncaught exception and safely returns an empty list.

`head` / `tail` (1–5000) return only the first/last N lines of output, replacing `| head` / `| tail` pipes (pipes buffer output, mute the visible terminal throughout, and easily trigger idle unblocking). The pure function `applyHeadTail(text, head, tail)` slices only real data lines and wraps the omission hint line back separately; with head+tail combined the tail is never one line short.

### Automatic stripping of trailing output-limit pipes + snapshot queries

`makeTerminalBashTool` strips the **trailing output-limit/pass-through pipes** models often write (`| tail [-n N|-N]` without `-f`, `| less`, `| more`, `| cat`) before running: the underlying command runs directly (live in the visible terminal + real exit code), and only the text returned to the model is trimmed to the detected last N lines; `buildTerminalBashLine` preserves the current shell's `$?` and pipefail config, does not force the first pipe command, and never rewrites exit code 141 into success. Pure functions `splitTopLevelPipes` / `detectTrailingLimiter` / `detectStdoutRedirect` (handling `cmd > log 2>&1 | tail -N`: strip the tail, then add `tail -N log` so the model still sees the log tail). Real filters/transforms such as `| grep`/`| head`/`| awk`/`| sed`/`| sort`/`| uniq` are **not** stripped (stripping loses semantics or floods unfiltered output), and `tail -f/--follow` is not stripped either — the prompt tells the model not to use it. `terminal(action="read")` supports head/tail/search output filtering while the cursor still advances on the raw stream; internal liveness hint queries use `queryTerminalOutput(output, q, running, exitCode)` (with 1-based line numbers), and the number of recent lines echoed by the idle hint is controlled by `terminalIdleNotifyLines()` (configurable via `PI_WEB_TERMINAL_IDLE_LINES`).

### Behavior semantics (with the setting on + `persist=true`)

- ① blocks until the command ends by default
- ② no output for `terminalBashIdleMs` (default 15s, 0 = wait forever) → **idle unblocking**: immediately return 「仍在后台运行」(still running in the background) + the output so far, and register a `watchOutput` completion observer; when the command really finishes the host's `notifyTerminalBashDone` tells the AI (sendUserMessage steer while streaming / sendCustomMessage nextTurn queued without waking when idle)
- ③ shell state survives across calls (cd/venv/ssh)
- ④ backgrounding only ends the current wait; the controller, cancellation signal and timeout stay in force until the task completes. abort_bash, a timeout or a signal cancellation closes that PTY to avoid reusing a shell in an unknown foreground state; the next call creates a new shell and the old cd/venv state is released with the cancellation.
- ⑤ pending and waiting bind this invocation's nonce; an old task completing cannot clear a new task's state. PTY exit/close/replacement wakes the waiter, returning a known exit code directly instead of a false timeout.

The toggle is read through `makeAdaptiveBashTool`'s `useTerminal` closure on every call → changes take effect immediately (customTools is fixed at runtime creation, so the choice cannot be made once at creation); `idleMs`/`defaultPersist` likewise read from settings. Regression: `tests/terminal-bash-test.mjs` (direct instantiation + small threshold injection + `persist`/`head`/`tail`/one-shot/routing cases, zero tokens, no server; win32 unverified).

**Frontend display and quota**: both the persistent `ai-bash` and one-shot `ai-bash-<n>` carry `TerminalInfo.agentBash=true` (the field only distinguishes purpose; ownership comes from ownerKind), and the frontend `TerminalPanel` pulls them out of the user terminal tabs into a separate collapsible 「终端接管 bash」(terminal-backed bash) group (`term-folder`, expandable/collapsible); `ensureSpawnAllowed` also counts only non-agent terminals, so frequent AI bash calls never eat the terminal slots available to the user.

## Unified terminal tool and permission boundary

The persistent terminal registers a single `terminal` tool with `action` in `create/list/close/input/key/read/wait`. The old seven tools no longer appear in the active tool list. `list/read/wait` are read-only; `create/close/input/key` change process or input state.

- Plan mode, the reader preset and restricted subagents keep the read-only actions; the model-visible schema narrows the action enum while the execution hard gate still checks the actual action independently. Leaving read-only mode restores the original schema.
- Old `terminal_<action>` approval rules match compatibly against the new tool's actual action; new `terminal` rules can match action by params. Old disable toggles migrate conservatively to disabling the unified tool, so an upgrade never re-opens previously forbidden input.
- Input newline approval and `key(Enter)` approval remain; after an approval returns, the cancellation signal is checked again to prevent sending input after a cancel.
- The UI's `terminal_create/input/...` are browser wire messages, independent of model tool names. The new `terminal_attach` only attaches to an existing PTY, resizes and replays retained history — it never creates or restarts; component mount sends attach only. Create and explicit rerun are sent directly by user actions.

## Terminal ownership and recovery

`TerminalInfo.ownerKind` states `client` / `conversation` explicitly, separate from the `agentBash` purpose field. Shells created by ordinary AI also belong to the conversation; input, resize, close, rename and output all carry ownership, and a terminal with the same ID but another owner is never used as a fallback target. User terminals validate a new directory against the current project root; existing processes keep their cwd and ownership. The server pushes the full list of user terminals plus the current conversation's terminals, the frontend reconciles authoritatively and keeps exited history. The session manager's own `terminal_list` must merge through `pushTerminals()`; list changes in background sessions do not overwrite the foreground directly. The merged list and output/exit for `ownerKind=client` are not filtered by the current conversation envelope; when the list arrives before a new snapshot, both sides' session identities are preserved and the render layer shows only the current session's rows, so a client CLI is never dropped and another session's terminal is never displayed.

Persistence is bounded to shell reuse and page-reconnect survival within the same service process; processes are not restored across a service restart.

## macOS launchd / TCC issue

On macOS, if the service is started by launchd (`process.ppid === 1`, LaunchAgent/orphan process), TCC attributes camera/microphone permission to node itself (no app bundle, no Info.plist) and silently denies it — ffmpeg stalls while grabbing frames. `terminals.ts` detects this case and prints a hint when the client first creates a terminal (switch to a url/file source, or run in the foreground in a terminal you have already authorized).

## Windows shell resolution

`resolveShell()` in `terminals.ts` resolves on every terminal creation, preferring bash — explicit `PI_WEB_SHELL` → `$SHELL` → Git Bash (ProgramFiles) → busybox fallback (`~/.pi-web/bin/bash.exe`; `ensure-bash.ts` downloads busybox-w32 when Git Bash is missing) → `$COMSPEC` → powershell. It matches the SDK bash tool (Git Bash / bash on PATH) so mixed PowerShell/bash usage cannot hang.

The bash tool itself shares its origin with the pi CLI: `server/bash-tool.ts` passes `settings.json`'s `shellPath` (global agent directory + project `.pi/settings.json`, `SettingsManager.getShellPath()`) through to `createLocalBashOperations`, and only when it is missing falls back to the Git Bash / PATH probing above (issue #866). The terminal panel does not read that config — it only honors `PI_WEB_SHELL`; the difference is deliberate: the terminal is a visible shell for the user to look at, while the bash tool must align with CLI behavior.

## UI containers for the terminal and source control (bottom panel / right panel tabs)

- **The layout is four blocks — left / center / right / bottom — all flex siblings**: the left panel, chat area (`.main`) and right panel (`.panel-drawer.drawer-right`) are the three blocks of one row, and the bottom panel (`.bottom-dock`, keeping the `.term-drawer` class name) is a full-width block inside `.app` after `.layout`.
