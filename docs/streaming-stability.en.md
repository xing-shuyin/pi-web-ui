# Streaming message stability constraints

Streaming content changes require a re-render; the stability requirement is that existing content must not be unmounted, have its state reset, or have the user's reading position moved by an identity handoff.

## Identity across three layers

1. `MessageList` maps the stream ID to a stable render key for the real message. The cluster wrapper uses the same stable key as its first message. Stabilizing only the inner Message key is not enough: a React key is only valid under the same parent node.
2. Consecutive assistant output keeps the same React parent ownership. In normal mode a cluster containing body text uses a transparent container and does not put body text inside the dense tool chrome; flow mode keeps the turn container. A message going from empty frame to thinking, tool, body and finalization does not migrate between parents. Theme switches or session switches make no promise of keeping the same node.
3. Blocks inside `Message` are identified by block position, not by message.id, which changes at finalization. `StreamMarkdown`'s frozen segments and active tail use the same Segment component and the same keyed list, so freezing the tail does not change the component type.

The block-position rule depends on the protocol's append order for content blocks. If insertion before an existing block, reordering or deletion is ever allowed, a stable block ID must be introduced and index-based identity must not be kept.

A streaming message's pending boundary is not overwritten by later snapshots. Finalization of the old message and the start of a new stream may arrive in separate frames or the same frame, but the next message must not inherit the old message's identity.

## Rendering and scrolling

A text block that was generated by streaming keeps StreamMarkdown after finalization and does not switch back to another static Markdown tree for “final correction”. Freezing a paragraph uses the latest text immediately but keeps MarkdownBody. Full syntax highlighting is enabled once a code fence closes, and changes to highlight-internal nodes are allowed.

Once the user scrolls up, finalization must not snap back to the bottom. The browser test leaves the bottom-stick state through real wheel semantics and then checks scrollTop; setting scrollTop from script alone cannot stand in for user scrolling.

Images, formulas and async plugin loads may legitimately change size; their completion must not be mistaken for an identity rebuild. This test suite makes no promise that no content change ever causes a layout change.

## Automated gates

`npm test` picks up the following component tests automatically:

- `message-finalization-dom.test.ts`: real Message → StreamMarkdown → MarkdownBody, where finalization keeps the body nodes.
- `stream-segment-identity.test.ts`: real Markdown, where paragraph freezing keeps the p/inline code, long-tail freezing drops no characters, and code fences highlight correctly.
- `message-list-identity.test.ts`: checks mount lifecycle and nodes under the real list branches, covering normal/flow, empty frame→tool→body, old-stream finalization and new-stream handoff.

`node tests/stream-stability-ui-test.mjs` uses its own Vite and Chrome, calls no model and does not drive the user's browser. It covers the real MessageList/Markdown, normal and flow layouts, paragraph freezing, normal/aborted/error finalization, thinking turning into body text, and the user's reading position. It is registered in `tests/run-smoke.mjs` and runs in CI smoke; without Chrome it is SKIPped per repo convention. The flow test enables theme capability tokens and does not load the full custom theme styles.

Test fixtures live only in tests/fixtures and never enter the production entry. Assertions rely on DOM identity, lifecycle and scroll position, not on screenshot pixels or React render counts.
