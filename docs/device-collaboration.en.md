# Groups / Bots / cross-device collaboration hard rules

> Server architecture and deployment chain: [`device-center.md`](device-center.en.md) (Hub and the local connector, binding and pairing, deployment)
> and [`device-center-deployment.md`](device-center-deployment.en.md); remote desktop internals: [`device-desktop.md`](device-desktop.en.md);
> chunked file sync internals: [`device-file-sync.md`](device-file-sync.md).
> For private chat with a single Bot (rooms with `kind: "direct"`) and Bot-owned memory see [`agent-bot-design.md`](agent-bot-design.en.md).
> **This document collects only the hard rules you must follow when changing code** (migrated wholesale from the 「设备中心与跨设备协作」(Device Center and cross-device collaboration) section of the old `AGENTS.md`).

## 1. Device Center entry point and the local Hub

The standalone Hub and the local connector live in `server/device-center/`; deployment and boundaries are in [`device-center.md`](device-center.en.md). The main UI's 「设备中心」(Device Center) is the native `devices` view (`DeviceCenter.tsx`), and the old `/devices` redirects to it; when unbound, local Bots/groups run through a private in-process loopback Hub (`local-hub.ts`, data isolated from external bindings), the overview keeps group management plus connect/create guidance, and going offline or a failed request must never clear known groups; installing the local Hub goes through the loopback same-origin endpoints in `hub-setup.ts` and a standalone Hub CLI, which must validate parameters, isolate the data directory, run mutually exclusively and cancel pending waits on shutdown; pairing endpoints accept only loopback sources and same-origin writes; group members are uniformly Bots, and devices only host and connect.

## 2. Group task dispatch and context

Group tasks go first to a stable Bot ID that was explicitly @-mentioned; an optional `primaryBotId` receives human messages with no explicit target and continues that Bot's most recent valid session; a Bot's public messages never trigger default dispatch, and removing the primary Bot clears the setting. `group-context.ts` freezes the primary Bot identity; the executor injects the coordination duty only when group and Bot both match, delegating through an existing persistent session and the relevant request/reply, and the role never widens permissions. Bot-to-bot relays inherit the parent task's budget; unbounded mutual dispatch is forbidden. Hub persistence has two layers: `device-hub.json` is the index (same schema at `version: 2`, with `messages`/`tasks`/`conversationMessages` as empty arrays), while messages, tasks and transcripts are appended per group/per conversation under `hub-log/`; each transaction first writes the index plus the add/remove deltas of all three collections into `hub-wal.jsonl` (monotonic sequence numbers and content checksums) and only counts as committed once flushed to disk; then it updates the append logs (`upsert`/`del` lines), and finally atomically replaces the index carrying `checkpointSeq` and cleans up the already-projected WAL. A failed projection does not roll back the committed transaction: the WAL must be kept, the committed in-memory version advanced, and projection re-done idempotently on the next write or restart; sequence numbers must never be reused, and a committed result must never be reported as an ordinary failure. Tombstones are compacted against live rows once past a threshold, loading keeps 500 per group and repairs a crashed half-line; a corrupted complete WAL line must refuse to open, and only an incomplete trailing line may be repaired. `readPersistedHub()` only replays in memory — it repairs no files and creates no directories. Legacy inline data migrates automatically in `open()`; before downgrading, export the full state (an older version reading the index sees only empty collections). Group context is frozen by `group-context.ts` before dispatch; recent public messages travel with the task (24 KiB) and ordinary chat is not written to disk again; explicit contract tasks seal the context actually selected into the Manifest described below; `device_collab read_history` re-reads the original text by stable cursor (500 kept per group, oversized messages can be segmented) and must verify the source Bot's device, account and group membership; clearing or eviction invalidates old cursors. History is reference data — it cannot authorize dispatch or execution. When a human message omits `targetBotIds`, the Hub resolves `@Name` / `@Name(<id>)` in the body against group members; with several members sharing a name it does not guess, non-members are not dispatched to, and it never falls back to the primary Bot just because the client did not resolve. Messages may carry `replyToMessageId`, which must point at a message in the same group.

### 2.1 Versioned contracts and code tasks

`device_collab`'s `send_task`, `conversation_create`, `conversation_send` and the matching Hub / local proxy endpoints accept `executionMode` and a nested `contract`. The default mode is `chat`. `code` must provide a definite `baseline: { repositoryId, commit }`; commit is a full SHA and repositoryId is derived from the locally normalized network origin (credentials stripped, repository path case preserved) or, for a repository with no origin, from the digest of all sorted root commits — never from an arbitrary tag or local path. Common SSH, SCP and HTTPS default-port addresses map to the same host/path; local, file and unknown transport origins are rejected outright. `contract` carries a business `id`, an increasing `revision`, goal, constraints, acceptance criteria and ordered `inputArtifacts`. The Hub computes the content digest; clients cannot supply an authoritative Manifest or approval evidence. An exact retry with the same idempotency key reuses the contract, a content conflict is rejected; one business id/revision can map to exactly one content digest; while an old revision is still queued, running, holding a granted lease or inside the recovery window, a new-revision request returns 409. A new revision can only be created after the old one is settled; a committed old result that lost its ACK can still be replayed exactly for confirmation, but an old business revision can never provide acceptance proof for a new one.

`work-contract.ts` is the digest and validation entry point for contracts, `ContextManifest` and `DeviceArtifact`. Before a contract task's first dispatch, the group context actually selected, taskState, ordered input-artifact id/digest references, the policy references for executing device/Bot/revision and the actual budget are sealed once into the task transaction together with the contract revision. Deferral, retry and restart dispatches use the original Manifest and never re-select history. Digests cover canonical JSON, inputs must be copied and deeply frozen; unknown fields, corrupted digests and mismatched contract references are all rejected.

`task-workspace.ts` binds the source repository, device, Bot revision, task/attempt, contract and Manifest digests to an opaque handle registered locally. A directory or forged JSON arriving over the network can never become execution capability. This batch of code tasks requires Bot.cwd to be a local Git top-level directory, the source checkout to be clean, and the workspace data directory to sit outside the source repository; subdirectory Bots are rejected outright without leaving a temporary worktree behind, and Canvas's existing subdirectory behavior is unchanged. Code tasks keep the conservative scheduling lock per Bot and source root — creating an isolated worktree does not relax concurrency. Code tasks use a new execution session, and the real tool cwd must come from a validated handle; an old transcript must never be resumed in another workspace. Baseline, HEAD, Git common-dir, gitdir back-pointer and real paths must be re-checked at every critical boundary across an await. A worktree only isolates where changes land — it is **not a filesystem or network security sandbox**, and existing tool permissions and approvals stay in force.

The contract JSON limit is 256 KiB, the Manifest limit is 96 KiB, and the contract-creation request limit is 384 KiB; at most 8 input artifacts, bounded by the contract total. The sealed context/taskState travel only inside the Manifest and are not duplicated on the outside; before dispatch the complete JSON frame is checked against the 512 KiB limit, and an over-limit frame is refused without dropping the device connection. Input artifacts carry their content and a SHA-256 and cannot reference a local path on the sending device. Each input patch first proves the outputTree it yields from the declared baseline, then they are composed in contract order; conflicting, tampered or oversized patches fail explicitly. This batch supports a single-parent chain of cumulative patches plus several non-overlapping inputs; passing an ancestor and a successor that already contains it as inputs at the same time is an explicit conflict — the dependency graph is never inferred or deduplicated automatically. An empty patch is a legitimate no-change artifact. The output is a cumulative binary patch from a fixed baseline to the outputTree, recording the inputTree of this execution alongside it; the raw patch limit is 128 KiB. The first capture fixes the artifact identity and digest, and a resend must not regenerate them. Git retention refs keep the baseline and artifact objects while the user's source checkout and index stay untouched. Hooks, fsmonitor and every configured content filter are disabled during preparation and snapshotting; snapshots are generated from raw file bytes to avoid implicit clean/smudge conversions.

Execution finished, artifact captured, independently verified and delivery accepted are four different facts. The code-execution phase records `executionCompleted`, `artifactProduced` and the artifact content; independent verification and delivery acceptance use the Integration / Review evidence loop in the next section and do not follow automatically from a terminal `completed` state or a Bot's self-reported checks. A code task may report completion only after the executor is confirmed stopped and the artifact captured successfully; a failed capture can still persist the fact that execution ended. Artifacts and proofs enter the persistent Outbox, the terminal fingerprint and the Hub's immutable acceptance record, with the ACK matching what was actually committed.

If the Hub has already durably settled a different terminal state, or the original attempt has permanently expired, the device receives a permanent-rejection ACK bound to the original task/attempt/status/fingerprint and atomically moves the complete original result plus a bounded reason code into the persistent quarantine area; that entry is then no longer replayed and other result uploads are unaffected. Field or digest mismatches, ordinary request failures, network errors and persistence errors must never trigger quarantine. The quarantine is capped independently at 128 entries / 2 MiB; when full it keeps the original pending result and refuses further clearing, and it never evicts old evidence. The unified `task-recovery-state.json` is written as version 2, reads version 1 and the old two-file state for compatibility, and commits the quarantine together with active leases and pending results in one atomic write, with a total state-file limit of 8 MiB. Before downgrading to device code that does not understand version 2, back up and convert all recovery state; deleting the quarantine to bypass the check is not allowed.

All explicit contract tasks and their sessions (including chat contracts and failed code tasks with no artifact) are exempt from the ordinary 500-entry history / closed-session pruning and must survive a restart load; a contract's identity and highest revision cannot disappear through history pruning. Ordinary chat without a contract keeps the original retention policy. History pages and tool results show only the bounded contract, Manifest, artifact identity and independent facts, while the original task keeps the full evidence. `device_collab task_evidence` pages through the raw patch using `evidenceKind: "artifact"`, `taskId`, `expectedDigest` and byte `offset` / `limit`; each page holds at most 24 KiB of raw bytes and returns base64 content plus the patch SHA-256, artifact digest and source metadata. Reads must pass same-account, device, group and session checks, and follow-up inputs must reassemble the full content and verify the digest. Automatic cleanup must not delete dirty worktrees or extra commits; retention refs of captured artifacts do not expire automatically for now — explicitly clearing or deleting the group clears the Hub-side contract, session and evidence records and resets that group's business-version authority, while retained objects in device repositories need separate explicit maintenance.

### 2.2 Artifact verification and acceptance by contract

Reuse `Delivery → Integration → Review`; no separate acceptance collection. A currently running author Bot can use `conversation_deliver`'s `artifactTaskId` to register a code artifact produced earlier in the same session by the same Bot / revision / device; the current task supplies the write permission and the completed task supplies the immutable artifact identity — the two must never be mixed. The Hub derives `artifactRef` and the sealed `acceptanceCriteria` from the committed task and rejects caller-invented references, digests, criteria or verification conclusions. Artifact delivery neither needs nor forges a commit; legacy commit delivery still requires the repository, a full baseCommit / commit and self-reported checks.

An artifact can prepare an Integration before acceptance. The device checks the canonical repository identity, baseline, cumulative patch and outputTree, materializes a real Git commit and then reuses the existing temporary merge and CAS adapters; this phase requires the target branch HEAD to equal the artifact baseline and preparedTree to equal outputTree, and it never fetches, rebases or merges an advanced target automatically. inputTree is for auditing only — patches are always replayed from the baseline. Public records carry only the artifact reference and digest, and the raw patch is still read through the controlled evidence endpoint. Reading an artifact by deliveryId in `task_evidence` must locate that delivery's artifactTaskId, and an explicit taskId / expectedDigest conflict must be rejected. Tool summaries keep every complete criterion and flag `acceptanceCriteriaCount` / `acceptanceCriteriaTruncated`; truncated criteria must never be read as the full requirement. When the criteria total exceeds the summary budget, page through the canonical JSON of the sealed array by bytes using `evidenceKind: "acceptance"`, the deliveryId and `expectedDigest: artifactRef.contractDigest`, at most 24 KiB per page, then verify criteriaDigest after reassembling the base64 and parse all criteria.

The verification command plan is submitted explicitly by an authenticated account owner in the verification UI for the first time and then frozen, holding the ordered commands, content digest, authorizing account and timestamp; the Bot's calling identity must be preserved until the Hub decides, and a Bot request must never count as account-owner authorization. A Bot may only reuse an existing, exactly identical authorized plan. Model text, self-reported checks, a package.json inside the patch or one correct digest grants no command authorization. The device still checks the target Bot's tool / command permissions, revision and root occupancy; verification runs only foreground commands from the trusted plan, at most 300 seconds each and 600 seconds total, with bounded output and recorded digests; `verification-limits.ts` sets the stop and transport margin on the RPC, proxy and UI deadlines uniformly. A worktree is not a sandbox for malicious code.

A real verification result must contain checks in exactly the plan's order and count, exit codes, output digests, the materialized commit and the tree identity before and after execution. Only when every exitCode=0, the check states agree and both trees equal preparedTree may the Hub compute the verification digest from allowlisted facts. A bare verified state, empty checks or missing entries form no credential. A successful Integration credential cannot be overwritten by re-verification; needing a different plan or a fresh verification means creating a new Integration.

An independent Review must bind the delivery's artifactDigest, integrationId, verificationDigest and the same contract / Manifest. accepted must also submit `criteriaResults: { criterionIndex, verdict, evidence }` per index of the sealed acceptanceCriteria, covering all of them, all met, and authors cannot review their own delivery. changes_requested may precede a successful verification but still binds the exact artifact. A contract upgrade, a device / Bot revision / group-membership change, a wrong artifact or another Integration's credentials cannot provide acceptance proof for the current delivery; plain commit equality, or two absent commits being equal, does not match an artifact Review.

Every mode of confirmed integration requires a real success credential: nothing may be applied straight from prepared / failed, and an old credential-less verified flag is never upgraded into trusted evidence. Artifacts additionally require the currently matching accepted Review and contract revision. Evidence identity is frozen before apply starts, and the same delivery / Review / contract cannot be replaced while an unclosed publish intent exists; operation, membership and target are re-checked before issuing a new write. The historical outcome of an authorized write is verified against the original intent — a permission change after publishing does not erase an effect that already happened. Verification credentials, the worktree, preparedTree and the target SHA are re-checked once more before device confirmation. Cancellation first aborts and waits for the owned process tree to stop, then cleans up; if the stop cannot be confirmed it keeps the root occupancy, Bot lease and workspace and reports neither success nor a forced delete. An account owner may cancel an old integration under the original persistent session identity; disabling the target Bot, changing its revision or removing it from the group grants no new execution permission and must not block a plain stop and cleanup. Legacy sessions that entirely lack an explicit stop marker and a real verification credential get their Bot / root conservatively quarantined on upgrade; only an old prepared state that the Hub explicitly recorded and that never started verification may be cancelled under the original identity. An old failed may also come from a timeout with an unconfirmed stop, so it is never grounds for automatic cleanup; other uncertain states need a local maintainer to check, and are neither auto-deleted nor used to let new tasks through on a missing marker. Publish intents, device persistent receipts and the re-check rules are in the next section.

### 2.3 Publish intents and the post-crash re-check

Before sending the first publish RPC, the Hub durably persists an immutable `publishIntent` through the existing WAL transaction. The intent binds the original account, group, conversation, Integration, device, Bot revision, a snapshot of delivery and Review, the real verification credential, repository identity, target ref, old commit and the tree to publish. The shared raw Git commit constructor derives one unique candidate commit from a fixed identity, timestamp, parent order and a message containing the intent digest; a retry must never produce a different commit. The protocol is 48. The complete intent, digest and candidate SHA included, is limited to 384 KiB of actual serialized UTF-8 bytes; when every field is legal on its own but the total proof is over budget, the Hub rejects outright before committing the intent and before the RPC, avoiding the 512 KiB relay frame limit. The constructor recognizes SHA-1 / SHA-256 object formats, but the existing SHA-1 limitation of the code-artifact path still applies — constructor support does not imply the whole artifact chain supports SHA-256.

The device publish log is independent of verification sessions and temporary worktrees. The log reserves a bounded record first, then creates the candidate objects and the retention ref; it durably records `cas_started` before the CAS, and durably records `publishReceipt` once the CAS is known to have succeeded, before returning or cleaning up the session. A corrupted log, insufficient capacity or a failed save blocks new CAS operations, and pending records and the cancel fence are never evicted automatically. The candidate retention ref keeps the associated tree and parent commits from being lost to worktree cleanup or ordinary Git GC. Files are replaced atomically and flushed; that recovery promise covers process crashes. Power-loss durability of Windows directory metadata and of Git object closure is outside the promise and is not equivalent to a full transactional guarantee across an abrupt host power cut.

`publishReceipt` records an observed historical publish effect and keeps the source of proof — `cas_exit`, `target_exact` or `target_descendant`; seeing the candidate or a descendant alone does not prove who performed the write. `publishObservation` records the current target ref separately, so later moves never turn a historical receipt into a failure. `conversation_read`'s tool summary projects only the intent identifier, candidate SHA, receipt source, current observation and stop facts within the existing output budget; it never copies the full sealed proof, private repository paths, process IDs or raw logs. When the CAS has started but there is no receipt, a branch still equal to the old SHA does not prove the publish never happened — another operator may have reset it. Keep it unknown; do not retry automatically or overwrite outside changes.

Startup, device reconnect and a manual `POST .../integrations/:id/reconcile` only query the original publish log and repository identity. A Git re-check creates no objects, refs, worktrees or commits, runs no verification and performs no CAS; it does not depend on the original worktree still existing, the Bot still being enabled or a new execution lease. Re-checking an unknown outcome may persist additional evidence but never resumes the write automatically. A repeated apply with an existing intent returns the current record; it cannot stand in for an implicit retry.

Only a human request carrying account-owner identity may call `POST .../integrations/:id/resume`, and it must submit the exactly matching intent ID, digest and candidate SHA and pass current permission and revision checks. The device must also hold durable evidence that the CAS never started, or that it was explicitly rejected and the stop confirmed; an unknown outcome after `cas_started` does not qualify for resumption. Bot credentials cannot resume an unknown publish. Cancellation first durably closes future writes inside the same operation gate, so a late confirm is fenced too; if the CAS already succeeded it returns the published fact. `publishStop.closed` means only that future writes are closed, while `stopConfirmed` separately means the original publish child process is confirmed stopped; `fencedAt` and `stoppedAt` — the latter existing only under positive stop proof — are recorded separately. When the past effect cannot be determined, keep `publishStop.pastEffect = unknown` and have the UI show the historical outcome as unknown; it must not be read as definitely unpublished. While the publish child's stop is unknown, the original Bot / root occupancy stays quarantined and recovers durably; a verification process stop marker or a publish receipt inferred from the branch never substitutes for proof that the publish child stopped. This batch conservatively quarantines Git children whose stop cannot be confirmed after a restart, pending a local maintainer check; it does not extend to Git Job supervision.

Old already-applied records keep their original historical markers and do not get retrofitted intents or receipts; an old in-progress record without an intent is not published automatically, and no new evidence is derived from old state. Worktrees, process supervision and logs are not a security sandbox; a third party editing the repository directly, a malicious same-account process and a POSIX process detaching itself from its process group remain bounded by the existing limits.

## 3. Bot registry and persistent sessions

`bots.ts` stores each Bot's fixed project root, role, model and tool/Skill/MCP allowlists per local device identity; groups use `botIds`, messages use `targetBotIds`, and tasks and `device_collab` file sync share the Bot registry lease/revision; an execution session must never impersonate another Bot. Group Bot persistent sessions are registered by `hub-conversations.ts` with a stable address and an immutable delegation source (sourceBotId/sourceConversationId/parentTaskId); both create and continue may carry a related request, the device's `runtime.ts` atomically persists the exact transcript mapping, and restore must validate Hub/device/group/Bot revision/directory; `switch_session` is allowed only on exact capability paths.

## 4. Concurrency, scheduling and progress push

The same device defaults to 4 executing + 32 waiting, configurable to concurrency 1–16 and waiting 0–128, scheduled fairly per group; fair-queue history persists to the device data directory `task-scheduler-state.json` (debounced atomic writes, restored on restart, neutral start on corruption); worktrees overlapping by Bot and real path run serially while independent worktrees may run concurrently; a continuation message for the same session is delivered after the previous round's terminal state and never interrupts a tool. Group progress goes out over bounded SSE validated per attempt, falling back to polling with a resync on disconnect; native questionnaires and one-shot tool approvals use the task-bound interaction bridge. Requests/replies bind the original session and requestId, results wake only the original initiator, automatic continuation shares the task-chain budget, and new human input may start a new chain. Changing the root is forbidden while busy or while a stop is unconfirmed, and an old file bundle must never land in the new root. Hub-side 「which task is dispatched first」 and device-side 「which local tasks actually run concurrently」 are two layers of responsibility, see §12 「Scheduling layers (Hub dispatch vs device execution)」 in this document.

## 5. File sync

File sync stages a preview first, then imports by revision; an existing difference must be explicitly overwritten; `sync_files recursive:true` supports a bounded directory transfer, rejects symlinks/junctions, must return an exclusion summary when skipping sensitive/ignored items, and never deletes target files; credentials must not enter tool receipts.

## 6. Remote page isolation and cross-device proxying

By default the Hub reaches a device through the single-port `/device/<id>/` path, isolating remote pages with a CSP sandbox (allow-same-origin forbidden) and a device-specific random capability path; the old separate domain/port stays for compatibility. The cross-device proxy allows only account-scoped group chat endpoints and must not expose local binding, directory or settings endpoints.

## 7. Group task recovery and reporting

`task-recovery.ts` owns group task recovery: task/attempt/lease claiming and the persistent terminal outbox, keeping lease-holding local execution across a network drop, with a bounded claim window when the Hub restarts; a device process crash never blindly re-runs side effects. Device leases and terminal states live in the versioned `task-recovery-state.json`: completion adds the result and removes the lease in one atomic replacement, and a crash during recovery must still leave a recoverable record; the old `task-active-leases.json` / `task-recovery-outbox.json` are cleaned up only after the new file is written successfully, and corrupt state is never overwritten. Records and replays are isolated per Hub/device identity, and result capacity is reserved for active leases before execution. The result of the same task/attempt is immutable: an identical replay is idempotent, different content is rejected; terminal transfer uses persistent entries, and the ACK must bind a Hub-persisted result matching the entry — echoing a request digest back without settling, or deleting a result without a digest, is forbidden. The old digest format is kept only to read already-persisted results; new digests encode fields explicitly so text separators cannot become ambiguous.

The v0.116.0-era `task-recovery-outbox.json` did not store leaseToken/generation on completion and had already removed the matching active lease; migration will not fabricate a lease from an attemptId or an old digest. Such results get an idempotent positive ACK only when connection credential authentication passes, device/account/Bot/group/attempt all match, and the terminal state, report, error and report metadata the Hub persisted are identical field by field — without modifying the result or lease or triggering downstream work; it must not be used to backfill artifacts or execution proofs. After confirmation the entry's original old digest is echoed back, which clears the replay even though the Hub has since stored a new digest. An unsettled legacy result cannot prove its lease and gets a permanent negative ACK `legacy_lease_missing`; an already settled one with different content uses `terminal_conflict`, and an expired attempt uses `attempt_expired`. After validating the receipt against the original task/attempt/status/fingerprint, the device atomically writes the complete result and the reason into the version 2 persistent quarantine; restarts and reconnects no longer send that entry automatically while the connection keeps serving other tasks. `legacy_lease_missing` marks a failure that needs manual recovery review: a maintainer can pull the report from the quarantine record, verify the actual side effects and then decide what to do — it must not be taken as task success, and the original side effects must not be re-executed directly. New tasks and any result carrying a wrong or incomplete lease still run the existing token/generation fencing.

Terminal acceptance validates task/attempt, Bot/device identity and the granted lease token/generation; old execution must not overwrite a stopped task or advance a new one. Creation, completion and startup recovery share the dependency-readiness rule: only a completed predecessor may be released, while failure, cancellation or interruption must block or cascade termination — checking merely “the predecessor is terminal” is not enough. A queued task that never received a lease may be re-dispatched; a queued task whose lease was granted but never durably reached running may also be executing, so it must enter the claim window and cannot be replaced and re-dispatched immediately. Window expiry settles idempotently and notifies the parent task and downstream. A queued task is itself the persistent dispatch intent; the in-memory sent set only stops the current process from sending twice and cannot carry recovery truth. The original full report is persisted by the separate `task-report-outbox.ts` and then uploaded in chunks, and a result ACK must not delete an unuploaded report by mistake; events, reports and details live in `task-journal.ts` / `task-report.ts`. **An empty audit stream is not an error**: when a task exists but never wrote a journal segment (still queued, failed before the first progress event, older than the logging feature), the Hub's `GET /tasks/:id/journal` returns a 200 empty page (`items: []`, with `journalUnavailable` attached) and only a missing task/group is 404; the UI must load detail and journal independently, and a degraded journal must never clear the task overview. **The local proxy must pass through the Hub's already-scrubbed failure reason** (`scrubHubMessage` strips known credential and token-shaped strings, then returns `error` + `hubStatus`); collapsing every 4xx/5xx into a fixed 「Hub rejected group request」 is forbidden. Group plans reuse the read-only hard gate: this round becomes ready only after a successful `plan_update` matches the final plan and the Hub confirms it, and human approval starts a separate implementation round. Canvas binding and Bot presets must validate the real graph/cwd and registry revision, never auto-running on a reference or hot-changing an in-flight permission. Staging and background jobs of a chunked file transfer must bind Hub/device/group/Bot/revision/real directory; an unconfirmed stop forbids continuing, and release happens only after both ends confirm the actual I/O fence.

## 8. Delivery and review (delivery ≠ acceptance)

Group development delivery is independent of execution state: `completed` does not mean acceptance passed. The delivery and review protocol lives in `server/protocol.ts`; a Bot delivery must bind its own running task, a stable conversation and the full commit SHA; a review binds the delivery ID and SHA, Bot self-review is forbidden, and a new revision must not reuse an old acceptance. The check source is fixed to `bot_reported` — never claim the host or CI verified anything, and never auto-run declared commands or merge. A human can start an independent integration pipeline: an isolated pre-merge created in a fixed Bot workspace on the target device, explicitly selected verification commands, and finally an atomic update to the target SHA on confirmation; the target branch is refused while checked out in any worktree, hard reset and automatic push are forbidden, and the integration session and operation generation must be persisted and bound to the exact delivery/review/Bot revision. Deliveries/reviews are persisted first, idempotent conflicts are rejected outright, and bounded history must not be silently evicted. Details in [`device-center.md`](device-center.en.md); full regression `tests/device-project-collaboration-test.mjs`.

## 9. Remote desktop

Device Center remote desktop streams native JPEG through the existing WebSocket in `desktop.ts`; `desktop-native.ts` handles the Windows/macOS helpers and `desktop-linux.ts` handles Linux X11 (ffmpeg/xdotool); VNC/noVNC is no longer involved. Read-only is enforced per connection by the server, browser draw ACKs bound the unconfirmed frames across devices, and disconnecting must release input. macOS 14+ needs screen recording/accessibility permission; the permission request is raised only by the device's local 「设备中心 → 本机远程桌面」(Device Center → local remote desktop) button and a remote connection only checks it; `/api/device-desktop/local/*` must never be relayed through the Hub/connector. Wayland is not supported yet; the enabled state lives in `desktop-settings.json`. See [`device-desktop.md`](device-desktop.en.md).

## 10. Group webhook integration

Groups support both inbound (Incoming) and outbound (Outgoing) webhooks:

- **Inbound webhook**: each group can create several inbound endpoints, each with its own secure Token. External systems (CI/CD, alerting, scripts) send an HTTP POST JSON request to `/api/rooms/:id/webhooks/incoming/:webhookId?token=...` (supporting `text`, `senderName`, `targetBotIds`, `replyToMessageId`). With `allowBotTrigger` on (the default), external messages are dispatched by group rules to an explicit mention or the primary Bot (`primaryBotId`), waking the Bot to run the task and collaborate in the group.
- **Outbound webhook**: a group can configure several external notification URLs subscribing to group events (`message`, `task_completed`, `task_failed`, `delivery`). When an event occurs a JSON payload is sent out asynchronously; an optional `secret` adds HMAC-SHA256 signature verification via `X-Pi-Signature: sha256=...`. Outbound requests carry a 5 second timeout and exception isolation so the main flow is never blocked.
- **Hub relay support**: inbound can switch to or configure a public Hub relay address (`hubRelayBaseUrl`), so the public Hub receives external requests centrally and schedules them to Bots on internal devices; outbound webhooks take an optional `relayViaHub` toggle — on, the Hub server acts as the egress proxy and sends for them; off, for direct LAN/intranet mode.
- **Inbound auth trusts only the webhook token**: the allowed values and the comparison have a single source in `server/device-center/hub-webhooks.ts` (`incomingWebhookToken` accepts the query `token` / `Authorization: Bearer` / `X-Webhook-Token` / body `token`, and `secureCompareTokens` compares in constant time), and the main web app and the Hub share the `isSelfAuthenticatedWebhook` decision. The main app's login gate lets through exactly this one path (`POST /api/rooms/:id/webhooks/incoming/:webhookId`): an external platform can never hold the local password, and folding it into account login would make public callbacks permanently 401; but it must **also** be decided only this way, never relaxed to all of `/api/rooms`. Guard: `tests/unit/incoming-webhook-auth.test.ts`.

## 11. Group standalone AI Router and external work items

The **AI Router** at the top of a group independently selects the running device, the `provider/id` model, the thinking level and the `reply` / `dispatch` / `work_items` tools. The Router understands messages and scheduling while Bots complete tasks under their own execution constraints; without it, legacy primary-Bot collaboration applies. The Hub can run standalone without an SDK: model inference comes from the daemon `ModelRuntime` on the designated device, independent of any active session or project execution tooling. Missing config, an offline device or an unavailable model is an explicit error.

The **work-item drawer** at the top shows the most recent work items and Router runs with bounded pagination, where business state is independent of the individual Bot executions. Work items, events, Router jobs and the write-back outbox are persisted by the Hub WAL and recovered through business revisions, frozen plans, lease / config fences and persistent action receipts; a failed run can be retried by hand. Clearing the group chat fences the old plan but keeps work items, while deleting the group clears the matching domain records.

The built-in channel module Superagent 0.1.3 feeds GitHub / Feishu events into the host work-item service and writes back to the original thread. Each external event's authorization is validated independently, and an auto work item grants no authorization to a followup whose author is not on the allowlist; manual authorization binds only the current latest `authorizedEventId`. The initial work-item description is kept and later events are appended as evidence, while close / reopen / merge events do not automatically mean business completion. Feishu supports signed plaintext or AES-encrypted text callbacks, and an uncertain delivery beyond 45 minutes needs a manual check; a channel mock test does not mean a real channel is connected.

The single entry point is **设备连接与跨平台协作**(device connections and cross-platform collaboration): devices and connections, groups and work items, external channels. AI Router and work items are managed right in the group list; the channel UI embeds the host module, no separate top-bar button is added, and it shows up in no ordinary plugin list, marketplace or plugin toggle. Full responsibilities, usage steps, manual recovery, public webhook boundaries, pagination / context budgets and recovery semantics are in [Group standalone AI Router and Superagent](group-orchestration.en.md); channel config fields are in the [Superagent README](../plugins/superagent/README.en.md).

## 12. Scheduling layers (Hub dispatch vs device execution)

「The same Bot cannot run concurrently」 is one shared semantic, but the two layers are responsible for different things — **they are not two duplicate queues and must not be merged**:

| Layer                  | Module                                                                           | Responsible for                                    | Semantics                                                                                                                                                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Hub dispatch layer     | `server/device-center/hub-task-queue.ts` (pure ordering lives in `bot-queue.ts`) | Deciding which `queued` task is dispatched first   | One execution slot per Bot; priority 0 = human private chat / 1 = human message in a group / 2 = automatic trigger; FIFO within the same priority; `BOT_QUEUE_MAX_PENDING=12`; median ETA; wakes only tasks with `blockReason: "bot_busy"` |
| Device execution layer | `server/device-center/task-scheduler.ts` (`runtime.ts` holds it)                 | Deciding which local tasks really run concurrently | 4 concurrent / 32 waiting, workspace overlap locks, group fairness, starvation promotion, isolating tasks whose stop is unconfirmed                                                                                                        |

`sameBotConflict` in `bot-queue.ts` is the single conflict decision shared by both layers: `checkConflict` in `task-scheduler.ts` and `conflicts` in `runtime.ts` both reuse it; `activeTaskForBot` / `rankBotQueue` serve only the Hub dispatch layer. The Hub's `store.subscribe` triggers `createBotQueueDispatcher().drain()`, while the device-side `DeviceTaskScheduler.drain()` is a separate path, and neither calls the other.

Guards: `tests/unit/hub-task-queue.test.ts` (dispatch arbitration), `tests/unit/bot-queue.test.ts` (pure ordering and ETA), `tests/unit/device-center-resource-locks.test.ts` (device-side locks).
