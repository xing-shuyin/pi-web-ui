# Attachments, images, and file handling

> Covers attachment modes, image Q&A, the vision bridge, and the file upload/download/preview protocols.

## Active content isolation

`/api/file`, `/api/attachment/:hash` and `/api/preview` set a CSP sandbox and nosniff before returning any content type; an HTML/SVG extension enumeration cannot be relied on. `allowJs=1` only permits `sandbox allow-scripts` and never grants `allow-same-origin`. Browser active documents such as `.shtml` and `.xht` therefore do not own the host origin either.

Live-preview modules and SSE are reached through a 256-bit random capability path generated on every plugin activation; the normal entry still requires host authentication, and only the GET/HEAD capability of this registered plugin may bypass the host token proxy. The proxy strips host auth headers/cookies, and responses keep an opaque origin, credential-less CORS and no-referrer; disabling the plugin closes SSE and revokes the path. The path itself grants read access to preview assets and must not be shared with anyone not allowed to view the project.

## Storage and transfer integrity

- The attachment store builds the legacy-directory index asynchronously on first query, and concurrent queries share the initialization; a successful save updates the index incrementally, so later hash lookups no longer scan the whole directory synchronously. HTTP attachment responses stream, support Range and reclaim on disconnect. Attachments imported externally during runtime require re-initializing the index.
- Saving over an existing local file first prepares a temp file on the same volume and uses the platform's native metadata-preserving replace mechanism; a failure keeps the original file and never falls back to truncated writes. Symlinks follow the actual target; files with multiple hard links refuse atomic replacement. Atomic visibility does not imply power-loss durability; when the platform cannot preserve metadata, the save fails explicitly. Saving over an existing remote file still uses SFTP and cannot promise atomic replacement.
- New file uploads commit the complete temp file exclusively; a same-name race must not overwrite. Conversation attachment paths include a UUID, avoiding same-name overwrites within the same millisecond.
- HTTP uploads validate client, path, type and declared size before receiving the body; a single file defaults to 32MiB and is adjustable between 1–100MiB via settings; at most 4 concurrent, 200MiB total reserved. Local files stream to disk; remote Buffers obey the same budget. Cancellation must wait until the actual write stream is released before returning the quota.

## Upload limits and progress

Upload size limits in settings are stored per entry point: chat attachments default to 20MiB, the file panel to 100MiB, and each file in a folder upload to 32MiB, all in the 1–100MiB range. The configuration is globally shared, and the frontend pre-check and server validation use the same values; legacy configs are back-filled with the defaults. WebSocket keeps a fixed 100MiB raw-file hard capacity that settings cannot bypass.

Progress distinguishes local reading, send awaiting acknowledgement, and the server save result. File-panel WebSocket uploads correlate through `uploadId` and `file_upload_result`, and a directory change is not evidence of upload success; HTTP folder uploads confirm through request transfer progress and the final response.

## Attachment modes (always path-only)

`ClientMessage.prompt.attachments[].mode` decides how attachments are sent to the model. **File contents are never injected into the prompt**
(not even small files): the server sends only a path reference, and the model reads on demand with its own read tool (with built-in truncation/paging).

| mode        | meaning    | server handling                                                                                                                                         |
| ----------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reference` | path only  | sends `<file path="..." size="..."/>` (uploaded files are absolute paths under the uploads directory)                                                   |
| `lines`     | line range | sends `<file path="..." lines="2-3" size="..."/>`, telling the model which lines the user picked (no file read, no content)                             |
| `inline`    | legacy     | **legacy value of the old "inject full text" mode** (sent by old clients/old drafts): the server treats it as `reference` and no longer injects content |

Images (`imageData`, workspace paths pointing at images) are still sent as image content (see below); directories, web references and conversation references each have their own card shape.

Attachments are sent as standalone custom messages (`sendCustomMessage` + `deliverAs: "nextTurn"` asides) and render as collapsible cards. The client-side `stripFileWrapper` regex must tolerate the `lines="..."` attribute.

**The message serialization cache is keyed by `role:timestamp` — several asides of the same prompt created in the same millisecond collide and must be told apart by a content fingerprint (`contentFingerprint`), otherwise only the first renders (already fixed, do not regress).**

### Lifecycle of pending attachments (follows the session, not the page)

The row of pending attachment chips in the composer (📎/🔗/💬/🖼/🌐) lives only in `App.tsx`'s `attachments` state
(never sent to the server, never persisted) and **is cleared on a successful send**. It and the body draft (stored per `sessionId`, restored when switching back to an old session)
are the two halves of the same "pending content for this session", so **both clear as soon as the session identity changes**:

- The criterion is `UiState.sessionId` (present on both the pi/DSH engines; `conversationId` changes on restart and cannot serve as session identity);
  the pure function is `advanceComposerSession` in `web/src/composer-draft.ts` (unit test: `tests/unit/composer-draft.test.ts`).
- Triggering scenarios: new conversation, switching conversations, manual takeover, switching projects (switching cwd) — a new conversation therefore starts clean.
- Transient states (reconnect, `sessionId` briefly empty in the snapshot) neither move the watermark nor clear, avoiding wrongfully clearing the user's pending attachments.
- No per-session persistence: switching away and back restores the body draft, not the attachments (to get "switching back to an old conversation brings the references back too",
  the chips would have to be stored per sessionId as well — that is a design upgrade).

## Chat text quotes

Select text or code within a chat message; releasing the mouse shows a 「引用」(Quote) button. Clicking adds a pending quote card through `composeToComposer` and keeps the composer draft. The card expands to show the original text and can be removed independently; duplicate quotes of the same source and text are deduplicated, and different fragments can be sent in the same message. The floating button hides on scroll, Escape or conversation switch.

- Protocol: `PromptAttachment.mode = "quote"`, `path` empty, `quote` stores the selected text, the source message identifier, the role and the session identifier. The original text is stored as a copy, preserving line breaks and code indentation.
- Frontend: `quote-selection.ts` validates the selection range, excluding action buttons, the composer and selections spanning messages; `SelectionQuoteButton` positions the floating button; `TextQuoteCard` shows quotes in the composer, in sent messages and in edit-and-reask.
- Standard pi engine: when idle, `buildAttachmentMessages` encodes the quote as a standalone `customType: "file"` context message with `details.mode = "quote"`, and `details.quote` serves history display and edit restoration. During generation, quotes are encoded at the end of the corresponding queued or interjected question, so a quote does not linger into the next question; serialization restores them as the user message's `details.quotes`.
- Standard pi engine queue: rendering splits out the quote cards; withdrawing restores the question draft and the quote attachments; removing deletes the quotes along with them. Both the composer and edit-and-reask allow sending quotes alone.
- DeepSeek Harness engine: quotes are sent as standalone text blocks, and `dsh-serialize.ts` restores them as the user message's `details.quotes` on history replay; continue, edit and branch contexts re-encode these quotes. Encoding and validation share `server/text-quote.ts`.
- Regression: `tests/unit/quote-selection.test.ts`, `text-quote.test.ts` and the attachment/draft unit tests; after a build run `node tests/quote-selection-ui-test.mjs`, which uses real Chrome and a local mock model service to verify sending, refresh and edit restoration without touching a real model.

## Image Q&A (no workspace path)

Pasted (Ctrl+V) / dropped into the composer (**the whole window is a drop target**, issue #19: the `.app` root handles file dragover/drop plus a full-screen `.app-drop-overlay` highlight (the only indicator; the composer does not stack a local mask); the composer's and the editor's own handlers call stopPropagation on drop to keep priority, so App additionally listens for drop in the window capture phase to reset the overlay — otherwise the full-screen overlay would stay up when the drop lands on the composer) / 🖼 uploaded images are sent with `attachments[].imageData` (base64) + `mimeType` + `name` — the server attaches them directly as image content and never goes through a file path (`path` is ignored). The browser side (`web/src/image-paste.ts`) first scales images proportionally to ≤1568px and converts to PNG/JPEG as needed, keeping the payload within the server's 2MB limit (`MAX_PASTED_IMAGE_BYTES`). When the current model does not support vision (`model.vision`), the frontend shows a warning.

## Vision bridge

When **the current conversation model does not support vision** (DeepSeek/GLM etc. whose `input` is only `text`), `buildAttachmentMessages` no longer sends images as image content (they would be ignored) but hands them to a **configured vision model** to transcribe into textual evidence before feeding the primary model (`server/vision-bridge.ts`):

- **Zero-config auto-discovery**: `findVisionModels` scans every provider in `ModelRuntime` with **`hasConfiguredAuth`** and finds models whose `input` contains `"image"` (qwen-vl, GLM-4V, Gemini…) — reusing credentials already present in models.json/auth.json and adding no new configuration. ⚠️ Unconfigured SDK built-in providers must be filtered out (e.g. amazon-bedrock ships Nova vision models but has no auth; without the filter the call fails).
- **Transcription**: `transcribeImages` uses `runtime.completeSimple` to send the whole batch of images (multiple images merged into one call) to the vision model, with a prompt that demands evidence first — verbatim OCR, layout, chart coordinates/legends, entities, and an explicit "cannot read" instead of invention when illegible (following modlens' evidence-not-imagination contract). Default 90s timeout (`PI_WEB_VISION_TIMEOUT_MS`), maxTokens 4000 to keep the context from blowing up.
- **Result shape**: the attachment card content becomes `[text(wrapped in <vision-bridge>), image(thumbnail)]`, `details.mode` = `"bridged"` (the frontend AttachmentCard shows a 「👁 已转写」(transcribed) label + expand to see the thumbnail and transcript; `stripFileWrapper` also strips the `<vision-bridge>` wrapper). A notice announces transcription start/completion/failure (on failure it falls back to sending as-is).
- **Images referenced from the file list trigger the same path**: in its preprocessing stage, `buildAttachmentMessages` also reads **attachments whose path points at an image** (extension ∈ IMAGE_EXT and not SVG, confirmed by `sniffImageMime` magic-number sniffing, ≤5MB `MAX_PATH_IMAGE_BYTES`) into base64, besides `imageData` — text-only models go through the vision bridge (the bridged card carries `path`), vision models get them directly as image content (no longer making the model read binary garbage with the read tool); SVG stays a regular file (the model reads the source).
- **Cache**: `visionBridgeCache` caches the transcript per batch hash (name + first 48 characters of base64) — re-sending the same image via edit-and-reask no longer burns vision tokens again.
- **Without a vision model**: a warning notice says 「未找到可用的视觉模型」(no usable vision model found) + the image is sent as-is.

### Settings panel: model, toggle, prompt

The vision bridge section of `SettingsModal` goes through `set_settings` + `UiSettingsState` and persists per client in client-state.json:

1. **Toggle** `visionBridgeEnabled` (on by default; when off, images are sent as-is + a warning notice 「视觉桥已在设置中关闭」(vision bridge disabled in settings))
2. **Transcription model** `visionBridgeModel` ("provider/id", default null = auto-pick the first; the server resolves it in `buildAttachmentMessages` via `resolveReviewModel` and validates that `getModel().input` contains image, falling back to auto-discovery when invalid)
3. **Transcription prompt** `visionBridgePromptMode` ("append"/"replace", same semantics as promptMode) + `visionBridgePrompt` (custom text, empty = built-in default) — assembled by `buildVisionBridgePrompt` (exported from vision-bridge.ts) and passed to `transcribeImages` as `systemPrompt`; append appends after the default prompt, replace swaps it out entirely (empty text still falls back to the default); **the prompt is part of the batch cache key** — after changing the prompt, re-sending the same image no longer hits the old transcript cache

`settings_state` carries `visionModels` (`collectVisionModels()` = the `findVisionModels` result) for the dropdown; presets **do not include** vision-bridge preferences (`SettingsPreset extends Omit<ClientSettings, "visionBridge…">`, current values are kept on apply); in `setSettings`, changes to vision-bridge fields **do not trigger** `applyRuntimeSettings()` (no reload needed, effective on the next prompt).

**Both replace input boxes are prefilled with "the original prompt"** (settings_state carries `defaultSystemPrompt` + `visionBridgeDefaultPrompt`): switching to replace mode fills an empty box with the built-in default text for direct editing, content identical to the default is saved as empty (= use the default), and switching back to append does not append twice.

## File conversation (no workspace path)

Any file dropped into the composer / 📎 uploaded is sent with `attachments[].fileData` (base64) — the server writes it into the global directory `~/.pi-web/uploads/<clientId>/` (**not inside the project**, `MAX_UPLOAD_BYTES` 20MB limit) and always attaches it as an **absolute-path** reference (the read tool accepts absolute paths), no longer inlining small text. The frontend routes by `isRasterImage`: **only raster images** (png/jpeg/gif/webp/bmp/avif…) take the imageData pipeline; **SVG and other vector formats are excluded** — createImageBitmap fails to decode SVG, and attaching SVG as a regular file so the model can read the source is more useful; every other file takes fileData.

## Unified image preview, OCR, and attachment annotation

- `web/src/components/ImageLightbox.tsx` is the only image preview implementation: message attachments, pending attachments, tool results, tool details, Markdown images, `present_files` cards, file-tree image previews and the image workbench generation gallery all reuse it. Entry points go through `image-lightbox-bridge.ts`, and the file preview panel's image branch uses the same component directly. Supports Esc, backdrop close, keyboard focus containment and narrow-screen layouts.
- The dialog opens as a **compact floating card** by default: `.img-lightbox-panel` uses `width: fit-content` + `--lb-image-max-w/-h` (`min(78vw, 880px)` / `min(62dvh, 620px)`) to open sized to the image, so small images do not stretch it and large ones shrink to the cap; full screen is toggled by the toolbar full-screen button / double-clicking the image / the `F` key and anchors on the root node's `data-fullscreen` (in full screen the overlay uses `padding: 0` and the floating card fills the viewport). Entering "annotate image" switches to full screen automatically so the canvas is large enough; the Esc order is "exit annotation → exit full screen → close". Narrow screens (≤640px) switch to a small card pinned to the bottom that absorbs `env(safe-area-inset-bottom)`.
- The toolbar is always icon buttons (`.img-lightbox-btn`): no visible text, tooltips via a `data-tip` pseudo-element (`opacity` 0.09s, no native `title` delay; hidden under `@media (hover: none)`), accessible names from the same source in `aria-label` (except for the OCR install state, where `label` is given separately); lossless clipping: the floating card does not set `overflow: hidden`, the image clips its own rounded corners. Z-order is still issued by `useOverlayZIndex()`.
- The "recognize text" button is always shown; without an OCR provider, clicking installs the official `image-ocr` through the existing `plugin_job`, enables it through `set_settings` when disabled, or reloads it when present but not loaded. Install progress and failure reasons show inside the current preview; the install authorization dialog is portaled to the body, sits above the preview, and the preview's focus containment temporarily yields to the authorization window. After installation there is no need to close the image; the button switches to recognition.
- `plugins/image-ocr` is a `view:false` / `preload:true` browser plugin: the top level only registers the provider; clicking downloads the pinned Tesseract.js 6.0.1, WASM and the Chinese/English language data. Images are read as bytes from the app's original address and recognized in a local Worker; the CDN only serves the program and language data. The first download needs the network, and remote images must allow CORS or be saved as attachments first. Results support selection, copy, a no-text hint and retry on failure.
- OCR jobs bind to the current image and provider; cancel, close, switching images, and plugin disable/uninstall/reload all invalidate old jobs, and the plugin terminates the executing Worker (including child Workers in the init phase). The engine only outputs text and never auto-sends it to the conversation.
- Every image preview has "annotate image": each open defaults to the pen, with arrow, rectangle, text, color and undo switches, and Pointer Events support mouse/touch/pen. Edits go to a separate canvas; cancel discards this round of changes. Pending attachments replace the image in the draft by the original attachment object's identity via `onSaveAnnotation`; other entry points stay in the preview after saving, allowing another annotation or restore of the original. Sent messages and the original workspace file are never overwritten. Once an attachment has been sent/removed or the draft switched, a late result is not written to a different attachment.
- The unified toolbar offers "attach to composer", "copy image" and "download file". Actions use the image in the current preview, including saved annotations; they only append draft attachments, keep the composer text and never auto-send. After the same image is attached successfully, repeat attach is disabled; previewing a pending attachment shows it as already attached. `composerSessionId` is captured before asynchronous image processing and re-checked on completion, so switching sessions or closing the preview cannot write the result into another conversation.
- Attach results reuse `image-paste.ts`'s ≤1568px / ≤2MB image processing and write `imageData`; results over the limits fail explicitly. The edit canvas caps its longest edge at 4096px to control memory. `image-preview-actions.ts` keeps the original download bytes, converts non-PNG to PNG for the clipboard as browsers require, and starts the write immediately on click to preserve user activation; downloads reuse `saveDownloadBlob`, and cancelling save-as is not reported as success. Failures are reported inside the preview and do not close the image.
- The preview offers image dimensions, zoom in/out, 100% original size and fit to window, and after zooming you can scroll to inspect details. `ImageLightboxTarget.actions` keeps caller-context actions (with text labels, while the other buttons are icon-only); the file preview uses the unified download directly, and plugins no longer build their own image lightbox.
- Provider and plugin bridge protocols are in "Image preview and OCR providers" in `architecture-plugins.md`. Regression: `tests/unit/image-ocr.test.ts`, `tests/unit/image-preview-actions.test.ts` (original bytes, MIME, clipboard activation, download cancel and failure), `tests/image-preview-ui-test.mjs` (`PI_TEST_REAL_OCR=1` verifies real Chinese/English engine download/recognition), `tests/image-ocr-install-ui-test.mjs` (after a build, verifies click-to-install when not installed, the authorization layering and re-enabling after disable, without calling a model).

## File preview protocol

- The client sends `{ type: "read_file", path }` → the server replies `{ type: "file_content", path, name, text, truncated, binary, lines, size }`.
- Read-only for the first **512KB** (`MAX_PREVIEW_BYTES`); **content sniffing decides text or binary**: no NUL and control characters below 2% means preview as text (`looksLikeText`) — unknown/extensionless files (jsonl, .log.1 etc.) open too; **text decoding falls back to GBK** (`decodeText`: strict UTF-8 fails → GBK → latin1, used by both preview and line attachments), so old Windows Chinese files are no longer mojibake; binary returns `binary: true` with `text` as a **hex view** of the first 4KB (`hexDump`, rendered by the frontend `.fp-hex`, the full file downloadable). Paths are validated via `resolve + relative`, and `..` escapes are rejected outright.
- **Media preview goes over HTTP**: image/video stream back via `/api/file?clientId=…&path=…` (`sendFile` supports Range), with the path resolved against **that client's session cwd** (the opened project) rather than the server's startup directory — the two may differ; when `clientId` is missing or the session does not exist, it falls back to the startup `CWD`. Path validation goes through `workspacePath()` (exported from agent-service).
- **HTML rendering goes over the directory-mapped HTTP route**: `/api/preview/<workspace-relative path>` (absolute machine-browsing paths get a `__abs__/` prefix, each segment URI-encoded); the iframe document URL carries the file's own directory, so relative references in the page (`<link href="../web/src/styles.css">`, `./app.js`, images…) resolve and load with normal browser semantics without rewriting the HTML; HTML documents carry a sandbox CSP (`sandbox`, or `sandbox allow-scripts` with `?allowJs=1`, never adding `allow-same-origin`), and other subresources are served with their real content-type; the preview dialog **always** requests with `allowJs=1` and puts `allow-scripts` on the iframe (scripts just run, no toggle), and the top bar's unified toolbar `host:fp-external` offers "open in new tab"; `..` escapes are rejected by `workspacePath()` (if the route layer's normalization fallback catches them, they land in the SPA 404 with no file disclosure).
- Line-number semantics: **a trailing newline does not produce an empty line** (`countLines` fixed), and the frontend/backend split logic must agree.

### File manager context menu: compress, extract, and folder upload

- `contextmenu.file` adds compress, extract, upload folder, and compress-and-download; it reuses the unified menu and confirms in `FileTransferDialog` with errors/upload progress.
- Compress recursively produces `{folder name}-{UTC time}.tar.gz` in the same directory; a single file produces `{original file name}.tar.gz`, and an existing archive of the same name is not overwritten.
- Extract is offered only for ZIP, TAR, TAR.GZ/TGZ and GZ; choose an existing target directory, with a conflict policy of skip (default), overwrite files, stop on conflict. It first unpacks into a private temp directory and fully checks conflicts, then writes to the target directory. I/O errors unrelated to conflicts can still leave partially written files.
- `server/file-archives.ts` uses Node libraries, never calling a shell or depending on the system tar/unzip. It rejects archive path escapes, Windows special paths, links and device files; it checks the target's symlinks and unlinks before overwriting, preventing modification of other files through hard links. Limits are 20,000 entries / 1 GiB; the TAR extraction stream also has a byte cap.
- Both engines share `/api/file-transfer/archive` and `/api/file-transfer/upload`, behind the existing auth middleware, requiring a connected clientId and a custom request header, with path rules matching the file manager (including absolute machine-browsing paths). The frontend preserves the reverse-proxy prefix via `appUrl()`.
- Folder upload preserves the top-level folder and recursive levels, sending binary HTTP requests file by file (32 MiB per file, no base64/WS) and never overwriting existing files. Browsers supporting File System Access also upload empty directories; the rest fall back to `webkitdirectory`, covering only files and their parent directories. On failure the already uploaded part is kept.
- Compress-and-download uses a private temp directory, cleaned after the HTTP download completes, disconnects, or fails; the browser saves through the existing blob save logic without a second download request. Temporary downloads are capped at 200 MiB to control browser memory; larger files can be compressed in place first and then downloaded with the existing streaming path.
- Regression: `tests/unit/file-archives.test.ts`, `tests/unit/file-transfer-routes.test.ts`, `tests/file-archives-ui-test.mjs` (run after a build, isolated port/data directory, zero model calls).

### System screenshot (Windows / macOS host)

- `host:composer-screenshot` in the composer action bar (scissors icon, by default after attachments and templates, i.e. the third slot from the left) is rendered by `SystemScreenshotButton.tsx` and follows slot ordering, visibility and icon editing. **Clicking immediately takes a "capture the current window" screenshot** (no menu, no window hiding); **hovering** expands a floating panel above it containing a single entry, "capture with the current window hidden". After choosing, drag a selection and release to finish; Esc cancels (also available on macOS), right-click cancels on Windows, and it auto-cancels on timeout. The floating panel reuses `useFloatingPanel` and `ctx-menu`, collapses 180ms after the pointer leaves the button/panel, and closes on outside click / Esc; touch and keyboard users still have the default click behavior.
- Position migration: `migrateScreenshotOrder` in `web/src/ui-slots.ts` anchors the screenshot button, not yet present in `order` in early layout snapshots, after templates (or attachments when there are no templates) — otherwise unsorted entries would sort after all sorted entries and drift to the right; new layouts just land on `order: 115`.
- `server/system-screenshot.ts` registers `/api/system-screenshot` after normal auth: GET queries capability, POST initiates a capture; `hideWindow` accepts only booleans and defaults to `true` when omitted, for compatibility with existing clients. Only one screenshot at a time per service; limited to Windows / macOS, loopback TCP and loopback Host, rejecting proxy-forwarding headers and cross-origin requests; on other platforms GET returns `available:false` and POST returns 501. Remote clients cannot capture the server's desktop.
- `server/system-screenshot-windows.ts` calls Win32 / WinForms through an async PowerShell STA helper process. In hide mode the frontend temporarily appends a random nonce to the window title, and the helper minimizes only when the foreground window title matches, preventing accidental minimization of other windows after a focus change; success, cancel and exceptions all restore the original window (including maximized state). Preserve mode does not change the title, minimize or restore the window, nor record window restore info. Disconnect cancels via stdin; the helper watches the parent process exit, and when a timeout force-kills it the server separately restores the hidden window.
- `server/system-screenshot-macos.ts` asynchronously calls native `/usr/sbin/screencapture -i -x -t png <private temp file>`: drag a region in the native overlay (space toggles window mode), Esc cancels without writing a file, and an empty file counts as cancel. Hide mode first uses `osascript` to read the frontmost app name / `unix id` / frontmost window title, and sets that app's `visible` to false only when either signal hits: ① the window title contains the nonce set by the frontend (browsers write `document.title` into the window title); ② the frontmost app's pid belongs to the ancestor chain of the host process running this server (`ancestorPids()` derives it upward with a single `ps -A -o pid=,ppid=`). ② is required: the desktop app's frontmost window is usually the embedded browser panel with the fixed title 「pi Browser」, so the nonce never reaches the title and ① alone would misjudge a normal hide request as a focus change. Only when neither hits (the user has switched to an unrelated app) does it return `window-not-focused`. Then `screencapture` runs, and finally `visible` + `frontmost` are restored. Without automation / accessibility permission the probe script fails and it degrades to "capture the window" rather than asserting failure. On first use macOS also requires granting screen recording under 「系统设置 → 隐私与安全性 → 屏幕录制」 (System Settings → Privacy & Security → Screen Recording) to the actual executing process (Node / terminal / Electron app), otherwise the capture is a blank desktop. The temp file is deleted after reading along with the private temp directory, and the clipboard is not modified.
- It captures the virtual desktop spanning all displays and then selects a region, supporting negative coordinates and mixed DPI; it returns only the selected PNG, writing no temp image and not modifying the clipboard. The result opens in the generic preview through `image-lightbox-bridge.ts`'s `openImageLightbox`, where it can be annotated, attached to the composer, copied, downloaded and zoomed; cancel shows no dialog and does not auto-add to conversation attachments. On non-Windows/macOS or remote access the button is disabled with a stated reason.
- Regression: `tests/unit/system-screenshot.test.ts`, `tests/unit/system-screenshot-windows.test.ts`, `tests/unit/system-screenshot-macos.test.ts`, `tests/unit/ui-slots.test.ts` (screenshot position and legacy layout migration), `tests/image-preview-ui-test.mjs` (hover expands / click captures); covering both modes, platform capability, legacy request defaults, parameter validation, nonce validation, the degraded path and floating-panel interaction; native C# compile validation and macOS script compile validation trigger no real desktop capture.

### Downloads

`web/src/download.ts`: does not use `<a download href>` (Chrome Safe Browsing blocks low-reputation file types such as .zip/.exe from non-HTTPS origins), but fetch → save blob; >200MB falls back to native navigation streaming download; on failure a toast shows the server error body (`downloadFailed` i18n key).

**Windows special case**: blob anchor downloads can still be silently blocked by Safe Browsing on Windows (no JS error, appearing as "clicking does nothing") — in a Chromium secure context (localhost/HTTPS) prefer `showSaveFilePicker` to write directly to the user-chosen file (bypassing the download pipeline); on Windows the save name is sanitized by `sanitizeFileName` (`<>:"\|?*`, trailing dots/spaces, reserved device names like CON/COM1); cancelling the save dialog is not an error (`cancelled`, no toast). `download-test.mjs` covers the regression (with the picker disabled to test the blob path).
