# Core architecture

> Required reading before you change code. This document covers global architectural decisions: snapshot-driven state, the single protocol source of truth, security boundaries, theme switching, multi-conversation concurrency.

## Turn timing

The bottom `host:working` uses the server timestamps in `UiState.turnTiming`: the clock starts when the message begins delivery, and tool calls, interjections and automatic retries ride the same clock. When the turn ends or is stopped, `finishedAt` is recorded and the final duration is kept; the next turn starts over. Snapshots explicitly send `null` to clear sessions with no timing, so switching conversations leaves nothing behind. The frontend refreshes the display every second and stops the timer once the turn completes; the timing text is independent of the hideable status labels so narrow layouts still fit.

## Collaboration completion notifications

The pi engine defaults both `steeringMode` and `followUpMode` to `all`: at each delivery point the whole current queue is delivered at once in enqueue order. The settings page exposes a switch for each; turning one off falls back to `one-at-a-time`, which suits handling independent tasks one round at a time. Preferences persist in the Web UI config and a change immediately updates every live pi session; new, restored and post-SDK-reload sessions replay them through the unified session override entry point, without writing to the user's pi CLI settings. Other engines keep their own queue semantics.

Each running conversation binds a unique `exec-UUID` identity to its Conversation object, and the messaging address reuses that identity; the parent-child relation binds the parent object once at dispatch time, and `cN` is only a holder-local display number. Takeover keeps the object and identity and changes only the holder and the display number; maintaining a global `cN → cN` alias is forbidden. The completion notification queue, parent-child requests, project ancestor resolution, task dependencies and wait fan-out all use stable identities; when the parent conversation closes, its identity becomes invalid and is not rebound even if the number is reused. Old numbers may only be resolved locally or globally uniquely — on ambiguity the result is unavailable. Completion notifications are delivered only to the original parent conversation; after it closes they degrade to a system Notice. Identity is valid only for the runtime lifetime inside the process; old objects or expired addresses are never persistently restored.

Completion sounds, desktop notifications and end-of-turn speech use a separate working-state edge: `isStreaming || completionPending`. `completionPending` is published in activity snapshots and running-session summaries and covers queued steering/follow-up, the prompt delivery window, and the aggregated wait plus async delivery of subagent notifications; it does not change the output semantics of `isStreaming`. Subagent notifications keep occupying the pending count while the worktree settles asynchronously and delivery runs; once delivery succeeds or fails, the status refreshes through the conversation's current holder. Consecutive continuation runs trigger the completion notification exactly once, after the queue drains; this applies to foreground and background alike.

## Mobile system notifications and multi-device

The React + Capacitor mobile client, Hub account-isolated push and device switching are covered in [`mobile.md`](mobile.en.md). Mobile notifications are triggered by the server's authoritative `onNotificationEvent` event and do not depend on WebSocket sinks; completion must not be reported early while retries, compaction, manual waits or subtask dependencies are still open.

Notification clicks carry instance, device, session and owner / conversation identifiers. Across clients, `open_shared_conversation` with `readOnly: true` views the original execution object, and the snapshot's `sharedConversation.readOnly` drives the read-only UI; the server only allows queries and answers to existing questionnaires / one-off approvals, and rejects prompt, terminal, settings and workspace writes. This mode can view independent conversations / subagents, but it does not relax the regular sharing entry point, nor does it migrate the owner or reload the session.

The shared view does not steal row actions from the left panel: when `dismiss / rename / pin / persist_conversation` does not point at the current shared conversation it is not a shared operation — local sessions go back to local dispatch, and cross-client elsewhere rows are routed by `daemon.dismissConversation` (`server/index.ts` must wire the facade, otherwise ✕ silently does nothing); read-only sharing still only admits sessions the viewer itself holds. Fork identity in row badges must survive restarts the same way: `forkFrom` lives only in memory, so the client must check both `forked` (the engine derives it from the session file header's `parentSession`) and the history row's `parentSessionPath`; otherwise a fork that is reopened or runs elsewhere degrades into a plain row.

## Desktop notifications target the conversation

`web/src/notify.ts` freezes the target conversation's `#s=<sessionId>` deep link when it creates a notification; background completion and background questionnaires explicitly pass their own stable `sessionId`, so the notification target does not drift while the user switches conversations or the Service Worker registration is still pending. The link keeps the deployment sub-path and drops the `token` and `view` query parameters; auth keeps using the Cookie. Notifications still set no `tag`, so Windows does not silently replace earlier reminders.

`web/public/sw.js` handles `notificationclick` by first focusing an already-visible same-origin app window showing the target conversation, then messaging the page through `pi-web-ui:notification-click` so it reuses the existing deep-link router to switch conversations; with no app window it opens the target deep link directly. An existing page needs no reload — on click it leaves the group or the other view and shows the chat; when the connection is not ready yet the existing pending-deep-link mechanism defers the switch. The plain `new Notification()` fallback handles clicks through the same subscription entry point. Target URL and window must stay within the app's origin and deployment scope; a notification without a target falls back to the app entry point.

Verification: `tests/unit/notification-click.test.ts` covers foreground/background target freezing, page notifications after a missing or failing Worker, message subscription and cleanup, forwarding to an existing window, new-window deep links, sub-paths and same-origin boundaries; `tests/unit/session-url.test.ts` guards the deep-link format and the stable session identity contract.

## Sidebar history session loading

Session order within a project is maintained by `web/src/conversation-order.ts` as a single record for the page lifetime, shared by history rows and active rows. The first load initializes from the server's latest history summary and may let it replace older timestamps in the warm-up cache; after initialization the ordering basis freezes until the page is refreshed and the latest order is reloaded. Sessions discovered later append to the end, and only a user's successful message send (including interjections, queued and attachment messages) moves that conversation to the top of all conversations in its project. Streaming output, tool calls, subagent creation/termination, background notifications, questionnaires, errors, modification-time updates, always-on markers or opening/switching conversations never trigger reordering.

The UI's `appSend` attaches a client-only `userInitiated` context to prompts; `useChat.send` updates the order after the WebSocket send succeeds, while plugins that call the sender directly or explicitly disable that context do not promote, and blank or disconnected sends do not promote either. The native CLI only consumes the narrow `native_cli_prompt_submitted` event (Claude/Codex `UserPromptSubmit`, Pi `input(source=interactive)`), deduplicated by session and eventId; terminal output, ordinary keystrokes, paste and working state cannot substitute for a user submission signal.

Session ID, sessionId and file path are associated with the same position, so the order survives switching between active and history representations, reopening or takeover. Subagents keep the parent-child tree (including worktree subagents); sending a message directly to a subagent promotes the whole parent tree it belongs to. Order lives only in page memory and is never written to storage; project ranking is covered in "Project (workspace) ordering".

## Project (workspace) ordering

Project order is decoupled from the "recent conversation" time; source of truth: `remember(clientId, cwd, { promote })` in `server/client-state.ts` plus `web/src/project-order-settings.ts`.

- **Time only counts real conversations**: `promote` (the default) is called only when a message is really sent (pi `ClientSession.prompt`, the `prompt` of `dsh` and `universal`); it refreshes the project's `lastUsed` and pushes `projects`. Browsing/switching/restoring (`set_cwd`, `switchConversation`, opening a history conversation, restoring `lastCwd` on connect) always use `{ promote: false }`: they only write `lastCwd`, clear the tombstone, add an unregistered project with `lastUsed: 0`, and never touch time; `withCurrentCwd()` no longer timestamps the current project either. Otherwise "just taking a look" would push a project to the top and the next load order would change.
- **Two client modes** (localStorage): auto mode (default) sorts by descending `lastUsed`, and `lastUsed === 0` (never chatted) falls back to "first seen in this browser", so newly added projects naturally sit at the top; manual mode (the "project order fully manual" setting) only honors the persisted drag/add order, puts newly appearing projects on top, and never reorders on chat. Dragging or Alt+↑/↓ switches to manual mode automatically. Switching modes does not jump: auto mode continuously mirrors the current order into storage, manual mode takes over the visible arrangement as is.
- The time on the right of a project row shows only when `lastUsed > 0`; verification: `tests/unit/left-panel-stage-d.test.ts`, `tests/unit/left-panel-actions.test.ts`, `tests/unit/left-panel-open-conv-order.test.ts`, `tests/unit/client-state-recent-projects.test.ts`. Adjacent project nodes use a themed border-color divider and spacing, and the divider spans the whole conversation subtree.

"Running conversations" (`conversations`) and "history sessions" (`sessions`) are two channels that often point at the same sessions, and the left panel must recognize them as one row — otherwise a single session renders twice. Division of labor: **row ownership is decided by the engine, identity is normalized by the client**.

- Row ownership: `ConversationSummary.rowKind` (`server/conversation-rows.ts`★ single source) — `open` = the conversation owns a row (running / waiting for an answer / subagent / pinned / ephemeral / native CLI / not yet persisted), `history` = already represented by a history row. All three engines (pi `agent-service`, claude/codex `universal`, `dsh`) compute it before pushing; the client only reads `rowKind !== "history"` and **no longer guesses from `sessionFile` / `pinned` / the disk index**. When `hasHistoryRow` is not declared it defaults to `open` (better one extra row than a conversation vanishing).
- Identity: the strong keys in `web/src/session-identity.ts` (conversation id / sessionId, the uuid derived from the canonical file name, or the session file path); a bare-token path counts as a session id (the universal base has exactly this shape), so the engine will not duplicate even if it omits `sessionId`. The weak key `fn:` (bare file name) is only used to associate status dots, unread markers and the stop button and must not participate in deduplication (different directories may share a name).
- The engine-side `conversations` summary must carry `sessionId` (= session id) and `modified`, otherwise the client can neither recognize the identity nor show the time nor sort correctly.

Compatibility branch: the client takes the `legacyOwnsRow()` heuristic only when **the whole payload carries no `rowKind`** (old server / mobile-server version mismatch); once the new version has shipped the whole block can be deleted (the removal condition is written in the function comment). Protocol changes bump `PROTOCOL_VERSION` in step (both `protocol-version.ts` copies). Verification: `tests/unit/conversation-rows.test.ts`, `tests/unit/conversation-rows-engine.test.ts`, `tests/unit/conversation-row-declared.test.ts` (a missing engine declaration fails), `tests/unit/session-identity.test.ts`, `tests/unit/left-panel-row-kind.test.ts`, `tests/unit/left-panel-universal-dedupe.test.ts`.

Verification: `tests/unit/conversation-order.test.ts`, `tests/unit/use-chat-conversation-order.test.ts`, `tests/unit/left-panel-open-conv-order.test.ts` plus the sidebar search, collapse and action regressions.

After a local conversation, a history session or an "elsewhere" conversation finishes running, a blue checkmark appears at the end of the row until it is viewed; viewing clears the marker. All session status icons (loading/running spinner, waiting question, error, unseen checkmark) share the rightmost 14px slot through `ConversationRowIndicator`, placed after the category/preset badge; the time is hidden while a status icon is shown and only appears when there is no status icon.

On refresh, projects and their expanded state are restored before the connection is established. `LeftPanel` requests history sessions for expanded projects only after `ready` and `status === "open"`, and registers the requested/loaded state only when `panelSend` succeeds; a disconnect clears the request records and a reconnect re-sends them automatically. Manual expansion and automatic restoration share the request records to avoid duplicate requests. An empty array `[]` from the server also means loading finished, and "暂无历史会话" (No history sessions) must appear without clicking the project.

After deleting a history session, refresh both the current project and the project the record belongs to; the owning project is determined from the running conversation or the transcript header captured before deletion, with SSH local cache paths restored to the logical workspace URI. Invalidating the list bumps the scan generation and releases the old scan's reuse; a scan started before invalidation must not write back files or the list cache, and its caller re-reads with the original project and pagination parameters so a stale `sessions` message cannot resurrect deleted entries. When a scan finishes it only cleans up in-flight records it still owns. Verification: `tests/unit/native-cli-conversation.test.ts` and `tests/unit/session-cache-bounds.test.ts`.

After a session finishes a turn (`turn_end`), push the session list once more using **that session's own cwd** (`scheduleSessionsPush`: the first turn pushes immediately, later turns within 600ms coalesce into one trailing push; nothing is pushed if the client never requested the list, and the timer is cleared when the session is destroyed). When content changes only invalidate the cache without pushing, the frontend's "running" group removes that row as the session ends while the left panel has no new list to fill in — the user sees "the conversation disappears once it finishes and only comes back after clicking the project"; deferring the push to the end of the throttle window instead makes the gap a visible flicker. Delete that cwd's `sessionInfosCache` before pushing, otherwise the old list (TTL 30s) is pushed back verbatim. Verification: `tests/unit/session-list-refresh.test.ts`.

Pinned ownership is decided by **the session file header's `cwd`**, not by "which project was open when the pin was clicked": `pinSession()` calls `readCwdFromSessionHeader()` before recording, and pre-opens pinned sessions only after filtering once more by ownership via `pinnedPathsOwnedBy()`. Pinning a session that belongs to B from project A's view records it under B; historical dirty data with the wrong project (`client-state.json` where the same path is attached to two cwd keys) is also blocked by this filter, so B's session is never pre-opened into A. Verification: `tests/unit/pin-session-cwd.test.ts`.

After pinning / unpinning, push a `sessions` summary **keyed by the session's own cwd**: the 📌 on a history row comes from `pinned` in the summary (computed live by `isSessionPinned()`), and `emitConversations()` only refreshes running and active rows without touching the summary — without the push, the icon after unpinning would linger until the project is clicked to reload the list. `setConversationPinned()` pushes `conv.cwd`; when the `pinCwd` used for recording differs from the current `cwd`, `pinSession()` pushes `pushSessionsForCwd(pinCwd)` instead. Verification: `tests/unit/pin-badge-refresh.test.ts`. Project expand/collapse state persists in `pi-web-ui:lp-expanded-projects`: a refresh **restores exactly what was recorded**, and only "first use with no record at all" expands the current project; the effect watching `currentCwd` does nothing on the first frame (otherwise a collapsed project pops open again after every refresh), and later project switches expand automatically. Pinned history rows still show while the project is collapsed (`isPinnedRowVisible()`; projects that have stayed collapsed since the refresh and were never expanded must still mount child nodes, and are exempt from the `maxVisible` truncation) — otherwise collapsing the project makes them vanish from the left panel, which makes pinning pointless. The history row context menu decides "钉住" (Pin) vs "取消钉住" (Unpin) by **that row's own `pinned`**: history rows from other projects are not in the current project's `sessions` list, so querying only the list would always show "钉住" (and clicking it pins again). Verification: `tests/unit/pin-badge-refresh.test.ts` and `tests/unit/left-panel-actions.test.ts` (cross-project history row case).

Each level of the sidebar subagent tree indents 12px from the first level, rows with and without subagents share the same title baseline, hierarchy is expressed by indentation alone, and no connector lines are drawn. The collapse button uses a thin outlined arrow that shifts right with depth; the icon is 12×12px with its own 18×24px hit area, a 2px gap to the title, and hover plus keyboard-focus feedback. Running conversations and other clients' conversation trees share the same layout, and the button expresses expansion via `aria-expanded`. In-level styles stay consistent with the structural reset rules at the end of `styles.css` so themes or selected states do not override the indentation.

Cross-project history reads all go through `pushSessionsForCwd`. UniversalSession (Claude/Codex) reads archives for the requested project and applies that project's title and pagination limits, returning `sessions.cwd` and each row's `cwd`; the read never switches the current workspace or overwrites the active conversation list. `use-session-list-requests.ts` tracks acknowledgements per project and shows a retryable state when 20 seconds pass without a response; another project's acknowledgement cannot end this project's loading. Disconnects and engine switches clear old requests; after reconnecting, expanded projects are re-read, and a late valid acknowledgement can restore the list. Verification: `universal-session-list.test.ts`, `left-panel-session-loading.test.ts`.

## Worktree entry

Git worktrees show up through the top bar's `host:worktrees` project entry with a count and a status dot for uncommitted changes, and no longer auto-open or sit in a permanent warning banner. The entry takes part in the unified layout and overflow menu, and clicking it switches to the in-page `worktrees` view; the list shows the main repository, the current worktree, the full branch name and path, with long text wrapping. A switch waits for the server to confirm cwd/currentPath before returning to chat and does not exit early on failure; removal lives in each item's management details and uses non-forced deletion after confirmation.

`useWorktreeRefresh` mounts independently of the details page and re-detects server facts via `refresh_worktrees`: every 30 seconds while the page is visible, immediately when the window regains focus or the page becomes visible again; hidden pages pause detection. A response is bound to the project cwd at request time, and stale project results must not be published after switching projects. The old banner's localStorage ignore state is gone.

## Conversation collaboration tool compatibility

Conversation collaboration has exactly one tool name, `conversation`, covering subagents and persistent conversations; transcripts, files and status are read on demand through `conversation(action="read"/"files"/"status")`, and `conversation_read` is no longer registered separately. The historical alias `subagent` is deleted: `makeSubagentTools()` produces only the single `conversation` definition, and the frontend renders only one switch.

Tool registration still takes `AGENT_TOOL_CATALOG` in `server/tool-manager.ts` as its source of truth. `subagent` and `subagent_*` (`LEGACY_SUBAGENT_TOOL_NAMES`) in old archives are folded into `conversation` by `normalizeDisabledAgentTools()`, so disabled states in old presets still apply without resurrecting as separate switches; old `subagent` overrides in `toolPromptOverrides` are likewise merged into `conversation` during normalization.

## Async ownership and persistence boundaries

- Edit-and-resend captures the Conversation/runtime at the entry point, and history truncation, cache cleanup and the actual SDK prompt all use that target; after an async resume verify the object is still held, and never re-read the active session. Tools resolve the current holder through the stable SDK session, so approvals and permissions after a takeover use the new holder.
- Tool guards and approval waits bind to an AbortSignal; every async guard/approval resume point and the pre-execution check tests for cancellation; cancelling removes pending approvals, and scanning only the items pending at cancel time is not enough.
- Persistent subagents and new conversations reserve a project slot before async initialization; history opens and forked branch commits count toward in-flight reservations. A failed subagent initialization cleans up registered sessions, runtime, terminals and temporary directories, and reclaims the empty worktree it created.
- ClientStateStore shared settings merge as per-field patches and publish a version event only after a successful save; SettingsService subscribes and applies runtime changes serially, reads frozen snapshots, and unsubscribes on destroy. ComposerDraftsStore shares state per file so clients do not overwrite the whole table. Both coordinate in-process only; they do not support multiple independent service processes writing the same data-dir.
- Settings state push, resource discovery and runtime reload are separate: `SettingsService.push()` only reads saved config and the current session's in-memory catalog, so creating/switching conversations does not scan disk, clean config or trigger a reload; opening settings (`get_settings`) goes through `refreshSettings()` → `refreshResources()` to explicitly scan skills and clean stale preferences, updating only the catalog without auto-applying to the runtime. Only settings changes and `reload_extensions` go through `applyRuntime()`, deferred while streaming; the resource catalog refreshes when the reload finishes. Externally installed/removed skills surface after settings are reopened, runtime state updates through an explicit reload, and the catalog cache is isolated per project cwd.
- Atomic writes may only replace a temp file in the same directory; a failed rename is retried a bounded number of times and then reported, and falling back to truncating the original file is forbidden. Settings/draft save failures must be reported; memory and disk must not pretend to succeed together.
- History windows carry historyGeneration; a history rewrite or cache rebuild invalidates old pagination requests, a missing/misplaced anchor returns resyncRequired, and the client requests a full sync. Repeated full snapshots keep the window determined by the character budget, and only paging forward extends it. Old socket callbacks must verify identity before cleaning up the shared terminal bridge.

## Command, search, and recovery state

- The WS handshake is limited to 15 seconds and handshake messages to 16KiB; ordinary control messages to 1MiB, and attachment messages follow the upload budget. The attach queue holds at most 256 entries totalling at most 8MiB; exceeding it closes the connection instead of silently dropping queued operations. `server/payload-limits.ts` is the single source for the limits.
- Settings saves validate and write to disk first, and only then update the runtime password. Scheduled-task config persists before publishing memory and notifications; a failed run-record write reports an error but still advances the in-memory trigger time to avoid duplicate execution. External side effects are not guaranteed exactly-once across processes.
- History search and list display limits are separate: search scans all candidates; the transcript is read as a stream with bounded concurrency, matches and anchors are found in a single scan, and a 256K body cache does not decide hits. A new query cancels the old one, and stale results are not published after switching projects. A single extremely large ordinary text record still needs single-record memory.
- Compaction recovery state is written by the host to `<sessionFile>.compaction-state.json`; the completion event enters the transcript only via the SDK's `appendCustomEntry`, and directly rewriting a running SDK session file is forbidden. All recovery entry points consume the interruption state, and with no receiver the notification enters the pending queue; repair of corrupted old transcripts is kept.
- `terminal_output.reset` means history replacement; live output keeps appending. Flush merged live output before replay; the display terminal supports reset and the SCM parser skips history-replacement frames.
- The plugin HTTP proxy propagates an early downstream close upstream; an upstream truncation terminates downstream, and a complete response completes normally.

## Message actions

Message action bar hints should appear on hover and use short action names. The primary copy button copies Markdown, with a dropdown for other formats. Re-asking removes the original question and everything after it in the current conversation via `edit_message`, then resends the question and attachments verbatim; edit-then-reask opens the editor first and submits through the same path. Fork uses `fork_session { position: "at" }` to keep the selected message and the context before it, creating a new conversation without auto-sending. The rewind button opens the editor on the current question (for an assistant message it targets the corresponding user question) and re-asks in the current conversation on submit; cancelling the edit leaves history untouched. Message rewind editing and optional workspace file restore are independent operations.

pi's `schedule` persists the creation origin separately when it creates a task (stable SDK session file + tool call ID) and does not rebind it when the delivery target changes. `edit_message` only revokes tasks created in the discarded suffix of the current branch that have not started yet (including recurring and canvas tasks); it writes the schedule store atomically first, then commits the re-ask branch marker synchronously. A failed schedule write keeps the original history and stops the re-ask; a failed branch commit restores the original leaf and tasks, and reports an explicit error if the restore also fails. `startedAt` is persisted before execution starts and only keeps re-ask from revoking external operations already attempted; it provides no cross-process exactly-once semantics. Plain forks, side branches, other conversations, already-started tasks and old tasks without an origin are all preserved; engines that do not wire the built-in schedule and direct checkpoint rollback are outside this cleanup path.

## Snapshot-driven

- **The server is the only source of truth**: after every SDK event, throttle 60ms then push a snapshot (`UiState`); the browser renders from snapshots only. Reconnecting only needs to resend `get_state`.
- **Incremental snapshots (protocol v2)**: persisted message content is immutable + object references are stable, so `emitSnapshotNow` detects append-only growth with an O(n) pointer-identity walk — if it can append it sends `snapshot_delta` (light fields + the `appended` tail, baseRev chain); mid-stream changes/truncation/conversation switch/forced resync fall back to a full `snapshot`. The frontend reducer merges along the rev chain and a gap triggers a debounced `get_state`; under backpressure delta and snapshot are equally droppable, and loss self-heals through a broken rev chain. `get_state` always returns the full snapshot. Regression: `snapshot-delta-test`. **Test adaptation**: tests waiting for "the snapshot after an action" must also accept snapshot_delta (follow the rev-chain merge style in conv-cwd/vision-bridge); the first snapshot after connecting is always full.
- **WS permessage-deflate**: WebSocketServer enables compression (threshold 16KB), cutting multi-MB snapshots for large sessions several-fold on the wire; small messages (notice/heartbeat) are not compressed, saving CPU.
- **Multi-tab serialization sharing**: emit sends the same message object to every socket of a client, and index.ts caches stringify results per object identity in a WeakMap — N tabs share one serialization, and a new snapshot is a new object that invalidates automatically.
- **Stable object references when serializing**: `uiMessageCache` + message-array signature comparison mean the array is not rebuilt when messages are unchanged, letting the frontend's `React.memo` skip a whole message — **do not** break this cache (stable ids, reference reuse).
- `UiState` carries `thinkingLevel` (currently in effect) and `availableThinkingLevels` (the levels the current model actually supports; the SDK silently clamps requests outside the set to the nearest — the UI may only enable these, otherwise clicking "low/medium" looks like it "won't change").

### `message_delta` live incremental channel

`message_update` events → push `message_delta` only for the **active conversation** (`conversationId` + a per-conversation monotonic `seq` + `messageId = stream-<ts>` (matching `serializeStreamingMessage`'s stable id) + live usage + thinking/text delta with `partial` stripped). It **does not go through the snapshot channel** — `send()` backpressure only drops snapshots, so increments always arrive and large sessions no longer stall on backpressure. The frontend's `applyMessageDelta` (`web/src/message-delta.ts`, a pure function, immutable — StrictMode double-invoking the reducer would double an in-place mutation) patches `streamingMessage` + `stats.tokens`; a seq gap triggers a debounced `get_state` resync; snapshots converge as the authority.

Also: while deltas are active (an increment within 1.5s) snapshots degrade to **event-driven checkpoints** — agent_end / tool_execution_end flush immediately, other events go through a 2s fallback timer (increments provide smoothness, snapshots only calibrate boundaries). Unit test: `tests/unit/message-delta.test.ts`.

### `tool_delta` same protocol

It also carries `conversationId` + `seq` and shares the same per-conversation monotonic sequence as message_delta (`conv.deltaSeq`); the frontend tracks seq in a per-conversation Map, and only a gap in the active conversation triggers resync (background conversations converge via snapshot when switched back).

### File claim run lifecycle

Claims in `server/claim-store.ts` cover exactly one actual run: on normal completion, final error, user stop or forced reset, `ClientSession` releases all claims for the conversation ID immediately, with no need to close or remove the conversation. The SDK's `agent_end` may fire before retries, compaction or extension continuations finish, so claims are kept while not yet idle and released at `agent_settled`; engines that are already idle may release at `agent_end`. The `finally` of prompt delivery errors and the forced-reset path also clean up. Cleanup on conversation close and the default 30-minute TTL act as a safety net; a new run must claim again.

### Protocol version negotiation

`hello` may carry `protocolVersion`, and `ready` returns the server version; on mismatch the frontend shows a persistent refresh banner (protection against "new UI / old WS" running mixed after an in-place app update). The constant lives in both server/ and web/ protocol-version.ts, and `check:protocol` verifies they match — bump in step when changing the protocol.

### On-demand history messages (server-side windowing, `server/message-window.ts`)

Frontend "scroll-up paging" only achieved **not rendering**: all the data still arrived. Measured, a 287-message / 17MB transcript serialized to a 4MB snapshot, so opening a conversation waited for the whole transfer plus parse. So move the window to the server:

- **Mount point**: the single send funnel per connection (`send` in `server/index.ts` wrapped in a `MessageWindowTap`). All five engines (pi / DSH / claude / codex / durable) go through this funnel, so engine changes are **zero** and behavior is uniform; future engines inherit it automatically.
- **Trimming**: `snapshot`'s `state.messages` is trimmed to a tail window and backfilled with `historyStart` (the window's first message index in the full list) / `historyTotal`; the count limit is `PI_WEB_HISTORY_WINDOW` (default 300) plus a **character budget** of 1.5M characters (screenshots/tool output shrink the window further; measured, the same session went 4.00MB → 1.28MB). `snapshot_delta` only merges newly appended messages into the cache and backfills the two counters.
- **Paging**: `load_earlier_messages {count|all}` → the server replies `earlier_messages` (the newly added earlier slice, **prepended** by the client). The window start is **monotonically non-increasing**: pages the client already paged in are not pushed back by later full snapshots (reconnect / `get_state`).
- **Never touch `rev`/`baseRev`**: each engine's incremental semantics differ, and rewriting version numbers would break their self-healing chains; paging only backfills earlier content and has nothing to do with rev.
- **Frontend support** (`web/src/components/MessageList.tsx`): `hasEarlier` = locally undisplayed + `historyStart`; when the wheel nears the top or "Load earlier" is clicked, expand locally if that suffices, otherwise ask the server for one page; opening in-page search or "Expand all" requests `all: true` in one go so the full text is searchable.
- **Compatibility**: both fields are optional (absent = full snapshot). An old frontend against a new server just loses a chunk of history with no way to page, so `PROTOCOL_VERSION` is bumped to 34 to trigger the refresh banner.
- **Regression**: `tests/unit/message-window.test.ts` (window start / budget / paging pure logic) + `tests/message-window-test.mjs` (WS message level: first-frame window, seamless paging, `get_state` not regressing, `all` returning an empty page at the end).

## Protocol single source (`types.ts` is a re-export shim, no more manual sync)

`server/protocol.ts` is the only source of truth; `web/src/types.ts` re-exports everything with `export type * from "../../server/protocol"` (pure types, erased at build time), and frontend-local types (FileContent/FileListing/ToolStatus) sit below the shim.

To add/modify any message: change `protocol.ts` only, then add one branch to the `dispatch` switch in `server/index.ts` and one to the `onmessage` switch in `web/src/use-chat.ts`. Note that protocol.ts must stay **pure type exports** (no const/function or other runtime code, which would break the type-only premise); `npm run check:protocol` guards these two invariants.

## Conversation messaging and task completion

Collaboration messages are sent only for decisions, blockers, interface changes or deliveries; ordinary progress folds into a phase report. The body should state the change, the recipient's action and where the details are. When the same sender sends a byte-identical body to the same recipient, the message ID is reused while the inbox has not consumed it, avoiding duplicate delivery and wakes; sending again is allowed after consumption. When injecting into the model, concise text keeps the source address, the full body and the permission boundaries of collaboration data while dropping internal routing JSON and redundant IDs; structured requests keep requestId, the full question and the reply method, and the inbox protocol stays unchanged.

`communicate` unifies `send/request/reply/escalate/read` for execution conversations in the same project; targets support `parent`, `root` and a stable conversation ID. An independent coordinator keeps its inbox and Q&A relations on the Conversation object identity, and a takeover does not rebuild the identity. `read` returns both the reachable conversation catalog and stable execution identity addresses, and a conversation with the same name in another view should be addressed by that address; the source endpoint must ride through delivery, and the sender must not be re-inferred from the recipient's local ID. The communication project is resolved along the parent-child conversation chain registered on the server: a subagent inheriting in an independent cwd/clone still resolves an ancestor project that remains reachable, managed worktrees map to the main repository; unrelated independent clones do not interoperate merely because the repository matches, and an unreachable ancestor falls back to the directory of the last resolvable conversation. Project identity is normalized through `normalizePathKey`. Messages are collaborative data with provenance and grant no execution permission; the host still validates sandbox and Bot boundaries against the execution conversation, and a parent-child relation exempts nothing. Read-only subagents may communicate; plan/delegation-review/goal-review modes refuse to dispatch work through this tool.

`send` returns a delivered or queued status without waiting for the recipient to process the task; `read` pages through and consumes its own inbox, and messages are kept during a circuit breaker. `request` waits for an answer, and the server limits message bytes, queue size and request count and rejects request cycles; the parameters only accept a plain-text `message` (`questionsFromMessage()` folds it into a single internal question), while structured `questions` are still accepted. `reply` is allowed only for the original recipient conversation, `message` is expanded into a `custom` answer per open question, and the old `answers` shape is still accepted; `escalate` hands the same PendingQuestion to the user and keeps the original deadline. `wait_all` returns early for requests waiting on the current conversation. Old `handoff/consult/answer/escalate` are compatibility entry points forwarded to the messaging service; historically hanging questionnaires remain settleable.

Task completion is registered through `conversation(action="complete", summary, evidence)`, separate from sending messages; the rules for reconciling evidence against the transcript are in the next section. `spawn.notifyOnDone` keeps boolean compatibility and also accepts `"manual"`. A manual turn that exits while running descendants, questionnaires, communications or undelivered subagent results remain keeps taskPending; early notification, consuming results and settling worktrees are forbidden. Completion registration cannot bypass these conditions. Once all dependencies settle, use the explicit summary; without registration the final body is the fallback. Errors and cancellations still notify, and an automatic wake does not clear a manual completion intent. Manual mode and the communication host currently require the pi engine; Universal explicitly rejects the unsupported manual mode.

## Subagent completion evidence, settlement edges and dispatch budget

A subagent saying "done" is not evidence. Besides `summary`, `conversation(action="complete")` requires `evidence`: `{files:[], commands:[]}` (files changed, verification commands run), `{none:true}` (read-only task, declaring no file changes) or `{blocked:"reason"}` (cannot finish — say so). Normalization lives only in `server/subagent-evidence.ts`: paths normalized with `/`, commands with whitespace collapsed, deduplicated and capped (50 files / 20 commands / 400 characters per entry); an empty object is invalid.

Reconciliation does not accept self-reports: `collectTranscriptFacts()` extracts **files actually changed** (path/file_path/paths/files of write-class tool calls, reusing `SUBAGENT_WRITE_TOOL_NAMES` from `subagent-security-gate.ts`) and **commands actually run** (the command of bash/powershell calls, command+exitCode of `bashExecution`, `toolResult.isError` falling back to failure) from the subagent's own transcript. Only falsifiable conflicts are rejected: a claimed command missing from the transcript / that command failing in the transcript / claiming `none` while the transcript shows writes; changed-but-undeclared files and claimed-but-unfindable files are recorded as doubts and downgraded to `partial` (`sed`/`mv` inside bash also change files, so this cannot be a veto). On rejection `complete` throws and lists the contradictions to the subagent so it fixes them before registering; on success the evidence is stored in `conv.subagentEvidence` and the verdict `pass / partial / unverified / blocked` is surfaced together with `wait_all`, `get_result`, `list` and the completion notification (`subagent-notify.ts`); the same verdict reaches the left panel via `ConversationSummary.subagentVerdict`, where `unverified / partial / blocked` show an evidence badge (`pass` takes no slot) — never let "unverified" look like "verified". Missing evidence does not block settlement, but the status must show `unverified` so the parent can decide whether to re-check — better explicitly unverified than falsely successful.

`wait_all` no longer polls. `SubagentSettleRegistry` in `server/subagent-settle.ts` only provides **edges**: a run-id change wakes subscribers, and the waiter recomputes on wake whether settlement really happened (and re-scans newly spawned descendants and undelivered requests). `agent-service` calls `notify/notifyAll` on turn end, stop, dismissal, questionnaire queue change and completion-notification delivery status change, and `shutdown` on `dispose`. A single wait slice is 30s, and the overall wait cap is still decided by the watchdog cap; the universal engine (`universal-session.ts`) implements the same interface with its own subagent listeners, with identical semantics. There is exactly one rule for "settled": no snapshot available (dismissed/collected) or an explicit terminal state; waits and "who's left" share `isSettled`, avoiding "everything finished yet it still reports a runner".

One call can fan out: `spawn`'s `tasks[]` dispatches several at once, validating the whole batch first (prompt, key shape and uniqueness, template availability, thinking level, isolation mode) and starting none if one is invalid; a batch is capped at `SUBAGENT_FANOUT_MAX = 16` with a startup concurrency window of 4 (not competing with the concurrency limit). Each task may carry `key` (alphanumerics plus `_.-`, ≤40), and the tool records `key → run identity` in a bounded table (256 entries) **on this conversation's tool instance**; `runIds` of `wait_all / get_result / steer / stop` accept either key or real id. The `steer` acknowledgement distinguishes `delivered` (fed into the current turn) / `queued` (queued for after the turn) / `restarted` (was idle, a new run in the same session) / `missed` (no delivery channel), so the parent does not have to guess.

Concurrency and depth do not stop cumulative cost, so a third gate was added: `server/subagent-budget.ts` accumulates dispatch counts per **run tree root** (walking `parent` up to the topmost conversation's stable execution identity), default 64 (`PI_WEB_SUBAGENT_MAX_SPAWNS_PER_RUN`, `0` disables). The reservation happens synchronously on the start path, is refunded on failure, and is forgotten with `forget` when the run tree root is dismissed. Subagent usage (`getSessionStats().tokens`) enters the snapshot's `usage` and is shown in lists and wait results as `input↓output↑`, so cost is read together with the context soft cap.

## Run ledger and restart continuation

A subagent's work must not vanish on restart. `server/subagent-ledger.ts` writes each dispatch to `<dataDir>/subagent-runs/<runId>/`:

```
status.json     machine-readable current status (atomic replace, last writer wins)
events.jsonl    append-only lifecycle stream (byte-capped, only a marker left after truncation)
```

Write discipline: all writes go into a **serial queue** per run and callers are always fire-and-forget; `status.json` uses `writeAtomic` and events use `appendFile`; any IO failure only records `lastError()`, and a ledger problem never interrupts dispatch or turn end (`flush()` on `dispose`). Bounded: run directories default 200 (`PI_WEB_SUBAGENT_LEDGER_MAX_RUNS`, `0` disables the whole ledger), 256KB of events per run, `prompt` 8KB, `outputTail` 4KB and 5 entries of each evidence kind. Eviction only picks finished runs and waits for that run's write queue to drain before deleting the directory — otherwise a queued `mkdir` would recreate it.

Restart reconciliation trusts only `bootId`: every record carries this process's random identity, and `recover()` marks `running` left by **another boot** as `interrupted` while leaving this process's live runs untouched; repeated calls are idempotent. `ClientSession.create()` calls it once fire-and-forget, and on a hit pushes a notice (listing the first 5 titles and ids) telling user/model they can `get_result` for evidence already produced or `resume` to continue. **Main conversation restart recovery is separate from subagents**: `streamingSummaries()` (the daemon's record of "was streaming at restart") skips subagents and persistent child sessions, so a child is not reopened as an ordinary tab and lose its parent-child relation.

The runtime syncs the ledger at each settlement point: dispatch records `running`; turn end, completion registration (with evidence), stop, dismissal, `steer` restarting a run and worktree finalization each `upsert` + `event` (`spawned / turn_end / completion_requested / stopped / dismissed / steer_restart / worktree_finalized`). Read side: `conversation(action="list")` appends ledger rows after live runs (skipping dismissed ones and those still in memory), and `get_result` falls back to the ledger when memory has no match, returning status, evidence, error, worktree, `sessionFile` and the output tail.

`conversation(action="resume", runId, message?)` must be honest: in-process subagent sessions are not persisted, so **the original transcript cannot be reattached**, and resuming is "re-dispatch with known progress" (`mode: "relaunch"`) — `buildResumePrompt()` assembles the prompt from the original task + the output tail before interruption + ledger evidence + the retained worktree + the old transcript path, and demands "don't redo what's done, keep existing conclusions, settle by evidence". When the worktree is still retained it re-dispatches with it as `cwd` (reusing uncommitted changes, not creating a new worktree); a subagent transcript with `persist=true` remains viewable in history. `resumedBy` marks the new run, and repeated resumes are rejected outright; a run still executing in the process is also rejected (do `wait_all`/`get_result` first).

Verification: `tests/unit/subagent-ledger.test.ts` (write/restart read-back/bootId reconciliation/event truncation/eviction/disable/resume relations/prompt), `tests/unit/subagent-ledger-tool.test.ts` (list appending/get_result fallback/resume success and four failure kinds/degradation for engines without a ledger).

## Questionnaire queue and parent requests

The shared `QuestionDialog` keeps single-select behavior: selecting a new option immediately advances to the next question; clicking the selected option again cancels and stays on the current question, consistently for mouse and number keys. The last question waits for the submit button or Enter by default; the questionnaire footer can enable "auto-submit after selecting on the last question", with the preference stored in the current browser, applying to single-question questionnaires too. Switching the preference and restoring a draft do not trigger submission; after cancelling a selection, submitting only the supplementary note is allowed, and hidden conditional questions submit no answer.

The standard pi engine pushes the current project's full pending queue via `question_queue`; each request keeps a stable ID, source conversation, top-level conversation, holder, creation time and optional deadline. The top-level entry, the source conversation and cross-view answers reference the same request, answers settle against the current holder, and takeover preserves request identity and deadline. The snapshot's `pendingQuestion` and the immediate `question_pending` are kept for other engines' compatibility; the frontend merges them at the queue entry and shows one questionnaire. The sidebar question mark, questionnaire notifications, cross-view summaries and the "waiting for user" state share the server's effective user questionnaire query, which only includes requests with `audience="user"` that are not yet settled; inter-agent `request/consult` must not trigger these hints before escalating to the user, and answered, cancelled or timed-out requests drop out immediately.

`questionPresentation` controls the current conversation popping up while queueing others (default `queue`), all popping up automatically (`all`) or a manual queue only (`manual`). Tool approvals use `toolApprovalPresentation` independently with the same three modes, defaulting to `all` so approvals from all conversations pop up automatically in sequence; the setting only controls reminders and does not change approval switches, rules or approve/deny results. Answering later keeps the questionnaire and draft, cancelling is explicit, and source jumps open the corresponding conversation. Questionnaires outside the current project must not enter the queue.

Subagents use `conversation(action="consult")` to ask the immediate parent conversation; the parent answers with `answer` or hands it to the user with `escalate`. `ask_user_question` always waits for the user, and the parent must not answer on its behalf. When `wait_all` hits a request not yet delivered to the current parent it returns `needs_input` early, and the same request does not wake repeatedly. If the parent cannot handle it, it escalates to the user, and the existing auto-wake budget keeps applying.

`questionTimeoutSeconds` defaults to 240 seconds for new subagent questionnaires and requests, `0` means no limit; the main conversation keeps its original wait strategy. The server owns deadlines and cancellation, a timeout returns an explicit result and never auto-adopts the recommended option. Escalation does not reset the deadline, and the browser countdown does not trigger cancellation. A finished questionnaire does not mean the execution session ends, and it does not free a concurrency slot early.

## Global runtime state (app-globals.ts: no prop drilling)

`web/src/app-globals.ts` is a module-level singleton store holding the few runtime values **the whole tree needs to know**: server identity/capabilities (changes once per connection) + connection state and current working directory (low-frequency changes, isolated through single-field subscriptions):

| Field                                                | Source                                                      | Consumers                                                                                                                                                 |
| ---------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `engine` (`"pi"` / `"dsh"`)                          | `ready.engine` (old servers omit it → falls back to `"pi"`) | The FooterBar engine icon; DSH gating in GoalBar/SettingsModal/ChatInput (no review model / no plugin marketplace / no mid-run steering)                  |
| `managed` (`PI_WEB_MANAGED=1`)                       | `ready.managed`                                             | TopBar update entry, PiSetupModal install guidance, SettingsModal plugin marketplace                                                                      |
| `tabs` (`PI_WEB_TABS`)                               | `ready.tabs`                                                | Top bar view tab allowlist (undefined = all)                                                                                                              |
| `service` (which platform hosts the service)         | `ready.service` (detected by `server/launch-origin.ts`)     | The "Restart service" button in the TopBar update panel (absent = foreground/dev/Docker → no button drawn, and the server also rejects `restart_service`) |
| `appVersion` / `serverVersion`                       | `ready`                                                     | TopBar version number                                                                                                                                     |
| `status` / `ready`                                   | useChat's reducer (`status` action / hello+snapshot)        | Left panel (whether it can fetch lists), ChatInput (whether the box is usable), TopBar / FooterBar connection dot                                         |
| `cwd` (the current conversation's working directory) | `chat.state?.cwd`                                           | Left panel grouping and the "current" marker, right panel path building, global search's current project marker, bottom bar directory picker              |

There are two write points, both single-sourced and mirroring rather than copying: `use-chat.ts` writes identity/capabilities when `ready` arrives (**synchronously before dispatch**, so not a single frame of `pi` flickers); another effect mirrors `ready` / `status` / `cwd` (the values are the reducer's real values, at most one frame late — the corresponding defaults can only be "not ready / disconnected / empty directory", which is invisible). Non-React code uses `getAppGlobals()` / `subscribeAppGlobals()`.

**Read rules**: components with narrow props (`LeftPanel` / `RightPanel` / `ChatInput` / `GlobalSearchModal`) always read from the global store and no longer take a prop; components that already consume the whole `ChatState` (`App` / `TopBar` / `FooterBar`) read `chat.*` directly (they own the data, so there is no point in a detour). Both sides come from the same reducer and cannot disagree.

**Subscription granularity**: use `useAppField("cwd")` when only one field is needed (getSnapshot picks one field and compares with `Object.is`) — `useAppGlobals()` re-renders subscribers on any field change, so use it only when the whole object is genuinely required. `cwd` relies on this isolation: a project switch notification only reaches components that actually read cwd, and does not drag along components that only read `engine`.

### Global action: `appSend`

The sender lives here too (lower half): `use-chat` wires `setAppSend(send)`, and anything else can `import { appSend }` and call it — its reference is stable, it does not enter state and does not trigger re-renders, so no hook is needed. `web/src/App.tsx` therefore no longer has `send={send}` prop drilling: the composer, dialogs, panels, plugin views, terminal and SCM all fetch it themselves.

Two exceptions (deliberate):

- The prop on `LeftPanel` / `RightPanel` is called **`panelSend`** — it takes App's wrapper function (whose side effect also closes the mobile drawer); the semantics differ, so it cannot be replaced by the global sender.
- **Wiring must happen during render** (`setAppSend(send)` sits right after the `useCallback`, not in a `useEffect`): child effects run before the parent's, so wiring in an effect would let dialogs that "fire a request on mount" (PiSetupModal / ModelConfigModal / TerminalPanel) call `appSend` while it is still empty and silently drop the message. `send` is a stable `useCallback([])` reference, so assigning again has no side effects. When unwired/disconnected, `appSend` returns `false` (matching `send`'s existing semantics).

**Two rules (otherwise you introduce hard-to-find rendering bugs)**:

1. **Only fields that rarely change**. Data from the snapshot stream such as `messages` / `state` / `settings` / `streaming` must **never** go in here: `memo()` components like `ChatInput` / `GoalBar` avoid streaming re-renders through "narrow props + stable references", and store notifications **bypass `memo()`** to re-render subscribers directly — one misplaced field means the composer re-renders on every token.
2. **The snapshot reference must be stable**: `getSnapshot()` returns the module-level `cached`, and only `setAppGlobals` replaces the object and notifies when a field actually changed (arrays compared element-wise, silently returning when field values are equal) — otherwise `useSyncExternalStore` decides "the snapshot changes every time" and re-renders forever. Replaying `ready` on reconnect relies on this to avoid a pointless refresh.

Regression: `tests/unit/app-globals.test.ts` (merge semantics / no notify on equal values / unsubscribe / fallback) and `tests/unit/question-dialog.test.ts` (the component test injects via `setAppSend` + records emitted messages).

The translation template only does literal substitution for `{{input}}` and `{{targetLanguage}}`, so dollar signs or template-looking text in the selection is not interpolated twice. The result card header can temporarily change the target language and re-request without changing the saved default. Every explanation or translation starts from a new topic, cancels the unfinished reference snapshot, and does not carry the previous window Q&A into the new selection. On request failure, network-level errors (`Failed to fetch`) are uniformly converted into a readable message instead of throwing the browser's raw error at the user.
- The attachments button at the bottom of the window supports uploading text / images, picking a local folder and explicitly referencing the current conversation. The context menu for conversations, files, folders and body file paths offers "Reference to Quick Ask"; built-in entries reuse the hidden/order of `contextmenu.session` / `contextmenu.file`, and the reference entry can be disabled. On right-click the target ID, owner, sessionFile or path/cwd are frozen and `active` is not re-read during async work. References show as removable chips, collapsing beyond two; adding a reference does not trigger a question and does not change the main conversation draft.
- `POST /api/quick-ask/context` accepts `{source, scope?, clientId?}`: the source may be a file, a directory, an explicit conversation, or an upload `{kind:"upload", name, data:base64, mimeType?}`. It returns `{attachment}` as a text / image snapshot; only user and assistant bodies are extracted, excluding system, tool, preset or main-session prompts, and reading does not switch sessions. A conversation defaults to the latest 10 messages with an optional full conversation; a directory defaults to a listing with an optional listing plus text, limited to depth 2 and 100 entries and skipping symlinks. Source IDs are generated stably from the canonical source and duplicate references are deduplicated; uploads get an ID from name and content. Context reads support cancellation and a 15-second timeout; a remote SSH workspace currently returns an explicit unsupported error.
- `POST /api/quick-ask` accepts the window's own `messages: [{role: "user" | "assistant", content: string, attachments?: QuickAskAttachment[]}]` and an optional `fallbackModel: "provider/id"`. Attachments may only hang off user turns; a snapshot is sent on first use or when content changes, and unchanged references on follow-ups do not consume the budget again. Old turn snapshots stay unchanged, and removing a pending reference chip does not rewrite old turns. Each topic holds at most 8 attachments, 32,768 characters of text each and 65,536 characters of total text including source boundaries; a single file / image is 2 MiB and images total 6 MiB. File encoding and image magic numbers are validated server-side, and unknown binaries, images the model does not support or over-limit inputs report explicit errors.
- This is a narrow exception to the main session's path-only attachment rule: Quick Ask creates no AgentSession and has no file-reading tool, so it only reads limited snapshots for references the user explicitly added, and hands them to a standalone ModelRuntime as untrusted reference text / image blocks inside the corresponding user message; it never promotes them to system and never scans or attaches the current main conversation automatically.
- `/api/quick-ask` returns `{text, model}` by default; the client requests real streaming with `Accept: application/x-ndjson`, and the event single source is `QuickAskStreamEvent` in `server/protocol.ts`: `start` provides the model, `delta` appends text, `done` provides the authoritative final text, `error` terminates the stream and reports the error. The response carries `no-transform` and `X-Accel-Buffering: no` to prevent compression or proxy caching of increments. The client decodes UTF-8 incrementally and treats a missing terminal event as failure; mid-stream errors keep earlier fragments. The server reads the system prompt and model parameters only from the standalone settings, calls ModelRuntime's streaming interface directly, creates no AgentSession, and never implicitly reads main conversation history, presets, project prompts or tools. Because it bypasses the host session, `sessionId` must be supplied by the caller (`modelSessionId()` in `server/model-session.ts`: pass the first user message as the seed for one topic so routing and caching stay the same across turns; one-off calls pass no seed), otherwise the opencode / opencode-go gateway answers 400 `MissingSessionID` when the `x-opencode-session` header is absent. Client cancel and timeout both abort the request, including a timeout after response headers were already sent; a cancelled old response must not write into a new topic.
- `GET /api/quick-ask/models` returns `{models: [{provider, id, label}]}` from the same standalone model runtime, so the window's settings can pick a model under every main engine without relying on Pi's proprietary subagent model list. Model catalog requests also support cancellation and timeout.
- When no reference is explicitly added, the main conversation only provides the default model ID. The selected-text entry sends a text snapshot through the `openQuickAsk` event, interpolates it with the standalone explanation template and uses it as the first user message, carrying no message ID, tool result metadata or main-session prompts.

## Security boundaries

- **Bind to loopback only by default** (`PI_WEB_HOST`, default `127.0.0.1`): a local personal tool is not exposed to the network; LAN/containers need an explicit `PI_WEB_HOST=0.0.0.0` (already built into docker-compose.yml — only then does the Docker port mapping work).
- **WS upgrade performs same-authority Origin/Host validation** (`originAllowed` in `server/index.ts`, `WebSocketServer({ noServer: true })` + manual `handleUpgrade`): when Origin is present its hostname + **effective port** must match the request Host (`example-host:8445` and `example-host:9443` are different origins in a browser); non-browser clients (no Origin) are allowed; `PI_WEB_ALLOW_ORIGINS` allowlist bypasses (dev:server already ships `http://localhost:5173,http://127.0.0.1:5173`, configure your own for reverse proxies); `PI_WEB_ALLOW_HOSTS` optionally provides a strict hostname allowlist. **Do not** add back "allow any local port" — that is exactly the hole the proposal was meant to fix.
- **quiesce admission control** (`AgentService.quiesce/unquiesce`): once draining starts **all new work is rejected** — new prompt (native slash commands excepted, pure config without tokens), new_chat, edit_message fork, switch_session, goal wizard; existing runs finish. Known clientIds may still attach to watch existing work (with a notice), while **a brand-new client attaching throws `QuiesceRejectedError` → index.ts closes the WS with 4403**, and the browser's reconnect loop recovers automatically after unquiesce.
- **Control socket** (`server/control-socket.ts`): the CLI's `server status|quiesce|unquiesce` talk to the running process over a local mode-0600 unix socket / Windows named pipe (`\\.\pipe\pi-web-ui-<port>`); `status` reports the real socket count (`noteSocketOpen/Close`, maintained by index.ts), active/pending counts and quiesce state; there is no unauthenticated HTTP endpoint.
- **Provider headers never go to the browser** (`models_config` no longer carries a `headers` field, which may contain Authorization/API key): `saveModelConfig` keeps the old value (`prevHeaders`) when the saved config has no headers. `UiProviderConfig.headers` is deleted from protocol.ts / types.ts, the frontend edits headers nowhere (only apiKey goes through the separate `set_provider_api_key` message from the browser).
- **Multi-key built-in providers (no model list copy + name-only communication)**: a built-in provider (e.g. opencode/openai) may hold **multiple API keys** at once in `<agentDir>/provider-keys.json` (`{ <providerId>: { activeKeyName, keys:[{name,apiKey}] } }`), and **the model catalog always reuses that provider's default system catalog**, never copying it into models.json (`clone_provider` is kept only for programmatic/test paths, the UI has moved to multi-key management). **Security**: the frontend **only ever receives the key's** name (`ProviderKeyInfo={name,active}`), and **raw key values / masked fragments never leave the server** — a key value is uploaded once over WS when added and written to disk (like auth.json); `activate_provider_key`/`remove_provider_key` both **address by name** and the server resolves the stored value. Protocol: `list_provider_keys` / `add_provider_key` (`{provider, apiKey, name?}`, names deduplicated automatically) / `activate_provider_key` / `remove_provider_key`, and the server replies `provider_keys`. **activeKey stays in sync with auth.json + the runtime override** (`applyActiveKey`), and switching a key re-pushes that provider's models via `pushModels`. For multi-key providers the frontend model dropdown **splits the "provider" column into one entry per key** (provider name on top, key name below, e.g. key1/key2 each a row under opencode, never concatenating `opencode-key2name`); **selecting a key entry shows that provider's models once, and clicking a model switches the active key** and then picks the model — no static copy, always current; single-key providers keep one ordinary entry.
- **Built-in provider OAuth login**: `ProviderStatus` also sends `supportsApiKey`, `supportsOAuth`, `oauthName` and `usingOAuth`, so the model management page and first-run setup page show only the auth entry points a provider really supports, with the matching account name. The server's `ProviderOAuthFlowManager` drives the SDK (software development kit) `ModelRuntime.login`, and the browser only receives choices, the verification URL, the device code and progress; access and refresh tokens returned by the SDK never enter the wire protocol. Each flow correlates replies by `flowId + promptId` and is cancellable; the active flow lives in `ClientSession`, and a reconnecting browser restores the current public state via `provider_oauth_flows`. After a successful login the OAuth credential becomes the provider's active auth and each project's saved API key selection is cleared to avoid being overwritten when switching projects; logout uniformly calls the SDK's `logout`.
- **Token reflection protection** (issue #45): in the `PI_WEB_TOKEN` auth middleware `/api/health` stays open for probes, but `Set-Cookie` is only sent when the request really carries a valid token (`tokenOk(req)`) — an anonymous hit on `/api/health` never reflects the real token cookie. Regression: the "health does NOT leak pi_web_token" check in `tests/token-auth-test.mjs`.
- **The logged-out page uses a native form login** (`server/unauthorized-page.ts` + `server/auth-login.ts`, `POST /__pi/auth`): the password form is a **real POST → 303 → GET** with an `autocomplete="username"` account field and an `autocomplete="current-password"` password field — only this makes Chrome/Safari/Firefox offer "save password" after login (the historical implementation was JS `preventDefault()` + a `?token=` redirect, which browsers do not consider a login, so the prompt never appears). The redirect target uniformly goes through `sanitizeNextPath`: only same-origin absolute paths are allowed (`//host`, `\` and control characters are rejected) and the `token`/`__tried_cached_token`/`auth_error` query parameters are stripped; a wrong password 303s back to `?auth_error=1`, and the logged-out page renders "口令不正确" (Incorrect password) accordingly. The old `?token=` / Bearer / X-PI-Token paths are all kept. Regression: `tests/unit/auth-login.test.ts`, `tests/unit/unauthorized-page.test.ts`, `tests/token-auth-test.mjs`.
- **dev compatibility**: when the vite :5173 proxy forwards /ws to :8788, Origin (:5173) ≠ Host (:8788), which relies on `PI_WEB_ALLOW_ORIGINS` (built into dev:server) to be allowed — do not delete it.

## Theme switching

- **Mechanism**: `web/src/styles.css` is the **shared baseline** (default dark theme + global layout, extracted only for reuse convenience, not a constraint on themes); a theme file is a **complete stylesheet** that may override anything (`:root` variables, any selector, layout changes, new tokens of its own — the theme link loads later and wins in the cascade). When selecting a theme the frontend injects `<link id="theme-stylesheet" href="/themes/<id>.css">` (`applyTheme` in `web/src/theme.ts`, localStorage key `pi-web-ui:theme`, applied by `main.tsx` before the first frame to avoid flicker). The only hard requirement: tokens referenced by `var()` must be defined somewhere (a theme defining them counts — see "variables must be defined first" below).
- **Server**: `GET /api/themes` lists themes (`listThemes` in `server/themes.ts`), `GET /themes/:id.css` serves the file (`resolveThemeFile`, user directory takes precedence). The id must match `ID_RE` (`^[A-Za-z0-9_-]+$`) to prevent path traversal. Both routes are registered in `server/index.ts` before the SPA catch-all (otherwise they are swallowed and return index.html). In dev mode Vite needs to proxy `/themes` (`web/vite.config.ts`, already added).
- **Theme sources**: built-in `<pkgRoot>/themes/*.css` (shipped with the npm package, the `package.json` files allowlist includes `themes/`); user customization just drops CSS files into `<dataDir>/themes/` (user overrides built-in on id collision). `pkgRoot` is resolved by `resolvePkgRoot()` walking up to the ancestor containing package.json, which is correct for both dev(server/) and prod(dist/server/).
- **Light themes**: `themes/white.css` (display name "白色" (White): pure white base + GitHub blue accent), `themes/paper.css` (display name "暖纸" (Warm paper): warm paper beige base + ochre accent, easy on the eyes), `themes/mist.css` (display name "雾蓝灰" (Mist blue-gray): misty blue-gray base + sky blue accent, cool style), `themes/sakura.css` (display name "樱粉" (Sakura pink): pink white base + sakura pink accent, soft style), `themes/md-preview.css` (display name "紫晕" (Purple halo)) + `themes/cyberpunk.css` (cyberpunk) + `themes/dazzle.css` (dazzle) are all generated by the root script `make-light-theme.mjs` from the `:root` variable list in `styles.css` as **pure palette files** (the generator reads styles.css and parses all variable names; a theme overrides only differing values, emitting only `:root` variables that differ from the host defaults plus optional shared-style imports / a non-layout tail: white/paper/mist/sakura carry `.hljs` light highlight overrides, md-preview carries a body gradient + transparent chrome). Variables added to styles.css are inherited automatically; rerun `node make-light-theme.mjs` to update palette-derived values. The identical status bar structure is centralized in `themes/bases/statusbar-flat-base.css`, and the generator keeps the corresponding import so manual patches are not lost on regeneration.
- **Switch state contract**: plugins, settings/MCP/scheduled tasks and Device Center share the switch appearance rules in `styles.css`, and each page keeps only its size and knob offset. Every built-in theme explicitly declares `--switch-bg-off`, `--switch-border-off`, `--switch-knob`, `--switch-bg-on`, `--switch-border-on`, `--switch-knob-on`; the on-state knob picks dark/light from the background color, and pages must not use the accent color or hardcode white. The generator always emits these six (even when equal to the defaults); `switch-theme.test.ts` checks that the knob contrast in both states is ≥3:1 for every theme.
- **Theme display name**: the CSS first line `/* theme-name: 中文名 */` is the display name in the dropdown (`listThemes` parses the first 300 bytes of the file); when absent it falls back to the file id — the file name must be ASCII (id validation `ID_RE`), so Chinese relies on this marker. An optional second line `/* theme-name-en: English Name */` is used by the English UI, falling back to the Chinese name when absent; both lines are generated by `make-light-theme.mjs`, so hand-editing a theme header is overwritten on the next run — change the generator to change the English name.
- **Panel collapse/expand button contrast (issue #100)**: `.panel-collapse-btn` at rest already has a background + border (the same level as the narrow-screen top bar's `.panel-toggle`), with fg/bg/border going through dedicated `--control-fg/--control-bg/--control-border` (defaulting to the secondary text color rather than `--text-faint`), and the expand rail `.panel-rail` widened to 26px with a "pill" backdrop behind the icon — so it is no longer invisible under light/custom themes. Themes can override these three variables independently; the light defaults live in the generator's `LIGHT_DERIVED`.
- **Chat background image/wallpaper (issue #100)**: `--bg-image: none` (themes may set `url(...)` to ship one) + `--bg-image-dim` (opacity of the `--bg` darkening, default 0.78) + `--bg-image-blur`. With `body.has-wallpaper` the body lays two full-screen fixed wallpaper layers: `body::before` paints the image (cover centered + blur) / `body::after` darkens; `.app` is lifted to z-index 1 above the wallpaper, and the message area / input area are transparent so the wallpaper shows through. **Container backgrounds win**: the top bar / status bar / left and right panels use independent variables `--topbar-bg`/`--statusbar-bg`/`--panel-bg` (default `color-mix` semi-transparent → the wallpaper shows through from the sides and under the top/bottom bars), and a theme overriding a variable back to a solid color (e.g. `var(--bg-elev)`) turns off the wallpaper for that region, while `transparent` makes it fully see-through; tune the global see-through rate with `--wallpaper-panel-alpha` (default 62%, smaller = more see-through). The same layer has two kinds of component backing: card-level `--card-bg` (tool call cards `.toolcall`, quick chips `.quick-chip`, new conversation prompt template cards `.empty-template`, the expand rail `.panel-rail`, all message bubbles `.thinking`/`.bashblock`/`.skillcard`/`.attachcard`/`.queued-bubble`/`.retry-notice`) and control-level `--chip-bg` (top bar `.chip`/`.tb-tab`/dropdown `.dd-menu`, goalbar collapsed hint `.goalbar-hint`, collapse button `.panel-collapse-btn`, code surfaces `.codeblock pre`/`.termline`/`.toolcall-output pre`, tool argument blocks `.toolcall-args pre`), also semi-transparent by default and sharing `--wallpaper-panel-alpha`, which themes can override back to solid individually; the whole chat panel (`.main`: message area + the stretch used by the goalbar / questionnaire panel + input area) shares `--msgs-bg` (same semi-transparent recipe; bubbles sit slightly more solid on the unified glass surface to create depth, and overriding it to `transparent` restores full transparency). **Paint containers only**: coloring the message area / input area / goalbar / questionnaire panel separately exposes the bare background in the gaps between elements and outside the column — under light and wallpaper themes that is a band across the whole panel one shade off the chat area (especially obvious once a goalbar appears), so the goalbar and questionnaire panel carry no background of their own (only border and shadow); with no wallpaper both layers are `display:none`, and the default semi-transparent background over a solid color differs imperceptibly. The input box `--inputbox-bg` defaults to the same recipe as `--chip-bg` following `--wallpaper-panel-alpha`. Dropdown popovers (sound/language/theme/model/thinking effort `.dd-menu`) use `--menu-bg`: default follows the semi-transparent `--chip-bg`, and the two transparent themes override it back to solid `var(--bg-elev2)` to keep dense lists readable. The terminal view reads `--term-bg` (xterm canvas + container): solid and out of the picture by default (terminal readability first), and semi-transparent themes may override it to a `color-mix` that follows the global see-through. The built-in "translucent" theme (`themes/translucent.css`) is made for wallpapers: `--wallpaper-panel-alpha: 45%` unifies container colors (top bar/status bar/panels/cards/controls/input box all follow) + `--term-bg: color-mix(#0b0d12 45%, transparent)` so the terminal is see-through too + `--bg-image-dim: 0.72`; without a wallpaper it looks darker, which is expected. The "fully transparent" theme (`themes/transparent.css`) is the extreme version: `--wallpaper-panel-alpha: 0%` (every color-mix surface = transparent, including `--term-bg`), leaving only borders and text; text relies on stronger darkening (`--bg-image-dim: 0.85`), and the tail switches solid hover/floating feedback (menu items, collapse summary, expand rail, collapse key, copy key, scroll-to-bottom button) to a uniform 25% translucent background to stay usable, plus one more layer of code-surface noise reduction: `--code-border: transparent` / `--code-pad: 0` (borders and padding of tool argument blocks `.toolcall-args pre`, tool output blocks `.toolcall-output pre` and terminal lines `.termline`) plus hiding the terminal icon duplicated with the card header `.termline-icon`. Code surfaces take borders/padding from `--code-border`/`--code-pad` (defaults `var(--border-soft)`/`8px 10px`), and card body padding from `--card-body-pad` (thinking blocks `.thinking-body` and tool cards `.toolcall-body` share `4px 14px 12px` so both card kinds' text left edges align within one message). A user wallpaper URL lives in browser localStorage (`pi-web-ui:wallpaper`, `web/src/wallpaper.ts`: allowlist http(s)/blob/data:image/site-relative paths, inline variables override the theme, `useWallpaperEffect` applies it at the App root and recomputes on theme switch), and the UI is in Settings → Message display (the address box submits on blur/Enter, the dim/blur sliders preview live; you can also click "Upload image" to pick a local file — it reuses the paste-image pipeline to scale proportionally to ≤1568px + re-encode as a data: URL stored in localStorage, with an inline hint on upload failure/oversize; data: images are not echoed back into the input box, the thumbnail below shows it is active, and the clear button wipes both address and preview).
- **Variables must be defined first (ghost token trap)**: a `var(--x)` referencing a custom property with no `--x:` declaration anywhere in the repo is guaranteed-invalid per spec — the whole declaration is invalid at computed-value time (a `background` without fallback ends up with **no background**; `box-shadow` loses both the shadow and the focus ring; with a fallback the hardcoded value is used silently, which under a light theme is always a dark block). `--bg-elev1` (the correct name is `--bg-elev`) was undefined throughout history yet referenced in 10 places, which is why the goalbar never had a fill. After adding/renaming variables run `tests/unit/css-tokens.test.ts` (static check: scans every `var()` reference in `web/src` + `plugins` + `themes` + `web/index.html`, including ones with fallbacks; runtime-injected variables and deliberate neutral fallbacks are registered in the test's exemption table with a written reason — new exemptions need a reason too).
- **Terminal follows the theme**: the xterm canvas reads `--term-*` variables through `buildTermTheme()` in `web/src/theme.ts`; on theme switch `TermXterm.tsx` listens for `pi-web-ui:theme-change` and hot-updates the canvas with `term.options.theme`; the CSS container `.term-main` / `.term-xterm .xterm-viewport` uses `var(--term-bg)` and blends with the canvas automatically. Rerun `node make-light-theme.mjs` after changing styles.css.
- **Button state contract**: ordinary buttons uniformly use `--button-bg/fg/border`, `--button-hover-bg/fg/border`; solid primary buttons use `--button-primary-bg/fg` and `--button-primary-hover-bg/fg`; danger buttons use `--button-danger-bg/fg` and `--button-danger-hover-bg/fg`. Themes should prefer overriding the paired variables rather than copying component selectors. Primary buttons keep the text/background pairing on hover and signal hover with an outer ring; a whole-element brightness filter that changes text and background together is forbidden. The send/stop hover backgrounds pair with `--on-send-blue-hover` / `--on-stop-red-hover` respectively — do not assume the normal-state foreground stays readable. `node tests/theme-buttons-test.mjs` needs no build and no server and verifies the final cascade and transparent-background compositing of ten button classes in normal/hover states per theme in real Chrome, with a contrast floor of 3:1; without Chrome it SKIPs explicitly, and it is part of the full smoke run.

## CSS layering (`@layer guard, base, theme, drawer;`)

- **Why layer**: `web/src/styles.css` is the shared baseline and themes are complete stylesheets loaded later, so the two compete for weight in the same document. Before the layering refactor the only way to seize weight across files was `!important`: 218 in the baseline and 613 on the theme side (`bases/obsidian-base.css` 220, `bases/zhujian-base.css` 143, `bases/zhupi-base.css` 132, `aetheris.css` 118), and themes could only escalate to beat the baseline — sinking deeper with each change, a textbook arms race. With explicit layers plus an unlayered override zone the baseline keeps just 1 (the mermaid runtime inline style, see below), and the outcome is decided by **layer order**; `!important` is no longer a weapon.
- **Four-layer responsibilities** (declared in exactly one place: `@layer guard, base, theme, drawer;` at the top of `web/src/styles.css`, before all layer blocks, fixing the order):
  - `@layer base`: the whole baseline (`web/src/styles.css` contents). The default layer; write selectors normally, no `!important`.
  - `@layer theme`: theme styles. **The server wraps them uniformly** — `readThemeCss()` in `server/themes.ts` inlines `@import`s and wraps the whole text in `@layer theme { … }` (only the outermost once; recursively inlined files are returned as is, otherwise they become nested layers). `themes/**/*.css` sources therefore **need no** `@layer` of their own and no `!important`: anything written in a theme beats base by nature.
  - `@layer drawer`: the bottom panel and the source control panel (`web/src/drawer.css`, pulled in via `@import … layer(drawer)`). It comes last, so it beats same-name rules in base and **needs no compound-class escalation**; new component layers may only be appended after this position.
  - `@layer guard`: the only survivor is mermaid — it writes font sizes into SVG inline `style` via d3 `.style()`, which no ordinary declaration can beat, so exactly one `!important` lives here (at the end of `styles.css`, with the reason stated). guard is declared first, so with the reversed order its important always wins. Do not move ordinary styles here out of laziness.
- **Unlayered override zone** (end of `styles.css`, after all layer blocks): structural resets that must beat themes or unlayered third-party libraries (highlight.js `github-dark.css`, loaded later in the bundle) live here — the code line reset (unlayered, beating `pre code.hljs` via higher specificity), the collapsed `.goalbar.goalbar-collapsed` skin removal (one unlayered line covers the theme-layer panel skin). **Unlayered ordinary declarations always beat ordinary declarations in any layer**, so no `!important` is needed here. CSS imported per chunk (e.g. `web/src/model-management.css` via `@import … layer(base)`) and plugin styles must also go into a layer and must not run around unlayered.
- **Layer order rules (two opposite directions, the easiest thing to trip on)**: ordinary declarations let the **later** layer win by declaration order (`theme` > `base` > `guard`); `!important` declarations go the **opposite** way — the earlier-declared layer wins (`guard` > `base` > `theme`). That is exactly why the guard layer is valuable: it is declared **first**, so the single mermaid exception placed there beats runtime inline styles; writing `!important` in base/theme only pins yourself down, worse the more you write. Note also: **unlayered styles always beat ordinary declarations in any layer** — which is why the unlayered override zone can beat themes and highlight.js with zero escalation.
- **Rules when adding styles**: (1) **no** `!important` in themes; rely on the theme layer winning; (2) when same-layer specificity is insufficient in the baseline, use a **compound class to raise specificity** (e.g. `.canvas-dropdown-item.canvas-inline-create`), never `!important`; (3) to beat a theme/third-party ordinary declaration use the **unlayered override zone** at the end of the file, never `!important`; (4) only runtime inline `style` (e.g. mermaid) justifies it, with the reason stated, inside `@layer guard`; (5) themes should stop writing ID-weighted selectors like `#root .foo` to fight the baseline for weight (layer order already solves it; leftover ID weighting is legacy baggage — delete it on sight). Guard: `tests/unit/css-layers.test.ts` (baseline `!important` ≤ 1, `themes/**/*.css` must be 0, layer declaration and guard placement, doc contract).
- **Visual regression gate** (mandatory after any style change): `npm run audit:themes` (screenshot the current tree → `.theme-audit/current`) → `npm run audit:diff` (pixel-diff against `.theme-audit/baseline`). A fixed fixture DOM (bubbles/Markdown/tables/code/thinking card/tool card/pill flow/input island/top bar/side dock/quick chips/plugin icons/`hide-model-row` compact mode) + one image per theme (35 themes); a per-theme difference > **0.05%** exits with code 1.
  - The baseline snapshot `.theme-audit/baseline` is the state "when the layering refactor completed" (gitignored). To get a **pre-refactor** baseline you have to shoot from a `HEAD` git worktree: `git worktree add ../baseline HEAD` → `node scripts/theme-audit.mjs --root ../baseline --out .theme-audit/pristine`.
  - Rebuilding the baseline is only allowed when the difference is genuinely an "intentional improvement"; otherwise check layer order first (a `theme` layer squashed by `base` is the most common mistake).
- **Accepted intentional differences (theme wins)**: after layering the `theme` layer always beats `base`, and the following 4 places that historically had the baseline's `!important` winning now render per the theme — this is **final, not a defect**, so do not use alignment blocks to force the old values back (the zhujian/zhupi/aetheris top bar alignment block is a historical special case; for new themes, treat the theme's direct output as the norm):
  1. `flow` / `flow-light` / `wallpaper-flow`: `.msg-assistant` vertical padding takes the theme's `0` (previously covered by the baseline compact mode's 2px/4px) — fixture difference ~2.0%;
  2. `flow` / `translucent` / `transparent`: `.quick-chip.active` takes the theme's background (previously covered by the baseline's accent background) — difference ~0.5%;
  3. `aetheris`: `.chip` radius and `.bar-item` padding take the theme values;
  4. `wallpaper-obsidian`: the plugin icon `.plugin-icon-svg` color takes the theme value.

## Center column geometry (the message column and input box are always the same width and aligned)

- **Single source of truth**: four tokens on `.main` — `--chat-pad` (minimum column side padding: desktop 20px / mobile 14px / 260px for the wide-screen chat column), `--chat-max` (column width cap 860px; the wide-screen chat column sets it to `100%` to remove the cap), `--chat-rail` (space yielded to the question navigation rail, desktop 48px), `--chat-inset = max(--chat-pad, (100% - --chat-max) / 2, --chat-rail)`. The message column, input box, goalbar, `/` command menu and extension questionnaire panel all use only `--chat-inset` (`.inputbar` uses it as horizontal padding, and all its children are self-sizing), and per-element corrections like `max-width: 860px; margin: 0 auto` / `calc(100% - Npx)` are **not allowed** — equal widths for the two columns are just two use sites of the same value.
- **Percentage basis**: `--chat-inset` contains percentages, so only use it on elements whose "containing block width == `.main` content width" (`.messages` / `.inputbar` / `.goalbar` / `.dialog-inline`); fixed overlays (the file preview's markdown zoom column, the `/help` panel) form their own containing block and keep fixed-distance values.
- **Scroll container compensation**: `.messages` has `scrollbar-gutter: stable both-edges`, and its content box loses one gutter on each side, so it uses `padding-inline: max(0px, calc(var(--chat-inset) - var(--msgs-gutter)))` (the outer `max(0px, …)` is defensive: a negative padding invalidates the whole declaration and the content goes flush to the edge); `--msgs-gutter` is maintained by `web/src/scrollbar-gutter.ts` — before the first frame it takes an initial value from a probe configured like `.messages` (it must be `overflow-y: auto` + `stable both-edges`; measuring with `overflow-y: scroll` yields 0px for overlay scrollbars, which does not match the real reserved width — this is exactly the root cause of the historical "message column 20px narrower than the input box"), and after `.messages` mounts it is overridden by measuring the real element, re-checked once on window resize.
- **Question navigation rail reservation**: `qn-rail` is pinned 14~38px from the right of the message area, and desktop (≥641px, where the rail exists) always reserves `--chat-rail: 48px` on both sides → the two columns keep the same width and both edges stay aligned; when the main column is wide enough (centered padding > 48px) `max()` takes the original value, so the wide-screen look is unchanged. A constant reservation rather than "reserve only when the rail exists" avoids the whole column suddenly shrinking by 28px when the first message is sent and the rail appears.
- **Regression**: `tests/chat-column-align-test.mjs` (multiple viewports × wide-screen chat column switch × mobile, comparing left/right edges and widths of `.msg` / `.msg-text` / `.msg-collapsed` / `.retry-notice` / `.inputbox` / `.goalbar` / `.slash-menu` / `.dialog-inline`, and asserting the rail does not overlap the message column).

## Multi-conversation concurrency

- Per client `convs: Map<convId, Conversation>`, **one independent `AgentSessionRuntime` per conversation**: `new_chat` creates a new runtime + new session file (old conversations keep running in the background, uninterrupted); `switch_conversation` only swaps `activeId` (touching no other runtime); the `runtime`/`session` accessors point at the current active conversation. **Conversations are owned by project**: `conv.cwd` is the owning project, and each project's active conversation is independent.
- **`set_cwd` no longer rebuilds the current conversation** — it switches to the target project's own conversation (that project's most recent activity; if there is none, create one and restore that project's most recent persistent session).
- **Workspace commands must be serialized (#872)**: `cs.cwd`, the active conversation and the runtime binding are one set of mutable state, and the commands that change them (`set_cwd` / `new_chat` / `new_cli_chat` / `switch_session` / `switch_conversation` / `fork_session` / `rollback_session` / `make_dir(setAsCwd)` / sandbox switches) are all async heavy work (stat, restoring the recent session, mounting the runtime, copying the sandbox). ws messages dispatch one by one, so while the previous one is still awaiting the next is already running — when "switch project then create conversation" races ahead, `newChat()` still reads the old cwd and the new conversation lands in the previous project (looking "missing" in the left panel).
  - **Single source of truth `server/workspace-queue.ts`**: at the dispatch layer those commands only "claim synchronously + enqueue", FIFO per conversation instance, each waiting for the previous one to settle; when idle it costs one extra microtask. New workspace commands must enqueue, and **must not** write their own "wait a moment then act" in the handler.
  - **Declarative target directory**: `new_chat` may carry `cwd` (`ClientMessage`), and the server does "switch workspace → verify → create session" inside the same queued task; **if the switch fails, no session is created** (error plus `new_chat_result ok:false`), never silently landing in the old project. `new_cli_chat` carries its own cwd, validates itself and is exempt from this interception.
  - **Client intent single source**: `web/src/pending-workspace.ts` remembers a `set_cwd` target that is "declared but unconfirmed" and automatically attaches it to the immediately following `new_chat` (entries do not each record it, and adding cwd per call site is forbidden); it is cleared when the snapshot lands in the target directory or the cwd transition is `done`/`error`.
  - **Queued commands must be bounded themselves** (own timeout / abort): the queue is FIFO, so a command that never settles blocks every workspace operation for that client. `prompt` and file-class commands are not queued (they take their own paths).
  - Regression: `tests/unit/workspace-queue.test.ts`, `tests/unit/pending-workspace.test.ts`.
- **"Running conversations" list lifecycle** (three fields per conversation: `listed` / `promptedSinceActive` / `lastActiveAt`):
  - Entering the list: an active conversation **that is streaming** when pushed to the background (new_chat / switch_conversation / set_cwd, **cross-project switches count too**) → `listed=true`; a session explicitly restored from history sets `listed=true` + `promptedSinceActive=true` on open and stays listed after the first switch-away even without a new message.
  - **Ephemeral conversation protection (#793)**: an already-started `isEphemeral` conversation is always retained when switched away and gets `listed=true`, regardless of the global `retainFinishedConversations`, the previous `listed` or whether this switch sends a new message; reopening and switching away again retains it too. A blank ephemeral conversation can still be reclaimed automatically, and an explicit ✕ still destroys it; retaining does not mean persisting — "Save as regular conversation" is needed to enter history.
  - Staying listed: finishing in the background does not remove it (the user may not have seen the result yet); **a conversation with a "used" live PTY also stays listed** (the terminal may still be running tasks), but **an exited terminal that only keeps its output does not prevent removal** — once the AI is done and all terminals have finished, switching away makes `removeConversation` call `killAll()` to close leftover terminals and the row disappears (`openTerminals` is passed `terminals.countBlockingLive()`, which counts only live and used PTYs — **an untouched empty shell (the one auto-created when the terminal tab is opened) does not count** and is released with the conversation on switch-away/✕ removal without blocking);
  - Removal: open it (make it active) → no further conversation (no prompt in between) → `displaceActive()` returns it on switch-away and `removeConversation` frees the runtime (the session is already persisted and can still be restored from the history list). **Subagents are exempt from close-on-switch**: when the active one is a subagent, switching away always retains it (`listed=true`, `displaceActive()` returns null) — having looked at it does not release it, and the background task keeps running; cleanup goes through explicit actions (single `dismiss_conversation` / right-click bulk `dismiss_finished_subagents`).
  - **Display policy vs `listed`** (issue #140): what the left panel pushes is decided by `shownInRunningList()` = `listed` **or** "current conversation + already has content" (has messages, or was named by the first prompt — naming and the first message happen at the same moment, and the rename block in `prompt()` calls `emitConversations()` on the side; `agent_start` pushes once more so the streaming green dot lights up immediately). A blank new conversation is still not listed (so double-clicking "New conversation" does not pile up empty rows). This is a **pure display policy**: the semantics of `listed` and the runtime-release rules of `displaceActive` / `shouldRetainActive` are completely unchanged (what should be released on switch-away still is) — so the ✕ on the current conversation's row must be judged by the same policy (`dismissConversation`'s "no-op when not in the list" uses the same function), otherwise you get "the row is there but clicking ✕ does nothing". Regression: `tests/running-list-test.mjs` (zero-token mock model) + `tests/panel-layout-test.mjs` (real browser: section title / "current" styling / streaming green dot).
  - Closing a parent conversation with a cascade hint: `dismiss_conversation` with `withFinishedSubagents=true` also closes the finished subagents under that conversation (transitively through descendants, matching the bulk policy; active ones are skipped) — closing only the non-running ones: running descendants are unaffected, and if descendants remain after closing, the parent stays with a hint; with only running descendants it is rejected. Without the flag and with finished subagent descendants it is rejected with a hint. Frontend: when a parent row has subagent descendants, one ✕ click expands two options — "Close finished only ({n})" (= the row-level bulk `dismiss_finished_subagents`, parent retained) / "Force close all" (`force=true`, see below).
  - Force close `force=true`: abort its own run (if running, `interruptRun`) + abort all subagent descendants (including running ones, `stopSubagent`) then dismiss the whole set; terminals/reviews/background wakes and other retained state are let go too. An active conversation can be closed as well (`vacateActive`: prefer switching to another listed conversation, otherwise create one first and then remove it). The DSH engine has no subagents: force only lifts the active/terminal restrictions and still rejects a running conversation (a single runtime cannot be aborted individually — click stop first). Frontend: every row (including selected/running) shows ✕; a running row without subagents uses a two-step confirm for force close (`dismissStreamingConfirm`); the row context menu has the same two options (`forceDismissConversation` with a two-step confirm).
- **Cross-client "elsewhere" rows (issue #145 / #291)**: `listExternalRunning(excludeClientId)` pushes conversations still held in other `ClientSession`s to the left panel (read-only awareness + manual takeover entry, with `owner`/`convId` locating the target). **Disconnect leftovers** (the last browser disconnected, `sinkCount()===0`) are still pushed during the grace period marked `ownerOffline` (the frontend "offline" badge) and disappear afterwards — the grace period is `PI_WEB_OFFLINE_ROWS_TTL_MS` (default 30 minutes; `0`/`off` = not pushed = the old policy). Why it is needed: after "closing the page mid-run on mobile → the run keeps going to completion on the server", opening the web UI on another device shows neither the row nor a way to take over (#291 skipped leftovers with sinkCount=0), leaving history as the only entry — and the leftover runtime still holds that transcript, so opening from history creates a second writer for the same JSONL. The grace period expires at the later of "disconnect time" and "last activity" (a background task still running after disconnect is not eaten by the TTL and re-arms on every streaming change), and on expiry `armOfflineRowExpiry` pushes once so the row disappears (the callback only pushes without reordering, avoiding a 1s poll). Regression: `tests/offline-takeover-test.mjs`, `tests/elsewhere-lifecycle-test.mjs`, `tests/unit/elsewhere-dedup.test.ts`.
- **Takeover is transactional (#556)**: `take_over_conversation` has two steps (the source session's `detachTakeoverConversations` removes → the target session's `insertTakeoverConvs` inserts), and in that instant the conversation hangs on neither side — if the second step errors, the runtime is still running but no list contains it (a "ghost session"; refreshing does not help, only restarting the service can recover it from the persisted session). Now a failed insert moves the whole payload back to the source session as is (`returnTakeoverPayload`: first `reclaimTakeoverConvs` removes the partially inserted leftovers, then rewire them back into the source page through the same insert machinery and switch back to active), and both sides get an honest acknowledgement; on a second failure it prefers staying on the target page (the inserting side has already marked the main conversation `listed`) rather than ending in an unowned gap. Regression: `tests/takeover-rollback-test.mjs` (test-only fault injection `PI_WEB_TEST_TAKEOVER_FAIL_INSERT`).
- **Resident conversations are unlimited by default**; new chats, restored history, forks and persistent subagents share `getMaxOpenConversations()`. The per-project count cap only applies when `PI_WEB_MAX_OPEN_CONVERSATIONS` is set to a finite positive number (floored, minimum 1); unset, `0`, negative or invalid values all mean unlimited. The cap counts ordinary conversations holding a runtime, including finished-but-resident ones and `persist=true` persistent subagents; `isSubagent` in-memory subagents and ephemeral sessions do not take a slot. When the cap is explicitly enabled, the concurrent-creation reservation and the history LRU collapse are kept; with the default unlimited setting, existing conversations are never collapsed for count reasons. It is optional resource control and does not represent the number of executing tasks.
- All conversations share **one ModelRuntime** (seeded when the first conversation is created, passed in reused by `makeRuntimeFactory`) — switching models in the top bar affects every conversation. **Message serialization caches (msgIds/uiMessageCache/signature) are isolated per conversation**: two conversations may produce the same (role, timestamp) key, and sharing would cross wires.
- **Project switch remembers {model, key} + global default model**: `client-state` persists `projectModels` (cwd→"provider/id") and `projectProviderKeys` (cwd→provider→keyName). **Selecting a model saves immediately** (`setModel` → `rememberProjectModel`, without waiting for a Q&A round — the SDK only writes `model_change` to disk once an assistant message exists, so otherwise a new conversation's model choice is lost if you switch away right after); **restored when switching projects/sessions** (`restoreProjectModelForCwd` + `restoreProjectProviderKeysForCwd` on set_cwd / switch_conversation / switch_session / ClientSession.create), and a new conversation also picks up that project's last {model, key}. Restoration silently skips deleted models/keys. **Global default** (`defaultModel` + `defaultProviderKeys`, stored under the `__settings__` global key, shared by all clients): "☆ Set as global default" at the bottom of the model dropdown records the current model (including the key at that time) as the global default with a ★ marker on the row; new projects without a project memory fall back to it (`set_default_model` / `clear_default_model` / `default_model` pushes, pushed on attach; pi engine only, the button is hidden under DSH). Fallback chain: project memory > global default > SDK default; keys likewise (`restoreKeyForModel` tries the project pin then the global pin). Deleting a key repoints global references in sync (`repointDeletedKeyInDefault`). Regression: `tests/unit/default-model.test.ts`.
- `snapshot` carries `conversationId`; `conversations` (ServerMessage) pushes **every project's listed conversations + the current conversation (once it has content, see `shownInRunningList`)** (the frontend groups by `cwd`, hiding the group title for the current project) + `activeId` (activeId is missing from the list only while it is still a blank conversation); `switch_conversation` (ClientMessage) **can switch across projects** — switching to another project's conversation also switches the workspace, filling in the `set_cwd` side effects (file tree/session history/project order/command catalog/onCwdChanged hooks).
- `switch_session` (restoring a persistent session) creates an independent runtime for the target session, then moves the current conversation to the background per the lifecycle above; if the target session is already in the running list its conversation is reused directly, and opening history never interrupts current generation. Regression: `tests/switch-session-background-test.mjs`. `edit_message` forks within the **current** conversation; `dispose` iterates and destroys every conversation; attachSink re-pushes conversations on reconnect.
- **Automatic continuation after a service restart**: `resumeInterrupted` locates the conversation to restore from the transcript file and delivers a `restart-resume` custom message straight to its SDK session (`display:false`, `triggerTurn:true`), keeping the SDK's retries, compaction and completion events; it appends no user "continue" bubble, and both live messages and reopened history hide that internal resume marker. Conversations start independently without waiting for the previous one to finish; concurrent `activeId` switches do not change the continuation target, and closed conversations or ones that already have a task are skipped. Regression: `tests/unit/restart-resume.test.ts`.
- Frontend: the left panel's "running conversations" section (shown when ≥1, active highlighted with a `当前` (current) sub-label and a streaming green dot; a blank new conversation hides the section), and MessageList forces a remount on conversation switch by keying on conversationId. Cross-project grouping lives in `web/src/conv-groups.ts` (pure function + unit test): **the current project's group shows no group title**, decided by "which group the current conversation is in" (`currentCwd` is only a fallback) — `conversations` pushes arrive first and the snapshot with the new cwd arrives later, so judging by `cwd` only would make the current project look like "another project" for one frame and flash the project name (per-frame browser regression `tests/conv-group-flash-test.mjs`).

## Other bridges

### Real-time tool end status (`tool_status`)

The server's `onEvent` listens to `tool_execution_start/end` (the AI tool-call path, distinct from `bash_execution_update` — that one is exclusive to the `!cmd`/direct terminal execution path). On `tool_execution_end` it immediately pushes `tool_status` (toolCallId/toolName/isError/exitCode/durationMs), **before** the toolResult snapshot lands — so the browser's tool card switches from "executing" to "finished · waiting for model · duration", distinguishing at a glance "the command is still running" from "the command finished and we are waiting for the model". The bash tool's details carry no exitCode (success returns truncation info, the failure's error text contains `Command exited with code N`), so the server extracts it from the error text with a regex; the `tool_execution_start` time is recorded in `conv.toolStartTimes` (per conversation) to compute the real duration. The frontend's `toolStatuses` Map is cleared once the toolResult lands (snapshot prune), falling back to the authoritative toolResult state.

### Tool hang watchdog

Every `tool_execution_start` arms a watchdog timer for the toolCallId (**preferring `ClientSettings.toolWatchdogTimeoutMs` from the settings panel's "Tools" page** (minutes, 0 = disabled, read live per run with no reload needed); when unset it falls back to the env var `PI_WEB_TOOL_TIMEOUT_MS` (milliseconds), then to the default 20 minutes) — if the tool is still running at timeout, `session.abort()` (kills the process tree) + a warning notice; `tool_execution_end` / `removeConversation` / `dispose` all clear the corresponding timer. **If the tool call explicitly declares a longer timeout** (currently only bash's `args.timeout`, seconds), the watchdog is extended to `max(base, tool timeout + 5s)` — otherwise an AI passing `timeout: 5400` (90 minutes) would be chopped together with the whole turn by the 20-minute watchdog. Recovery rebuilds + rebinds the session (same conv record, UI stays online); a watchdog timeout goes through the same `interruptRun`. **It only stops runs and never touches background services** — those are managed separately by the "background tasks" panel. Regression: `tests/unit/tool-watchdog.test.ts`.

**`ask_user_question` exemption**: a blocked questionnaire waits for a "human answer", not a hung tool — skip it by tool name before arming (`event.toolName !== ASK_USER_QUESTION_TOOL_NAME` in `tool_execution_start`). It has its own ending path: user answer/cancel, conversation dispose (`cancelPendingQuestions`), **no time limit** (standard pi engine; the DSH engine has no such watchdog and questions use their own 10 minutes via `PI_WEB_DSH_QUESTION_TIMEOUT_MS`). Likewise, a hanging questionnaire does not count as "lost connection" — the stall check (`startStallTimer`, warning after 180s without SDK events by default) skips conversations where `isWaitingOnUser(conv.id)` holds. Regression: `tests/question-bridge-test.mjs` (`PI_WEB_TOOL_TIMEOUT_MS=2000`, leaving it unanswered past the threshold still does not terminate).

### Approval queue and shared display

`UiState.pendingApprovals` is the authoritative pending-approval queue for every conversation held by the current connection (including background conversations), ordered by creation time; both full and incremental snapshots carry it, so a refresh or reconnect restores it. `pendingApproval` is kept for single-item compatibility. The immediate `tool_approval_pending` appends or updates by ID, and `tool_approval_resolved` only removes the matching ID and must not clear other pending items. Replies still locate the original conversation by stable ID through the server's `findPendingApproval`; "allow this category/all" still only applies to that conversation.

The frontend questionnaire and approvals share `PendingQueue`'s list, count, waiting time, stable selection, jump and handle-later logic while keeping `QuestionDialog` and the approval editor separate. New requests and snapshots cannot preempt an already-open request; the approval editor initializes only on request ID, so snapshots do not overwrite parameters being edited. Handle-later only defers display and produces no approval reply; the deferred state lives only for this page lifetime.

### Three-tier approval bypass and the custom rule library

Human-in-the-loop approval (`tool_approval_pending`) used to have only three one-off options — "approve / deny / edit and allow" — so the same class of high-risk operation had to be clicked every single time. The approval system now has two layers: a **rule evaluation engine** and a **bypass policy**:

#### 1. Custom rule library and matching engine (`<dataDir>/approval-rules.json`)

Rules are persisted by `ApprovalRulesStore` in `server/approval-rules.ts` and shared globally by all clients. Rules are edited and ordered visually on the settings panel's "Approval rules" page, matched top-down in list order, and the first hit wins:

- **Applicable tools** (tools): a single tool (e.g. `bash`), a combination (e.g. `["write", "edit", "patch"]`) or the wildcard `*`;
- **Checked field** (field): `command` (command string), `path` (target file path: accepts `path` / `file_path` / `file`, see `extractTargetPath()`, and extension implementations such as pi-better-edit's `edit` use `file`), `params` (full parameter JSON string);
- **Match mode** (match):
  - `regex`: case-insensitive regular expression match;
  - `glob`: path wildcard (supports `*` for one segment, `**` across directories and segments, with forward/back slashes normalized);
  - `contains`: substring match;
  - `prefix`: prefix match;
  - `outside_workspace`: out-of-workspace write detection (based on the current workspace cwd and extra roots' physical paths);
- **Hit action** (action):
  - `ask`: trigger human-in-the-loop approval (a dialog lets the user decide, with in-place parameter editing and allow-category);
  - `deny`: deny outright, blocking execution and returning an error to the model (no dialog, no pending approval created);
  - `allow`: bypass approval and allow (allowlist, skipping later rules and built-in detection, executing the tool directly).
- **Built-in rule conversion**: the former 10 hardcoded built-in high-risk detections (`rm -rf`, Windows `del /s /q`, disk formatting, destructive Git, dangerous `chmod`, system directory redirects, sensitive config `.env`/SSH/Shell and out-of-workspace writes) are all converted into default built-in rules (`builtin: true`) that users can freely disable, retarget or restore to the defaults in one click.

#### 2. Three-tier bypass policy (fast no-ask at runtime)

The gate is unified at the `ClientSession.askApproval` entry (pure function `approvalSuppressionReason(policy, enabled, categoryId)`, `server/tool-approval.ts`, unit test `tests/unit/tool-approval.test.ts`):

1. **Global off**: the "Tool execution approval" master switch on Settings → "Tools" (`ClientSettings.toolApprovalEnabled`, on by default, a pure runtime switch that does not enter presets). With it off, no approval pops up at all — built-in high-risk detection passes straight through, and a plugin pre-guard's `ask` is also treated as allowed (`withToolGuard`'s `ask` branch only sets `needApproval`, and everything is finally decided by `askApproval`); the moment the switch is turned off, pending approvals are all approved by `autoApprovePendingApprovals` (so nobody sits staring at a dialog).
2. **Allow all for this conversation** (dialog button, `tool_approval_response.scope = "all"`): any later high-risk operation in that conversation is not asked again.
3. **Allow this category for this conversation** (dialog button, `scope = "category"`, only shown when the hit came from a rule tier): only the same tier is allowed. A tier is `UiApprovalCategory{ id, label, labelEn }`, and ids are stable and must not be renamed: `bash.rm-rf` / `bash.win-del` / `bash.disk` / `bash.git-destructive` / `bash.chmod` / `bash.system-redirect` / `file.sensitive.env` / `file.sensitive.ssh` / `file.sensitive.shell` / `file.outside-workspace` / `phone.gesture` / `phone.input` / `phone.key` / `phone.launch` / `plugin:<pluginId>` (a plugin pre-guard's `ask` is tiered per plugin). Blocks without a tier (custom reasons) are only affected by the first two.

**Phone control tiers (#902)**: the `phone` tool's `op` splits into read tiers (`status`/`dump`/`screenshot`) and control tiers (`tap`/`long_press`/`swipe`/`input`/`key`/`launch`, single source `PHONE_READ_OPS` / `PHONE_CONTROL_OPS` in `server/phone-tool.ts`). **Read tiers create no rules** (not intercepted by default); control tiers derive 4 built-in `ask` rules from `PHONE_APPROVAL_GROUPS` (`builtin.phone.*`, `field: "params"` matching `op`, tolerating whitespace/case), so each tier can be disabled individually (equivalent to granularities such as "only allow reading the screen" or "ask only for launch") and can also "remember this category" per tier. Tool descriptions and settings copy must state "enabling it grants whole-device control, but each control op asks first" and must not fall back to the old "no per-operation approval" wording. Regression: `tests/unit/phone-tool-ops.test.ts`.

**Where the policy lives**: `Conversation.approvalPolicy = { allowAll, categories: Map<id, UiApprovalCategory> }`, **memory only** (not persisted to client-state), and on the conversation object rather than the ClientSession — a manual takeover moves the conversation itself, so the policy travels with it; a service restart / new conversation goes back to asking. Once remembered, **other pending approvals in the same conversation already covered by the new policy are approved too** (`approveCoveredPending`), with one acknowledgement notice.

**Revocation**: Settings → "Tools" lists the approvals remembered by the current conversation (`UiSettingsState.approvalPolicy`, computed live by the server's `approvalPolicyState()`), and each "Revoke" goes through the client's `set_approval_policy` (`allowAll` assignment + `categories` replaced wholesale as the keep-list; pure memory state, not `set_settings`). The dialog itself no longer appears once the policy takes effect, so the revocation entry must stay in settings.

Regression: `tests/approval-policy-test.mjs` (protocol side: switch persistence / policy pushed back to the panel / garbage messages are a no-op), `tests/approval-rules-test.mjs` (custom rule protocol side), `tests/unit/approval-rules.test.ts` (matching engine unit tests), `tests/unit/tool-approval.test.ts` (tiers and the three-tier decision).

### Pending questionnaires in snapshots (restoring the dialog on reconnect)

`question_pending` is an immediate channel: it is only pushed to connections that were online "at the moment of asking", so a page refresh / WS reconnect / new tab never receives that historical message while the server is still blocked waiting for a human — the panel vanishes into thin air (`QuestionDialog` has no other entry). So pending questionnaires also hang off the snapshot (`UiState.pendingQuestion`; the standard engine filters per conversation: `pendingQuestionForSnapshot()` only carries the current conversation's, and switching back re-pushes the snapshot; DSH's question bridge is runtime-level and not per conversation). When `use-chat.ts` receives `snapshot` / `snapshot_delta` it uses the pure `resolvePendingQuestion` in `web/src/pending-question.ts` to decide whether the panel stays: if the snapshot has a pending questionnaire it is restored (ids already answered are skipped — answer messages and in-flight snapshots interleave), but only a panel "restored from a snapshot" accepts being collapsed by a snapshot (so an old snapshot from before an answer does not flash away a panel just popped up by the immediate channel). Unit test `tests/unit/pending-question.test.ts`.

### Background task list

The bash tool takes a listening snapshot before and after execution (`snapshotListeningPorts`, Windows netstat / POSIX lsof), and newly appearing LISTENING processes from the diff are recorded in `bgServers` (port→pid→since→name, with the name fetched best-effort via `lookupProcessName` tasklist/ps); after startup a notice suggests "stop it individually or close them all from the top bar's background tasks". **The list is persisted per client** (a ClientSession field, not conversation-level) — it survives conversation end/switch/reconnect (attachSink re-pushes `bg_servers`), and entries are removed only when the task is stopped or the process exits on its own (the 30s `refreshBgServers` timer re-snapshots ports, and an entry is alive only if both port and pid match; dead entries are pruned silently).

**Automatic leftover cleanup** (the "auto-clean leftovers" dropdown + "Clean now" at the bottom of the panel): thresholds `0/15/30/60/120` minutes (`ClientSettings.bgAutoCleanupMin`, **default 0 = off**), read live inside the same 30s timer → `BgServerTracker.cleanStale(thresholdMs)`: first `verifyBeforeKill` re-checks the port→pid ownership (on mismatch the entry is dropped, **never kill a stranger process**), then `staleLeftovers()` (pure function, covered by unit tests) picks entries that are **not pinned** and `now - since >= threshold` → `killPidTree` + a summary notice. Each row can be 📌 **pinned** (`set_bg_keep`): pinned entries never take part in automatic cleanup (in the field: a dev server deliberately left running for debugging should not be swept away). Manual "Clean now" uses a 30-minute fallback when the threshold is off, and the message may override with `minutes` (>0 takes effect). Plugin-registered always-on tasks (`registerBackgroundTask`) **do not** take part in automatic cleanup — they live inside the host process and are the plugin's `stop` callback's job. Regression: `tests/unit/bg-servers.test.ts` / `tests/bg-cleanup-test.mjs`.

**False-positive filtering** (`BgServerTracker.filterAgentSpawned`): a port diff is only a candidate and must also pass `shouldTrackBackgroundServer` — (1) a process name on the blacklist `NON_AGENT_PROCESS_NAMES` (WeChat/QQ/Telegram and other desktop apps) is skipped outright; (2) one bulk PowerShell CIM / `ps -Ao pid=,ppid=` fetch builds the full parent-child map, and the parent chain is walked: hitting the server process (`process.pid`) or another new pid from this diff (an intermediate layer left by bash) → record; walking all the way to the system root (pid 0/1) with no hit → a self-started desktop app (e.g. a Chrome the user launched, whose parent chain is explorer), skip; a broken chain (parent exited/reparented) → record conservatively. **Chrome is not blacklisted**: browsers launched by AI (Playwright etc.) have a parent chain that reaches the server process, distinguishing them from the user's own Chrome (parent chain explorer).

Protocol: `bg_servers` (ServerMessage, pushes the full list) / `kill_background_server` (stop one by port) / `kill_background_servers` (close all; `killAllBackgroundServers` runs `killPidTree` on each pid, `taskkill /F /T` on Windows) / `list_bg_servers` (request a refresh when the panel opens); the frontend `BgTasksModal` (each task row has "Stop" + "Close all" and "Refresh" at the bottom, with placeholder copy for an empty list).

### Stop only the bash command (the conversation continues)

A running bash tool card shows "Stop" → sends `{ type: "abort_bash" }` → `ClientSession.abortBash()`. The server uses a **killable bash tool** (`makeKillableBashTool`, overriding the SDK's built-in bash by name through `customTools`): during execution it registers its own AbortController in a client-level `bashKills` set, and abort kills only those controllers → the bash child process tree is killed (the tool throws "Command aborted", caught by the agent loop as a tool error result) → **the agent run and the conversation continue**; unlike the SDK's `session.abortBash()` (which only works for the extension `executeBash` path, not the agent tool path), this really works for bash tool calls inside conversations.

When a command is aborted the SDK **splices the output produced before termination into the tool error result** (the AI sees the output + "Command aborted"); afterwards `abortBash()` also injects a "user manually stopped" hint via `sendUserMessage`, so the AI clearly knows it was the user rather than a failure.

### edit's soft parameter (the former edit_soft is merged in here)

The built-in `edit` requires oldText to match the file exactly (including indentation/whitespace). For languages where indentation is not semantic (e.g. JS/JSON), the model's oldText is often a few spaces/tabs off and the edit fails. pi-web-ui **overrides** the built-in `edit` through `customTools` (`makeEditToolDefinition` in `server/edit-tool.ts`, wrapping point still `composeEdit` in `toolOverrideSpecs`), adding only one parameter `soft` on top of `path` / `edits`:

- Without `soft`: forward the SDK implementation as is (including its own lenient matching of trailing whitespace/full-width characters); this host does not reimplement exact matching, so the two cannot drift; the prompt guideline explicitly says "if the text is not found, retry the same edit with soft=true", and the model self-heals in one step.
- `soft: true`: try the exact substring first, then on failure do lenient matching by "identical per-line core (trim) sequence" (ignoring leading/trailing whitespace differences), and on a hit **write newText verbatim as whole lines** (the indentation is the final indentation). Write only on a unique match, error on overlapping edits, and participate in the same per-file mutation queue (`withFileMutationQueue`).

`edit` is a core built-in tool (`CORE_TOOL_CATALOG`), not a togglable item in `AGENT_TOOL_CATALOG`, so there is no "lenient editing" switch: the model passes `soft` as needed. The DSH engine does not expose this parameter.

**Multiple edits must be sorted by position then applied in reverse** (`applySoftEdits`): all edits are located against the same original content, so after computing each `start/end` you must **first sort ascending by position** and then apply in reverse for the left-side offsets to stay stable. An early implementation missed the sort and applied in reverse of the edits' array order — if the model put a later edit first, the later replacement changed the length first, the earlier offset shifted, and garbled content was written (historical bug: `protocol.ts` / `use-chat.ts` / `ChatInput.tsx` were corrupted). The built-in `edit` likewise sorts by `matchIndex` first (`edit-diff.js`); align with that. Regression tests cover all 6 permutations.

**Illegal fragment defense**: lenient matching requires every oldText line to be a complete line. (a) If an exact hit spans multiple lines but starts/ends mid-line (e.g. `a);\nfoo(`), plain substring replacement eats the residual characters at the line start/end and writes glued content (`foo(z();b);`) → reject and ask for whole lines; (b) if the lenient phase misses as a block and the first/last line is only part of a line, report a "fragment" error instead of a generic "not found"; (c) single-line fragments (e.g. `b();`) do not change line structure and keep working.

`soft` only takes effect in the lenient branch (`applySoftEdits`): the SDK's lenient matching cannot handle leading indentation, which is exactly what this fills in; non-soft calls cost nothing extra and do not rewrite regions the SDK would match exactly.

### read override: list directory entries when the path is a directory (`server/read-tool.ts`)

The SDK's built-in `read` only handles files (`read("server")` returns `EISDIR: illegal operation on a directory`), and the SDK's own `ls` is not in the default active set (`["read","bash","edit","write"]`), so a model wanting to peek at a directory had to switch to bash. pi-web-ui therefore **overrides by name** the built-in `read` through `customTools` (the bash override was the precedent): take `createReadToolDefinition(cwd)` as the base implementation, and in `execute` first check whether the path is a directory — if so, route to the SDK's `createLsToolDefinition(cwd)` (one entry per line, directories with a `/` suffix, sorting and entry/byte truncation identical to the SDK's `ls`), prefixed with a `[Directory: <path>]` line; everything else (files, images, missing paths, read errors) forwards the base as is, behaving exactly like the built-in. In the directory branch `limit` is the entry cap and `offset` is ignored.

Switch `readDirEnabled` (first row of Settings → Tools, on by default): this is a **behavior switch** (whether `read` itself is on lives in the settings page's "core tools" section and goes through ActiveSet; this one governs the override layer's directory listing and is unrelated to whether the read tool itself is enabled), not an ActiveSet switch — so it does not enter `AGENT_TOOL_CATALOG` in `tool-manager.ts`, the override definition reads settings live on every call (changes take effect immediately, no reload) and it does not enter settings presets either. The DSH engine has no customTool registration surface (tools come from the shipped preset), does not support this override, and the snapshot is always true.

The parameters additionally accept `file_path` as an alias for `path` (some clients/models habitually send `file_path`): `path` stays required in the schema, and `prepareArguments` normalizes a call carrying only `file_path` into `path` before validation (when both are given `path` wins), and passes the normalized `path` on when forwarding to the built-in. The frontend tool card header's path hint (`web/src/tool-args.ts`) already accepts both names (as do the SDK's own renderers).

**The base may also be a third-party extension's registered `read` or `bash`**: the SDK's merge chain is `[...extension-registered tools, ...customTools]` with later writes winning, so an override layer placed directly in the creation-time `customTools` would **silently displace** an extension's tool of the same name — and the official `docs/extensions.md` §Overriding Built-in Tools explicitly states extensions may override `read`/`bash`/`edit`/`write`. So the four overrides `bash` / `read` / `write` / `edit` are **not registered at creation** but injected by `server/tool-overrides.ts` after the session is built, preferring the extension implementation as the base — see the next section, "Overrides coexisting with third-party extension tools of the same name".

### Overrides coexisting with third-party extension tools of the same name (`server/tool-overrides.ts`)

pi-web-ui overrides the SDK built-ins `bash` / `read` / `write` / `edit`. The SDK's registry merge chain is `allCustomTools = [...extension-registered tools, ...customTools]` followed by `definitionRegistry.set(name, …)` one by one — **later write wins**: putting the overrides into `customTools` at creation time breaks the promise in `docs/extensions.md` that "extensions can override built-in tools" (an extension's same-name tool never gets a turn, and review/sandbox extensions are completely bypassed — e.g. `@buyong/pi-codex-auto-review`'s bash review never fires and the command runs bare, issue #750).

The current approach: these four core overrides are injected **after the session is built** by `installToolOverrides(session, specs)` — for each one, take the extension implementation from `session.extensionRunner.getAllRegisteredTools()` by name as the base (only when unavailable fall back to pi-web-ui's own full implementation), decorate it with `composeWith`, then **prepend** it back into `session._customTools` and call `_refreshToolRegistry()` (the same technique as `syncPluginToolsIntoSession` for plugin tools):

- `bash`: with an extension bash → keep all of the extension's own definitions and unique parameters (e.g. the review parameter `sandbox_permissions`), wrap the outside with the host hard safety gates (target review turn read-only / reviewer mode interception / plan mode hard gate / sandbox boundary hard fence / session read-only permission / approval rule engine / plugin guards), and bridge `bashKills` (so the UI's interrupt button can interrupt commands inside the extension) and `applyHeadTail`; without one → native interruptible bash with adaptive routing to PTY terminal bash (`makeAdaptiveBashTool`). When an extension takeover is detected, a notice tells the user that terminal takeover has stepped aside.
- `read`: with an extension read → `withReadDirSupport(extension definition)` — the base's name/label/description/parameter schema/`prepareArguments`/render slots are all preserved, adding only one directory note, one directory guideline and the directory branch (which still reuses the SDK `ls` sorting/`/` suffix/truncation rules); without one → `makeReadDirTool()` (built-in base + English description + `file_path` alias). When forwarding, **extension parameters are not rewritten** (`file_path` normalization belongs only to the built-in version; extensions bring their own `prepareArguments`).
- `write` / `edit`: with an extension tool of the same name → use its definition as the **base** wrapped by the permission sandbox (execution first passes read-only / out-of-workspace interception and approval, then delegates to the extension implementation); without one → wrap the SDK built-in implementation.

Four invariants: (1) the extension implementation's schema / description / prompt guidance / rendering are not replaced (extension-unique parameters such as better-edit's `windows` still work); (2) prepending the overrides ⇒ tools of the same name registered by pi-web-ui **plugins** (also customTools, written after the override layer) are still the final winner, preserving the relative order from before the change; (3) repeated injection is idempotent (remove the same name first, then prepend); (4) when the session object shape does not match (the SDK renamed a private field) return `null` and degrade to "the override was not installed" (equivalent to the pre-change behavior, never worse); a missing `extensionRunner` likewise falls back to the built-in base.

`extractTargetPath()` (`server/approval-rules.ts`): the permission sandbox and approval rules judge by "target file", so all three spellings must be recognized — the SDK built-in uses `path`, `read` has the `file_path` alias, and some extensions (`pi-better-edit`'s `edit`) use `file`; recognizing only `path` yields an empty string once an extension implementation is layered on, is judged in-workspace and **silently allowed**. The rule engine's `path` field uses the same function.

The switch is still a behavior switch (`readDirEnabled`) and does not enter `AGENT_TOOL_CATALOG` in `tool-manager.ts`; the DSH engine has no customTool registration surface and does not take it. Tool definition prompts follow the pure-English convention (`tests/unit/tool-prompt-hygiene.test.ts`). Regression: `tests/unit/tool-overrides.test.ts` (base resolution / prepend order / idempotence / degradation), `tests/unit/read-dir.test.ts` (`withReadDirSupport`'s schema, description, forwarding and directory branch), `tests/unit/approval-rules.test.ts` (`extractTargetPath` and rule fields).

### Reviewer mode: automatic delegation (`server/delegate-mode.ts`)

The server-side implementation of "force the AI to open a persistent subagent", shaped as a **session-level switch + fully automatic routing + pure-delegation gate** (off by default):

1. **Automatic routing** (`ClientSession.dispatchToDelegate`): as soon as `prompt()` comes in it asks whether to take over — when on, the text goes to **one always-on persisted execution conversation** (one per session, reused across turns; the same channel as goal mode 2.0's execution conversation: `spawnSubagentConversation(..., persist=true)`, persisted, in history, resumable). The first turn's prompt goes straight to spawn to start it, and **only after that** does each turn append via `sendUserMessage` (sending again on the first turn is rejected by the SDK: `Agent is already processing a prompt`). The main conversation **does not run a model** this turn and only sends a notice. When the execution conversation finishes → one notice in the main conversation (with a summary of the last reply + openable from the left panel), **no automatic acceptance** (v1 policy: acceptance is done by the human/main conversation in the next turn).
2. **Pure delegation gate** (`withDelegationGate`, mounted at the same three places as plan mode: the whole `customTools` list / the `write`·`edit` overrides / the always-on terminal's `checkSafety`): write-class tools, non-routine bash (reusing `bashCommandIsReadOnly`) and **dispatch-class tools** (`spawn`/`delegate_task`/`set_goal`/…) are all rejected. Dispatch-class is rejected for a different reason than plan mode: there it is "don't bypass the read-only constraint", here it is "handing out work is the server's job, don't open another context yourself".
3. **Soft constraint** (`DELEGATION_SYSTEM_PROMPT`): tells the model it is the reviewer and what it should do (set acceptance criteria → look at diff/tests → accept or state the next round's requirements).

**Priority vs. plan mode**: with plan mode on, **no automatic dispatch** (plan mode already rejects spawn/side-channel tools, so auto-dispatch on top would deadlock), and only one prompt section is injected — plan mode's turn produces the plan in the main conversation itself. The DSH engine has no customTools registration surface (nowhere to mount the gate) → `setDelegateMode` explicitly replies with a notice and refuses instead of failing silently.

State: the boolean persists with the session transcript (customType `delegate/mode`, replay in `readDelegateModeFromSession`); **the execution conversation id is not persisted** — it is a live object in this process and the first request after a restart rebuilds it (better one extra execution conversation than pointing at a nonexistent id). The decision is a pure function (unit test `tests/unit/delegate-mode.test.ts`), end-to-end regression `tests/delegate-mode-test.mjs` (zero-token, already in the smoke ALL list).

The persisted execution conversation holds an ordinary conversation runtime and shares the project count with goal mode's execution conversation. Unlimited by default; only after `PI_WEB_MAX_OPEN_CONVERSATIONS` is explicitly configured does a dispatch at capacity throw and suggest turning the mode off or freeing a slot.

### Plan mode: plan only, no implementation (`server/plan-mode.ts`)

The goal bar's **expanded row** has a **Plan** button (`host:goal-plan` slot, not rendered by the DSH engine — it has no customTools registration surface, so there is nowhere to mount the gate). It went through two adjustments: (1) moved from the composer toolbar switch (`host:composer-plan`) into the goal bar — the semantics are "take the input you wrote in this box and plan with it", which belongs to the same line as the goal, so it only hangs on the edit row and **does not go into the collapsed pill**; (2) changed from a "switch" to a **one-off action** — one click = `set_plan_mode{true}` (opening the gate) immediately followed by a `prompt` (sending the goal input as a message), the two arriving in order on the same WS → this turn runs inside the gate; empty input only opens the gate without sending a message. The button no longer has an `active` / `aria-pressed` lit state, matching its neighbors "distill" and "send": "one click sends directly". When goal mode is turned off (`goalModeEnabled=false`, the whole goal area is not rendered) it hides along with it. The gate itself stays session-level and hot-effective: once on, **this conversation only investigates + produces an implementation plan and makes no changes**, producing a `plan_update` step board (PlanBoard) + the plan body. **The only exit from the gate is "Start implementation" in the plan board** (PlanBoard.tsx: `set_plan_mode{false}` + sending an implementation request) — after removing the switch semantics this exit must be added, otherwise you can get in but not out. **Orthogonal to goal mode**: goal mode is "let the executor finish the goal", plan mode is "hold off for now, give me the plan".

Two layers of protection, both required:

1. **Hard gate (`withPlanModeGate`, the only enforcement point)**: decorates the outside of tool definitions and decides once before `execute`, outside the permission sandbox and plugin guards. A hit returns an `isError` tool result (`details.planModeDenied`) that hands the model the alternative path "write it into the plan and wait for confirmation". Mounted at three places: (1) the whole `customTools` list (including the bash override, `patch`, `eval`, subagent dispatch and scheduling tools); (2) the `write` / `edit` injected by `installToolOverrides` (`composeWrite`/`composeEdit` in `toolOverrideSpecs`, with `edit` carrying its own `soft` parameter); (3) the always-on terminal tool's `checkSafety`. When off it only costs one boolean check.
2. **Soft constraint (`PLAN_MODE_SYSTEM_PROMPT`)**: `appendSystemPromptOverride` appends a pure-English hard-rule section based on current session state, rebuilt via `session.reload()` when the switch changes, effective next turn. The real payload of this prompt is two rules:
   - **No code dumping** (`## Output shape` section): `NEVER write the implementation` — no whole files, no complete functions, no "finished version code"; describe only which files change, the structure, key decisions, risks, verification and the first step; code is allowed only as "short snippets at tricky spots (~20 lines, at most two)". **This is the patch for the hard gate**: the gate stops the model from writing files, so the model dumps the whole implementation as prose (burning tokens with nothing landed — one real report: "asked it to write a single-page snake game and it pasted hundreds of lines of source"). Note the regression: no Chinese inside the prompt section (`tests/unit/plan-mode.test.ts` asserts no CJK; UI strings like "Start implementation" must be rephrased in English).
   - **Small requests get a short plan** (`## Plan board` section): only "3+ steps or a real unknown" warrants a `plan_update` listing pending steps first; small well-defined requests like "write a single-page snake game" **skip the board** and go straight to a short plan (which files to touch / structure / acceptance / first step), saving one tool round trip.

   The prompt body is editable in **settings panel → prompts → plan mode prompt**: `planModePromptMode` (append/replace) + `planModePrompt` (custom body), with the same semantics as the vision bridge / AI commit message (empty custom = built-in default; under replace the input is prefilled with the built-in default for direct editing), assembled by the pure `buildPlanModePrompt` (unit tests cover the three combinations). **Only the prompt changes; the hard gate is unaffected** — the server read-only constraint always applies. This setting does not enter settings presets (same as scmCommitMsgPrompt).

The decision is a pure function (unit test `tests/unit/plan-mode.test.ts`): `planModeDenial(toolName, params)` sorts into three kinds — **write-class tools** (`write`/`edit`/`patch`/`rm`/`git` and similar) are rejected outright; **bash read-only allowlist** (`splitShellSegments` splits on `;`/`&&`/`||`/`|`, and every segment must pass: no redirects / command substitution / background / heredoc, the command in the allowlist, `git` only allows read-only subcommands like `status|diff|log|show|blame|…`, interpreters only allow `--version`/`--help`) — deliberately conservative, better to reject once and make the model switch commands; **side-channel tools** (`spawn` / `delegate_task` / `set_goal` / scheduling etc.) are rejected too: the gate is **session-level**, and a subagent conversation's `planMode` is false, so allowing them would leave a back door.

State persists with the session transcript (`plan/mode` custom entry, replay in `readPlanModeFromSession`, the same policy as `permission/preset`), restored on conversation switch/reload; the snapshot field `UiState.planMode` always provides a boolean (using `undefined` would drop the key in `snapshot_delta`, and the frontend's spread merge would keep the previous conversation's `true`). Known boundary: plugin / MCP-provided tools do not go through these three mount points and are only bound by the soft constraint. Regression: `tests/plan-mode-test.mjs` (zero-token: switch snapshot / write-class rejected / bash read-write split / restoration after turning off / transcript persistence).

### The model operating browser pages (the `browser_page` tool)

Lets the model read/operate the page you opened in the browser directly (see "AI operating pages" in `plugins/page-picker/README.md`).
**Four links in the chain**, and it does not work if any is missing:

```
Model ── browser_page tool (server/agent-service.ts makeBrowserPageTool)
  │   params: op (pages/read/click/type/scroll/goto/wait/eval) + target/origin + per-action params
  ▼
ClientSession.pageCall()  ── sends page_request (with id + timeoutMs, default 30s / cap 120s, **with an idle timeout**)
  │   no "human is waiting", so it is not watchdog-exempt; when the frontend is offline it returns an actionable error ("open the pi-web-ui page")
  ▼
the pi-web-ui page in the browser ── use-chat.ts receives page_request → host bridge `window.__piWebUiHost.pageCall()`
  │   (`pageCall()` in web/src/plugin-host.ts, host API introduced in v3, currently v11; when the bridge is missing, say "install/enable page-picker and refresh this page")
  ▼
page-picker extension ── content script → service worker → chrome.scripting.executeScript(world:MAIN)
  │   admission: sender.tab.url must be "a pi-web-ui page bound to the server address" + the target in the extension's permission list + op passing the allowlist
  ▼
target page ── built-in actions (read/click/type/...) execute in the page's main world, results return to the model the same way (page_response)
```

**Why the other end is fixed to a pi-web-ui page**: the extension can only be called by something in the browser (the model lives in the server process), and `window.__piWebUiHost` is a ready-made, already-authenticated in-page bridge (the plugin system uses the same one). Cost: that tab has to be open; benefit: zero new listeners on the server, natural reuse of the login state, and **the human sees which browser the model is touching**.

**Protocol**: `page_request` (server→client, `op` interpreted by the extension, the server only passes it through) / `page_response` (client→server). It does not enter snapshots (there is nothing for a human to answer; a refresh simply fails this call) — that is exactly how it differs from `question_pending`.

**Reference to conversation (the human-in-the-loop entry)**: `web/src/components/BrowserControl.tsx` turns permitted pages into "web page reference" attachments (`mode:"page"`, `path` = page origin, `name` = title); **with exactly one permitted page the top bar button becomes that page's title** (clicking the body = reference, the ▾ on the right = open the panel), and with several pages every item in the panel has "Reference to conversation". For `mode:"page"` the server's `attachments.ts` **does no stat and reads no file** and only gives the model one `<browser-page url title>`: "this page is permitted, use `browser_page`, `target=<origin>`" — the user does not have to type the URL. **Screenshots** (`op:"shot"`) do not go through page execution: `captureVisibleTab` can only capture the active tab and only accepts `<all_urls>` or activeTab (a normal host permission is not enough) — so the extension switches the tab first, captures, crops (`planCrop`), **switches back**, and requires the user to grant an extra "all sites" permission in the extension. Images reach the model two ways: if the main model is vision-capable the tool result carries the image block directly (visible that turn); a text-only model goes through `ClientSession.transcribeToolImage()` → the vision bridge transcribes it into textual evidence (the same selection logic and prompts as user attachments).

**All gates live on the extension side** (permission table + allowlist + master switch + eval switch): the server does no action allowlisting, otherwise "what the extension can do" would be scattered in two places.

**The entry point is on the web side** (top bar "Browser" button + `web/src/browser-control.ts` + `BrowserControl.tsx`): the capability lives in the extension, and the web page can only do three things — report status (extension action `status`), send the person to the extension's options page (action `openOptions`, since a web page cannot navigate to `chrome-extension://` itself), and give copyable examples. Status is **queried on demand** (not in the snapshot stream): once on mount + refresh when the panel opens + a 45s poll. When the model acts on the target page, a "AI is operating this page" hint flashes in the page's bottom-right (shadow DOM, pointer-events:none, 2.2s fade) so users do not think the page is moving itself. Regression: `tests/unit/browser-page-tool.test.ts`, `tests/unit/page-picker-ai-ops.test.ts`, `tests/page-picker-bridge-test.mjs`, `tests/page-picker-edge-ext-test.mjs`.

### Extension UI bridge

The extension's `setWidget/setStatus/notify/select/confirm/input` → `widgets/statuses/notice/dialog` messages; dialogs reply via `dialog_response`, and Esc counts as cancel. `Dialog.tsx` (extension dialogs) and `QuestionDialog.tsx` (shared model questionnaires) render body/options/details/preview with rich `Markdown(rawHtml)` (markdown + raw HTML mixed, model's choice, trust the model; chat body rendering with the default `rawHtml=false` is unaffected), and the optional `preview` shows an "option preview" box.

In `snapshot`, `streamingMessage` is the in-progress message (streamed at 60ms granularity) and `messages` are the persisted ones.

### Durable engine data source: AgentEvents only, never `pi.live` slots (`server/durable/durable-event-projector.ts`)

Pi Durable (`@earendil-works/pi-durable`) splits the same thing into two projections, and **the responsibilities must not be mixed**:

- `pi.live` (`conv.watch()`) is a **cheap, trimmable runtime progress projection**: tool slots carry `output` only while `running`, and it is trimmed on settlement; slots **never carry `input`** (the arguments the model supplies for a call live in the tool task's `state.checkpoint`). So scraping slots gives neither arguments nor results.
- `watchEvents(harness, conversationId, ctx)` is the authoritative event stream: `tool_execution_start.args` (already resolved by the engine from the checkpoint; nested calls get the slot's `arguments` directly), `tool_execution_end.entry` (model calls, `model[0]` is the ToolResultMessage) or `.result` (nested calls), `message_start/message_update/message_end` (body and thinking), `tool_execution_update` (progress output).

Historical pitfall (#774): the driver used to diff `pi.live`, reading `slot.input` (never exists) and the settled `slot.output` (already trimmed), leaving tool cards with empty commands and empty results and polluting the persisted session down the same path (`argumentsText: "{}"`). Everything now goes through `DurableEventProjector` to project the event stream: it tracks the dispatched body/thinking lengths by `contentIndex` (streaming increments and the final paragraph persist without duplication or loss), and aligns tool results "success carries only `output`, failure carries only `error`" downstream; nested calls (`parentToolCallId`) do not produce separate cards, preserving the "one card per parent call" display policy. Regression: `tests/unit/durable-event-projector.test.ts` (including a guard that the driver must not read `slot.input/slot.output` again).

### Correlated host conversation creation

Host startChat/openSession sends new_chat with an optional requestId and waits for new_chat_result carrying the same requestId and the exact conversationId captured by the engine on creation/reuse. Rejection, missing ACK or timeout cancels prompt delivery; observing an unrelated conversation switch is never sufficient. Older clients may omit requestId. Prompts may include targetConversationId (the UI conversationId, not the SDK sessionId); dispatch rejects a mismatch against activeConversationId before synchronously entering prompt. Engines capture the conversation before awaits and reject stale targets before entering streaming state.

Device center setup keeps remote read-only guidance available when local pairing APIs are forbidden. Setup metadata restores installed URLs; unsuccessful status queries do not imply absence. Installed but unhealthy or unowned centers show CLI diagnostics rather than reinstalling. Installation continues on the server when the page is left; reopening and reloading metadata restores progress and pairing actions.
