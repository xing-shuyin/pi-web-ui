# 渠道调度模式 S0 · 安装与使用手册

> S0 **不新增任何代码**。它只是把渠道 AI 的默认行为从"亲自干"改成"派活 + 汇报"，
> 靠三样现成的东西拼起来：`conversation` 工具（spawn 支持 worktree/隔离）、
> 子代理完成通知（默认开）、渠道对父会话回复的回传。
>
> 读这份文档就能装完并立刻用起来；不需要改 `server/`、不需要改插件。

---

## 1. S0 到底靠什么成立（先确认它真的能跑）

| 环节                      | 现成能力                                                                                     | 位置                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 派活                      | `conversation({action:"spawn", tasks:[{prompt, type, isolation:"worktree", notifyOnDone}]})` | `server/conversation-tool.ts:7`、`server/subagents.ts:560`                                     |
| 任务在独立上下文/分支里跑 | 子代理有独立会话；`isolation:"worktree"` 给独立工作树与分支                                  | `server/subagents.ts:385`                                                                      |
| 干完自动回报              | `conv.notifyOnDone = notifyOnDone ?? true` —— **默认就是开**                                 | `server/agent-service.ts:1759`                                                                 |
| 回报能到你手机/桌面       | 完成通知投递给父会话（渠道会话）→ 父会话跑一轮 → 助手回复被插件回传原目的地                  | `agent-service.ts:2645`；飞书 `plugins/feishu/runtime.mjs:205`、QQ `plugins/qq/index.mjs:1670` |

**所以 S0 = 一份提示词 + 一次渠道工作目录配置**，没有别的。

---

## 2. 安装（3 步，10 分钟）

### 步骤 1：把渠道的工作目录指到目标项目

渠道插件的 `workspace` 设置（QQ/飞书/微信等都有）。**这个目录决定"任务默认在哪个项目里跑"**，配错就白跑。

- 目标项目必须是 git 仓库（否则 `worktree` 隔离用不了，只能 `none`，见 §5 坑 4）。
- 如果希望一个渠道同时管多个项目：S0 做不到，只能 `/cwd` 切（会重置会话上下文）或在指令里写明路径让 AI 传 `cwd`。

### 步骤 2：在该项目的 `.pi/APPEND_SYSTEM.md` 写规则

生成的提示词会作为"追加段"注入系统提示词（`{{append}}`，`docs/architecture-system-prompt.md:28`）。
文件位置（SDK 解析）：`<cwd>/.pi/APPEND_SYSTEM.md`，否则全局 `~/.pi/agent/APPEND_SYSTEM.md`
（`dist/core/resource-loader.js:948`）。

⚠️ **信任门控（最容易踩的坑）**：项目级文件只在"项目受信任"时读。
判定规则（`dist/core/trust-manager.js:151`）：只要 `.pi/` 下有 `settings.json` / `mcp.json` /
`extensions` / `skills` / `prompts` / `themes` 中的任一个，就需要信任；而**无人值守（渠道）场景没有 UI，
默认判为"不受信任"** → 你的规则会被**静默忽略**，AI 会照常亲自改文件。

- 本仓库的 `.pi/` 里只有 `commands.json` / `sftp.json` 等，**不需要信任 → 直接生效**。
- 如果你的项目有 `.pi/settings.json`（装了项目级扩展/技能），**先去网页里打开该项目并点"信任"**，再回渠道用。

把下面这段贴进 `.pi/APPEND_SYSTEM.md`：

```markdown
# 渠道调度模式（渠道会话专用）

你在这个会话里负责「接单 + 汇报」，不负责「施工」。

## 派活是唯一执行路径

- 任何需要改文件、跑命令、多步排查的请求，一律用 conversation 工具 spawn 子任务；不要在当前对话里自己做。
- spawn 固定参数：`isolation:"worktree"`（只读分析用 `"none"`）、`type:"implement"`（只读分析用 `"explore"`）、`notifyOnDone:true`。
- 任务描述必须自洽：目标、验收标准、不要做什么、相关文件路径。子任务看不到当前对话，不要写"如上所述"。
- 同一个请求涉及多个互不相关的文件/模块时，可以一次 spawn 多个（`tasks[]`，每个带 `key`）。同时在跑不超过 2 个。

## 当前对话里只做三件事

1. 接单：把用户意图整理成任务描述，回一句"已开任务：<一句话>"。
2. 汇报：子任务完成通知到达后，按下面的格式写报告。
3. 答疑：用户问进度，用 `conversation({action:"list"})` 或 `status` 查，不要凭印象回答。

## 报告格式（每次都用，不要贴代码）

结论：一句话说清做完没有。
改动：文件列表 + 每个文件改了什么（每个 ≤2 行）。
分支：worktree 分支名；说明"未合并，review 后 git merge <分支>"。
验证：跑了什么命令，结果如何。
待确认：需要用户决定的事（没有就写"无"）。

## 禁止

- 不要主动合并分支、不要 push 远端。
- 不要在控制面使用 write / edit / patch / bash。
- 任务失败如实说明卡在哪一步；同一任务不要重试超过 2 次。
```

### 步骤 3：验收（4 条可观察断言）

1. 下达一条"改文件"的指令 → 当前对话里**没有** `write`/`edit`/`bash` 调用（只有 `conversation`）。
2. 网页左栏「运行的对话 / 别处运行中」能看到一条独立会话（子任务）。
3. 完成后渠道里收到一份按上面格式写的报告，含**分支名**。
4. `git worktree list` 能看到该任务的分支。

任一条不满足 → 先查步骤 2 的信任门控。

## 3. 怎么用（对话即界面）

### 场景 A · 改代码（最常见）

```
你：  把 README 的安装段落改成 pnpm，做完告诉我
AI：  已开任务：改 README 安装段落为 pnpm（worktree 隔离）
      …（几分钟后）
      结论：已完成，3 处命令从 npm 改为 pnpm。
      改动：README.md（安装步骤 / 依赖安装 / 常见问题）
      分支：pi/task-8f2a（未合并，review 后 git merge pi/task-8f2a）
      验证：pnpm install --frozen-lockfile 通过
      待确认：无
```

### 场景 B · 只读分析（不动文件）

```
你：  帮我看看这个仓库的鉴权是怎么做的，给结论
AI：  （spawn type:"explore", isolation:"none"）… 报告直接是分析结论，无分支
```

### 场景 C · 并行两件事

```
你：  ①给设置页加个开关 ②补一条 e2e 测试
AI：  已开两个任务：设置开关 / e2e 测试
      …（先完成的先报，各自带分支）
```

> 两条报告会分别回来。要追某一条，说"看下第 2 个"，AI 用 `conversation action:list` 查。

### 场景 D · 查进度 / 中途叫停

```
你：  进度怎么样？
AI：  （conversation list）1 个在跑：改 README（2 分钟），另一个已完成。
你：  停掉它
AI：  （conversation stop）已停止。
```

### 场景 E · 换个项目干活

```
你：  在 E:\other-repo 里把 CI 超时调大
AI：  （spawn 时传 cwd:"E:\other-repo"）
```

> 目标目录必须存在；跨项目权限沿用现有 read/cwd 规则。

### 场景 F · 需要你拍板的事

S0 里任务**不能中途问你**（子代理的 `ask_user_question` 在无人值守下 240s 超时、浏览器也看不到，
`agent-service.ts:7180`）。所以：

- AI 会在**开任务前**问你（在控制面里，正常对话）；
- 任务跑到一半发现歧义，正确行为是**停下来交半成品报告**并把问题写进「待确认」；
- 你在渠道回一句话 → AI 据此开**续任务**（新子任务，不污染上一个）。

## 4. 你能得到 / 得不到

| 得到                 | 说明                                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| 任务不在控制对话里跑 | 子代理独立上下文，控制面只留"接单 + 报告"，上下文不会被施工过程撑爆                                 |
| 并行                 | 一次 spawn 多个；默认上限 16（`MAX_SUBAGENTS`，可用 `PI_WEB_MAX_SUBAGENTS` 调），但 S0 建议自己限 2 |
| 改动可 review        | worktree 隔离 → 独立分支，**不自动合并**，你 review 后 `git merge`                                  |
| 报告回到渠道         | 完成通知自动触发父会话跑一轮，回复按渠道分块回传                                                    |

| 得不到                       | 缺什么           | 升级到哪                                  |
| ---------------------------- | ---------------- | ----------------------------------------- |
| 统一任务编号 / `/tasks` 清单 | 没有任务簿       | S2                                        |
| 跨重启存活                   | 通知依附父会话   | S2（独立会话 + orphaned 标记）            |
| 任务中途提问/审批            | 子代理提问无人接 | S2（提问桥/审批桥）；S0+ 至少能"禁止提问" |
| 群聊看板 + 发起人绑定        | 没有 owner 概念  | S2                                        |
| 控制面"真的"不会写文件       | 只靠提示词       | **S0+**（工具门控，服务端强制）           |

## 5. 已知坑（按踩到的概率排序）

1. **提示词静默失效**（信任门控）：见 §2 步骤 2。这是唯一会让 S0"看起来没生效"的原因。
2. **父会话必须活着**：完成通知走父会话；`/new`（渠道重置套新 epoch）或宿主重启后，未送达的通知就没了。
   worktree 分支还在，可以手动 `git worktree list` 找回来。
3. **通知会排队**：父会话正在压缩/等回话时，通知进投递门排队，**不丢但会晚到**（`deliveryMode`，红线）。
4. **非 git 项目**：`isolation:"worktree"` 会失败 → 只能 `"none"`，此时改动直接落在工作目录，**并发写同一文件会互相覆盖**，所以非 git 项目请串行。
5. **worktree 不会自动合并**：这是特性不是缺陷，但报告里必须写分支名，否则你自己都找不到改动。
6. **执行面仍可能调用 `ask_user_question`**：S0 没有门控，只有提示词约束 → 偶发 240s 卡顿后超时。要彻底解决上 S0+。
7. **长报告被分块**：渠道有 Markdown 分块（10 份 `markdown-chunks.mjs`），长报告会拆成多条消息，注意读完整。
8. **群聊默认要 @**：飞书 `groupResponseMode=mention`（`plugins/feishu/bot-bridge.mjs:343`），TG/Discord/Slack/QQ 同样。
9. **并发不设限会互相打架**：多任务同仓库并发写 → 每个都开 worktree；非 git 就只能串行。
10. **重试放大**：AI 失败重试 2 次以上会重复产生分支/文件，提示词里已写"不超过 2 次"。

## 6. 什么时候该升级

| 信号                               | 说明                 | 升级                       |
| ---------------------------------- | -------------------- | -------------------------- |
| 你经常问"我刚才那个任务呢"         | 需要统一编号与清单   | S2（任务簿）               |
| 任务经常 > 30 分钟或跨天           | 父会话撑不住         | S2（独立会话）             |
| 任务中途必须问人超过每周 1 次      | 提示词解决不了       | S2（提问桥）               |
| 想彻底禁止控制面写文件             | 提示词不可靠         | **S0+**（门控，60–120 行） |
| 机器重启后报告丢了让你很难受       | 需要 orphaned + 恢复 | S2                         |
| 群里多人下单、要让别人也能看见进度 | 需要 owner 绑定      | S2                         |

**建议**：先用 S0 跑两周，把"你实际怎么用"记下来，再决定 S0+ 还是 S2——不要按想象的需求写 2k 行。
