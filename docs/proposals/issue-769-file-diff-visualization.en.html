File-edit visualization architecture: rendering editor & writer visually

The pain point raised in issue #769: tool calls currently show only unformatted raw argument JSON, so while developing you cannot intuitively perceive what the Agent changed. This document offers 4 systematic solutions, high-fidelity interactive demo prototypes, an architecture-selection comparison, and a rollout path — stepping out of the “patch the symptoms” mindset to deliver an elegant, efficient code-review experience.

🌟 Progressive 3-Tier Experience Strongly recommended · balances top-tier UX with architectural decoupling
Core design philosophy: serve both “quick scan” and “deep review”. Tier 1 (card header) shows the file plus an add/delete stat pill; Tier 2 (inline in the card body) shows a compact unified diff with word-level highlighting, and auto-collapses past 20 lines; Tier 3 (immersive inspector) expands into a side-by-side Split Diff comparison with file navigation.

1. Word-level diff highlighting

It does not just color whole lines: it computes exactly which variable or phrase inside the line was added or changed (dark green / dark red background), so tiny edits are obvious in one second.

2. Switch freely between three views

Compact Unified by default; switch to Split for precise comparison; flip back to Raw JSON with one click when debugging Agent arguments — troubleshooting stays fully intact.

3. Large-file protection and smart collapsing

When the write tool lands thousands of lines, everything past the threshold collapses behind a “Show remaining N lines” control — hard protection against UI jank.

Solution 1 pros and cons:

  • Strengths: tiny footprint (~200 lines), changes concentrated in a single UI component, zero server-side dependencies (uses the SDK's native details.diff directly).
  • Limitations: with complex multi-file changes you still scroll card by card through the main conversation; once long lines wrap, side-by-side clarity is gone.

Solution 2 pros and cons:

  • Strengths: the visual comparison matches a senior developer's intuition best — strict line-by-line, word-by-word alignment is visible at a glance. Ideal for reviewing refactors.
  • Limitations: horizontal space is tight on small screens and mobile, so you have to write media-query logic that degrades back to a single column.
Solution 3: Workspace Changeset Hub / Timeline Drawer Task-level overview · stop the whack-a-mole local view
Core idea: Step out of the isolated card of a single tool call, aggregating every file edit the Agent produced in this conversation or task into one “Changeset Drawer”. Only a lightweight header pill remains in the chat stream; clicking it summons the immersive file-comparison drawer on the right.

🛠️ Architectural and system-level root-cause roadmap (stop playing whack-a-mole)
Why is merely writing two if (block.name === 'edit') branches in the frontend “treating the symptom”? Here is the root-cause system design analysis:
+----------------------------------------------------------------------------------------+ | 1. Server-side source of truth and context-budget guarantees | | | | [Agent Core / SDK] | | | | | |-- edit succeeds --> result.details: { diff, patch, firstChangedLine } (built in)| | | | | |-- write succeeds -> guard details budget <= 64KB (AGENTS.md hard rule) | | Server sends only { isNewFile: boolean, totalLines: number, oldLines?: number } | | Never inject huge raw file content - avoids WS backpressure and payload drops! | +----------------------------------------------------------------------------------------+ | v (WebSocket protocol: message_delta / snapshot) +----------------------------------------------------------------------------------------+ | 2. Frontend-robust data model (FileMutationModel) | | | | [tool-args.ts] unified parser: parseFileMutationArgs(name, argumentsText, details) | | | | | +-- 🛡️ Streaming resilience: partial JSON (e.g. {"path": "src/a.ts", "edits": [...)| | | Regex gets path + first hunk early, shows "replacing line N...", no blank screen| | | | | +-- 🧩 One normalized shape: edit / edit_soft / write / patch -> UnifiedDiffBlock[] | +----------------------------------------------------------------------------------------+ | v +----------------------------------------------------------------------------------------+ | 3. Presentation reuse and multi-viewport consistency | | | | [FileChangeCard.tsx] core, tightly cohesive component | | | | | |-- 1. Regular chat-stream card (expanded, ToolCallBlock.tsx) | | |-- 2. Minimal/Flow mode modal (centered, ToolInspectorModal.tsx) | | |-- 3. Floating file-preview drawer (side drawer, file-preview-bridge.ts) | | | | ✅ Reuses .scm-diff colors + CSS vars from styles.css (--green/--red/--bg-elev) | | ✅ Meets text-contrast + a11y rules (AGENTS.md: semantic-contrast / accent-contrast) | +----------------------------------------------------------------------------------------+

Root-cause fix checklist:

  1. Model-layer abstraction (web/src/file-diff.ts): Decouple from concrete tool names: normalize edit's oldText/newText, the SDK's details.diff, and write's content into one shape, with streaming fault-tolerant parsing.
  2. Render-layer component (web/src/components/FileChangeCard.tsx): Implement unified diff, split diff, word-level highlighting, line-number alignment, and collapse protection (show at most 20 lines by default, collapse the rest).
  3. Seamless linkage across both viewports: Wire it into both ToolCallBlock.tsx (regular conversation stream) and ToolInspectorModal.tsx (Flow inspector mode) so the experience is consistent site-wide.
  4. Detail polish and safety tests: Follow the AGENTS.md rules strictly (details ≤64KB, CSS variables defined before they are referenced, compliant text contrast) and add unit tests in tests/unit/file-change-card.test.ts.
