# 渠道任务面设计（Channel Task Plane）

> **一句话**：渠道只当**控制面**（收单、回报、确认），真正干活的是**每条任务一个独立会话**；
> 用「工具白名单」把控制面与执行面**物理隔开**，而不是靠提示词求 AI 别在同一个对话里干完。
>
> 本文只讲设计与边界，不含实现。事实全部可在仓库里核对（附文件:行号）。

---

## 0. 结论

| 问题                                 | 现状                                                                                                                                                           | 结论                                                                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 为什么现在一定是"渠道里唯一一个对话" | `chatFromPlugin` 的会话键 = `plugin:<pluginId>:<accountId>`（`server/agent-service-daemon.ts:1170`），而 accountId 来自 peer（chat/thread）                    | **一个 peer 恒等一条会话**；只有 `/new` 才轮换 epoch 换新会话                                                                          |
| 能不能一个 peer 开多条任务会话       | 能，已有原语：**新的 accountId 就是新会话**，回执带 `conversationId` 可精确回投（`agent-service-daemon.ts:1214`、`:1243`）                                     | 不需要新机制，只需一层"任务簿"把 accountId ↔ 任务绑定                                                                                  |
| AI 怎么把报告发回渠道                | 没有                                                                                                                                                           | 复用 `onRunEvent`（`run_end` 带 `conversationId`/`runId`/`stopReason`，`server/plugins.ts:164`）+ 渠道 `send`，按 `proactive` 能力降级 |
| AI 怎么在任务中途"请求"我            | **当前是断的**：无人值守（伪客户端）提问 240s 超时（`agent-service.ts:7180`），且浏览器看不到（`notifyUserQuestion` 只发手机推送，伪客户端无 socket，`:5821`） | 必须有**提问桥**；这是本设计最不能省的一块                                                                                             |
| 危险操作审批怎么办                   | 无人值守审批 120s 超时（`server/tool-approval.ts:25`），到期默认拒绝                                                                                           | 二选一：审批桥（渠道里点）/ 策略化（只读任务自动放行安全集）                                                                           |
| 任务会话怎么回收                     | scheduler 有 `releaseSchedulerClient`（`agent-service-daemon.ts:1096`），**插件侧没有对应释放**                                                                | P0 必须补 `releaseTaskClient`，否则任务会话常驻内存                                                                                    |
| 控制面该落在私聊还是群聊             | 各渠道会话键 = 发送者 + 会话空间 + thread（`plugins/feishu/runtime.mjs:5`、`plugins/telegram/channel-behavior.mjs:95`、`plugins/qq/index.mjs:81`）             | **私聊做控制面**；群聊只做只读看板/广播，详见 §8                                                                                       |
| 工作量                               | —                                                                                                                                                              | 见 §0.5：**先用 S0（零代码）跑两周，再决定要不要这个工作量**                                                                           |

**一句话边界**：本设计**不改**入站投递门（红线 `delivery-gate-single-source`）、不让任务与会话互相 `prompt`/`steer`、不把多条任务的上下文合并——渠道路由仍是"一条控制面会话 + N 条执行面会话"。

## 0.5 更简洁的实现路径（先读这节）

**能少造很多。** 原设计里的「任务簿 + 提问桥 + 审批桥 + 四档隔离 + 释放接口」，都是为了解决**"执行面无人值守"**带来的问题。只要把执行面设计成**单向的**（只交报告、不与人对话），这些问题大部分自动消失——因为**所有与人交互都回到控制面，而控制面本来就是一个正常的渠道对话**。

### 三档阶梯

| 级别    | 做法                                                                                                                                                                   | 新增代码                                                        | 放弃                          |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | ----------------------------- |
| **S0**  | 控制面 AI 直接用现成的 `conversation` 工具 spawn 子代理（`isolation:"worktree"`、`persist:true`、`notifyOnDone:true`）；完成通知回父会话 → 父会话写报告 → 渠道自然回传 | **0**（只改提示词 + `/task` 帮助文案）                          | 统一任务编号/清单、跨重启存活 |
| **S0+** | S0 + **dispatcher 门控**：控制面会话禁 `write`/`edit`/`patch`/`bash`、执行面（`isSubagent`）禁 `ask_user_question`、spawn 默认注入 worktree+notifyOnDone               | **~60–120 行**（`applyToolGating` 旁加一个分支，仿 bot 白名单） | 同上                          |
| **S2**  | 本文其余章节：独立会话 + 任务簿 + 提问/审批桥 + 回收                                                                                                                   | ~1.5–2k 行                                                      | —（换来跨重启与统一视图）     |

### 为什么**不**做"薄 `task` 工具"（曾经写在这一档，现已废弃）

1. **逆着仓库自己的方向**：`subagent_*` 的 9 个工具刚被折成单个 action 式 `conversation`（`server/conversation-tool.ts:7`），再开一个能做 spawn 的 `task` 等于把同一个活变成两条路。
2. **每会话都要付 schema**：`message` 工具省下的预算，又被一个新工具花回去；且模型在两条路之间摇摆，行为不可预测。
3. **它想买的"清单/编号"用更便宜的方式拿**：`/tasks` 要跨 11 个渠道各写一份命令解析（每个 `channel-behavior.mjs` 都有自己的 `parseCommand`/HELP），成本比想象高；而让它"只在多渠需求出现后再做"更划算。
4. **真正需要机制保证的两件事与工具无关**："控制面不干活"和"执行面不提问"是**工具门控**，在 `applyToolGating` 旁加一个分支就能做到（仿 bot 的 `botToolRegistrationAllowed`，`agent-service.ts:10324`），不需要新工具、新 catalog、新一批守卫。

> 只有出现下列信号，才值得回头讨论"窄工具"（而不是现在拍）：模型调 spawn 经常漏 `isolation`/`notifyOnDone`（日志可统计）、或需要在多个渠道强制配额与术语一致。即使到那一步，更优解也是在 **spawn 路径里注入默认值/校验**，而不是新增一个平行工具。

### 为什么 S0 就成立（逐条对应需求）

| 需求                   | S0 里谁满足                                                   | 依据                                                                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 我通过渠道下达任务     | 控制面 AI 读消息 → 调 `conversation` spawn                    | 渠道入站 → `host.chat` 已存在                                                                                                                                                                            |
| AI 通过渠道向我发报告  | 子代理完成 notice → 父会话跑一轮 → 助手回复被插件回传原目的地 | `subagent-notice` 投递意图（`agent-service.ts:2645`）+ 插件对 web 发起轮次的回传（`plugins/telegram/channel-behavior.mjs:358`、`plugins/qq/index.mjs:1670`、`plugins/discord/channel-behavior.mjs:424`） |
| 任务不能都在一个对话里 | 子代理有独立上下文；`isolation:"worktree"` 给独立工作树       | `server/subagents.ts:385`（isolation 校验）、`server/conversation-tool.ts:7`                                                                                                                             |

### 省掉的四件事，为什么能省

1. **提问桥** → 让执行面**不许提问**（工具白名单去掉 `ask_user_question`）。要澄清就在**开任务前**于控制面问；执行面卡住时按最保守解释继续，或直接交半成品报告。
2. **审批桥** → 执行面用 `policy`：只读/工作区内写入放行，危险操作直接拒绝（`server/tool-approval.ts:47` 的既有规则集）；要更高权限就换 worktree/沙盒，而不是在渠道里点"允许 `rm -rf`"。
3. **报告管道**（模板/节流/补发）→ **报告就是控制面的一条普通回复**，复用渠道既有回传与 `host.delivery` 的排队/状态。不新增管道，也就没有"窗口补发"的复杂度。
4. **四档隔离** → 只留两档：`worktree`（要改文件）/ 默认（只读分析）；沙盒当显式开关。

### S0 的两个真实弱点（升级触发条件）

1. **父会话必须活着**：notice 走父会话投递门（压缩期排队但不丢），父会话被 `/new` 或 server 重启后，未送达的 notice 就没了。
2. **没有统一任务编号与清单**：`/tasks` 只能看 subagent 列表，跨渠道没有一张表。

任一条成立就升级到 S0+ / S2：任务经常 > 30 分钟 / 需要跨重启继续 / 出现"任务中途必须问人"的真实案例（编码任务里少见）/ 需要群看板 + `ownerUserId` 绑定 / 需要固定巡检（可先用 scheduler 承担）。

> 注：§10 的"为什么不直接用 subagent"对比仍然成立，但它比的是**长期任务面**；对"当场下单、几十分钟完成"的常见任务，L0 明显更划算。

**建议：用 S0 跑两周真实使用（成本 0），再拿数据决定要不要 S0+ / S2——而不是先写 2k 行去猜需求。**

## 1. 现状：为什么它一定是同一个对话（代码事实）

| 事实                                                            | 位置                                                                                     | 后果                                            |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 会话键 `clientId = plugin:<pluginId>:<accountId>`               | `server/agent-service-daemon.ts:1169`                                                    | accountId 决定落到哪条会话                      |
| accountId 由渠道插件按 **peer** 生成（`feishu:<chat_id>` 这类） | `plugins/feishu/index.mjs`（sessionRoutes）、`plugins/telegram/channel-behavior.mjs:212` | 同一个群/私聊 → 永远同一条会话                  |
| 只有 `/new`、`/cwd`、切模型才轮换 epoch 换 accountId            | `docs/architecture-plugins.md#外部通道会话重置`                                          | 换会话是"重置"，不是"分任务"                    |
| 无人值守提问超时 240s（`questionTimeoutSeconds`）               | `server/agent-service.ts:7178-7182`                                                      | 任务中途提问 → 4 分钟后静默超时                 |
| 无人值守审批超时 120s                                           | `server/tool-approval.ts:25`                                                             | 危险操作 → 2 分钟后默认拒绝，任务卡死或半途失败 |
| 伪客户端的会话可见性：进"别处运行中"                            | `server/client-id-utils.ts#isUnattendedClientId`                                         | 这是好消息：任务会话天然能在网页左栏被看见      |
| 插件侧客户端无释放入口                                          | 只有 `releaseSchedulerClient`（`agent-service-daemon.ts:1096`）                          | 任务会话只增不减 = 内存与 SDK 会话泄漏          |

**结论**：今天的渠道 AI 是"接待员兼施工队"，接待台和工地是同一个房间。要做的不是给这个房间加隔断，而是**把工地搬到独立房间，并给接待员一份施工单和一部对讲机**。

## 2. 目标模型：三层 + 一本任务簿

```
                 ┌──────────── 人 ────────────┐
                 │  飞书 / QQ / Telegram / …  │
                 └──────┬───────────────▲─────┘
        入站（收单）    │               │   出站（报告 / 请求）
                        ▼               │
   ┌──────────────────────────────┐    │
   │ 控制面会话                    │    │   ← 只挂：message / task / read
   │ plugin:<channel>:<peer>       │────┘     **不挂** bash / write / edit / patch
   │ 角色：Dispatcher（接待台）    │
   └───────────┬──────────────────┘
               │ 开任务（Task 簿，宿主单源）
               ▼
   ┌──────────────────────────────┐
   │ 执行面会话（每条任务一条）    │   ← 全套工作工具；独立 cwd / 模型 / 预算 / 审批策略
   │ plugin:<channel>:task-<id>    │
   └───────────┬──────────────────┘
               │ onRunEvent（按 runId 认领）
               ▼
   ┌──────────────────────────────┐
   │ 回传面：报告 / 提问 / 审批     │ → 渠道 send（proactive 决定可达）
   │ 不可达 → Web 收件箱 + 待补发   │
   └──────────────────────────────┘
```

三条分工铁律：

1. **控制面不干活**：不是提示词约定，而是**工具白名单**（没 `bash`/`write` 它想干也只能开任务）。复用 bot 的按会话工具白名单机制（`botToolRegistrationAllowed`，`agent-service.ts:10327`）。
2. **执行面不接单**：任务会话**不挂** `task` 工具（防递归开任务）、不挂 `message`（防它自己乱发渠道）。
3. **回传不经过对话**：报告走渠道 `send`，**不**注入任何会话（不碰 `deliveryMode` 门）。

## 3. 任务实体与状态机

```ts
interface ChannelTask {
	id: string; // "t-7f3a"（渠道里可引用：#t-7f3a / /open t-7f3a）
	title: string; // ≤24 字，AI 生成，用于报告抬头与列表
	brief: string; // 任务说明（进执行面首条 prompt）
	origin: {
		// 可追溯：谁在哪个群、哪条消息下的单
		channel: string;
		peerId: string;
		thread?: string;
		messageId?: string;
	};
	/** 发起人（群消息里也必须落到人）：飞书 sender.open_id / TG from.id / QQ author.id。审批与 DM 报告都以它为锚。 */
	ownerUserId: string;
	/** 报告投递目标，与 origin 分离：origin 记来源（可能是群），reportTo 决定发去哪（通常 = 发起人私聊）。 */
	reportTo: { channel: string; peerId: string; thread?: string };
	execution: {
		accountId: string; // plugin:<channel>:task-<id> 的路由键
		conversationId?: string; // 首轮回执后写入，用作精确回投
		cwd: string;
		isolation: "session" | "worktree" | "sandbox"; // 见 §5
		model?: string;
		thinkingLevel?: string;
	};
	policy: {
		reportOn: Array<"start" | "milestone" | "end" | "error">; // 默认 ["start","end","error"]
		digestEveryMs?: number; // 长任务可选，默认关
		askTimeoutS: number; // 覆盖无人值守默认 240s
		approval: "bridge" | "policy" | "deny"; // 见 §7
	};
	budget: { maxTurns?: number; maxMinutes?: number };
	status: "accepted" | "running" | "waiting_user" | "done" | "failed" | "cancelled" | "orphaned";
	artifacts: { files: string[]; conversationId?: string; sessionId?: string };
	createdAt: number;
	updatedAt: number;
	lastReportAt?: number;
}
```

状态机：

```
           ┌──────────► cancelled（/stop t-7f3a，任何状态可进）
           │                ▲
accepted ──┴──► running ────┘
                  │  ▲
      提问/审批 ──│  │── 用户回答 / 超时（按策略继续或失败）
                  ▼  │
             waiting_user
                  │
                  ├──► done（run_end 且 stopReason=end）
                  ├──► failed（run_end 且 error / 预算耗尽）
                  └──► orphaned（宿主重启，见 §8）
```

终止即释放：`done`/`failed`/`cancelled` 三态统一走 `releaseTaskClient(taskId)`（仿 `releaseSchedulerClient`），并写一条终态报告。

## 4. 开任务：三条路径 + 判定表

| 路径     | 触发                                                            | 行为                                                                    | 默认                      |
| -------- | --------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------- |
| **显式** | `/task <说明>`、`/t <说明>`、消息以 `任务：` 开头               | 立即开任务，回执 `已受理 #t-7f3a`（含标题）                             | ✅ 开启                   |
| **提案** | 控制面 AI 判断"这是多步活"，调 `task_propose`，宿主**不**立即开 | 渠道回一条确认卡：`将开任务 #t-7f3a：<标题>｜1 开始 / 2 先聊 / 3 改为…` | ✅ 开启                   |
| **自动** | 私聊 + 提案通过预算                                             | 直接开，只在回执里告知                                                  | ❌ 默认关（`/auto` 打开） |

判定维度（控制面 AI 的提案依据，也是"别把闲聊变任务"的闸门）：

| 维度                    | 倾向开任务                                       |
| ----------------------- | ------------------------------------------------ |
| 是否需要改文件 / 跑命令 | 是                                               |
| 预估轮次                | > 2 轮                                           |
| 是否已有同名任务在跑    | 是 → 提示 `#t-… 已在跑`，不重复开                |
| 来源                    | 群聊且未 @ → **永不自动**；私聊可提案            |
| 预算                    | 超出 `maxTurns`/`maxMinutes` 的请求 → 拒绝并说明 |

防递归：执行面会话**不挂** `task` 工具（否则任务里再开任务，配额与报告都会失控）。

## 5. 隔离：四档，默认 L1、自动升档

| 档                | 会话                      | 工作目录                                    | 适用                                      | 何时自动选                                    |
| ----------------- | ------------------------- | ------------------------------------------- | ----------------------------------------- | --------------------------------------------- |
| **L1 独立会话**   | 新 conversation           | 与控制面同项目 cwd                          | 只读分析、查资料、总结、写报告            | 默认                                          |
| **L2 独立工作树** | 新 conversation           | `git worktree` 新分支                       | 改代码、且**同仓库已有 running 任务**     | 检测到同 cwd 已有 running → 自动升 L2         |
| **L3 沙盒**       | 新 conversation           | `docs/architecture-sandbox.md` 的沙盒工作区 | 高风险/不可信输入（外部链接、陌生人指令） | 渠道来源不在白名单 / 用户 `/task --sandbox`   |
| **L4 周期任务**   | 新 conversation（可复用） | 固定 cwd                                    | 定时巡检、日报                            | 显式 `/task --every 1h`（可选接 `scheduler`） |

硬约束：

- **cwd 变更必须走 `server/workspace-queue.ts`**（红线 `workspace-queue`）；`chatFromPlugin` 的 cwd 在首次创建时由 `checkPluginCwd` 校验（`server/client-id-utils.ts`），之后该会话 cwd 固定。
- 工作树由宿主创建（不要指望执行面 AI 自己 `worktree` 工具兜底：它不知道"还有别的任务在用同一目录"）。
- 同一 cwd 的并发任务数 > 1 且要写文件 → **必须** L2/L3，否则互相覆盖。

## 6. 回传：报告回路

事件 → 报告映射（事件源：`onRunEvent`，按 `runId` 认领，`server/plugins.ts:164`）：

| 事件                          | 报告                                                         | 形态         |
| ----------------------------- | ------------------------------------------------------------ | ------------ |
| `run_start`                   | `#t-7f3a 已开工：<标题>`                                     | 一行，可关闭 |
| 预算 50% / 每 `digestEveryMs` | 进度摘要：轮次、改了哪些文件、当前卡点                       | 可选，默认关 |
| `run_end` + `stopReason=end`  | 结论报告：**结论 / 改了什么 / 怎么验证 / 下一步 / 打开会话** | 主报告       |
| `run_end` + error             | 失败报告：原因 + 建议（`/open` 看详情、`/retry t-7f3a`）     | 主报告       |
| 超预算                        | `#t-7f3a 已停止：超出预算（12/10 轮）`                       | 主报告       |

报告纪律（防刷屏、防爆）：

1. **正文 ≤ 1500 字**，超长结论转附件或 web 深链；`details` 仍受 64KB 红线约束。
2. **每任务最多 6 条**（start + 4 进度 + 1 终态），超出只更新不新增（渠道发新消息要花额度/配额）。
3. **必须带可执行指令**：`/open t-7f3a`（→ `host.sessions.open(conversationId)`，`docs/architecture-plugins.md#项目--会话-api`）、`/stop t-7f3a`。
4. **可达性降级**（`proactive` 能力）：

| `proactive`                       | 报告怎么发                                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `always`（飞书/TG/Discord/Slack） | 直接发；失败重试 2 次后落 Web 收件箱                                                                                                            |
| `windowed`（QQ / WhatsApp）       | 直接发 → 失败则落 Web 收件箱并标 `pending_delivery`；**用户下一条消息到达（窗口重开）时批量补发**（这是 QQ 场景的关键，不做就等于报告静默丢失） |
| `webhook-only`（企微）            | 只推单向卡片，不带期望回复的指令                                                                                                                |

## 7. 请求：提问桥与审批桥（本设计的核心件）

### 7.1 为什么必须桥

- `ask_user_question` 在伪客户端（`plugin:`/`scheduler:`）下按 `questionTimeoutSeconds` 超时（默认 240s，`agent-service.ts:7180`）；
- 且**浏览器看不到**：`notifyUserQuestion` 只做手机推送（`agent-service.ts:5821`），伪客户端没有 socket 会话，`emitQuestionQueue` 也到不了人；
- 结果：任务里的 AI 一问就"哑火" 4 分钟，然后被当成"用户没回应"继续跑。这正是你说的"AI 没法向我发请求"的根因。

### 7.2 提问桥流程

```
任务会话 ask_user_question
   → 宿主拦到 pending question（audience=user，conversationId 属任务会话）
   → 任务簿查到 task → 渠道发：
       #t-7f3a 需要你确认
       1) 允许改 public/index.html  2) 只改 src/  3) 自行回答
       （回数字或直接回一句话；15 分钟内有效）
   → 渠道入站消息（同 peer）匹配到「该任务正在等待回答」→ 解析答案
   → 宿主按 question_answer 同路径 resolve PendingQuestion
   → 超时：渠道回「已超时，任务按保守默认继续」+ 任务状态转回 running
```

要点：

- **不新增"永不超时"**（无人值守必须有兜底）；`policy.askTimeoutS` 只允许在 60–1800s 之间放大。
- **答案解析要保守**：只接受 `1/2/3`、选项文本前缀、或显式 `答：…`；模糊回复不猜，回一句"没听懂，请回数字"。
- **撤回要跟着走**：`question_retracted` 事件（`agent-service.ts:7203`）→ 渠道那条提问消息作废（编辑成"已在网页回答"或补一条）。
- **伪客户端提问在网页不可见**这件事，顺手修：hub 把镜像写进消息中心收件箱，网页也能看见与回答（可选，P1）。

### 7.3 审批桥 vs 审批策略（三选一，按任务配）

| 模式                 | 行为                                                                                                                                                                                                                     | 适合                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| `policy`（推荐默认） | 任务的工具审批**自动判定**：只读 + 工作区内写入放行；危险操作（`rm -rf`、系统目录、`.ssh`、`chmod 777` —— `server/tool-approval.ts:47` 的既有规则集）直接拒绝并报告"该任务被限制为只读，请改 L2/L3 或 `/approve t-7f3a`" | 只读/沙盒任务               |
| `bridge`             | 把 pending approval 镜像到渠道（`#t-7f3a 请求执行：rm -rf build｜1 允许 2 拒绝 3 本任务全程允许`），回填审批结果                                                                                                         | 需要写文件/跑命令的 L2 任务 |
| `deny`               | 一律拒绝（超时兜底行为），只用于外部/陌生人来源                                                                                                                                                                          | L3 高风险                   |

注意：审批桥必须复用既有审批队列与超时兜底（`unattendedApprovalTimeoutMs`，`tool-approval.ts:33`），**不要**另造一套"渠道审批"状态机。

## 8. 控制面落在私聊还是群聊

### 8.1 先纠正一个容易搞错的前提

本项目 11 个渠道的会话键**不是「每个群一条」**，而是「**发送者 + 会话空间 + thread**」：

| 渠道     | 会话键                                           | 位置                               |
| -------- | ------------------------------------------------ | ---------------------------------- |
| 飞书     | `sha256([openId, chatId, threadId])` —— 含发送者 | `plugins/feishu/runtime.mjs:5`     |
| Telegram | `${chat.id}:${message_thread_id                  |                                    | 0}:${from.id}` | `plugins/telegram/channel-behavior.mjs:95` |
| QQ       | `peerAccountId(authorId)` → `qq_<hash>`          | `plugins/qq/index.mjs:81`、`:1033` |

推论（三条，都直接影响选型）：

1. **同一个群里，A 和 B @机器人 → 落到两条不同会话**，上下文天然不互相污染。
2. **群里别人回 `1` 不会误批你的审批**（他的回复进他自己的会话，匹配不到你的 pending question）——安全，但也意味着**群里谁都批不了你的审批**。
3. 报告若发到群里（peer = 群 chat），那是**写给全群看的广播**：后续任何人的回复都进各自会话，这条广播**不能当交互入口**。

### 8.2 结论：私聊做控制面，群聊做看板

| 维度     | 私聊（控制面）                                               | 群聊（看板/广播）                                                                                                       |
| -------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 任务归属 | 唯一 owner，无歧义                                           | 归属仍清晰（per-sender 会话），但**旁人都能看见同一条广播**                                                             |
| 审批     | ✅ 唯一人能批，回复能命中                                    | ❌ 发起人以外的回复落不进该任务；发起人自己在群里回也容易串会话                                                         |
| 报告内容 | 可以给全文/路径/代码片段                                     | 必须 redact（路径、内网链接、代码），只给一行摘要 + 深链                                                                |
| 噪音     | 只打扰你                                                     | 每任务 6 条报告 = 刷屏；群里默认应压到 1–2 条                                                                           |
| 平台准入 | 飞书可在可用范围内主动开 DM；QQ 单聊需先有会话（`windowed`） | 机器人在群里即可发（飞书 `groupResponseMode=mention`，`plugins/feishu/bot-bridge.mjs:343`；TG/Discord/Slack/QQ 都要 @） |
| 现成机制 | 各渠道已支持                                                 | 各渠道已有「群默认必须 @ 才响应」的门                                                                                   |
| 实现成本 | 低（per-sender 会话天然一对一）                              | 中（要 redact、要压噪音、要处理"发起人没有 DM 通道"）                                                                   |

**默认形态（推荐）**：

- **私聊** = 唯一完整的控制面：`/task`、审批、完整报告、`/open`。
- **群聊** = 只读看板：允许 `@bot /task …` 下单，但只回两条——`#t-7f3a 已受理（发起人：张三）` 与终态一行摘要（可关）；**详细报告与所有审批一律回发起人私聊**。
- **降级**：发起人从未与机器人有私聊通道（QQ 最常见）→ 报告回群但强制 redact，或只落 Web 消息中心收件箱并 `@` 发起人提示去看。

### 8.3 三条硬规则（进任务簿，不靠提示词）

1. `ownerUserId` 必填，群消息也必须解析出人（飞书 `sender.sender_id.open_id`，`plugins/feishu/bot-bridge.mjs:314`；QQ `author.id || author.user_openid`，`plugins/qq/index.mjs:895`）。
2. **审批只接受 owner 的回复**；非 owner 回数字 → 静默忽略（不回"仅发起人可审批"，否则会泄露"这里有个别人正在跑的任务"）。
3. `origin`（来源，可能是群）与 `reportTo`（投递目标，通常 = 发起人私聊）**必须分离**；群里下单时两者不同，这是本设计唯一必须加的两个字段。

## 9. 多任务与生命周期

| 项         | 设计                                                                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 并发       | 每 peer running ≤ 2，全局 ≤ 4（可配）；超出时排队并在渠道回"前面还有 #t-…，已排队"                                                                       |
| 排队可视化 | `/tasks` 列表：`#t-7f3a running 2 分钟 · 飞书 · 产品研发群`                                                                                              |
| 释放       | 终态 → `releaseTaskClient(taskId)`（**新增**，仿 `agent-service-daemon.ts:1096` 的 `releaseSchedulerClient`：删 client、`dispose()`、poke 外部运行列表） |
| 重启恢复   | 宿主启动时任务簿里 `running` 全部标 `orphaned`，并在渠道发一条"任务 #t-… 因重启中断，`/resume t-…` 重跑或 `/open` 查看"；不自动重跑（避免重复副作用）    |
| 容量       | 任务簿保留 30 天 / 200 条；终态记录保留摘要，正文不存                                                                                                    |
| 幂等       | 任务 id 由 `channel + peer + messageId` 派生，重复投递同一消息不会开两条任务                                                                             |

## 10. 与现有能力的复用映射（能不新造就不新造）

| 需求             | 现有能力                                                        | 做法                                 |
| ---------------- | --------------------------------------------------------------- | ------------------------------------ |
| 多会话并发       | `chatFromPlugin` + accountId                                    | 直接用（新 accountId = 新会话）      |
| 首轮之外继续投喂 | 回执 `conversationId` → `host.chat({conversationId})`           | 直接用                               |
| 报告事件源       | `onRunEvent`（`runId`/`conversationId`/`stopReason`/`message`） | 直接用，按 runId 认领                |
| 任务工具白名单   | bot 的按会话工具过滤（`botToolRegistrationAllowed`）            | 复用同一套门控，加 `dispatcher` 标记 |
| 提问/回答        | `PendingQuestion` + `question_answer`                           | 桥接，不重写                         |
| 审批             | `server/tool-approval.ts` + 超时兜底                            | 桥接/策略化，不重写                  |
| 打开会话给用户看 | `host.sessions.open(id)` / `host.openSession`                   | 直接用（`/open` 指令）               |
| 重启恢复         | `server/orphan-manager.ts` 的 adopt 判定                        | 复用判定思路，任务簿只标 `orphaned`  |
| 周期性任务       | `server/scheduler`                                              | L4 可选绑定，不重复实现 cron         |
| 通知兜底         | `host.notify` + 消息中心收件箱                                  | 渠道不可达时落这里                   |

### 为什么不直接用 subagent 干这个活

|                | 任务 = 独立会话（本设计） | 任务 = subagent                                                        |
| -------------- | ------------------------- | ---------------------------------------------------------------------- |
| 父会话必须常驻 | 不需要                    | **需要**（完成通知走父会话投递门 `deliveryMode`，压缩/等回话时会排队） |
| 长任务/跨重启  | 可独立存活、可 `orphaned` | 依附父会话生命周期                                                     |
| 并发数量       | 每 peer 2–4，可排队       | 受 subagent 最大并发与父轮次约束                                       |
| 报告路径       | hub → 渠道（不经对话）    | 父会话里的一条 notice → 还要再转发到渠道，链路更长                     |
| 适用           | **渠道收单的长时间施工**  | 主对话里的并行调研/小任务                                              |

结论：**subagent 适合"主对话里顺手并行"，渠道任务面适合"独立施工 + 独立回报"**，两者并存不冲突。

| 红线                                | 本设计是否触碰   | 规避                                                             |

## 12. 分期与验收

### P0 — 显式开任务 + 报告回传（3–4 人日）

- 任务簿（`server/channel-task-plane.ts`）+ `/task` `/tasks` `/open` `/stop` 四条指令
- 执行面会话用 `plugin:<channel>:task-<id>` 开；`releaseTaskClient` 补齐
- `run_end` → 一条终态报告（飞书；`proactive=always`）
- 验收：飞书里 `/task 把 README 的安装段落改成 pnpm` → 渠道收到 `已受理`，**控制面会话里没有出现改文件的工具调用**，2 分钟后收到结论报告 + `/open` 能打开执行会话；`/tasks` 能看到历史

### P1 — 请求回路 + 失败降级（4–6 人日）

- 提问桥（含超时、撤回、模糊回复不猜）+ 审批 `policy`/`bridge`
- QQ `windowed` 报告的 `pending_delivery` 与"窗口重开批量补发"
- 并发配额与排队、重启 `orphaned` 标记
- 验收：任务中途提问 → 飞书里回 `1` → 任务继续；把 `PI_WEB_UNATTENDED_APPROVAL_TIMEOUT=1` 调小 → 渠道收到"审批超时已拒绝"；QQ 断窗后报告在网页收件箱可见、下次发消息时补发一次

### P2 — 隔离档与隐式提案（3–5 人日）

- L2 工作树 / L3 沙盒自动升档；AI 提案式开任务（含"已有同名任务"去重）
- 消息中心视图加「任务」页签（与收件箱并列）
- 验收：同仓库两个写文件任务 → 第二个自动进工作树，互不污染；群聊未 @ 不触发提案

## 13. 风险与不做

| 风险                                    | 对策                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------- |
| 控制面 AI 仍然"顺手干活"                | 工具白名单物理限制（没 bash/write）+ 单测断言 dispatcher 会话的工具集            |
| 任务会话泄漏内存                        | `releaseTaskClient` + 并发上限 + 终态清理；任务簿容量上限                        |
| 报告刷屏 / 烧额度                       | 每任务 ≤6 条 + 终态只更新不新增 + `windowed` 渠道合并补发                        |
| 提问桥误解析（用户随手回"1"）           | 只在"该任务正在等待回答"窗口内匹配；模糊不猜；15 分钟失效                        |
| 重启后重复副作用                        | `orphaned` 不自动重跑，必须人确认 `/resume`                                      |
| 任务之间上下文隔离过度（AI 不知道前情） | 首条 prompt 注入 `brief` + 控制面最近 3 轮摘要（**摘要而非全文**）               |
| 渠道 target 差异                        | 复用消息中心的 `peerId` 目录（`docs/proposals/message-hub-feasibility.md` §4.6） |

不做：

1. **不**让任务会话之间共享上下文（要共享就变成一个大任务）。
2. **不**做"任务自动重跑"（副作用不可逆）。
3. **不**把任务完成通知塞进某个网页对话里冒充用户消息。
4. **不**为 QQ 的主动消息额度做绕过/攒额度。
5. **不**在任务面提供 `message`/`task` 工具（防递归、防乱发）。
