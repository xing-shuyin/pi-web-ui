The rules below are distilled from past production incidents and hard core-architecture constraints; they must be followed strictly when writing code.

## 一、Communication protocol and data security

- **The `details` field is hard-capped at ≤64KB**: over-limit payloads are dropped whole on both delivery and persistence. New tools must never stuff in large raw payloads (follow `present-files-tool.ts` for excerpt budgeting); frontend rendering must degrade gracefully when details are absent (`present-items.ts`).
- **Server-side URLs must be wrapped in `appUrl()`**: including `/ws`, `/api/*`, `/plugins/*`, `/themes/*`, so sub-path reverse-proxy deployments never 404.
- **Decode the token cookie before validating it**: `pi_web_token` is stored via `encodeURIComponent`, so the server must call `decodeCookieToken` before validating (`server/auth-cookie.ts`).
- **The passphrase form on the logged-out page must use a native POST** (`POST /__pi/auth`, `server/auth-login.ts`): account field `autocomplete="username"` + password field `autocomplete="current-password"` + a real form submit (no JS `preventDefault()` building a `?token=` redirect), otherwise browser password managers never offer to save the password; the return URL always goes through `sanitizeNextPath` (no open redirects, `token` stripped) (guards: `tests/unit/auth-login.test.ts` · `tests/unit/unauthorized-page.test.ts`).
- **Never use the home directory as the workspace root**: setting `$HOME` as the workspace root is forbidden, preventing a recursive scan over a bad mount from freezing the event loop.
- **Far-future timers must be sliced with `armDelay`**: in Node.js, `setTimeout` above 2^31-1 milliseconds (about 24.8 days) overflows the integer and is truncated to 1ms, causing an infinite loop. Anything beyond 6 hours must be sliced (guard: `plugin-cron-overflow-test.mjs`).
- **Text decoding and line counting rules**: previews and attachments always use `decodeText` (UTF-8 → GBK → latin1); `countLines` does not count a trailing empty line, and the frontend must pop the trailing empty string. See [`architecture-attachments.md`](architecture-attachments.en.md).

## 二、Tool definitions and prompt rules

> Complementary to 「编码约定」(Coding conventions) in [`development.md`](development.en.md) and to [`tool-context-budget.md`](tool-context-budget.en.md): this section is the **prohibition view**, those two are how it works.

- **Tool prompts split responsibilities across three places (never restate across them)**:
  1. The Tool Schema `description`: only "what it does and its boundaries", ≤600 characters;
  2. `promptSnippet` in the system prompt: only "when to trigger", ≤80 characters, no tool-name prefix;
  3. `promptGuidelines` in the `Guidelines` block: only "call order / prohibitions / cross-tool routing".
     _Must be tight, plain English; violations are caught by the guard unit test_ (guard: `tests/unit/tool-prompt-hygiene.test.ts`). The model-visible text for `bash` / `edit` has its single source in `server/tool-prompts.ts`.
- **Editing capability has exactly one tool name**: lenient matching is the `soft: true` parameter of `edit` (`server/edit-tool.ts`); adding a second editing tool such as `edit_soft` is **forbidden** — splitting one capability across two tools forces the model to choose and doubles the toggle, prompt, and approval-rule wiring for no reason. Old saved toggles only need folding in during normalization, with no runtime branch left behind.
- **Hard constraint on tool lazy loading: never break the prefix cache**:
  Vendor prompt caches require an identical system-prompt prefix. The system prompt's `{{tools}}` catalog must stay complete and unchanged by load state; newly loaded tool highlights enter the conversation with the `load_tools` acknowledgement; the registry may only be appended to (`toolsAdded`) and must never be edited in place or removed (guard: `tests/lazy-tools-test.mjs`, doc: [`tool-context-budget.md`](tool-context-budget.en.md)).
- **One tool with multiple execution paths must have a single prompt source**: for bash, the native, terminal, and adaptive routing paths share `server/tool-prompts.ts`; hardcoding or copying the description inside an execute override is forbidden.
- **The default timeout for bash / powershell has its single source in `server/bash-timeout.ts`**: when the model omits `timeout`, execution uses `DEFAULT_BASH_TIMEOUT_SEC` (120s, overridable via `PI_WEB_BASH_TIMEOUT_SEC`), and oversized values are clamped to `MAX_BASH_TIMEOUT_SEC` (1 hour) — never fall back to "no timeout" and let the session watchdog (20 minutes by default) collect the body. All three execution paths (`bash-tool.ts` local/SSH, terminal takeover in `terminals.ts`, powershell in `agent-service.ts`) must go through `withDefaultBashTimeout()`; writing their own numbers or treating `0` as "unlimited" is forbidden (the SDK throws `Invalid timeout` on 0/negative) (guard: `tests/unit/bash-timeout.test.ts`).
- **Schemas carry field names and types only**: exported JSON Schema must not include decorative constraints such as `minItems` / `maxItems` / `minimum` / `maximum` / `minLength` / `anyOf`, and must not write a `description` for self-explanatory fields; constraint validation moves into the handler (`readArguments` and friends), candidate values go in `enum`, and what each parameter accepts goes in that parameter's **single** signature line (`communicate`, and `action`/`op` in `browser_page`, are the models). Only a few genuinely non-obvious fields (`read.offset`, `bash.persist`, `edit.soft`, `present_files.items[].focus`, `skill.name`) keep one short note. For `write` / `grep` / `find`, which ship with the SDK but whose wording is ours, `withSlimPrompt()` in `server/tool-prompts.ts` swaps in our text and schema while implementation stays on the SDK (guard: `tests/unit/tool-schema-slim.test.ts`, which also compares field names against the SDK's built-in definitions — SDK parameter additions or removals fail it outright).
- **Tool disabling has exactly one funnel**: `disabledAgentTools` (toggles) and `toolOnDemandTools` (on-demand list) are unioned by `effectiveDisabledAgentTools()`, subtraction only, with no second gating path; writing another `setActiveTools` filter for a new toggle is forbidden (guard: `tests/unit/tool-manager.test.ts`, the "on-demand list" case).
- **A new tool touches three places**: a new toggleable tool must be registered in `tool-manager.ts` (the `AGENT_TOOL_CATALOG` source of truth), in `agent-service.ts` (the `customTools` list), and in `tests/unit/tool-registration.test.ts`; built-in tool overrides must go through `tool-overrides.ts`.
- **Per-tool wording is editable**: user-customized text is stored as a preference only in `toolPromptOverrides`; a new configurable dimension must be patched in all three places — the patching logic, the wire protocol, and the settings-page editor (guard: `tests/unit/tool-prompt-overrides.test.ts`).

## 三、UI layout and style rules

> The shared baseline is `web/src/styles.css`; themes are covered in [`architecture-core.md`](architecture-core.en.md)「主题切换」(Theme switching).

- **Project selection state follows only the currently open project**: running and unread states are expressed by the project badge, and no other project's title may get a state background; keep normal hover feedback.

- **CSS variables must be defined before use**: an undefined `var(--x)` voids the entire CSS declaration; inline code's `--link-soft` must meet the text-token ≥4:1 contrast floor on `--bg` (guards: `tests/unit/css-tokens.test.ts`, `theme-text-contrast.test.ts`; the inline-code check has been folded into the text-token guard).
- **Top-pinned overlays in the desktop app (Electron) must leave room for the macOS traffic lights**: the buttons are drawn natively and float above the WebView without taking layout space (`trafficLightPosition` in `desktop/main.ts`), so the topbar yields via `padding-left`; any `position: fixed; top: 0` top-pinned overlay (`.panel-drawer` in phone / narrow split-pane layouts) must push down with `var(--desktop-titlebar-h, 0px)` (`padding-top` or `top: calc(...)`), otherwise the project list header lands right on the close button in narrow split panes. That token is 38px only under `body.is-desktop-mac:not(.is-desktop-fullscreen)` and 0 elsewhere.
- **Text on a solid accent background must use `--accent-contrast`**: `background: var(--accent)` with `color: #fff` turns into white-on-white in light accent themes (the pure white of `flow`/`wallpaper-flow`, `#e2e8f0` in `wallpaper-obsidian`, `aetheris`/`cyberpunk`/`nord` and others), making buttons vanish. Always write the foreground as `var(--accent-contrast, #fff)`; same for plugins: a privately prefixed alias (e.g. `--xxx-accent: var(--accent)`) **must be declared as a pair** with `--xxx-accent-contrast: var(--accent-contrast, #fff)`, and reusing the host's global `.btn.primary` is preferred — never a one-way background alias with hardcoded white text; a translucent `color-mix(… var(--accent) 30% …)` tinted background uses `var(--text)`; if a theme sets `--accent` to a light color it must also declare the inverted `--accent-contrast` (guards: `tests/unit/accent-contrast.test.ts`, `semantic-contrast.test.ts` dynamic symbol tracing of aliases).
- **Solid semantic backgrounds follow the same rule via `--on-*`**: `background: var(--green|--red|--amber|--blue|--send-blue|--stop-red)` with `color: #fff` vanishes just the same (in the default theme white on `--amber` is 1.67:1, on `--green` 1.92:1, on `--red` 2.77:1). Write the foreground as `var(--on-green|--on-red|--on-amber|--on-blue|--on-send-blue|--on-stop-red)`; status colors derive by picking whichever of white/dark has higher contrast, action colors (blue/send/stop) keep white text when it reaches ≥3:1, and themes derive them automatically via `make-light-theme.mjs` (guard: `tests/unit/semantic-contrast.test.ts`).
- **A theme's "text tokens" need light/dark floors**: `--text-faint` (3.05:1), `--accent` (3.5:1), `--amber/--green/--red/--blue/--link/--link-soft/--info-blue/--skill-blue/--auth-green/--plugin-purple/--amber-text/--red-text/--err-text/--md-strong/--code-text` (4.5:1) must have enough contrast on `--bg` and `--bg-elev2` — a light theme copying the dark defaults wholesale blurs warning text, status chips, and links together (we once had `--plugin-purple` at 1.50:1). The `TEXT_FLOORS` in `make-light-theme.mjs` keep hue-darkening automatically; hand-written themes declare it themselves (guard: `tests/unit/theme-text-contrast.test.ts`).
- **Long text and long paths must not overflow**:
  - Line containers (flex containers) need `min-width: 0` and `max-width: 100%`;
  - Wrappable text (prose inside `.md`, paths) needs `overflow-wrap: anywhere` and `word-break: break-word`;
  - Single-line text uses `overflow: hidden` and `text-overflow: ellipsis`;
  - Standalone panels and modal lists (the plan board, sandbox diffs) must declare `overscroll-behavior: contain` so the page scrollbar cannot be pushed through; but in-flow tool output and code blocks — anything not a standalone overlay — must never declare `overscroll-behavior: contain`, which would create a wheel black hole that locks the surrounding conversation stream (guard: `tests/unit/text-wrap.test.ts`).
- **Card headers and action-button placement rules**:
  - The right end of a collapsible card header (`.chead`) holds **only its own copy button** (`.chead-copy`, pinned with `flex: none`); message-level action buttons must never hang inside a card header; the header hint text sets `flex: 0 1 auto` + `min-width: 0` to absorb shrinking, with a max-width cap on narrow screens — `flex-wrap: wrap` is forbidden.
  - The message-level action bar (`.msg-actions`) applies only to assistant messages with body text and to user messages; the assistant action bar must anchor right after the last body block, never drifting away from tool cards.
- **UI extension points and overlay rules**:
  - Dropdown menus must portal to `body` + `fixed` layout so parent `overflow` cannot clip them;
  - Overlays consistently use `useFloatingPanel`; force-closing an overlay inside a `scroll` event is forbidden (recompute the anchor only, close on mousedown/Escape);
  - **Stacked overlays must never hardcode z-index**: any overlay that can sit above another overlay (tool details, file preview, image preview, fullscreen diff, approval/authorization modals…) takes its layer number from `useOverlayZIndex()` in `web/src/overlay-stack.ts`; inline `style.zIndex` overrides the theme; the stack starts at `var(--z-overlay-stack)` (100000) and grows in open order, with transient notices pinned at `var(--z-notice)` (100050) always on top. **Stop picking yet another bigger number to "out-rank" others** (stacking 100001/100005 only buries the next nested overlay); modals that need their own stacking context use the `.overlay-layer` shell. Static overlays top out at 10000 (guard: `tests/unit/overlay-stack.test.ts`).
  - The side dock (`SideDock`) is an in-flow flex item whose floating mode is controlled by `sideDockFloat`; never hardcode fixed positioning that covers the side buttons.
- **The strip above the composer belongs to the message area**: the quick-phrase row merely floats over it, and body text shows through the gaps **between** chips (the chips are solid little cards that must hold their own against text underneath). The strip height has its single source in `.main`'s `--composer-strip` (= `--composer-pad-top` + `--quick-row-h` as measured and written by ChatInput + 6px); changing the composer's top padding or the phrase row's spacing must account for three places at once: the negative margin on `.messages-wrap`, the bottom padding on `.messages`, and the container-bottom-anchored `.scroll-bottom` / `.qn-rail` (all must add `+ var(--composer-strip)` back), and the phrase row must never go back to `position: absolute` (it would fight the pills and floats for the same strip and always overlap when wrapping). Guard: `messages-behind-composer.test.ts`.
- **Drag and touch interaction rules**:
  - Icon editing and dragging must listen to Pointer events; HTML5 DnD is forbidden (touchscreens do not fire it); built-in icons must be registered in `host-icon.tsx`; menu row text is uniformly 12.5px (guards: `host-icon.test.ts`, `topbar-overflow-menu.test.ts`).
  - The mobile horizontal swipe gesture (`swipe-drawer.ts`) must stay clear of the system edge-swipe zone; during the gesture write inline transform directly with transitions disabled, and clear the inline value on release so the CSS class transition takes over; the mobile scrim stays mounted (guard: `swipe-drawer.test.ts`).
- **Message action semantics**: the hint shows on hover and stays short; re-ask and edit-then-re-ask truncate the original question and everything after it in the current session, then resend; fork includes the selected message and creates a new conversation; rollback opens the editor on the corresponding user question, resubmitting re-asks in the current session, cancelling leaves history untouched. See [`architecture-core.md`](architecture-core.en.md)「消息操作」(Message actions).
- **New-session initialization interaction**: switching or creating a session must focus via `focusComposer()` (except on touchscreens), any non-chat view switches back automatically, and pending attachment chips clear with the new session (guard: `composer-draft.test.ts`).

## 四、Architecture and runtime constraints

- **Goal Mode 2.0 runtime iron rule**: the main conversation acts as reviewer while the server starts a separate executor that persists to disk; rounds, generations, and stall circuit breaking are all server-controlled, and the model must never call wait/spawn itself; review instructions must inject execution evidence (`goal-evidence.ts`); aborting or closing the session stops the loop — no endless round continuation (guards: `goal-delegated.test.ts`, `goal-evidence.test.ts`, doc: [`goal-conversation-design.md`](goal-conversation-design.en.md)).
- **Reviewer delegate mode (Delegate Mode)**: once on, the main conversation only reviews and never does the work, user input is dispatched automatically to an always-on execution session; a gate forcibly intercepts write operations and subagent dispatch; plan mode outranks delegation (`server/delegate-mode.ts`, `server/plan-mode.ts`).
- **Preset dependencies and partial application**: the top-level `plugins` of an exchange document carries plugin requirement metadata only — no configuration, secrets, storage, or authorization; installation reuses an explicit `plugin_job`. Fields a partial preset does not carry must neither be defaulted nor cleared from current settings, and `plugins` must never enter runtime settings; save, apply, deferred load, and apply failure each get their own acknowledgement (see [`preset-sharing.md`](preset-sharing.en.md)).
- **Preset sharing must be strictly allowlist-sanitized**: imported external JSON must pass the allowlist validation in `server/preset-share.ts` (`preset-fields.ts`), unknown fields are dropped, and a dryRun confirms the result; spreading it into `ClientSettings` without validation is forbidden (guard: `preset-share.test.ts`, doc: [`preset-sharing.md`](preset-sharing.en.md)).
- **Atomic writes / retries have their single source in `server/atomic-file.ts`**: `writeAtomicSync` / `writeAtomic` / `readFileSyncRetry` carry **real backoff** for EPERM/EACCES/EBUSY (20/60/150/400ms) — on Windows, antivirus and indexers briefly hold freshly written files, so transient `rename` failures are normal, and spinning retries (no sleep) amount to no retry at all. The Hub upgrade worker cannot import TS, so `bin/lib/atomic-file.mjs` is generated from the same implementation by `npm run gen:atomic` (run automatically at the end of `build:server`) — never edit it by hand; a failed upgrade bookkeeping write **must not** block rollback (restore the old service first, downgrade the metadata to best-effort) (guards: `atomic-file.test.ts`, `atomic-file-generated.test.ts`, `hub-upgrade-runtime.test.ts`).
- **Windows minimized notifications**: while minimized on Windows, page visibility is inaccurate, so judge by the window rectangle (`isCollapsedWindow`); notifications must not carry a `tag` field, which the system would silently swallow.
- **Compaction soft cap needs two-layer monitoring, and model swaps must go through `applySessionModel`**: the SDK's `compaction.reserveTokens` is the **in-turn** checkpoint (the inter-tool-call gap `_compactBeforeNextAssistantResponse`) and must be computed per session as `cw - cap`; otherwise an autonomous long run (subagent / dozens of tool calls in one turn) never goes idle and never compacts (`#773`); the reserve also depends on the session's **current** model, so any bare `session.setModel()` leaves the threshold stuck on the previous model's `W - C` — always swap models through `applySessionModel`; when cap ≤ keepRecent + headroom, do not inject (otherwise every tool gap compacts again). `server/soft-cap.ts`.
- **Calling `ModelRuntime` directly requires your own `sessionId`**: the SDK injects `options.sessionId` only inside an AgentSession; modules that bypass the session and call `completeSimple` / `streamSimple` directly (quick ask, commit message generation, vision transcription, group routing) must pass `modelSessionId()` (`server/model-session.ts`: pass a stable seed for the same topic, nothing for one-shot calls), otherwise the opencode / opencode-go gateways reject the missing `x-opencode-session` header with a flat 400 `MissingSessionID` (guard: `tests/unit/model-session.test.ts`).
- **Official model catalogs are replaced as a whole**: rewrite the SDK catalog idempotently through `patch-remote-catalog.ts`, leaving no stale definitions, and it re-applies automatically after upgrades.
- **Three DSH runtime rules**: shipped presets use file: clone isolation from `preset-clones.ts`; questionnaire and filter hooks hang off agent scope; usage metrics consume live frames and assistant/message.usage (`dsh-usage.ts`). See [`dsh-engine.md`](dsh-engine.en.md).
- **Session takeover and state migration**: `take_over_conversation` relocates the runtime body itself and **is transactional** (if the source side has detached but the target side fails to attach, it moves back exactly as it was — never leave a ghost session that is "still running but held by nobody", see `#556` / `tests/takeover-rollback-test.mjs`); **the "elsewhere" row for a disconnected remnant has a grace period** (`PI_WEB_OFFLINE_ROWS_TTL_MS`, 30 minutes by default, marked `ownerOffline`, still takeover-able — closing the page mid-run on a phone and switching devices can still take over); `ask_user_question` / `browser_page` resolve the session object captured at creation (`bridgeTarget`); cross-page answers carry the owner.
- **Workspace commands must be serialized (`#872`)**: `cs.cwd` / the active conversation / runtime binding are one set of mutable state, so every command that changes them (`set_cwd` / `new_chat` / `new_cli_chat` / `switch_session` / `switch_conversation` / `fork_session` / `rollback_session` / `make_dir(setAsCwd)` / sandbox switching) goes through the session-level FIFO in `server/workspace-queue.ts` (the dispatch layer "claims synchronously, then enqueues"); session creation may declare its target via `new_chat.cwd`, and if the switch fails, no session is created (acknowledgement `ok:false`). **Forbidden**: patching cwd in each frontend call site, and writing session creation as a concurrent call that does not wait for `set_cwd`. The client-side intent source of truth is `web/src/pending-workspace.ts` (guards: `tests/unit/workspace-queue.test.ts`, `tests/unit/pending-workspace.test.ts`).
- **Host-provided packages may only be declared in `peerDependencies` (`"*"`)**: the pi extension loader scans `dependencies` only (hitting `@earendil-works/pi-coding-agent` / `typebox` triggers a warning: nested copies bypass the loader's injection and create duplicate runtime modules). This package is both an extension and a standalone server, and the server child process genuinely needs these two packages (`PI_WEB_SDK=bundled` still carries its own copy) → they land in `optionalDependencies` (npm installs them by default). Guard: `tests/unit/extension-host-packages.test.ts`.
- **Layout page renames / plugin `arrange.label` must reach the render layer**: the merge engine sets `UiSlotEntry.labelExplicit` for "explicitly specified wording"; built-in entries (topbar buttons, bottom-bar value badges) always draw hardcoded i18n and live values and yield only while the flag is raised (name-type entries override the built-in wording; value-type entries insert the name before the value without swallowing live data). Working only on the settings page = a false promise (`#555`, guard: `tests/unit/bar-item-unified.test.ts`).
- **Plugin changes must bump the version (Bump Version)**: any change to code/features/static assets (not pure docs) in a built-in official plugin (`plugins/<id>/`) must bump `version` in `manifest.json` (keep `version` in `package.json` in sync if present). Reason: the hot sync shipped with the package (`syncBuiltinPlugins`) and the updater (`plugin-updater`) both treat `compareVersions(srcVer, tgtVer) > 0` as the sole authoritative source of truth for upgrade decisions; miss the bump and existing users' old plugin code in the data directory is never hot-updated after a host upgrade, leaving defects in place (guard: `tests/unit/plugin-version-bump-guard.test.ts`).
- **A plugin's code directory is a pure cache; state lives only in `plugin-data/<id>/`**: `plugins/<id>/` is replayed on materialize/upgrade (integrity decided by the `.pi-materialized.json` receipt, half-written trees are patched in place), so settings / secrets / scheduled jobs / capability-consent flags all go through `pluginStateDir()` and must not be written into the code directory; the copy blacklist can only be decided **by relative path** in `server/fs-copy.ts` — `cpSync`'s filter receives absolute paths, and an npm -g install (whose package directory already contains `node_modules`) would filter the entire tree into an empty copy that still counts as installed (guards: `tests/unit/plugin-copy-single-source.test.ts`, `plugin-bundled.test.ts`, `plugin-paths.test.ts`, origin `#856`).
- **After changing a test plugin, update the local plugin right away**: the plugin actually loaded at runtime lives in the data directory (`<dataDir>/plugins/<id>/`, e.g. `~/.pi-web/plugins/<id>/`). When modifying or testing a built-in plugin in the workspace, besides bumping the version, copy the latest source over the corresponding plugin in the local data directory promptly, so debugging never drifts from behavior because of cached old code.
- **i18n literal requirement**: the entry values in `i18n.tsx` must be string literals (concatenation with `+` only), so the static parser in `scripts/i18n-diff.mjs` keeps working.

- **No synchronous child-process calls on the server (`spawnSync` / `execSync` / `execFileSync`)**: these three APIs fork+exec on the event-loop thread and **block until the child exits**. If the child hangs before `exec()` (reliably reproduced on Termux/Android), the main thread sits forever in `read()` on the spawn error pipe — timers, sockets, and `/api/health` all stop, and only an external watchdog can kill the process. Async `spawn` / `execFile` are not dragged out to child exit, and `timeout` only means anything for the async versions (the sync ones never even reach timeout handling). Two viable routes: switch to async spawn with a timeout; or **statically derive** the answer (the npm prefix in `server/global-loader.ts` and the computed prefix in `server/dsh/runtime/runtime-root.mjs` were both changed this way). The scan covers **plugin main-process code** (`server/plugins.ts` loads `plugins/<id>/index.mjs` into the main process with `import()`, sharing the event loop with the server; standalone processes such as `bin/`, `assets/`, `build.mjs` are excluded). Existing occurrences are registered **by count** in the guard's shrink-only list; new code should go straight to async or static derivation (guard: `tests/unit/sync-child-process-guard.test.ts`, origin `#830`).

## 六、Source comments

- Do not write source comments by default; delete comments that restate code, file-header introductions, section headings, historical changes, temporary notes, and commented-out dead code, so stale explanations never mislead later judgment. Maintenance rules and architecture notes belong in the matching `docs/` document.
- Keep license headers, types, build/check instructions, metadata read at runtime, and short notes that explain non-obvious security boundaries or constraints; judge text inside strings, regexes, and templates by its actual purpose.
- Tests locate source by real code structure or stable identifiers, never by the text of ordinary comments.

## 七、Terminal command execution (stall prevention)

Hangs have only five root causes; write rules **by root cause**, not by patching each "command that looks stuck" (`| sort` merely buffers so progress is invisible — it reads to EOF and never deadlocks on its own):

1. **Waiting on stdin**: `npx` install confirmation, `git commit` without `-m`, REPLs, `read -p`. Force non-interactive explicitly (`CI=true`, `npx --yes`, `npm i --no-audit --no-fund`, `git commit -m`); executors always wire child stdin to `/dev/null` and return on EOF.
2. **Never exiting**: `--watch`, dev servers, foreground daemons, infinite loops. Never run them in the foreground. **Inside the product (any user project) use `bash({background:true})`**: the call returns a job id + log path immediately, the process is registered in the topbar "background tasks" panel (stop individually / close all / excluded from leftover cleanup); in the source repo and CI, still use `safe-exec --detach` hosting + polling.
3. **Pagers**: `less` / `more` / `git log` paging by default, waiting for a TTY keypress. Use `PAGER=cat`, `GIT_PAGER=cat`, `git --no-pager`; executors inject them by default.
4. **Output flooding the context / background children inheriting stdout**: write raw output to a file first and echo only the tail; analyze with `grep` / `read --offset` in steps, never direct pipes like `cmd | sort` / `| less` / `| head` that only finish once they hit EOF, drop the TTY, or hold a pipe handle.
5. **Silent hangs**: the process is alive but produces nothing again (waiting on a lock, the network, a handle it will never get, or having handed the work to a dead grandchild). Judge by `--idle-timeout`: N seconds with zero output means force-kill. Enable only for tasks that must emit heartbeats when healthy (off by default); leave naturally quiet ones such as builds and type checks alone.

Duration tiers and usage (`scripts/safe-exec.mjs`, a cross-platform Node wrapper):

| Scenario                  | Command                                                                              | Criterion                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Unit tests / lint / types | `node scripts/safe-exec.mjs --timeout 60 -- npx vitest run <file>`                   | Returns `124` on timeout                                                          |
| Full build / compile      | `--timeout 600`, always with `--log`                                                 | Returns `124` on timeout                                                          |
| Expected >3 minutes       | Host with `--detach` → poll with `--wait <jobfile> --json` → terminate with `--kill` | Returns immediately on start; `--wait` returns early when the task finishes early |
| A single AI tool call     | The pi `bash` tool's `timeout` parameter + the session-level tool watchdog           | `session.abort()` on timeout                                                      |

`124` means **change strategy**, not retry: read the log first to locate the stall (slow? network? lock?), then adjust the tier or move to the background. Process-tree termination has its single source in `killPidTree` from `server/process-utils.ts`; do not hand-write `taskkill` / `kill -9` snippets elsewhere. Guard: `tests/unit/safe-exec.test.ts`.

Background hosting protocol (the AI can copy this verbatim; do not invent your own polling):

1. **Start**: `--detach --timeout <总秒> [--idle-timeout <N>] --log <path> -- <cmd...>`, and take `job=<jobfile>` from the output (or from `--json`).
2. **Wait**: run only `node scripts/safe-exec.mjs --wait "<jobfile>" --wait-sec 10 --json`. It times internally and returns at once when the task finishes early, otherwise returning this window's `newOutput` (the cursor has advanced, so **output never repeats**). No `sleep`, no `&&` chaining, no reliance on `$?`.
3. **Judge**: `status` `RUNNING` → keep `--wait`; `SUCCESS` / `FAILED` → look at `exitCode` and the log; `ABORTED` (including the `childAlive: true` case of "still not dead after the watchdog grace") means the child is still running — `--kill` first, then rerun; `TIMEOUT` / `IDLE_TIMEOUT` must never be retried as-is — read the log and change the tier or drop the pipes; `pipesForced: true` means a grandchild inherited the output pipe and settlement was forced, so the log may only run to the exit.
4. **Collect**: `--kill "<jobfile>"` kills the child process tree first and then reaps the daemon; the three artifacts `.pid` / `.state.json` / `.cursor` stay next to the log and can be deleted after a terminal state. `--status` can be used freely (read-only, does not consume increments), but never use `--status` in a polling loop instead of `--wait`.
