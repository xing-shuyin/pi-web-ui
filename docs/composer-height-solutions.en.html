UX & architecture remediation plan

Composer height runaway & message-area occlusion remediation

Four complete designs — root-cause analysis, interaction evolution, engineering rollout — plus interactive sandbox prototypes, answering the reported defect where the composer “keeps growing until it covers the messages, refuses to shrink back down, and is force-filled to a huge floor height even with no text”.

4 logic defects in the current code that blind every guard (why can't it shrink? why does empty content fill the screen?)

1. Math.max creates an “increase-only, never-decrease” deadlock

The code runs Math.min(Math.max(scrollHeight, composerH), cap). Once long input pushes scrollHeight to 500px, dragging down to bring composerH to 150px does nothing at all — scrollHeight keeps pinning the height.

2. A hard-coded 720px is detached from viewport safety

COMPOSER_MAX_H = 720 is hard-coded. A 1080P or laptop viewport is often only 750–850px tall, so the composer plus its toolbar eat 100% of the viewport and squeeze the message area (.messages) down to 0px — completely invisible.

3. localStorage persists a “ghost height”

One drag upward — or one accidental touch — writes the floor height into localStorage. After that, clearing the text or starting a new conversation still opens the composer at a screen-filling 720px (as in the screenshot: no text, full screen), while “double-click to restore” hides on an invisible hairline nobody can find.

4. Overlapping handle, unclickable zones

The top drag strip sits at opacity: 0. Once the composer has grown to the top edge, the handle collides with and is crowded out by the quick-prompt pills, the cursor lands on a prompt chip instead, and the 14px sliver of a handle is impossible to hit.

Solution 1 mechanism: percentage viewport cap + free bidirectional clipping

The golden rules that kill both “grows but never shrinks” and “empty text fills the screen”:

Dynamic relative cap: drop 720px for maxHeight = min(40vh, 320px), so the messages own ≥60% of the safe viewport at all times.
Real control in both directions: dragging sets a target cap, userH. When userH < scrollHeight, inner vertical scrolling takes over (overflow-y: auto), so users can flatten the composer at any moment to read the messages above.
Smart empty-state collapse: with no content it always stays compact (40px); the height the user dragged only acts as a ceiling for long text. The giant empty box from the screenshot never comes back.
// ChatInput.tsx: rebuilt core height calculation const MAX_SAFE_CAP = Math.min(window.innerHeight * 0.42, 320); let targetH = COMPOSER_AUTO_H; if (!text.trim()) { targetH = COMPOSER_MIN_H; // empty text must never fill the screen } else if (userH != null) { // free downward compression; overflow goes to inner scroll targetH = Math.min(userH, MAX_SAFE_CAP); } else { targetH = Math.min(ta.scrollHeight, MAX_SAFE_CAP); } ta.style.height = `${targetH}px`; ta.style.overflowY = ta.scrollHeight > targetH ? "auto" : "hidden";

Solution 2 mechanism: Splitter as a rigid safety gate

Treat the message stream and the composer as a genuine flex split view:

Rigid message floor: declare .messages { min-height: 240px; flex: 1 1 auto; } and the composer can never encroach on that region.
Physical dampening: while dragging the splitter, the moment the message area would drop below 240px the gesture locks into hard damping and cannot punch through.
Multi-tasking friendly on large screens: fits a widescreen IDE-style desktop; each pane owns its own scrollbar and responsibilities stay clean.
/* CSS rigid layout blocks intrusion */ .main-chat-container { display: flex; flex-direction: column; height: 100vh; } .messages { flex: 1 1 auto; min-height: max(240px, 40vh); /* message space that must never be violated */ overflow-y: auto; } .composer-pane { flex: 0 0 auto; max-height: calc(100vh - 240px); /* dynamically locked ceiling */ }

Solution 3 mechanism: separate long-form editing from everyday chat (strongly recommended)

The industry's end-state pattern, adopted by every modern top-tier AI app (Claude 3.7 Projects, Cursor Composer, GitHub Copilot):

Radically compact main view: the composer is pinned between 40px and 140px (no more than 5 lines) and never presses down on the messages.
Immersive space on demand: when you paste several lines or the text grows, the bottom right highlights “⛶ Expand editor”; the modal offers comfortable layout and token estimation.
Zero mental overhead: no more nervously tugging up and down inside a cramped, easily deformed chat box; the marginal-disaster class of auto-height bugs is eliminated at the root.
// two-way sync between the modal and the main composer function openZenEditor() { zenTextarea.value = chatTextarea.value; zenModal.style.display = "flex"; } function saveZenEditor() { chatTextarea.value = zenTextarea.value; zenModal.style.display = "none"; triggerComposerAutoResize(); }

Solution 4 mechanism: discrete magnetic tiers

Remove the uncertainty of pixel-level dragging and hand users explicit expectations:

Three fixed mental models: 44px (quick command), 160px (multi-line question), 280px (reviewing a large code block), hard-capped at 280px.
State at a glance: the top right always names the current tier and switching is one click, so the invisible “what floor height am I in?” confusion is gone.
Combine with drag snapping: if the user drags manually, release snaps smoothly to the nearest tier (magnetic snap) for a silky feel.
