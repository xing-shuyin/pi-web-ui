# Plugin System

Voice engines register only with the server-side `host.tts.registerEngine()`; system announcements, QQ and other tools all go through `host.tts`. The browser-side `ttsProviders` keeps only a read-only entry point for the central catalog; see [`architecture-tts.md`](architecture-tts.en.md) for details.

> Optional UI components, stored in `<dataDir>/plugins/`. Not installed means not present; rescanned on the fly at attach.

## GitHub daily workbench

`plugins/github-workbench/` (official catalog, v0.1.3) uses `rightpanel.tabs` to add a 「工作台」(Workbench) tab with a GitHub SVG icon next to 「文件列表」(File list) on the right, usable alongside the current conversation, reusing the serving machine's `gh` login. The narrow sidebar toggles between list and detail views and shows them side by side when the container is ≥480px wide, with the type segmented buttons and expandable search adapting to the sidebar width; styling uses host theme variables throughout. On tab unmount only the in-memory filters, page number, selected items, scroll position and per-item comment drafts are kept — restored when switching back, cleared on page refresh / plugin reload. Read requests are cancelled on unmount; in-flight writes are awaited, and the submit lock is shared across mounts to avoid duplicate comments. Repository auto-detection and personal todos work independently; repository todos, review requested, assigned to me, created by me, mentions and custom searches all paginate by update time. Details show the body, the latest page of comments and the PR branch / merge state / change stats, and support quoting into the current conversation draft, commenting, and close / reopen. Both 「引用到对话」(Quote to conversation) and 「交给 AI 处理」(Hand to AI) add only a short reference attachment (type, number, repo, link); the user fills in the request and sends it, the existing body and attachments are preserved, and identical references are deduplicated automatically. Full diff, CI and line-level review are viewed via GitHub links; AI can fetch the latest information on user request.

Source of truth: `plugins/github-workbench/index.mjs` (async `gh api` plus authenticated HTTP routes), `client/entry.mjs` (Shadow DOM workbench, tab state restore and the host `compose` reference-attachment bridge), `client/styles.mjs` (theme and container-responsive styles), `manifest.json`; for installation and search syntax see the [plugin README](../plugins/github-workbench/README.en.md). Routes cover only `/status`, `/items`, `/detail`, `/comment`, `/state`; write requests use fixed parameters and pass content over JSON stdin, no shell. All external text is escaped; input / output / pagination / timeouts are capped; unloading the plugin terminates the backend subprocess, tab switches cancel reads, a stale detail response never overwrites a newer selection, and a failed comment keeps its draft to avoid duplicate submission. The client preserves the deployment root path from the bundle URL; only github.com is supported. Targeted guards: `tests/unit/github-workbench.test.ts`, `tests/unit/github-workbench-client.test.ts`.

## Image preview and OCR providers

Host bridge API v15 adds `host.openImagePreview({src, alt?, onSaveAnnotation?, actions?})` and `host.imageOcrProviders.register({id, label, labelEn?, recognize})`. `recognize({src, signal, onProgress})` returns `Promise<{text:string}>`; progress is 0–1. Registration returns an unregister function; `list()` returns only id/display name. `onSaveAnnotation(dataUrl)` is provided only when the caller can accept an annotation result, and the preview closes after the save callback succeeds. `actions` accepts `{id,label,onSelect,closeOnSelect?}` to keep the caller's actions in the unified toolbar; the image workbench's generation gallery uses it to keep edit, reference image, copy path and download, dropping the old standalone lightbox; when the host lacks the bridge API it falls back to opening the original image in a new window.

`web/src/image-ocr-providers.ts` is the single source of truth for client-side OCR registration, and a registration belongs to the plugin scope active at load time; `plugin-loader.ts` cleans up providers on disable/uninstall, on epoch changes and on load failure; removing the bundle on disable bumps the import cache salt so that re-enabling within the same epoch still runs top-level registration, instead of hitting the ESM cache and leaving the provider unrestorable. A disabled plugin that is still loading must not register late or re-enter the loaded set. The shared `ImageLightbox` subscribes to that registry and manages cancellation and late results; plugins must not ignore the cancel signal. `plugins/image-ocr` is a view-less plugin with `preload:true` providing local Chinese/English recognition, with the actual engine/font data loaded lazily, and terminating the outer Worker ends the initialization and recognition child workers as well. First use needs network access to fetch the program/font data; images are never uploaded to a recognition service.

The OCR button in the preview is always visible; when the provider is missing, the host reuses the existing plugin install background job to install the official plugin, a disabled plugin is enabled through settings, and install progress/errors stay in the current preview. For the full entry points and the pending-attachment annotation boundary see [`architecture-attachments.md`](architecture-attachments.en.md#unified-image-preview-ocr-and-attachment-annotation).

## Lifecycle constraints

The plugin manager distinguishes activating, loaded and invalidated instances by generation; reload coalesces concurrent requests and immediately revokes the side effects already registered by an in-flight activation. A stale activation that resumes later may only clean up itself and must never write back into the new generation's registries; an invalidated host must not register anything further, and late async resources must still be reclaimed. The set of applied tool names for tool sync belongs to each SDK session and must not live in a single set shared across sessions.

For official live-preview isolation and its dedicated access path see [attachment architecture](architecture-attachments.en.md#active-content-isolation). Official SFTP and remote workspaces reuse `plugin-sdk/ssh-host-trust.mjs`; unknown or changed host keys are refused, and trusted configuration is described in [Environment variables](env-vars.en.md#ssh-host-authentication).

## MCP project runtime

The registry in `server/mcp-project-runtime.ts` creates an independent `McpBridge` and config watcher per normalized absolute cwd; a bridge's cwd is never rewritten after creation. SDK session creation first waits for project initialization; tool snapshots and later syncs select by the stable `conversation.cwd`; the DSH provider passes its own cwd explicitly. The plugin `host.mcp` captures cwd at the async operation entry point.

Global config shares the on-disk file but not connection instances: global management operations refresh every created project, project operations refresh only their own project, and external file saves are handled by each project's watcher. Initialization, reload and disposal all retain their owning entry identity; reload is queued after the initial load, and shutdown stops watchers first, closes the bridge, then waits for in-flight operations to drain. Tool changes sync existing sessions and reapply gates, while also refreshing the corresponding project's client-side MCP list and settings.

**Resource lifecycle**: each project has its own bridge and watcher, so the connection count is the sum of the effective servers of retained projects (global servers also get one connection per project). Every minute the registry checks in least-recently-used order and calls `disposeProject(cwd)` for any project that has been idle for more than 5 minutes, has no retained Pi/DSH session references, and has no in-flight initialization, reload or creation lease. All background, idle and subagent sessions count as references; when the ownership check is missing or fails, the project is conservatively retained. The whole SDK creation holds a lease and the timer restarts on release; watcher and tool-change broadcasts do not extend the user's idle time. There is no hard cap on the number of projects, and a retained session can still pin its connection; a project only becomes reclaimable after its sessions close. The reclaim timer is unref'd; server shutdown clears the timer, disposes everything and waits for in-flight operations.

### MCP OAuth login

OAuth login from an HTTP MCP card starts with `mcp_oauth_start {reqId,name,scope}`; the `McpOAuthUi` inside the ClientSession resolves the exact scoped config from the captured cwd and calls `mcp-oauth-login.ts`. `mcp_oauth_result` returns only the request ID, login ID, authorization/callback URL and status — never credentials or raw provider errors. Both the login ID and the request ID are bound to the initiating client; no other client can complete or cancel them.

The dialog sends `mcp_oauth_status {reqId,id}` every 1.5 seconds to watch for the local loopback auto-callback; a remote browser can paste the full redirect URL and send `mcp_oauth_finish {reqId,id,redirectUrl}`. After a successful persist it refreshes every created project in the registry using the project captured when login started (credentials are shared via agentDir), and concurrently completed requests share a single reload. Unmounting the dialog sends `mcp_oauth_cancel {reqId}`, and destroying the ClientSession cancels too; cancelling during startup reclaims the late login instance. Completed records are reclaimed on the next login so they never fill up the client's eight active login slots.

## Shape

A plugin = a `<dataDir>/plugins/<id>/` directory:

- `manifest.json` (name/version/description)
- `index.mjs` server-side entry (optional, `export default { activate(host) → deactivate? }`)
- `client/entry.mjs` view entry (optional, `export default { mount(el, ctx) → cleanup? }`)

**Client dependencies may only live under `client/`**: the host serves only the `client/*` subtree (see 「静态服务」(Static serving)), so once a relative import in `client/entry.mjs` resolves outside `client/` (typical: written as `../sdk/index.mjs`), the browser reports `Failed to fetch dynamically imported module` and **the whole bundle does not execute** (a blank plugin page while the server shows nothing wrong: manifest validation passes, `active:true`, `error:null`). The scaffold generated by `plugin create` therefore copies the SDK per runtime: the server-side `sdk/` contains `index.mjs`, `client.mjs`, `client-utils.mjs`, `testing.mjs`; the client-side `client/sdk/` copies only `client.mjs` and `client-utils.mjs` and additionally generates a compatibility `index.mjs` that merely re-exports `./client.mjs`, preserving existing client import paths. New templates import `./sdk/client.mjs` directly, test templates import `./sdk/testing.mjs`. Generation also runs `plugin-sdk/import-check.mjs` to report out-of-bounds/missing files (regression: `tests/plugin-scaffold-test.mjs` + `tests/unit/plugin-import-check.test.ts`).

`plugin-sdk/client.mjs` is the browser entry, exporting `defineView`, `defineRenderer`, UI helpers and re-exporting `client-utils.mjs`; these two files and their full dependency closure must not import any Node built-in module and do not include the test harness.

`testing.mjs` is for Node tests only, exports `createMockHost`, and resolves this platform's paths with `node:path`'s `resolve` / `sep` directly — it does not emulate other platforms. The server/compatibility umbrella entry `index.mjs` exports `definePlugin` and re-exports the client and test entries, so old server-side scripts can still import everything. Type entries are `index.d.ts`, `client.d.ts`, `testing.d.ts` (sharing the interface declarations in `index.d.ts`); package subpaths are `/client`, `/testing`. Guards: `tests/unit/plugin-sdk-browser-safe.test.ts`, `plugin-host-primitives.test.ts`, `plugin-sdk-mock.test.ts`.

`SDK_VERSION` is defined in `client.mjs` and kept in sync with the SDK `package.json` version. `plugin upgrade-sdk` fills in/refreshes files per the server-side and client-side manifests, supports reading the version from `index.mjs` in old versions, recreates a missing `client/sdk/` that client code references, removes a mistakenly copied `testing.mjs` from the client and keeps the client compatibility entry; repeated upgrades must stay idempotent.

**Not installed means not present** — if the directory is absent there is no protocol/UI trace at all; the directory is rescanned at attach, so a newly dropped-in plugin appears as a topbar view tab without a server restart (each import happens once per process and is cached; deleting the directory → deactivated on the next attach).

### External channel web continuation callback

Channel sessions are owned by the stable scope of contact, group, channel and thread; shared web viewing does not change execution ownership. Runs started by a channel are claimed by the acknowledgement's `runId`; for runs the web starts without a channel run marker, the host must first receive `run_start`, then collect the final assistant body by the bound SDK `sessionId` and send it back to the original destination. Old hosts allow only the full `clientId + conversationId` and must not guess from a bare `c1`; an unknown `runId` must not borrow a session binding. A repeated end event must not be delivered twice.

Route recovery must validate the channel account, destination and session reset generation together; after a reset, account logout or scope switch the old binding is invalid. Tool-call preambles are not final replies, and timeout acknowledgements and early events follow the same identity rules. The platform's webhooks, session reply window and proactive-send permissions remain in force, and failures must be reported honestly. The plugin and its route helper files stay independently installed and do not depend on other channel plugin directories.

### External channel session reset

`/new`, `/clear` and `/reset` for WeChat, QQ, Telegram, Discord, Slack, Matrix, Feishu, DingTalk, WeCom, WhatsApp and iMessage share each channel's own session-switch flow. Command words accept any case and full-width forms; arguments are kept verbatim, and a prompt following a reset command goes straight into the new session without being parsed as a command again. Existing numeric shortcuts use the same flow.

Switching context must rotate the session generation in `accountId` and drop the old `conversationId` at the same time; deleting only the local mapping does not guarantee the host creates a blank session. An explicit new session in WeChat/QQ must also detach the old web delivery binding. A successful change of workspace (`/cwd`, `/workspace`), model or thinking level switches context too; a query without arguments keeps the current context.

Download, queue and `host.chat` requests carry the generation captured at start. Late acknowledgements, end events and async settings validation after a reset must not overwrite the new session state; a late stale run is aborted by its real `runId`. Channels that cannot switch while running must explicitly ask the user to stop first and must not report a successful reset. History is preserved, and an abort failure must be reported to the user. Regressions: `tests/unit/channel-plugins.test.ts` plus the per-channel behavior and reset tests.

### Plugin directories: code is a pure cache, state lives separately (`plugin-paths.ts`★ / `plugin-materialize.ts`★)

In the data directory a plugin splits into two independent roots:

| Path                          | Contents                                                       | Discardable?                                                                |
| ----------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `<dataDir>/plugins/<id>/`     | The code itself (manifest / index.mjs / client / dependencies) | **Yes**: bundled plugins can be replayed, `node_modules` can be reinstalled |
| `<dataDir>/plugin-data/<id>/` | State: `storage.json`, `secrets.bin`, `schedules.json`         | **No**: user config, channel grants, scheduled task progress                |

- State paths go only through `pluginStateDir()` / `pluginStateFile()`; the old layout (state living in the code
  directory) is moved over idempotently by `migratePluginState()` during scan/activation, and when both exist the
  state directory wins (an old copy never overwrites new state).
- Materializing the code directory is `materializePlugin()`'s job, and it leaves an acknowledgement
  `.pi-materialized.json`: **existing ≠ prepared** — it only counts as installed when every file registered in
  the acknowledgement is still present; a directory present but missing the acknowledgement/files = half-broken,
  filled in place on the next start.
  New installs go through staging + rename for an atomic commit; the post-copy acceptance check (`manifest.json`
  present + file count > 0) fails loudly and never accepts an empty directory.
- The copy blacklist (`.git` / `node_modules` / `whisper-cache`) may **only** be decided in `server/fs-copy.ts`, by
  **relative path**. Past incident: three places each matched `node_modules` against `cpSync`'s absolute paths,
  and under an npm -g install the package directory itself sits under `…/node_modules/pi-web-ui`, so the whole
  tree was filtered into an empty copy that was still marked installed (issue #856).
- Uninstall deletes the state directory too (a reinstall does not resurrect old settings); rollback rolls back code
  only, not state.

### Declarative settings (`secret` type / `optionsFrom` dynamic options) and the plugin SDK (plugin-sdk/)

- The sixth `settings` schema type `secret`: unlike `password` (masked in the front end, stored plaintext in storage.json),
  `secret` is stored in encrypted `secrets` (key `setting:<key>`, plaintext never touches disk). On the browser side
  `settingsValues` only sees presence (boolean); only the plugin runtime's `getSettings()` gets the real value; saving an
  empty string = leave unchanged. `PluginSecrets` shares one file cache across instances (saving and reading through
  different instances never sees a stale value).
- Besides static `options`, a `settings` schema `select` may declare **`optionsFrom`** so the host computes the options
  on the fly (plugins need not maintain a list that goes stale): `"models"` = models with configured auth (value
  `provider/id`, labels the same as the settings panel's model picker) / `"thinkingLevels"` = SDK thinking level tiers
  (`off`…`max`, labels via `thinking.<value>`). Both prepend an empty option = **follow the global default** (the plugin
  falls back itself when it gets an empty string); options are computed on the **browser side**
  (`web/src/plugin-setting-options.ts`, model list from `UiSettingsState.subagentModels`), so the server **does not
  validate** values of fields with `optionsFrom` (only a 200-character length guard), and an invalid value errors out
  when used (e.g. `host.chat` switching models); a currently stored value missing from the list (model deleted /
  storage.json hand-edited) is kept and not silently eaten by the dropdown. Example: 「模型」(Model) and
  「思考强度」(Thinking level) in `wechat-ilink` use exactly these two sources.
- Form layout: **single-column rows** (labels in a fixed left column + controls in the right column, checkboxes next to
  their label, `hint` always shown as small text under the label, stacked vertically at ≤720px); all styling lives in
  the `.plugin-settings-*` section of `web/src/styles.css`; rendering is in `web/src/components/PluginSettingsForm.tsx`.
  Field rows carry `data-key` (= the schema `key`) for per-field targeting/debugging.
- `plugin-sdk/` starter kit: server umbrella entry `index.mjs`, browser entry `client.mjs`, Node test entry
  `testing.mjs` and their respective type entries; runtime environment and copy boundaries are covered in
  「形态」(Shape) above, examples in `plugin-sdk/README.md`.

### Plugin styles and the unified color contract (Plugin Style & Theme Contract)

Every plugin UI mounted in host views, drawers, floating layers or slots must follow the unified theme color contract:

1. **Inherit host CSS variables**:
   Plugins mount inside the host DOM tree and inherit the `:root` theme tokens globally (`--bg`, `--bg-elev`, `--border`, `--text`, `--accent`, `--accent-contrast`, etc.). Each may carry a sensible hard-coded fallback so it still works standalone without a host.
2. **Hard rule: solid fills pair with inverse-contrast tokens (no more whack-a-mole white-on-white)**:
   - **Accent solid fill**: `background: var(--accent)` must and may only pair with the foreground `color: var(--accent-contrast, #fff)`; hard-coding `color: #fff` is strictly forbidden (under light/pure-white accent themes such as `flow`/`wallpaper-flow` it becomes invisible white-on-white);
   - **Alias variables must be declared in pairs**: if a plugin introduces namespaced variables for scope isolation (e.g. `--nt-accent`), it **must also declare** `--nt-accent-contrast: var(--accent-contrast, #fff)`; aliasing the fill and forgetting the foreground contrast is strictly forbidden;
   - **Semantic solid fill**: `background: var(--green|--amber|--red|--blue)` must pair with `color: var(--on-green|--on-amber|--on-red|--on-blue)`;
   - **Tinted/translucent fills**: controls using `--accent-soft` or a `color-mix(...)` fill follow the regular body color `color: var(--text)`.
3. **Prefer the host component baseline**:
   The host already injects `.btn` and `.btn.primary` globally (with contrast and hover filters built in); primary action buttons should reuse the host `.btn.primary` instead of being hand-written again.
4. **CI static check hard block**:
   `tests/unit/accent-contrast.test.ts` and `tests/unit/semantic-contrast.test.ts` dynamically trace alias and prefixed variables in all built-in plugin code; an unpaired alias or hard-coded white text turns the build red immediately.

### Capability declarations and enforcement (manifest.permissions)

Host-controlled APIs are gated by **capability family**; an undeclared family is refused with an error naming which family is missing:

| Declared family | Host APIs covered                                                                                                                                                                                        |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fs`            | `host.fs` (including the cross-directory `*Path` family) and `host.project.create`                                                                                                                       |
| `ui`            | manifest `"ui"` and `host.ui.*` (undeclared → the whole `ui` block is ignored and runtime requests are refused)                                                                                          |
| `tools`         | `host.registerAgentTool`                                                                                                                                                                                 |
| `http`          | `host.route` + `host.registerProxy`                                                                                                                                                                      |
| `chat`          | `host.chat` (headless calls)                                                                                                                                                                             |
| `llm`           | `host.llm.complete` (isolated, tool-less completion; implementation in `server/plugin-llm.ts`, injected via agent-service `completeForPlugins` + index.ts `llmProvider`; returns `{ok:false}` under DSH) |

`host.llm.supportsImages === true` means the host accepts image inputs. `images?: Array<{data: string; mimeType: string}>` uses standard pure base64 with padding (no data URL); only JPEG/PNG/WebP are accepted, and the decoded signature is checked against the MIME type. At most 8 images, each ≤1 MiB after decoding, ≤6 MiB total; over-limit or invalid input is rejected before the SDK session is created. Images are passed through the SDK `prompt(text, {images})`; when the current model does not support images an explicit `{ok:false,error}` is returned. The optional `signal?: AbortSignal` is only for in-process host cancellation and is not transported over JSON; cancellation or timeout aborts/disposes the session, and the timer is cleared on success or failure alike. If cancelled during initialization, a late session is reclaimed as well; the concurrency slot is held until the actual task finishes.

**Strict mode** = `permissions` declared **or** `apiVersion >= 2`; **legacy full-privilege mode** = no `permissions` and
`apiVersion < 2` (allowed, but one warning per activation period: 「apiVersion 2 起将默认拒绝」(apiVersion 2 will deny by
default)). Host API version `PLUGIN_API_VERSION = 2`; a plugin with a higher `apiVersion` is refused activation outright
and told to upgrade pi-web-ui (instead of hitting undefined interfaces at runtime).

### Capability derivation and new families (v2)

- `fs:read` / `fs:write` derive from `fs`: legacy `fs` equals read+write fully open (backward compatible); declaring only `fs:read` → cross-directory writes (the `*Path` write family) and `project.create` are refused (reads allowed); declaring only `fs:write` → reads refused. Error messages state which family is missing.
- `net` + `netAllowlist`: outbound is allowed only when permissions include `net`; manifest.netAllowlist is matched per host (exact or dot-suffix, see hostMatches in `tests/unit/plugin-extensions.test.ts`); missing/empty allowlist = deny all, no match = deny.
- `dom:anchor`: scoped DOM at anchors mount points only (no user grant needed); the full `document` still requires `dom` + user grant (see 「特权 DOM 访问」(Privileged DOM access)) — the difference is 「范围」(scope) vs 「整页」(whole page).

## Reversible side effects (effect stack, DSH benchmark P0-2)

Everything a plugin registers is a **reversible side effect**. The host's internal `PluginEffectStack` (`server/plugins.ts`,
exported for unit tests) collects a disposer (with a label) for every registration/subscription during activation and
**unwinds in reverse order** on deactivation (disable / uninstall / `plugins_reload` / shutdown):

| Registration surface                                                                                                                                                   | Label recorded on the stack                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `host.registerAgentTool`                                                                                                                                               | `agentTool:<name>`                                                                                        |
| `host.registerCommand`                                                                                                                                                 | `command:/<name>`                                                                                         |
| `host.route`                                                                                                                                                           | `route:<METHOD> <path>`                                                                                   |
| `host.registerProxy`                                                                                                                                                   | `proxy:<prefix>`                                                                                          |
| `host.fs.watch`                                                                                                                                                        | `watch:<relPath>`                                                                                         |
| `host.schedule`                                                                                                                                                        | `schedule:<id>`                                                                                           |
| `host.registerBackgroundTask`                                                                                                                                          | `bgTask:<id>`                                                                                             |
| `host.leftPanel.setRunning`                                                                                                                                            | `leftPanel` (clears this plugin's entries on deactivation)                                                |
| `host.ui.register`                                                                                                                                                     | `ui:register(<ids>)`                                                                                      |
| `host.events.on` / `onStats` / `onStreaming` / `onSettingsChanged` / `onMessage` / `onToolEvent` / `onRunEvent` / `onAttach` / `onCwdChange` / `onConversationChanged` | the corresponding method name                                                                             |
| `host.effect(label, dispose)`                                                                                                                                          | `plugin:<label>` (side effects the plugin **creates itself**: its own intervals / listeners / WebSockets) |

Semantics detail:

- The unregister function **returned by the call** = revokes only that one entry (idempotent); not calling it is fine —
  deactivation catches it.
- `release()` runs in reverse order, and **a throwing cleanup only records one diagnostic** (`pushRuntimeDiag`) without
  blocking other cleanup; it returns the list of failed labels for logging.
- On **mid-activation failure** (`activate()` throws), the side effects registered so far in this round are unwound in
  reverse first, then the error placeholder row is written — tools/routes/timers registered halfway are not left behind
  for a plugin that is already broken.
- `dispose()` (shutdown / `reload()`) unwinds each plugin's effect stack first, then sweeps proxy prefixes and background
  tasks indexed by pluginId as a backstop, and finally clears the global tables.
- Unit test: `tests/unit/plugin-effects-install-spec.test.ts` (reverse order / idempotence / throw isolation / with a real
  `PluginManager`, deactivation reclaims tools, commands, routes, bus subscriptions and self-created effects, and
  `effects.size` drops to zero).

- `icon` (emoji/single character, used in the topbar tab instead of the generic puzzle icon)
- `iconSvg` (inline SVG string; when present it renders in preference to `icon`: topbar view tabs / right panel tabs / the settings panel list and marketplace all draw the SVG; the server only validates shape (`<svg…</svg>`, ≤8KB, no script/event handlers, see `server/icon-svg.ts`), and the front end sanitizes once more before rendering (see `web/src/plugin-icon.tsx`); `icon` remains as the legacy fallback)
- `description` (plugin blurb in the settings panel; view tab tooltips use only the plugin name, not this)
- `version`
- `apiVersion` (compared with `PLUGIN_API_VERSION`; if greater, activation is refused with an upgrade prompt)
- `permissions` (capability declaration array)
- `settings` (declarative settings schema → the ⚙ panel renders the form automatically)
- User overlay (P2-9, not in the manifest): the `settings` section of `<dataDir>/plugin-overrides/<id>.json` — three-layer merge schema default < overlay < panel-saved value. The overlay is the user's pinned new default (no fork of the official default, no loss on update); panel saves always win; secrets never come from the overlay; bad keys warn into diagnostics (`settingsSources` marks each key's source as default/override/stored)
- `view` (boolean, defaults to `true`): whether there is a standalone view tab. **Pure renderer plugins set `false`**;
  the front end then does not eagerly load their bundle and only lazy-loads it when a fence matches in a message
- `preload` (boolean, defaults to `false`): still **preload the client bundle on every page entry** with `view:false`.
  For plugins 「没有视图 tab、但顶层代码必须一直跑」(no view tab, but top-level code must always run) (persistent
  floating window, reminder polling, shortcuts…): such bundles may omit `export default { mount }`, and finishing
  top-level code counts as a successful load; implementation in the `preloaded` set of `web/src/plugin-loader.ts`
  (it does not enter the view registry, so it creates no tab)
- `renderers` (string array): the fenced-code languages this plugin can render (`"mermaid"` etc.), one-to-one with
  `default.renderers[lang]` in `client/entry.mjs`
- `ui` (object): the plugin's **entire contribution** to host UI (slot entries + `arrange` intents, see
  「UI 扩展点（slot 框架）」(UI extension points (slot framework))); in strict mode `permissions` must include the `ui`
  family, otherwise the whole block is ignored
- `build` (object, optional): build declaration for source installs (`{ install?, command, outputs? }`, see
  「源码安装（--build）」(Source install (--build)))
- `netAllowlist` (string array): outbound host allowlist (active when permissions include `net`, no match = deny, empty = deny all)
- `engines` (object, e.g. `{"pi-web-ui": ">=1.2.0"}`): engine constraint; unsatisfied = refuse activation; ranges support
  `>=`/`^`/exact, and an invalid range is allowed through (semantics in satisfiesEngines in
  `tests/unit/plugin-extensions.test.ts`)
- `peerPlugins` (string array): peer-dependent plugin ids; missing ones only warn and do not kill the plugin
- `requires` (object, P2-8 hard dependency): `{ hostApi?, families?, plugins? }`; any unsatisfied entry refuses activation
  with a teaching-style error — `hostApi` is the host API floor (upgrade if you are ahead), `families` must be known
  families that are also declared in the plugin's own `permissions`, `plugins` must be installed and activated
  successfully. `ensureLoaded` activates in dependency topological order (cycles denied outright), and when a provider is
  removed/fails its consumers are deactivated too and get a placeholder row (the cascade converges in one round; reload

- `agentToolsDefaultOn` (boolean, defaults to `false`, i.e. off by default): whether plugin AI tools enter conversations by
  default. Omitted means off by default (new users get them in the factory `disabledPluginTools` list and must enable them
  manually; this only affects new users and factory reset, existing configs are untouched); set to `true` to opt in to

  `tests/unit/plugin-tools-default-off.test.ts`)

Tools registered via `host.registerAgentTool` used to only enter conversations — invisible and not toggleable for users. Now they are visible in two places and toggleable in one: settings → UI plugins expands each plugin's own tools (name/label/description) with a per-tool toggle; settings → Tools has a per-plugin summary section at the bottom (the same toggles). ## Fenced-code renderer plugins

> Lets plugins render ` ```lang ` fences in messages into custom DOM (first implementation: mermaid → SVG).

**Shape**: `manifest.json` declares `view:false, renderers:["lang"]`, and `client/entry.mjs` default-exports
`{ renderers: { lang: (code, ctx) => HTMLElement|null } }`. Returning `null` = do not render, fall back to a plain code
block. A renderer can use any stack (no shared React instance); the main app only mounts the returned DOM into the message
stream; ctx uses the same narrow channel as view mount (`send`/`onData`).

**Protocol**: `UiPluginInfo` gains two optional fields, `renderers`/`view`, delivered with the plugins manifest.

**Distribution**: ordinary plugins ship via the GitHub repo; built-in modules that are explicitly bundled, such as
Superagent, are the exception. Ordinary plugins use `pi-web-ui install <owner>/<repo>/<subdir>`
(install natively supports subpath sources) or copy the directory into `<dataDir>/plugins/`. Renderer plugins needing a
large engine may vendor it (e.g. the mermaid plugin's `vendor/mermaid.bundle.mjs`; the build artifact ships with the
plugin, loads locally first and falls back to a CDN by default).

**Front-end routing**: `web/src/plugin-fence.ts` maintains a 「语言 → 插件 id」(language → plugin id) registry (built from
the plugins manifest); `PreWithCopy` in `Markdown.tsx` looks it up when it hits a ` ```lang ` fence — if a plugin claims
it, `PluginFenceBlock` **lazy-loads** that plugin's bundle on demand and renders (downloaded only on a hit, unlike view
plugins which are loaded persistently in `syncPluginViews`); loading/failure/returning null all fall back to a plain code
block, never blank. On an epoch change (plugins_reload) the cache is cleared and bundles are re-fetched with `?e=`.

**Note**: a renderer is bare ESM executed directly by the browser and **cannot import npm packages** (no bare specifier
resolution). Plugins needing large dependencies ship a pre-built bundle (e.g. vscode-editor) or vendor it for local
loading (e.g. the mermaid plugin's `vendor/mermaid.bundle.mjs`, local first, CDN fallback by default).

## Front-end integration

## Static serving

`GET /plugins/:id/client/*` maps to the plugin directory's client/ subtree (**only this subtree is exposed** — the manifest and the server-side index.mjs may contain credentials and are never downloadable; id validation + resolve prefix check prevent traversal). In dev mode vite already proxies /plugins.

Bundle URLs for front-end dynamic imports get the app root prefix via `appUrl()` in `web/src/base-url.ts`
(with an nginx subpath reverse proxy the page lives under /pi/ and the request becomes `/pi/plugins/<id>/client/entry.mjs`),
so subpath deployments need no extra configuration; at the root, behavior is identical to root paths.

### Privileged DOM access (`dom` capability family)

The slot framework's principle is 「插件声明、宿主渲染」(plugins declare, the host renders) — plugins cannot touch the
host shell's DOM. Plugins that must break through this layer (mount native DOM into the topbar/composer/anywhere, change
styles, intercept events) declare `permissions: ["dom"]` and go through a **user grant**:

- The server records the consent table in `<dataDir>/plugin-dom.json` (`PluginDomConsent` in `server/plugin-dom.ts`,
  the same rules as the directory grants table: globally shared, a bad file counts as an empty table, only changes are
  written).
- Without a grant the plugin's client bundle gets a flat **403** (the static gate in `server/index.ts` decides via
  `PluginManager.isDomBundleBlocked`) — the bundle is same-origin with the page, so JS cannot block `document`; the gate
  has to sit where it is served. An unauthorized plugin appears in the manifest with `wantsDom: true` + `error`, greyed
  out with the reason.
- Grant/revoke goes through `plugin_dom_consent` (the 「授权/撤销 DOM 访问」(Grant/revoke DOM access) button on the plugin
  row in settings, with a ⚠ warning); after writing the table the server **bumps epoch and re-pushes the manifest** (the
  browser drops its module cache and re-fetches the bundle).
- An authorized bundle can call `window.__piWebUiHost.dom.anchors()` to get stable mount points
  (`data-pi-anchor="app|topbar|composer"`, introduced in v7, `web/src/plugin-host.ts`) — the bundle natively has
  `document`; anchors is merely a version-stable query entry point so you never guess class names again.

Design trade-off: what is restricted is not the **capability** (after a grant it is the full DOM) but **who may** — the user
nods once in the settings panel. The server-side `index.mjs` is already fully trusted Node code and is outside this gate.

## MCP tool bridge (server/mcp-bridge.ts)

**Project ownership**: bridges and watchers are isolated per project; connection and reclaim boundaries are in 「MCP 项目运行时」(MCP project runtime) above. Management operations capture the project directory before awaiting, so the admin page never reads/writes B's config while reloading A's instance.

**Config and state**: a project config with the same name overrides the global one, global rows are marked `overriddenBy`, and the project instance's tools and run state are not borrowed. When a new config fails to start and the old instance is kept, the state carries `usingPreviousConfig` and error details, and the admin page shows the failure reason. Argument editing preserves string-array boundaries (including empty arguments, spaces and backslashes); unedited config fields such as `protocolVersion` are preserved on save. The enable toggle and the actual run state are displayed separately.

**Skill directory sync**: `server/skill-maintenance.ts` copies or links directory skills as complete resource packs (Windows directory links use junctions), including scripts, reference material and assets; standalone Markdown skills stay single-file compatible. Path decisions use path segments and physical paths, rejecting recursive targets, out-of-bounds resource links, cycles and conflicts, and a failed copy cleans up only the targets it created.

Reads `<dataDir>/mcp.json` to start external MCP servers (stdio, newline-delimited JSON-RPC, zero third-party dependencies; `{servers:{name:{command,args,cwd,env}}}`), and after the initialize→initialized→tools/list→tools/call handshake adapts each remote tool into a PluginAgentTool (name normalized by sanitizeToolName) that joins plugin.d.ts's pluginToolsProvider (the same customTools pipeline as plugin tools). A single server's failure is isolated (rejectAll + logs, no process blowup); dispose kills the child process; requests match by id with a timeout watchdog.

**Child process lifecycle and self-healing**: an unexpected exit (OOM / killed externally / self-crash) does not permanently disable the server — when `McpClient.call()` finds the child dead it first **lazily restarts** (respawn + initialize handshake + tools/list) and then sends the call; only an explicit `close()` disables it permanently (no resurrection). Lazy rather than 「退出即后台重启」(restart in the background on exit) is deliberate: a misconfigured server is only tried when actually called and never spins up processes idly (restart loops are naturally bounded by call frequency). Three invariants: concurrent calls share a single reconnect (the `starting` promise; check `starting` before `child`, otherwise the second call would fire tools/call before the initialize reply), a close() during a restart reclaims the just-started process leaving no orphan, and a start/handshake failure also reclaims the half-started process and gives the caller a clear error (`服务器进程已退出且自动重启失败：<根因>` — "server process exited and automatic restart failed: <root cause>", replacing the previous generic error that merely ran out the timeout). After a restart `McpClient.tools` is re-fetched.

**Config hot reload (server/mcp-hot-reload.ts)**: saving `<dataDir>/mcp.json` takes effect immediately, with no service restart. At startup `McpBridge.load()` still runs only once, after which this watch line takes over (wired in `index.ts`: `reload → mcpBridge.reload()`, `onToolsChanged → service.applyPluginAgentTools()`; the latter is the 「Bridge 层工具列表热刷新」(Bridge-layer tool list hot refresh) half — `syncPluginToolsIntoSession` injects/removes by name diff, and both existing and new sessions keep up). Four invariants: ①**no content change means no child process is touched** — the fingerprint is a normalized snapshot (`mcpServerSnapshot`: only command/args/cwd/env/protocolVersion, with env key order and server order irrelevant), so editor saves, reordered keys and changed indentation trigger no restart; ②**only servers whose spec really changed are replaced** — `McpBridge.reload()` returns `{kept, started, stopped, failed, servers, tools}`; unchanged specs keep their original instance (changing one does not restart the others), and removed/replaced old instances are closed last, leaving no orphans; ③**if a new spec cannot start, the old instance stays**, because a botched config must not take working tools offline; ④**a JSON parse failure only logs + one warning and keeps running servers** (half-written states during saving are common), whereas **deleting `mcp.json` means intentionally emptying all servers** and is applied as usual — the two 「没有配置」(no config) meanings are deliberately kept distinct. Watching uses `fs.watch` (`persistent: false`, does not hold the process), automatically falling back to 2s polling when the directory does not exist yet or the network drive does not support it.

**Tool result content blocks map by type** (previously only `type==="text"` was concatenated, so screenshot/chart tools always returned an empty string): `image` blocks pass through as the SDK's `ImageContent` (`{type,data,mimeType}`, resized uniformly by the SDK's `normalizeToolResultImages` once in the conversation, so an over-limit image never makes the provider fail the whole response); text-type `resource` (`resource.text`, the path filesystem MCPs' read_text_file takes) passes through as text; blob (PDF etc.) and audio degrade to a 「mimeType + about N bytes, cannot inline」 hint (the SDK content union is only text|image|thinking|toolCall, with no blob carrier); plain text results are still concatenated strings (the old shape does not break existing callers). Note that Web UI tool cards, per existing behavior, render text only (images in tool results appear as `[image result]` in `serialize.ts`); the model context is unaffected.

**OAuth-protected remote servers (`server/mcp-oauth.ts`, Issue #786)**: pi's built-in MCP extension stores each server's OAuth state in `<agent-dir>/mcp-auth.json` (key `mcp__<server name>|<url>`; legacy keys that only wrote the URL are still read and taken over), and pi-web-ui's bridge **reuses that credential store** instead of building its own: it fetches the access token before the request (refreshing first when within 30s of expiry, matching pi's rule) and sends `Authorization: Bearer …`; on a 401 it force-refreshes once with the stored refresh token and retries the same request, writing the result back in pi's format (2-space JSON + newline, 0600) and keeping rotated refresh tokens. Concurrent/cross-process refreshes are serialized with the same-named `<agent-dir>/mcp-auth-refresh-<hash>.lock` directory lock (stale 20s), and the `staleToken` criterion ensures no duplicate refresh when 「别的进程已换过 token」(another process already swapped the token) (a second refresh under rotation destroys the grant). **Web login**: the admin page starts authorization via `mcp_oauth_start/finish/status/cancel`, and `server/mcp-oauth-login.ts` reuses `@earendil-works/pi-mcp/oauth` for discovery, dynamic client registration, PKCE and code exchange. A temporary loopback callback listener completes authorization in the local browser automatically; on remote deployments the browser's final redirect URL can be pasted back into the admin page. Random state, callback origin/path and single-exchange checks protect grant ownership; the PKCE verifier and tokens stay server-side, and only the authorization URL, attempt ID and status are sent down. Unfinished state lives in memory only, expiring after ten minutes; cancel or client destruction aborts network requests and closes the listener. After success it merges and writes inside the shared credential store lock, then reconnects the project bridges captured when it started; each ClientSession manages its own logins and cannot submit someone else's ID from another client. The CLI's `pi mcp login <server>` remains compatible. Servers with an explicitly configured `Authorization` header use static credentials and never touch any of this.

Refresh writes are performed as compare-and-swap inside `mcp-auth.json.lock`: comparing the source key, tokens, absolute expiry time, client registration and discovery read before the network call. Deleted credentials are not restored; when re-login or a change of client or authorization endpoint has occurred, the stale refresh result is discarded and the token currently in the store is returned (null if deleted). Merging preserves other servers and the current entry's non-credential fields; an old URL key is migrated and deleted only when it was actually refreshed, so unrelated old keys are never wrongly deleted. The refresh-failure fallback also re-reads the store, avoiding sending a token captured before logout.

Every HTTP RPC registers as an in-flight request and starts its timeout before reading credentials; the same cancellation signal spans refresh-lock/store-lock waits, the token request, the response body, retries and the pre-write-back check. The `staleToken` for a 401 comes from the Authorization actually sent by that request and must not use a client-wide 「最近 token」(latest token). Concurrent refreshes are serialized with the cross-process lock without sharing a cancellation controller: cancelling a waiter does not terminate the lock holder, cancelling the lock holder does not commit a late result, and the other callers re-read the store themselves. Timeouts, caller cancellation and `close()` end the RPC immediately; notifications have their own 8s deadline cancelled by `close()`. A refresh-token rotation that already happened at the authorization server cannot be undone; a local cancellation discards the result, in which case a re-login may be required. Regression: `tests/unit/mcp-oauth-concurrency.test.ts`.

**Three-tier acceleration and sparse checkout for plugin installs and updates (Sparse Checkout & Fast Path)**:
to eliminate cloning tens of megabytes of a full Git repository on every install/update of a subdirectory plugin, the CLI and the background job implement three optimizations:

1. **Local bundled fast path (Local Bundled Fast Path)**: for official built-in plugins (`plugins/<id>`), a fresh install or main-program upgrade (bundled version higher than the installed one) prefers the host's bundled local code directly — zero network time, zero traffic; offline or on network failure it degrades automatically to the bundled copy; `--remote` forces the remote path.
2. **Git sparse pull with blobless filter (Sparse + Blobless Checkout)**: for remote subdirectory plugins, prefer `git clone --depth 1 --filter=blob:none --sparse --no-checkout` together with `git sparse-checkout set <subpath>`, fetching only commit-tree metadata and the target subdirectory's file blobs without downloading unnecessary repo content (tens of megabytes for the whole repo drops to tens of KB); with older Git it degrades smoothly to a regular shallow clone and a direct tarball.
3. **Session-level shared repo cache for batch install/update (Shared Repo Cache)**: during catalog sync (`--catalog`) or multi-plugin batch operations, metadata for the same source repo is fetched once, and multiple subdirectories are checked out incrementally and reused via `git sparse-checkout add`, so the same repo is never cloned repeatedly.

## UI extension points (slot framework, issue #146)

A plugin's contribution to host UI goes through **declarative mount points (slots)**: plugins declare only
「有什么条目、想放哪儿」(which entries exist and where they want them placed), while rendering / ordering / overflow /
accessibility all belong to the host, and **plugins never touch the DOM**. The contract is in `server/protocol.ts`
(`UiSlotId` / `UiContribution` / `UiArrangeOp` / `UiPluginUi` / `UiLayoutPrefs` / `UiSlotSpec`); server-side parsing and
runtime registration are in `server/plugins.ts` (`parseUiItem` / `parseUiContributions` / `parseUiArrange` / `UI_SLOTS` /
`UI_SLOT_ALIASES`); the front-end merge engine is `buildUiSlots()` in `web/src/ui-slots.ts` (pure function, unit-tested).

**Failures are not silent (DSH benchmark P0-1)**: `buildUiSlots(..., { diagnostics })` can collect diagnostics from the
merge process (unknown slot / unknown kind / a `when` the host does not understand / arrange target missing / the same
plugin declaring the same id twice / plugin disabled or activation failed), each with `pluginId` + `entryId` + `slot`
attribution; when `diagnostics` is not passed, behavior is **verbatim identical** to before. The app `console.warn`s them,
and the top of the 「界面布局」(UI layout) page in settings renders a collapsible banner at the same time
(`uiLayoutDiagTitle` / `uiLayoutDiagHint`) — previously these cases were silently dropped, showing up as
「注册了但界面上没有」(registered but not on screen), the hardest thing to debug. The render layer also ships
`web/src/components/SlotErrorBoundary.tsx`: each entry is wrapped **independently**, so a render error in one entry drops
only that entry and greys it in place without blowing up the whole toolbar.

> Do not confuse this with the **plugin view tab**: the 🧩 view tab that appears in the topbar after install
> (`plugin:<id>`) is synthesized from the `plugins` manifest by `withPluginViewItems` into a `kind="view"` entry
> (`<id>:__view`) that then goes through the slot framework and renders in the same stream as the host's own three tabs
> (an errored plugin's tab is kept greyed out by TopBar as a fallback, because the merge engine drops its contribution
> wholesale).

### The 22 mount points

Every mount point has a host-defined `UiSlotSpec`: with `cardinality` of `list`, multiple entries render side by side; with
`single`, the merge engine picks the first visible entry by final ordering and hides the remaining visible candidates while
producing a layout diagnostic. All of these 22 existing mount points are `list`, because they all express a side-by-side set
of toolbar items, menu items, tabs or page entries; `modal.dialog`'s 「同一时刻只开一个」(only one open at a time) is an
open-state-machine constraint, not slot cardinality. A future exclusive mount point only needs to be marked `single` in
`UI_SLOT_SPECS` in `web/src/ui-slots.ts`; the plugin manifest shape does not change.

| slot                         | Location                                                                                                                                                                                                                                                                                              |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `topbar.primary`             | Topbar primary row (same row as the built-in tabs; a single flat flow, see “topbar flattening” below)                                                                                                                                                                                                 |
| `topbar.overflow`            | Topbar overflow menu (hidden entries + entries declared here directly as permanent residents)                                                                                                                                                                                                         |
| `bottombar`                  | Footer bar (the connection status / context / cost row)                                                                                                                                                                                                                                               |
| `composer.leading`           | Composer leading area (left of the file upload button, plugin-only space)                                                                                                                                                                                                                             |

### How to write it in the manifest

```json
{
	"permissions": ["ui"],
	"ui": {
		"topbar": [
			{
				"id": "inbox",
				"label": "收件箱",
				"labelEn": "Inbox",
				"icon": "📬",
				"kind": "action",
				"action": "webmail:open-inbox",
				"group": "mail",
				"order": 10
			}
		],
		"contextmenu.file": [{ "id": "send", "label": "发到邮箱", "action": "webmail:send-file" }],
		"settings": [{ "id": "mail", "label": "邮箱", "icon": "📬" }],
		"arrange": [{ "id": "host:github", "hide": true }]
	}
}
```

Both shapes are accepted: grouped by slot (recommended, as above) or flat `{ "ui": { "items": [{ "slot": "...", ... }] } }`
(same shape as `host.ui.register`'s runtime argument; both reuse one parser). The whole contribution shares a **32-entry**
cap and `arrange` a 64-entry cap; invalid entries / duplicate ids / unrecognized slots are silently dropped (tolerant but not
lax: skip bad fields rather than dropping the whole contribution over one dirty record).

> Compatibility: the top-level `manifest.topbar` field from before this version (the first draft of the same issue)
> **is no longer parsed** — write `manifest.ui` now (alias `ui.topbar`). The only compatibility kept is the host
> action bridge's old name `host.onTopbarAction` (= an alias of `onUiAction`, see 「插件 → 宿主动作桥」(Plugin → host
> action bridge)).

### Entry fields (`UiContribution`)

`id` (unique within the plugin, must match the plugin id charset; **global id = `<pluginId>:<id>`**, which is the key for
user preferences and `arrange`), `label` (Chinese UI text) + `labelEn`, `icon` (emoji/single character, or a name from the
host icon vocabulary) + `iconSvg` (inline SVG, rendered in preference to `icon` when present),
`hint` / `hintEn` (tooltip, rendered as the `title` attribute — when only one language is given the other falls back to it), `kind`, `children`,
`order` (defaults to 100, lower first), `group` (same group laid out contiguously), `hidden`, `action`, `view`, `when`, `badge`.
Text fields are truncated (label 60 / icon 16 / hint 200 characters).

**kind vocabulary**: `view` | `action` | `badge` | `menu` | `page` | `organizer` | `divider` | `toggle` | `input` | `progress` | `select` (defaults to `action`;
defaults to `page` when `slot == "settings.pages"`). Semantics: `view` switches views (`view` defaults to `plugin:<id>`); `action`
reports the click back to the plugin (via `host.onUiAction`); `badge` only shows status text/a corner badge (refreshable via `host.ui.update`);
`menu` expands `children`; `page` is a whole page in the settings panel; `divider` is a separator; `organizer` is an organizer (a kind
kept in the vocabulary; no render layer currently handles it specially); `toggle` is a switch (`checked`, clicks report back to the plugin), `input` a single-line field
(`value`, Enter reports back with the entered value), `progress` a progress bar (0-100, display only), `select` a dropdown (`options` candidates +
`value` current value; changes report back as `onUiAction(itemId, value)`). `select` renders in every slot: topbar/composer/message toolbar/
terminal-SCM-goalbar shared toolbar/footer/left panel session row/notice bar become native dropdowns, context menus expand into submenus (selecting
a child reports the parent entry + value, see `expandSelectEntries`), and right panel tabs open as tabs by existing convention (same as toggle/input).

**`children` is one level only**: during parsing a child's own `children` is cleared (no nesting), and children have no stable global id —
so children **do not participate** in `arrange` or user preferences. In the current implementation only **context menus** draw `children` as submenus
(`ContextMenu.tsx`); other slots draw only the parent entry.

**`when`**: a host context condition; values the host does not understand are ignored without error. Currently only context menus evaluate it
(`evaluateWhen` + `buildWhenContext` in `web/src/context-menu-state.ts`; `ContextMenu.tsx`
builds the context on the spot from the slot + the right-clicked object): the literals `"disabled"` / `"never"` are always greyed, `"always"` is always enabled,
conditions starting with `!` (e.g. `"!message.hasSelection"`; evaluated against the context when there is one, and greyed directly in legacy fashion when there is none),
and the affirmative applicability conditions — `file.isDir` / `file.isFile` (file menu, by target.kind), `session.isRunning`
(session menu), `message.hasSelection` (message menu), `search.isSession` / `search.isProject` / `search.isFile` /
`search.isFolder` / `search.isPlugin` (global search menu, by target.kind) — are **kept but greyed** when false. Unknown condition names default to enabled
(adding new conditions later does not break old plugins).

### Merge precedence (four levels) and 「同一份计算」(one shared computation)

The final entries of every slot are computed by `buildUiSlots(plugins, { locale, t, disabledPlugins, layout })`:

| Level                  | Source                                                                                                                                                                                                                                                                                                                                      | Rule                                                                                                                                                                                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Host defaults        | `BUILTIN_UI_ITEMS` (**119** `host:*` built-in entries across **13** slots: topbar 18 / file context menu 27 / SCM toolbar 12 / footer 10 / file preview header 9 / goal bar 8 / composer actions 7 / session context menu 6 / message toolbar 5 / terminal toolbar 3 / search context menu 10 / left panel sections 3 / right panel tabs 1) | Baseline for visibility, order, grouping and wording                                                                                                                                                                                                                        |
| 2 Plugin contributions | `UiPluginInfo.ui.items`                                                                                                                                                                                                                                                                                                                     | For the same id, a later-declared plugin overrides earlier ones (**position stays where first declared**, so re-declaring does not push entries to the end of the list); errored plugins and plugins disabled in 「界面插件」(UI plugins) are dropped wholesale             |
| 3 Plugin arrangement   | `ui.arrange` (may change `slot` / `hide` / `group` / `order` / `label` / `hint` / `icon` / `iconSvg`)                                                                                                                                                                                                                                       | Can only change **existing** entries (a missing target = silently ignored); modifying someone else's entry records it in that entry's `arrangedBy` (including `movedFrom`) — the visibility guarantee for 「插件不许偷偷改宿主 UI」(plugins may not secretly alter host UI) |
| 4 User preferences     | `settings.uiLayout` (`UiLayoutPrefs`: `hidden` / `shown` / `order` / `groups` / `labels`)                                                                                                                                                                                                                                                   | Highest: whatever the user clicked has the last word; `shown` is applied after `hidden` (「显示」/Show is an undo of a previous hide and must take effect)                                                                                                                  |

Equal order / absent ordering info keeps declaration order (stable sort as the fallback). **「同一份计算」(one shared
computation) is the framework's core invariant**: the render layers
(TopBar / FooterBar / ChatInput / Message(List) / RightPanel / LeftPanel / SettingsModal) and the settings panel's
「界面布局」(UI layout) page run the same `buildUiSlots()` — the order / grouping / wording seen on the layout page is what
takes effect on screen, so that page can hide entries one by one (checkboxes), reorder with ↑/↓, restore a single entry or
「全部恢复默认」(restore all to defaults), and marks plugin-modified entries as 「插件调整过」(adjusted by plugin)
(`arrangedBy`). Restore undoes only **user preferences** (the plugin's `arrange` intents still apply; to undo those too, disable the plugin); the
`source` / `userOverrides` / `arrangedBy` / `movedFrom` fields on an entry are the layout page's basis for explaining
「这条是谁挪走的」(who moved this one).

**How labels (`labels`) land**: `UiSlotEntry.label` has two kinds — host built-in default (`t(labelKey)`) and **explicitly
specified** (the user renamed it on the layout page / plugin `arrange.label` / an entry the plugin declared itself); the latter sets
`UiSlotEntry.labelExplicit`. The render layer must honor that flag: built-in entries always draw their own hard-coded i18n text
and live values (topbar buttons, footer numeric badges), and yield only while `labelExplicit` is set — name-type entries
(the view trio / search / plugin entries…) use the user's text in place of the built-in text; value-type
entries (context / cost / cache / message count / connection state…) insert the name before the value and
**never swallow live data** (`named()` / `withName()` in `BarItem`). Without the flag, rendering is byte-identical to the old
version, so 「插件的 label 与用户的改名对内置条目也真的生效」(plugin labels and user renames really do apply to built-in
entries too) (issue #555; regressions: `tests/unit/bar-item-unified.test.ts`, `tests/ui-layout-ui-test.mjs`).

### Overflow and hiding

Only the **topbar** has an overflow concept: the main row itself is unlimited (laid out flat like the footer, horizontal
scrolling on narrow screens / wrapping on desktop), and `hidden` entries plus entries declared directly in
`topbar.overflow` as permanent residents go into the 「⋯」 overflow menu — that is, a plugin can move a host built-in entry
off the main row, but it stays present in the overflow menu and on the layout page, so one click on 「恢复」(Restore) puts
it back (plugins can tidy everything but cannot lock the user out). Other slots have no overflow: `hidden === true` simply
means not displayed (context menus do not even generate the item). The layout page groups all 22 mount points exhaustively
(`uiLayoutSections` in `SettingsModal.tsx`, in the same order as `SLOT_IDS` — both strictly follow the actual on-screen
DOM/visual order: topbar → notices → left panel → main column → right panel → terminal/Git views → footer → floating
layers → context menus → settings pages → dialogs; the search box filters, and ↑↓ is disabled while searching). The
topbar / footer / composer action area render in segments by alignment (left start → center → right end), and the layout
page lists them by segment the same way (segment headers are the on-screen segments); ↑↓ moves within a segment and
changing segments goes through the alignment dropdown. The left/right side docks (`sidebar.left` / `sidebar.right`) follow
the same model but on a **vertical** axis: start=top → center=middle → end=bottom, with the layout page's segment headers
and alignment dropdown using 「靠上/居中/靠下」(top/middle/bottom) wording (the same value set, the same
`uiLayout.align` preference).

### `host.ui.*`: runtime registration

| Method              | Semantics                                                                                                                                                                                                                              |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `register(items)`   | Register / override entries (same id overrides the manifest declaration, at most 32 per call); returns an unregister function (moving this call's ids into `removed`)                                                                  |
| `update(id, patch)` | Partially update a **currently effective** entry (manifest and runtime-registered both count; nonexistent ones are always ignored, so plugins cannot conjure entries and bypass declaration review); typical use is refreshing `badge` |
| `remove(id)`        | Remove an entry — manifest-declared ones too (the id goes into `removed` and does not come back during merges until a reload re-parses)                                                                                                |
| `arrange(ops)`      | Append arrangement intents (concatenated with the manifest's `arrange` order); only modifies existing entries and leaves an `arrangedBy` trace                                                                                         |
| `list()`            | Snapshot of the currently effective contribution `{ items, arrange }` (for debugging / self-inspection)                                                                                                                                |

The effective result = manifest baseline + runtime registrations (same id overrides, `removed` deletes), delivered with the
`plugins` manifest's `UiPluginInfo.ui`; every `register` / `update` / `remove` / `arrange` re-pushes the manifest once. Slot
resolution at registration time follows the **same rules** as the manifest (map aliases first, then validate the enum) — early
runtime registration lacked this validation, so a plugin writing an alias (or a typo) got a slot the front end did not know,
showing up as 「注册了但界面上没有」(registered but not on screen), the hardest thing to debug.

### Built-in entry implementations stay in their components (a pitfall we hit)

The app dispatches **plugin** actions only (`triggerPluginUiAction`: look for a handler under that plugin name, otherwise
lazy-load its client bundle and retry, and if nobody takes it, show one line of text); `host:*` built-in entries are
implemented inside the component that renders / opens them, dispatched by the component on `entry.id` — e.g.
`host:file-add-root` / `host:file-open-project` in `RightPanel.tsx`, `host:conv-force-dismiss` in `LeftPanel.tsx`,
`host:msg-edit-reask` in `Message.tsx`. Reason: these actions need the component's own context (which directory was
right-clicked, which conversation, the message's attachments and re-ask logic) that the app does not have. Context menus
therefore also pass the 「host 条目分派器」(host entry dispatcher) (`onHostAction`) with the request into the single global
menu state in `web/src/context-menu-state.ts` when opening. **Pitfall we hit**: early on built-in entries were handed to the
app as plugin actions too, and all those clicks did nothing (the app lacked the context and could only fail silently).

### Modals (`modal.dialog`)

The 22nd slot: entries a plugin declares with `kind="view"` pop up as modals on demand through the host bridge (`PluginModal.tsx`).

```json
{
	"permissions": ["ui"],
	"ui": {
		"modal": [{ "id": "preview", "label": "预览", "kind": "view", "view": "plugin:my-plugin" }]
	}
}
```

```js
// client/entry.mjs: a button click pops this plugin's own modal; closing is by the user (Esc/backdrop/✕) or closeModal()
window.__piWebUiHost.onUiAction("my-plugin:open", () => {
	window.__piWebUiHost.openModal("my-plugin:preview");
});
```

- Open/close via host bridge v10 (`openModal(id)` / `closeModal()`): the id is the global id (`<pluginId>:<itemId>`);
  nonexistent / hidden by the user on the layout page → returns `false`; only one is open at a time (a later one replaces the earlier).
- Content dispatches by kind: `view` mounts the plugin view (bundle lazy-loaded, showing loading until ready, using the same
  `ensurePluginViewLoaded` as topbar actions); other kinds become a single large button (clicking calls `onUiAction` and closes the modal).
- Open/closed state is browser-local (not in the snapshot, not in layout): a refresh closes it; `hidden` only controls
  「能不能开」(whether it can open).
- The layout page has a separate 「弹窗」(Modal) group (entries can be hidden; ordering is meaningless — only one modal is open at a time).

## Directory grants and cross-directory fs (issue #146)

`host.fs` has two legs with a clear division of labor:

- **Workspace-relative** (`list` / `read` / `readText` / `write` / `remove`): `WorkspaceFS`, paths anchored to the **live cwd root**
  (following `set_cwd`), out-of-bounds rejected.
- **Cross-directory** (`listPath` / `readPath` / `readTextPath` / `writePath` / `removePath`): anchored to 「用户点过头的目录」(directories the user has approved), and every operation requires the path to be granted or it throws — the error message tells you to `await host.fs.requestAccess(dir)` first.

**Grant flow** (`requestAccess(dir, reason)`):

1. Normalize the path (`normalizeGrantPath`: **absolute paths only**, relative paths rejected outright) → if it falls inside the workspace (cwd + extra workspace
   roots) or is already in the grants table → return `true` directly, **without bothering the user**.
2. Otherwise the server pushes `plugin_path_request` (`{ id, pluginId, path, reason? }`) to **all online clients**, the browser shows a
   confirmation dialog (`App.tsx`), and the user's answer comes back as `plugin_path_response` — **only the first answer counts**; no answer within 120 seconds
   counts as a refusal.
3. Approval is written into the grants table `<dataDir>/plugin-grants.json` (`PluginGrantsStore` in `server/plugin-grants.ts`), so it is never asked again;
   `authorizedDirs()` returns the directories currently approved for this plugin.

**Grants table semantics**: globally shared (not per-client — a grant is 「这台机器上的这套插件配置允许访问哪些目录」(which
directories this plugin setup on this machine may access), and every browser sees the same table); **a parent directory grant covers
child directories** (a directory grant is inherently a subtree grant, otherwise users would just click agree blindly), but not the reverse (with only
`/proj/a` granted, accessing `/proj` still asks); matching is done on path segment boundaries, never bare prefix matching (`/proj` does not
cover `/project`); win32 comparisons fold case, but **storage keeps the written form**; unreadable / bad JSON / wrong shape all count as
an empty table, and **the read path never writes back** (otherwise one disk hiccup would silently wipe all user grants); only writes that really change
something hit disk (temp file + rename atomic write), and write failures are best-effort (the in-memory state still applies for this session).

**Supported paths = workspace (cwd) + extra workspace roots + this plugin's granted directories**; everything else throws. The
difference from 「插件自己 `import node:fs` 碰任意路径」(a plugin touching arbitrary paths itself) is exactly the layer the host can
enforce — a plugin's server-side code is fully privileged Node code, and real restriction would need an OS sandbox (out of scope for this project), so the
value here is covering more scenarios with supported paths while guaranteeing 「用户知情 + 可撤销」(user-informed + revocable).

**Revoking**: the 「已授权目录」(Authorized directories) section on the 「界面插件」(UI plugins) page in settings lists the grants table and revokes them
individually (`plugin_path_revoke`; the protocol also supports clearing per plugin and clearing the whole table). The browser additionally
keeps a localStorage record (`pi-web-ui:plugin-path-grants`, see `App.tsx`) — that is what the **host action bridge** records to avoid
a dialog on every `openSession` / `sessions.open` (directories in 「最近项目」(Recent projects) also count as known and do not prompt), and it is a
separate thing from the server grants table that the plugin's own `host.fs` uses.

## Dynamic capability grants (host.requestPermission)

The manifest governs 「有没有这个能力族」(whether the capability family exists) (static); this table governs 「运行时的具体范围」(the concrete
runtime scope) (dynamic):

```js
// net: add a host beyond the allowlist (no manifest edit + reinstall needed)
if (await host.requestPermission({ family: "net", hosts: ["api.example.com"], reason: "同步笔记本" })) {
	await host.net.fetch("https://api.example.com/notes");
}
// llm: let the user set the model scope (empty models = no limit)
await host.requestPermission({ family: "llm", models: ["openai/gpt-4o-mini"], reason: "只用便宜模型总结" });
```

- **Precondition**: the base family must already be declared (net→`net`, llm→`llm`), otherwise `false` immediately with no dialog — the
  same rule as `requestAccess` requiring `fs:read`. Enforcement at execution time: `net.fetch` checks the static allowlist **or** the dynamic
  table; `llm.complete` is fully open once declared, but tightens to the approved models when a model-scope grant exists.
- **Flow**: static hit / existing grant → `true` immediately; otherwise `permissionRequester` pushes `plugin_permission_request` to all
  online clients and waits for the first answer (120s timeout = refusal; after an answer `plugin_permission_resolved` is pushed so other clients dismiss it).
  `remember=true` persists to `<dataDir>/plugin-permissions.json`, otherwise it is memory-only (lost on restart).
- **Audit/revoke**: `plugin_permissions` snapshot (pushed at attach + re-pushed on change, session grants flagged), revoked individually in the
  「已授权能力」(Authorized capabilities) section of settings (`plugin_permission_revoke`, supporting per plugin / per family / per host or model / clear the whole table).
- Always `false` under DSH/no browser. Implementation: `server/plugin-permissions.ts` + `PluginManager.permGrants` +
  wiring in `index.ts` (isomorphic to directory grants).

## Scheduled task persistence (host.schedule's persistent)

```js
host.schedule("0 9 * * *", sendDailyReport, { persistent: true, id: "daily", catchUp: "once", label: "日报" });
```

- Declarations upgrade from 「分钟步长」(minute steps) to **full 5-field cron** (minute hour day month weekday, English names accepted for
  month/weekday, standard OR semantics for day-weekday, server local time zone; the old `"*/N * * * *"` is a subset and keeps working). Millisecond numbers are still
  accepted (10s floor for the in-memory version, 60s for the persistent one).
- **Firing uses chunked setTimeout**: `armDelay()` slices 「距离下次触发」(time until the next fire) into chunks of ≤6 hours, recomputes on each wake-up,
  and fires only when the time really arrives; `nextCronFire` returns `null` for 「一年内没有下一次」(no next fire within a year) (e.g. `0 0 31 2 *`), and
  the background panel shows 「不再触发」(will not fire again). Why: Node's setTimeout overflows to 1ms for delays above 2^31-1ms (≈24.8 days), which
  combined with a legal expression whose next fire is 42 days/a year away becomes an infinite loop of 「1ms 后再触发」(fire again in 1ms) (and each fire calls back
  into the plugin → disk write + broadcast). Regression: `tests/plugin-cron-overflow-test.mjs`.
- `persistent: true` requires a valid `id`: the declaration + `lastRun` persist to `<pluginDir>/schedules.json`, and every
  `activate` **re-calls** `schedule()` to rebuild it (idempotent: keeps `lastRun`/`createdAt` and only updates the declaration).
  Deactivation only stops the timer and does not break persistence; `off()`/stopping from the panel = delete the declaration (it does not come back).
- `catchUp: "once"` (default `"skip"`): if a restart finds a missed run (anchored to last fire/creation time, with the next fire already in the past),
  it runs once after a 15s buffer (waiting for model/network readiness).
- Persistent tasks automatically appear in the topbar 「后台任务」(Background tasks) panel (⏰ + next time, stoppable). Implementation: `server/plugin-schedule.ts`
  (parsing/next fire/persistence, pure-function unit tests) + wiring in `plugins.ts`.

## Project assembly API (host.project.create, issue #146)

Lets a plugin stitch 「几个仓库 + 若干配置文件」(a few repos + some config files) into one workspace. **Precondition**: the plugin needs the `fs`
capability family, and the target directory must be inside the workspace or granted (otherwise it returns
`{ ok: false, error: "项目目录未授权：先 await host.fs.requestAccess(...)" }` — "project directory not authorized: call await host.fs.requestAccess(...) first").

```js
const res = await host.project.create({
	dir: "/abs/path/to/workspace", // must be an **existing** absolute path (this API does not create a new root)
	repos: [{ url: "git@github.com:me/app.git", subdir: "app", ref: "main" }],
	files: { "app/.env.example": "FOO=1\n" }, // relative path → text (≤1MB each, ≤32 entries)
	gitInit: false,
});
// res = { ok, error?, log, dir }; log is the line-by-line execution log, and progress is also broadcast to the browser via notify
```

Execution order: validate the root directory → validate `repos` / `files` (**pure computation, all before touching disk**) → `mkdir` subdirectories →
`git clone --depth 1 [--branch <ref>]` → write files → optional `git init`. Three hard constraints:

- **Out-of-bounds rejection**: `subdir` and `files` keys are always resolved as relative paths and must still be inside `dir` after resolution
  (absolute paths and `..` are rejected), with the target (or its nearest existing ancestor) re-checked via realpath — preventing junctions / symlinks
  from directing writes outside the directory; `replace: true` is not allowed on the project root (that would delete the user's own directory, not
  「清空一个子目录」(empty a subdirectory)).
- **No option injection**: git runs via `spawn`, not through a shell; a URL starting with `-` is rejected outright (option injection like
  `--upload-pack=` can execute arbitrary commands on the remote, and an argv array does not stop it); the git child process disables all interactive
  prompts (`GIT_TERMINAL_PROMPT=0` / `GCM_INTERACTIVE=never` / ssh `BatchMode`), and a single git command that exceeds 5 minutes takes the whole
  process tree down with it — the server has no TTY, so interactive auth would hang until the watchdog times out.
- **No half-finished results**: any failing step stops immediately and returns `{ ok: false, error, log }` (the reason at the first failure point + the
  steps already taken), swallowing nothing and faking no success; a half-built project labeled 「成功」(success) is worse than a plain error.

The assembled directory is just an ordinary directory — where to go next is the plugin's own decision (e.g. `host.openSession({ cwd, roots })` to open
a new session, or `set_cwd` to switch over); `host.project.create` performs no implicit project switch / conversation open.

## Workspace ownership of plugin HTTP requests

`ctx.apiUrl()` from file preview automatically carries the current tab's `clientId`. The host captures cwd and extra roots for that client and threads
them through the whole async HTTP handler via `AsyncLocalStorage`; `host.cwd`, `resolveInWorkspace` and host file access use that per-request snapshot
and are unaffected by other tabs switching projects. Explicitly supplying an unknown client rejects the request; legacy endpoints that supply no client
keep using the global workspace snapshot from the start of the request.

## Multi-root workspaces (`set_workspace_roots`, issue #146)

**Semantics**: AI still works only in the main cwd (the pi SDK is a single-cwd model, and multiple roots are **not** multiple workspaces); extra roots
affect only two things — 「哪些路径算工作区内」(which paths count as inside the workspace) (the plugin's supported paths) and the right panel file
tree's roots (one root expanded at a time, no merged view).

- **Protocol**: upstream `set_workspace_roots { roots? }`; snapshot field `UiState.workspaceRoots` (delivered by both engines; the DSH engine has no
  plugin host, so multiple roots only benefit the file tree). An empty array = back to a single root.
- **Normalization** (`server/client-state.ts`: `normalizeWorkspaceRoots` / `MAX_WORKSPACE_ROOTS = 8`): absolute paths only, deduplicated (case-folded on win32), at most 8
  (excluding the main cwd), resolved to canonical form; dirty elements (numbers / empty strings / objects) are dropped individually rather than falling back
  wholesale. Deliberately **does not validate that directories exist**: a root may be a temporarily disconnected drive or mount point, and roots the
  user set must not be silently cleared.
- **Persisted per project**: stored as `workspaceRoots[cwd]` in client-state.json, so switching projects switches to that project's own set; an empty array
  deletes that project's key (no empty shell left behind). Rewriting the same set = no-op (no snapshot push, no disturbing plugins).
- **Front end**: the **root selector** in the right panel crumbs (rendered only when roots exist; lists the main root + each extra root, each
  removable — removing the root being browsed falls back to the main root). **Two add-root entry points**: the file tree context menu
  「添加为工作区根」(Add as workspace root) (visible only on directory rows, hidden when already listed or when it is the main root), and
  「＋ 添加为工作区根」 in the footer cwd selector header (adds the currently browsed directory as a root — the footer is already where the
  working directory is changed, so users can find it). Adds and removals both write the whole list back via `set_workspace_roots`; the server-side value
  is the single source of truth.
- **Plugin-side impact**: `PluginManager.isInsideWorkspace()` counts the cwd and **all extra roots** as 「工作区内」(inside the workspace) ⇒ those roots need
  **no grant** in `host.fs` (the cross-directory family) or `host.project.create` (the user adding a root = 「我认它是我工作区的一部分」(I consider it part of
  my workspace)). Root changes sync to plugin hosts via `notifyWorkspaceRoots`; the `onCwdChange` hook is deliberately **not** fired — that hook means
  「当前目录变了」(the current directory changed).
- **Why not localStorage**: multiple roots are not a pure UI preference — the server-side plugin host (`isInsideWorkspace`) uses them to decide which
  paths need no grant, so the source of truth is server-side and delivered with the snapshot (which also yields multi-tab consistency and per-project
  persistence). Conversely, plugins **cannot** add roots themselves: `set_workspace_roots` is a host-side (user) action — which is exactly why every
  directory in `host.openSession`'s `roots` must first pass user authorization and roots can never be a side door.

## Project / session API (host.openSession / host.sessions, issue #146)

`startChat({ prompt, cwd })` is the 「已受理」(accepted) short form (backward compatible); use the awaitable version when you need a result, a directory
grant, or multiple roots:

```js
const res = await host.openSession({ roots: ["/repo/a", "/repo/b"], prompt: "先看 README" });
// res = { ok: true, sessionId } | { ok: false, error }
```

- `cwd` / `folders` / `roots` all take **absolute paths**: `cwd` wins, otherwise the first of `folders` / `roots` becomes the cwd and the rest become
  **extra workspace roots** (at most 7, see 「多根工作区」(Multi-root workspaces)).
- When a directory is **not in recent projects** and this browser has not authorized it, the host first shows a confirmation dialog (the result is recorded in
  browser localStorage `pi-web-ui:plugin-path-grants`); **every extra root must pass this gate too** (becoming a workspace root means plugins read it
  without further grants, so `roots` must never be a side door). User refusal → `{ ok: false, error }`, and the current session and workspace are left intact.
- Order: authorize → switch cwd (waiting for the server snapshot to catch up) → write extra roots (**after** switching projects: the server stores roots per
  project) → open a new conversation (waiting for activeId to settle) → optionally send `prompt`; every step has a timeout (8s default), and timeouts /
  failures all return structured `{ ok: false, error }`.

**Session list and open** (`host.sessions`, introduced in v2):

| Method     | Behavior                                                                                                                                                                                                                                                                                                                                                                |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list()`   | Array of `{ id, title, cwd, kind, isStreaming? }`: **running conversations of this client** (`kind:"running"`, id = conversationId, each with its own cwd) + **history sessions of the current project** (`kind:"history"`, id = session file path, cwd = the current cwd — the server's history session list is scanned by cwd)                                        |
| `open(id)` | Cross-project first switches cwd (the same directory grants; without it the target file cannot be found) → `running` uses `switch_conversation`, `history` uses `switch_session` → wait for activeId to change; returns `{ ok: true, sessionId }` or `{ ok: false, error }` (disconnected / id not found / switch timeout all use this acknowledgement and never throw) |

## Group work-item host API and Superagent public webhooks

`host.workItems` (contract in `plugin-sdk/index.d.ts`) reuses the existing `chat` permission. The host trusts a plugin with that permission to submit work-item grants based on local config; an external payload is not a source of authorization. `server/plugins.ts` injects the plugin's own `connectorId`, forwarded to the Hub via `server/device-center/local.ts` and handled within the account / group and source scope; the plugin does not provide a second model or executor.

- `rooms`, `ingest`, `list`, `get`, `update`: map rooms, receive deduplicated events, read work items and update by business revision; `list` currently returns the first bounded preview page and promises no full history.
- `claimDelivery`, `completeDelivery`, `failDelivery`: claim from the persistent outbox, acknowledge while holding the lease, or record the failure, with the host scheduling later retries.
- A work-item grant does not replace per-event authorization: a followup that fails the author allowlist cannot ride an existing auto work item, and a manually authorized `authorizedEventId` binds only to the current latest event. The initial description is preserved and followups serve as independent event evidence; a task result does not automatically complete a business work item.

Superagent 0.1.3 is a host built-in GitHub / Feishu channel module that reuses the plugin runtime internally. The background outbox polls only channels with a configured room mapping and send credentials; it stays idle when nothing is configured and resumes automatically once config is completed. Polling runs serially, normally waiting 15 seconds after each round, with exponential backoff up to 5 minutes when a host call fails; a failure in one round warns only once, a successful recovery is logged once, and diagnostics contain only available HTTP status codes and connection troubleshooting hints, never echoing upstream error content. After uninstall it no longer schedules, claims across channels or emits poll logs. Before main-site authentication it exactly allows only `POST /api/superagent/webhooks/github` and `POST /api/superagent/webhooks/feishu`, routing to the plugin's corresponding route and validating the channel signature. Requests are capped at **1 MiB**, and the host stores the raw byte Buffer (`req.rawBody`, rawBuffer semantics) for signature verification; it refuses when the plugin is unavailable or the raw bytes are unavailable. Config, work-item management and manual write-back keep using the existing main-site authentication and plugin validation under `/plugins-api/superagent/*`; that must not be a reason to expose the whole plugin namespace.

UI and remote device paths reuse `appUrl()` / the plugin's `apiBase()`, preserving the app root path and authentication. Public callbacks use the reachable URL shown on the plugin page; a remote page root path is never treated as an implicit relay. The Superagent directory enters the npm publish whitelist, `server/builtin-modules.ts` declares the host-required module, and `server/plugin-bundled.ts` prepares it offline before scanning, so it can be opened from **设备连接与跨平台协作 → 外部渠道** (Device connection and cross-platform collaboration → External channels) on first startup; no extra install or standalone topbar entry. `DeviceChannels` uses the existing scoped importer and the embedded `PluginView`, follows the narrow context and unmount cleanup, refreshes per epoch and isolates stale loads; an explicit retry bumps the bundle cache salt. Built-in modules never appear in the ordinary plugin marketplace, installed list, menus, layout or permission lists; managed counts and update prompts exclude them too, and ordinary install / update / uninstall plus custom same-name override entries refuse to touch them. Legacy plugin disable / uninstall records do not control host modules, missing files are re-prepared, and existing settings and secrets are preserved. `<dataDir>/bundled-plugin-installs.json` keeps controlling only the first preparation of ordinary optional pre-installed plugins and is not the install basis for required modules. Feishu supports plaintext or AES-encrypted signed text callbacks, and uncertain deliveries with no acknowledgement for more than 45 minutes need manual verification; GitHub recovers retries through a stable comment marker. Real external credentials and channels were not connected in this round; mock tests do not mean production-ready.

For full responsibilities, the group-top AI Router / work-item drawer usage, the four WAL sets, frozen plan / lease / config fence / effect receipts, pagination and context budget see [Group standalone AI Router and Superagent](group-orchestration.en.md); for channel configuration and support scope see the [Superagent README](../plugins/superagent/README.en.md).

## Settings page: the three extension menus and collapsible plugin details

The 「扩展」(Extensions) group in the settings page has **3 side-by-side nav items**: Skills / MCP servers / Plugins (`tabs[]` and `TAB_GROUPS` in `SettingsModal.tsx`). Skills and MCP each keep their existing sub-pages and components (`McpServersPanel` only moves), and are not folded into the plugin page; host built-ins such as tool toggles, approval rules, UI layout and presets stay in their original groups.

**The plugin page has two sub-pages** (`pluginTab`):

- **Installed plugins**: `<InstalledPluginsPanel/>` is a single-column collapsible list that aggregates `chat.plugins` (UI plugins) and `settings.extensions` (Pi / agent session extensions), and fills in health, raw error text and tool counts for SDK built-in extensions from the server-side `extension_inventory_data` (`server/extension-inventory.ts`). Clicking a row expands the details in place, at most one row at a time, **with no left/right split**; UI plugin details contain the config fields (`PluginSettingsForm`), `settings.pages` plugin pages (`PluginPage`) and run logs; Pi extension details contain registered capabilities and load info. Enabling and disabling write back to `settings.disabledPlugins` / `settings.disabledExtensions` respectively — the unified list is only a projection, **no third copy of state is created**; SDK hidden built-in extensions are marked 「只读」(read-only). Pi extensions have no built-in marketplace; installing and removing goes through the terminal with `pi install npm:<pkg>` / `pi remove npm:<pkg>`.
- **Plugin marketplace**: every control of the UI plugin marketplace is kept as is (official / community sections, custom catalog sources, sync and batch install, submit a new plugin, official repository link, check for updates, install job progress), and the data still comes from `plugins/catalog.json`, `OFFICIAL_PLUGIN_CATALOG_URL` and `chat.pluginCatalog`; the skills marketplace and MCP marketplace stay in their own menus and are not moved here.

`pluginSub` is a derived value (the installed sub-page is `"installed"`, the marketplace sub-page is `marketOrigin`), so the existing marketplace block needs no rewrite. The `extension_inventory` request is now triggered by `tab === "plugins"`, and the new list reads the same inventory.

Removed entry points: the old 「界面插件」(UI plugins) tab, the Pi extension list on the old 「插件」(Plugins) tab, `PluginManagerModal` mounting in `TopBar`, the top-level tabs generated by `settings.pages` (`plugin-page:*`), the `ExtensionInventory` read-only list mount, and the 「插件设置」(Plugin settings) button in `PluginMenu`. The topbar 🧩 degrades into a read-only quick launcher that keeps only one 「管理插件 →」(Manage plugins →) deep link (`openSettings("plugins")`). The DSH engine's plugin marketplace and patch management stay on the `dsh-extensions` tab (advanced group) and do not enter 「插件市场」(Plugin marketplace).

The `PluginManagerModal.tsx` / `ExtensionInventory.tsx` files are kept (the former is still rendered directly by unit tests, the latter is still the source of the server-side inventory capability), but they are no longer mounted on any user-visible settings / topbar entry. New i18n keys live in `web/src/i18n/messages/core/{zh,en}.json` and require `npm run i18n:sync` after changes; style prefixes are `.ip-*` in the last layer of `web/src/styles.css`.
