# Native remote desktop for authorized devices

Device Center borrows the native capture and input approach of [krd](https://github.com/zzjcool/krd), reuses the device access ticket and connector, and renders JPEG into a browser canvas. Opened from the local Device Center, it shares [LAN-preferred access](device-center.en.md#lan-first-access) with the full 「打开设备」(Open device) conversation UI: prefer the private-network path validated with TLS PSK, try device-to-device P2P when unreachable, and use the original Hub WebSocket relay when that fails. No VNC service, noVNC or fixed desktop port is needed. The picture never enters the chat snapshot or the model context.

Windows supports an H.264 hardware-encoding path (see 「H.264 hardware-encoded path」 below), enabled automatically when the browser supports WebCodecs and staying on JPEG otherwise.

## Chat-page preview and enlarged operation

After entering a remote chat page through a device channel, the right column automatically shows the desktop of the device that page belongs to. The current device identity comes from the authorized portal capability path; preview, live picture and input all reuse that path, so the controlled machine no longer requests LAN/P2P/Hub tickets from itself. After closing the preview, 「显示此设备的桌面」(Show this device's desktop) restores it; picking the current device in the device list goes through the same entry point. The connection badge shows 「复用当前连接」(Reusing current connection) and does not guess whether the substrate is LAN or P2P. Standalone tabs are opened on behalf of the remote page by the trusted outer layer and do not relax the remote sandbox permissions.

The desktop toolbar groups by connection, view options and auxiliary panels, and follows the chat page's theme colors. `desktop-theme.ts` defines the color tokens allowed to sync; the parent page forwards them to the desktop sandbox through source-window-constrained messages, and the desktop accepts color values only — it loads neither arbitrary styles nor URLs. A theme switch never rebuilds the iframe or the WebSocket. Standalone pages follow the system light/dark preference by default; on narrow screens the horizontal toolbar and a separate status row are kept, settings, text input and connection info expand mutually exclusively, and Escape or an outside click collapses them. Theme forwarding over the Hub relay requires the Hub to be updated to the same version.

When opening the remote desktop from the local Device Center or a group member, the chat page shows a preview of one selected device above the right column, with the files and plugins areas kept below. The preview can be collapsed, resized in height, switched to another device or closed. “选择设备” (Select device) opens the device list right next to the button, shows the current device and online status, and switches the preview when an online device is clicked without navigating to Device Center; closing the list cancels incomplete reads. Clicking “放大并操作” (Enlarge and operate) creates the live desktop window, and moving between window and fullscreen only changes layout without recreating the iframe or requesting a ticket. The × in the enlarged window and “返回预览” (Back to preview) both keep the selected device and restore the right-column preview; only the × on the right-column preview itself closes the whole desktop. Returning to preview releases the live connection and any held mouse/keyboard state, then requests a new preview ticket. Switching chat sessions keeps the selected device; switching devices or closing the desktop cleans up the old page. Mobile browsers default to fullscreen after enlarging; the native mobile app still uses its own device adapter.

`web/src/device-access.ts` owns device selection and the preview/live state, and `use-desktop-target.ts` requests a one-shot ticket when the page mounts; async responses are constrained by AbortSignal and the device-selection generation. When the device list hits a transient 502/503/504 it auto-retries at most twice within the same 15-second window; closing the list cancels requests and waits and does not rebuild an existing preview. `desktop-preview.tsx` only asks the sandbox page to start a request while the preview is visible. Collapsing, hiding the right column or the browser going to the background cancels requests and polling. The window reuses `RemoteDesktopWindow.tsx` and the unified overlay z-index. Both modes show the actual LAN/P2P/Hub path and update the badge after a LAN fallback.

`/desktop-preview` serves a standalone read-only page that requests `/api/device-desktop/preview` over the existing authorized channel, waits 3 seconds after each frame before requesting again, and keeps at most one request in flight; images target a 640 px longest edge. The capture side uses preview mode: Windows/macOS wait 3 seconds per round, Linux X11 runs at 1/3 FPS. Lowering only the browser's display rate does not count as lightweight capture.

`desktop-preview.ts` merges concurrent requests for the same device, reuses frames from the last 2.5 seconds and queues at most 8 requests; the preview helper shuts down 6.5 seconds after the last request. Starting a live desktop stops the dedicated preview helper and preview requests reuse the newest frame from live capture (keeping the live dimensions at that point); when the live desktop exits and preview requests remain, the low-frequency helper comes back. The preview is always read-only and never requests macOS control authorization. Disabling the desktop, exiting the service, cancelled requests and late capture callbacks each have their own cleanup.

The device side, the local service and the Hub all need to support the new preview entry point. When an old device does not, the preview shows as unavailable and the original live desktop can still be opened; a full-speed desktop stream is never used to fake a lightweight preview. Browsers hitting the Hub directly pick a LAN or cross-network direct connection over WebRTC and fall back to Hub relaying; the controlling side does not need pi-web-ui installed — see [browser direct connection](device-center.en.md#direct-channel-for-browser-only-access-to-the-hub).

### Preview verification

After a standalone tab or a standalone desktop-shell window opens successfully, the main page keeps the device selection and returns to the small preview; the preview stays viewable after the standalone window closes. When the browser blocks the popup or the desktop shell fails to open, the original operation window stays put and the selection is not cleared. The new window has no opener, so close notifications cannot cross origins; while the main page is visible, the preview reuses the standalone window's live frames on the server, and low-frequency capture resumes after the window closes.

Numpad `Numpad0`–`Numpad9`, add/subtract/multiply/divide, the decimal point, Enter and NumLock travel as distinct physical keys and must not be dropped as unknown keys. On Windows, numpad Enter and the divide key keep the extended-key flag, and numpad Enter is recorded and released separately from the main Enter; macOS uses system Carbon key codes and Linux uses X11 keypad keysyms. The NumLock digit/navigation state is whatever the controlled system reports. `tests/device-desktop-windows-keys-test.mjs` compiles the real C# helper and verifies 22 key descriptions plus the release flags without injecting test keystrokes into the user's desktop; browser tests cover real keyboard events through to the WebSocket.

`tests/device-current-desktop-test.mjs` uses real Chromium on port 8996 to verify the nested sandbox, continuous preview, direct control, Chinese input, going back and reopening under the Hub/LAN path, confirming there is no 「再次打开自己」(open yourself again) request; it checks that the one-dark, white and nord themes sync instantly without reconnecting, plus mobile width. It uses simulated capture frames and does not represent cross-machine frame rates.

`tests/unit/device-desktop-preview.test.ts` verifies caching, concurrent reuse, cancellation and the switch to live capture; native/Linux cases check the low-frequency parameters and the read-only constraint. `node --import tsx tests/device-desktop-window-test.mjs` uses port 8997 and real Chrome to verify continuous preview in the nested sandbox, pause on collapse, pause on right-column hide, enlarged operation, no reload into fullscreen, returning to preview, mobile width and cleanup on close, with screenshots under `artifacts/device-center/`. That UI test uses a simulated desktop and does not represent measured cross-machine performance.

### Version upgrades

The controlling side, the controlled side and the Hub must all be updated and their running processes restarted to use the matching new capabilities. Updating the npm package and refreshing the page will not replace a backend that is still running. An installed service can be restarted with `pi-web-ui server restart`, adding `--name <original service name>` when a custom name was used; foreground runs restart with their original working directory, port and data-directory arguments. Update a Hub service the same way it was installed via `pi-web-ui hub update` / `hub restart`, then check the actual version with `pi-web-ui hub status --json`. The original data directory, authentication and device bindings are preserved.

The remote device serves its own Desktop settings. After updating it, reopen its desktop from the device list. On Windows x64, a global npm install or the first interactive launch normally updates the built-in desktop component. Accept the administrator prompt, or run `pi-web-ui desktop service install` on the remote computer to retry a cancelled installation. macOS requires Screen Recording permission for capture and Accessibility permission for control.

If the clipboard entry disappears after opening a remote chat page from the Hub, or the whole chat page appears inside the preview when switching devices, first check the actual version returned by the Hub's `/health`. An old Hub may forward an unrecognized `__desktop_target` address to the device's chat home page; updating the controlled side's npm package cannot replace the Hub's wrapper page and forwarding logic. After updating the Hub service, reopen the entry from the device list instead of reusing a short-lived access address from before the upgrade.

First verify continuous two-machine preview, enlarged operation, returning to preview and pause-on-hide, then verify the LAN and cross-network paths. See the relevant PR for test release and on-device verification scope; native platforms, monitor refresh rates and different NAT environments each need separate verification.

## Group member desktops

Entering a group chat makes the right column show “群组远程桌面” (Group remote desktop): preview cards are ordered by computer by default, and “全部成员” (All members) plus the member buttons below switch to a single member's picture; clicking a picture opens the original live control window, and closing the enlarged window returns to the group preview. Group members are bots, `GroupDetail.room.botIds` bounds the member set, and only a bot's explicit `deviceId` can map to a desktop target; a bot ID is never treated as a device ID. When several bots share one computer they keep their own member buttons and one shared preview. Cards show both the member name and the device's “备注 · 计算机名” (remark · computer name). Offline computers keep a status card, and member buttons with no device link are not operable.

`group-active-context.ts` exposes the current group state, `group-desktop.ts` derives the device mapping, `GroupDesktopPreview.tsx` handles member selection and visibility, and `DesktopPreviewFrame.tsx` shares preview, theme and status handling with the regular desktop. The device catalog refreshes only while the panel is visible; only visible cards request a desktop entry, and scrolling out of the grid, collapsing the panel, switching pages or selecting another member stops that preview. A computer being enlarged has its preview paused. Switching groups, leaving the group and member removal release that group's control windows. The remote button on the original left-panel member also targets the corresponding preview in the group, without affecting `@` mentions or task dispatch.

Desktops still open through the existing device access authorization and LAN/P2P/Hub selection; a local device ID returned by the device catalog reuses the current Web connection instead of looping through the Hub to connect to itself. Showing group members in the UI does not widen access permissions and never enables the controlled machine's desktop automatically. This batch needs no Hub protocol change; the Web pages that view groups must be updated, and member machines already running a compatible desktop service can stay on the current build.

## Dynamic quality and transfer resolution

Under **Desktop settings → Mouse pointer**, choose **Show local pointer** (the default) or **Show remote pointer**. This preference is saved per remote device and can be changed during a read-only or control session. If the setting is disabled, update the capture component on the remote device.

「画质」 (Quality) in the toolbar offers Automatic / Smooth / Balanced / Sharp, a longest-edge cap for the transferred picture (follow window, 960, 1280, 1920, 2560 px) and 10 / 15 / 30 / 60 / 120 / 240 FPS targets. New devices follow the selected remote display’s nominal refresh rate up to 240 FPS, using 60 FPS when the rate is unknown. Explicit frame limits are remembered. Sharp mode samples up to 1.5 times the fitted image size to preserve small text. Turning off Fit to window maps each stream pixel to one physical viewer pixel. Resolution keeps the screen aspect ratio and never upscales the source; OS display settings are not modified. Mouse and keyboard keep using normalized coordinates. Settings apply within the current connection, read-only connections included. Connection info shows the target and the actual capture, send and display frame rates separately; an idle desktop may send only low-frequency keepalive frames, and that cannot be used to measure peak frame rate.

- Automatic mode caps resolution at the container size and at most 2× pixel density, and never shrinks the picture because of network round-trip latency. JPEG and H.264 share the acknowledgement feedback in `desktop-video-flow.ts`: the lowest measured round-trip time is the baseline, and only persistently growing queueing delay lowers quality, then capture frame rate, ramping back up as it recovers. A stable high latency alone does not trigger a sharpness drop. Manual quality pins the corresponding quality and frame rate, while transfer-window and queue limits still apply.
- Congestion detection covers all valid feedback within one second: when more than half the feedback shows over 80 ms of extra queueing or a decode queue greater than 3, it steps down after two consecutive windows; when more than half shows over 250 ms of extra queueing or a decode queue greater than 8, it steps down within that single window. Stepping down is not subject to the five-second cooldown, and a single timely ACK cannot mask delay on the majority of frames; a small number of delayed feedback samples never triggers a step-down on its own. Stepping up still requires thirty consecutive healthy windows (each window with at least 90% of feedback under 30 ms of extra queueing and a decode queue below 2), avoiding an immediate upshift-then-downshift after a brief improvement. Rebuilding the encoded stream clears the sampling buckets so a single frame's startup latency is not mistaken for stable congestion. Manual settings still apply immediately, and in-flight frame, byte and disconnect-detection limits are unchanged. Acceptance must measure input-to-picture response and picture age; FPS or stall counts alone cannot prove low latency.
- `desktop-quality.ts` validates configuration and the base parameters requested by the user. `ready.dynamicQuality` declares the capability; old capture sides do not receive the new configuration. Quality messages are independent of mouse/keyboard authorization, numbers are range-limited, and they cannot trigger local installation, display settings or any other command.
- The Windows service binds the `profile-v2` check value in the protected directory to the installed binary, preventing a rollback from misdeclaring capabilities. Global npm install/upgrade updates the system service automatically through the install script; when scripts are disabled, the first launch in a terminal installs it, and a cancelled run can be retried manually with `pi-web-ui desktop service install`. Quality survives session-switch recovery, and mouse/keyboard input is still not replayed.
- Windows prefers DXGI Desktop Duplication, reusing GPU staging textures and Bitmaps; it falls back to GDI when unavailable, and the lock screen and session recovery still go through the existing system service. Mac uses a continuous SCStream, reuses CIContext and keeps only the newest frame waiting to be encoded. JPEG clients negotiate through a `jpegFeedback=1` request and send the cumulative `jpeg_ack.id` only when `ready.jpegFeedback=1`; sequence numbers count JPEG frames on the ordered WebSocket. The window starts at two frames and derives the in-flight byte budget from the actual acknowledged byte rate and the lowest acknowledgement time, with an extra 100 ms of queueing budget; the transfer time of one large image multiplied by the target FPS is not link capacity. At most 64 frames and 4 MiB of unacknowledged data, plus one extra slot for the newest frame waiting to be sent; once the client skips stale frames it never draws, cumulative acknowledgements release the corresponding window. A JPEG watchdog detects 15 consecutive seconds without valid acknowledgement progress; duplicate or forged sequence numbers do not extend the timer, and continuous acknowledgements are not misread as a disconnect because of old frame age. Old clients or old services keep the two-frame window and per-frame `ack`. On Linux X11 the ffmpeg capture process is replaced on adjustment, keeping the WebSocket and input state, so old capture frames never enter the new stream; the first frame may take a moment during the switch.
- The preview still uses low-frequency, low-resolution read-only capture; cards invisible in the background do not hold continuous capture. Only the fixed local `/desktop` / `/desktop-preview` built-in pages stay same-origin; remote ticket pages always remain an opaque sandbox, and messages validate both the source window and the origin.

## H.264 hardware-encoded path

JPEG measures about 100 Mbps at 1920×1080@60 and about 162 Mbps at 2560×1440@60 (200–330 KB per frame, 10–15 ms of GDI+ software encoding), which relays and most cross-network links cannot feed, making the frame-rate options pointless. Windows therefore adds an H.264 path: capture with `ffmpeg`'s `ddagrab` (DXGI zero-copy), hardware-encode with NVENC to Annex-B, split into access units in Node and send frame by frame, and hardware-decode in the browser with WebCodecs `VideoDecoder`.

- Measured (RTX 4060 Laptop, 2560×1440): a steady 55 fps / 12.6 Mbps at @60; a steady 111 fps / 17.7 Mbps at @120. First frame takes about 310–350 ms (ffmpeg startup + NVENC initialization). At equal quality, bandwidth is about 1/10 of JPEG and encoding costs no CPU.
- Enabling conditions: the browser supports WebCodecs (HTTPS or localhost) and video is negotiated on `desktop-ws?video=1`. Without the system desktop service installed, the ddagrab/NVENC path is used; when the service has the `video-v1` capability bound to the binary hash, the built-in native capture-and-encode path below takes over. Old services with only `raw-v1` can still use the previous Node encoding bridge; older services and browsers without WebCodecs keep using JPEG.
- Encoding parameters: `-preset p1 -tune ll -rc cbr -g <fps> -bf 0`, with the bitrate derived by `videoBitrate()` in `desktop-video.ts` from resolution/quality/frame rate (about 5–9 Mbps at 1080p, 9–14 Mbps at 1440p, ×1.4 at 120 fps). Changing quality or frame rate restarts ffmpeg (a new IDR), and the browser resyncs on the next keyframe.
- The FFmpeg path's VBV buffer budget is 100 ms of the target bitrate, capping the burst of periodic keyframes so a single keyframe does not block the ordered cross-network channel for hundreds of milliseconds; the average bitrate, target frame rate and one-second keyframe interval are preserved. VBV is an encoder constraint, not a hard guarantee on per-frame bytes or network latency.
- Packetization and frame dropping: `createH264Splitter` cuts access units by Annex-B start code and the first VCL slice (`first_mb_in_slice==0`); parameter sets ride along with keyframes, adding one frame of latency over JPEG. H.264 frames cannot overwrite older ones with newer ones the way JPEG frames can, so a backlog over the threshold is dropped until the next keyframe.
- Capture and display are decoupled: ffmpeg handles the picture only; mouse and keyboard are still injected by the Windows native helper in `input` mode (no capture thread), keeping control available.
- Distribution: release packages ship `bin/ffmpeg/<platform>-<arch>/ffmpeg.exe` (downloaded by `npm run build:ffmpeg`, overridable with `PI_DESKTOP_FFMPEG`, see [environment variables](env-vars.en.md)). A missing binary does not affect the JPEG path.
- Input permissions, read-only connections, the clipboard and display selection are unchanged: video mode replaces only the picture encoding, and control and authorization checks are still enforced by the server.

### Service video path built into pi-web-ui

The DXGI capture source must live in FFmpeg's `-filter_complex` and be bound to the selected monitor's GPU with `-filter_hw_device`. `-f lavfi -i ddagrab` establishes an independent default device and cannot guarantee that a multi-GPU selection takes effect. At native resolution NVIDIA submits BGRA textures directly first, avoiding unnecessary scaling and color conversion; at lower resolutions the scaling path is chosen again. When the GPU video processor is unavailable, DXGI capture is kept and the scaled frames are read back and uploaded as NV12 textures before being handed to the hardware encoder; plain CPU frames must never be submitted to a D3D11 NVENC session, and a scaling failure must not immediately switch to GDI. Intel textures are mapped through a QSV context derived from the same GPU. GDI is only tried after every DXGI path fails, and the output still uses passthrough instead of inflating the statistics with duplicated frames.

The layering of capture, encoding and browser display is an independent implementation, designed with reference to RustDesk's [video capture/encode loop](https://github.com/rustdesk/rustdesk/blob/master/src/server/video_service.rs). This implementation does not launch the RustDesk application and does not port its full engine or protocol. Users install only pi-web-ui; enabling lock-screen control on Windows for the first time still requires granting this app's desktop service administrator rights.

`PiWebDesktop` still owns the current desktop, the lock-screen desktop and mouse/keyboard input. `video-view` / `video-control` start the protected native encoder component inside the selected Windows session and on the actual input desktop; FFmpeg does capture, scaling and H.264 encoding in the same process, so raw pixels never pass through a C# pipe or Node. DXGI adapters and outputs are matched by the monitor's actual bounds, multi-GPU is supported, and `DISPLAY2` is never treated as a second output of some adapter. Encoder selection mirrors the VRAM → HWRAM → software order of RustDesk `video_service.rs::get_encoder_cfg`: GPU textures encoded directly in hardware first, then DXGI readback or GDI capture paired with a hardware encoder, and libx264 only after every hardware path fails. NVENC/AMF texture paths use D3D11 scaling, QSV uses hardware frame mapping. GPU enumeration is independent of display outputs, so hardware encoding capability is still checked when RDP or the lock screen has no DXGI output. Rotated or unsupported outputs go through GDI. Connection info shows the actual capture, encode and decode backends and keeps bounded fallback reasons available through a details tooltip.

The encoder component may only come from `Program Files\pi-web-ui-desktop\ffmpeg.exe`: the installer checks the in-package build manifest SHA-256, copies the file into the administrator-protected directory, and startup compares the hash inside that protected directory again; the SYSTEM capture process uses neither PATH, `PI_DESKTOP_FFMPEG`, caller-supplied paths nor scripts. The input desktop comes from the local `OpenInputDesktop`, and a connection cannot name an arbitrary session or desktop. The encoder process is placed in a kill-on-close Job and cleaned up when the client closes, the service exits or the desktop changes.

A quality, frame-rate, picture-size or input-desktop change reopens the encoder. Each new stream clears the old packetization state through a reset marker and re-sends parameter sets and an IDR; the SPS determines the codec, and the browser rebuilds the decoder on a stream reset, never reusing reference frames from the previous encoding session even when the codec string is identical. Decoder selection follows RustDesk `codec.rs::Decoder::new`: check `prefer-hardware` with the actual codec and enable hardware explicitly when it is supported; use `prefer-software` only when the capability check says no or runtime initialization fails. Asynchronous probes and stream switches discard callbacks from older generations and wait for a keyframe when recovering; inputs waiting for decode are capped at 32 frames/16 MiB to avoid accumulating latency. The protocol uses encoded chunks of at most 64 KiB, with a 16 MiB H.264 framing cap and a 4 MiB per-frame cap; pipes, error logs and startup/stall waits are all bounded. Capture rate is controlled by the capture side, input and encoding time bases are explicit, and CFR auto-duplication on output is disabled — duplicated frames are never passed off as a performance gain.

Installed old services with only `raw-v1` keep probing and running the encoder from a normal user process through `desktop-video-encoder.ts`, retaining the 32 MiB raw-frame limit and consumption acknowledgement. JPEG preview still reuses the GDI DIB surface or DXGI capture and is unaffected by the video component starting.

The default Windows FFmpeg can be prepared on Windows, macOS or Linux with `npm run build:ffmpeg -- --platform=win32-x64`; the compatibility encoder and native components must first be built on a Windows x64 build machine with `npm run build:desktop-codec`, or that machine's build output copied into the packaging environment. `scripts/ffmpeg-build.json` pins the default build URL and SHA-256; the package carries the executable, licenses and build provenance. `pack:p2p` and the pre-publish npm steps validate these components, so users need not download FFmpeg or RustDesk separately. If an old desktop service did not update automatically, run `pi-web-ui desktop service install` to retry.

`node --import tsx tests/device-desktop-video-test.mjs` uses the real encoder and Chrome to verify the 60/120/240 configurations and resolution changes within the same window; the input is synthetic pixels, not the actual desktop FPS. Service video to the browser and dynamic resolution have been verified on Windows locally; a static picture through the current console's GDI/libx264 path runs at about 30 FPS, versus about 18 FPS for the previous raw pipeline under the same conditions. Those numbers are not acceptance for a dynamic desktop or a high-refresh display. GPU paths, different GPUs, lock screen → sign-in and cross-network high refresh still need on-device measurement; the target frame rate is a ceiling, and historical ddagrab/NVENC results must not be applied to the new service path.

`libx264` in connection info means the controlled side is software-encoding; even if the same row shows hardware decode in the browser, it does not mean capture and encoding use the GPU. Real service tests record the `fallback` reason; on Windows they also check the display adapter's `ConfigManagerErrorCode`. Device Manager Code 31/43 and a failing standalone hardware-encode probe indicate a GPU or driver fault that a higher FPS cap cannot fix; restore the GPU first, then reconnect and retest the hardware backend and the actual frame rate.

## Live resolution, color and connection info

“画质 → 传输分辨率” (Quality → Transfer resolution) offers follow window, follow controlled screen, preset sizes and custom width/height.
The configuration goes out over the current authorized WebSocket; it does not change the controlled computer's system display mode and does not alter other viewers' settings.
Preset/custom sizes bound the transferred picture, scaled down from the original screen aspect ratio without stretching or upscaling a low-resolution screen;
the actual size is shown in the panel and in connection info. The longest edge has a 640 px floor; the new Windows native GPU path and the Mac
ScreenCaptureKit path support up to 4096 px, while old services and the compatibility path keep the 2560 px cap.
Window resize, resolution and color-range changes keep the existing connection; the video encoder is rebuilt when necessary and sends a keyframe, and the player keeps the old picture until a new frame arrives.

The Windows native GPU path uses an explicit BT.709 RGB→NV12 shader instead of the driver video processor's implicit color conversion.
The H.264 VUI declares BT.709 primaries, sRGB transfer and limited/full range consistently; QSV mapping preserves frame color metadata.
Both “常规色彩（SDR）” (Standard color (SDR)) and “完整色阶（SDR）” (Full color range (SDR)) use hardware encoding; full range is 0–255 and still lossy 8-bit 4:2:0,
so it is not passed off as lossless true color or HDR. HDR is not selectable today; other paths that have not confirmed full-range capability never receive that option.
The service protects compatibility with a `display-options-v1` capability file bound to the installed binary's digest; old services receive the old configuration clamped to 2560.

Connection info is shown by default and no longer closes on a picture click, Escape or other menu toggles; only clicking 「连接信息」 (Connection info) again closes it.
The trusted outer layer stores the resolution mode, custom width/height, SDR color range and diagnostic switch per device, using the same origin-validating bridge as the existing quality preferences.
Verification entry points: `tests/device-desktop-quality-test.mjs` (browser configuration, persistence and read-only),
`tests/device-desktop-windows-service-test.mjs` (native service compilation/IPC),
`tests/desktop-rustdesk-codec-test.mjs` (synthetic GPU color blocks, grayscale, limited/full SDR, 4K switching, real browser decoding).
Verification with synthetic images is not cross-network FPS, all-GPU or on-device Mac acceptance.

## Multiple monitors

The Windows / Mac native capture side enumerates the monitors visible to the current session, and the toolbar shows the number, size and a primary marker. Selecting one releases the old input and reconnects to the chosen screen; the capture area and mouse coordinates use the same monitor's bounds, negative coordinates and portrait orientation included. Returning to preview keeps showing the selected screen; browser windows from the same origin remember the choice per device, and standalone tabs sync with the main window through localStorage. Different site origins share no storage.

`desktop-displays.ts` validates the capture-side metadata, `desktop-display.ts` stores the front-end selection, and `desktop-display-portal.ts` owns the standalone entry. Metadata shares the bounded frame protocol with JPEG but does not consume picture ACKs; the Windows service sends metadata only after subscription and stays compatible with the old Web. When a monitor is specified, frames are delivered only after the source is confirmed to match. If the selected screen disappears, it falls back to an available primary screen. The preview cache is isolated per monitor. Linux does not offer this selector yet.

Simulated dual screens, portrait, input mapping and preview have browser verification; Mac has been switched one by one across three monitors on a real machine with frames received. Real Windows dual screens, different scaling combinations and high-refresh hardware still need further verification.

## Clipboard sync

**Desktop settings → Translate Windows and Mac shortcuts** swaps Ctrl and Command/Windows when controlling the other operating system. The switch defaults to off and is saved per device. Repeated copies of identical text are coalesced during bidirectional sync.

When a browser hits the Hub directly, the trusted outer layer provides 「剪贴板 · 浏览器文本传递」 (Clipboard · browser text transfer): paste and send manually, read the remote's current text, copy to the local machine, at most 16 KiB per transfer. HTTP pages can select text and press Ctrl/Cmd+C, and secure contexts get a copy button; the controlling side's clipboard is never read automatically. Images, files and background automatic sync still require opening the device from the pi-web-ui client on the controlling machine's localhost. Read-only connections may read and are refused writes; closing the panel or disconnecting stops this transfer immediately. Manual connections register no clipboard listener.

Local direct connections, remote sessions and standalone tabs all show the 「剪贴板」 (Clipboard) entry next to 「连接／断开」 (Connect/Disconnect) at the top left of the desktop toolbar, using the same dialog panel. A click sends `desktop-clipboard-show` along the validated iframe chain to the outermost control page; that message only opens the UI, carries no sync direction and cannot enable the local clipboard. The local native sync direction is chosen in the panel too, and closing the panel keeps the chosen automatic sync direction. Players declare the built-in entry through `desktop-clipboard-available.toolbar`, so the outer layer stops duplicating the button; old controlled sides keep only the compatibility entry at the top left of the outer layer. Switching devices or disconnecting stops the transfer and clears old text. The standalone desktop page also offers the manual text panel.

The trusted outer toolbar offers off / ours-to-theirs / theirs-to-ours / two-way sync, off by default, and only copies made after enabling are synced. With both ends updated, open the remote device from pi-web-ui on the controlling machine's localhost; a browser talking straight to the Hub does not yet offer automatic system clipboard sync. The native dependency `@crosscopy/clipboard` covers Windows x64, Mac x64/arm64 and Linux x64; when the platform or permissions do not allow it, only the clipboard feature stops. A read-only desktop never writes the clipboard on the controlled side.

Supported: text (1 MiB), PNG images (16 MiB, at most 32M pixels) and up to 32 regular files. Once both sides negotiate the streaming capability, one batch of files may total up to 16 GiB; old sides are still limited to 32 MiB and support neither folders nor symlinks. Files are read in chunks from validated original file handles, and the receiver writes chunks into its own temporary directory, setting the system file clipboard only after verification completes. Available disk space is checked before receiving; each process holds a 32 GiB reservation for concurrent transfers, completed files are kept for at most 16 batches / 32 GiB, and the current batch is no longer deleted immediately by the old 128 MiB limit. Disconnecting cleans up incomplete files; original files are never modified. Text and images keep no history; completed temporary files are not guaranteed to be cleaned up automatically across processes.

`desktop-clipboard-protocol.ts` defines the limits and messages, `desktop-clipboard-native.ts` wraps native reads/writes, echo suppression and file staging, `desktop-clipboard-transfer.ts` handles bounded file I/O and SHA-256, `desktop-clipboard-connection.ts` handles direction, chunking and acknowledgement windows, and `desktop-clipboard.ts` handles endpoint authorization. A separate WebSocket keeps file contents out of the desktop frame queue; the new version allows up to 32 chunks of 24 KiB awaiting acknowledgement, while old sides still acknowledge chunk by chunk. Timeouts, insufficient disk and source-file changes cancel only the current transfer and keep the sync direction so the copy can be reissued; protocol or integrity errors still drop the connection. The browser shows transfer progress. The browser bridge accepts messages only for the direction the user selected and from the matching window, so a remote page cannot enable our clipboard on its own. The local viewer endpoint lives under `/api/device-desktop/local/`, where remote relay is forbidden, and remote endpoints reuse desktop authorization. The opaque iframe's local-network permission serves only the existing capability entries and does not change origin isolation.

`desktop-preferences.ts` stores quality, resolution cap, frame rate, fit-to-window, read-only and the user's explicit clipboard direction per device identity. The trusted outer layer does the persisting; opaque pages read and write picture preferences through an origin-validated message bridge but cannot write the clipboard direction. A ticket refresh does not clear preferences; standalone tabs, returning from an enlarged view and reconnects restore the configuration. Read-only connections temporarily restrict the sync direction and keep the original choice; resuming the listener never sends clipboard contents that existed before it was enabled.

## Platforms and enabling

Without the desktop background service installed on Windows, capture depends on the interactive user session pi-web-ui runs in. When that session becomes Disconnected or switches to the lock-screen desktop, a working LAN/P2P/Hub channel cannot keep a plain user capture side running. With the service described below installed, capture follows the currently available user/console session and can reach the Windows lock-screen sign-in desktop; signing in is still handled by Windows. The service's capture process exits on sign-in or session switch, and Node rebuilds capture with 250 ms to 2 s backoff inside a 30-second recovery window, keeping the current browser connection and dropping input during the switch; it resumes after the first new frame. Only past the recovery window does it report a retryable error to the page, and the foreground retries every 10 seconds. A manual disconnect or window close cancels capture rebuild; foreground retries pause while the page is in the background. Preview capture errors do not wrongly trigger a LAN/P2P fallback.

### Windows lock-screen desktop service

A global npm install of the package on Windows x64 installs or updates the built-in desktop service automatically, needing only confirmation of the Windows administrator prompt. When npm lifecycle scripts are disabled, starting pi-web-ui in a terminal or running the existing `server install/start/restart` installs it automatically, so no separate desktop install command is required. Background starts, CI, Linux and macOS never raise a Windows authorization prompt.

The installer decides whether an update is needed from a fingerprint of the native sources and the encoder manifest; after a cancel or failure with the same fingerprint it does not keep prompting. A manual uninstall turns automatic installation off, and `PI_DESKTOP_SERVICE_AUTO=0` disables it too. Use the following maintenance commands only for an explicit retry or check (install requests administrator authorization itself):

```powershell
pi-web-ui desktop service install
pi-web-ui desktop service status
```

The installer uses Windows' .NET Framework compiler to build a fixed capture program, places it in `Program Files\pi-web-ui-desktop` (writable by administrator/SYSTEM, read-only for the bound account) and registers the auto-starting `PiWebDesktop` service. The original account SID is recorded before elevation, so authorizing with other administrator credentials does not mis-bind to the administrator. A failed build does not replace the existing program, and a failed start attempts to restore the previous version. Uninstall with `pi-web-ui desktop service uninstall`, which removes the service enablement marker and restores plain-user capture selection while keeping the protected install files. Automatic installation does not change the remote desktop enable preference or existing access authorization.

The Windows video path chooses NVENC (NVIDIA), AMF (AMD) or QSV (Intel, integrated GPUs included) by the monitor's actual DXGI adapter, trying GPU texture encoding first, then hardware encoding of in-memory frames, and libx264 last. Media Foundation serves only as the system compatibility backend in forced-hardware mode. Success means the backend actually starts and produces video; failures move on to the next candidate, and diagnostics show the backend and the failure reason.

The default FFmpeg and the desktop hardware-compatibility encoder ship with the npm package. The compatibility build keeps the NVENC 12.1 ABI and includes AMF, QSV/oneVPL and Media Foundation; its hardware paths are tried first, and the default build plus software fallback remain after a failure. NVIDIA still checks which APIs the driver actually supports first. Both programs are SHA-256 verified and copied into the protected directory, and the service accepts only fixed enumerated choices, never external executable paths. The protected file keeps the name `ffmpeg-nvenc-compat.exe` for compatibility with old installations. Build provenance and licenses ship with the package; the compatibility build entry point is `scripts/build-ffmpeg-compat.mjs`, the release side prepares both binaries with `scripts/fetch-ffmpeg.mjs`, and end users install neither FFmpeg nor RustDesk separately.

`scripts/patch-ffmpeg-desktop.mjs` holds the pinned FFmpeg source patch (`desktop-timing-v2`): a high-precision waitable timer on Windows, non-blocking DXGI frame acquisition, bounded sleep when nothing updates, sampling-clock reset when behind, and texture and color-conversion compatibility for the D3D11 video processor. When high-precision timing is unavailable the original sleep fallback stays, with no global system clock adjustment and no busy loop. GPU BGRA→NV12 uses BT.709 limited, and the native encoding command writes the matching color matrix/range into the H.264 VUI; raw BGRA, CPU conversion and the default encoder do not carry this tag. Changing these patches requires rebuilding the binaries, updating the archives and binary digests, and shipping the matching sources and third-party licenses.

The output/send FPS in the info panel counts video frames, including frames `ddagrab` duplicates to a fixed output rate; it is neither the monitor refresh rate nor the independent picture update rate. A 60 Hz monitor cannot be used to verify real 120/240 Hz with this count. Server stats carry a monotonic-clock `elapsedMs`, which the front end uses to compute output/send FPS so arrival jitter of relayed stats messages is not mistaken for dropped capture frames; the local draw rate is still computed on the browser clock. H.264 has no per-frame ACK like JPEG, so the acknowledgement wait shows `—` and the default 0 must not be taken as evidence of zero latency. For diagnostics, the compatibility FFmpeg's debug log lines `Desktop update` and `Duplicated output frame` distinguish desktop updates from duplicate frames (disable log deduplication with `-loglevel repeat+debug`).

Without the system service installed, plain-user capture still probes every vendor's and the system's hardware encoders and works with NVIDIA drivers; the capability cache lasts one minute and is invalidated on failure. That path still provides no secure-desktop capability. 60/120/240 are capture target ceilings, actually limited by display output, driver, encoder capability, network and browser. Browser H.264 WebCodecs needs a secure context (HTTPS or localhost); a public HTTP Hub uses JPEG, and encoder test frame rates do not describe the display frame rate at that entry point.

The Web backend calls the service over a local named pipe owned by the same user; the pipe rejects network logon accounts, the service checks the client account, and the client checks that the pipe's server process matches the PID registered with the SCM. The service accepts no scripts, executable paths, arbitrary session numbers or external commands — only preview, read-only, control and the corresponding raw-pixel/compressed-video modes plus bounded desktop input. The controlling side's existing HTTP/WS authorization, device ownership checks and read-only restrictions still apply.

The service starts a separate SYSTEM capture process in the calling account's active session or on the current console and follows both the normal and the sign-in desktop through `OpenInputDesktop`/`SetThreadDesktop`; it refuses access to another signed-in account's desktop. The capture process transfers over a SYSTEM-only random pipe, and a Windows Job guarantees termination after disconnect and service exit. Input validation and read-only restrictions are enforced separately in Node, the service and the capture side. Window handles/images/input never pass through chat or the model; no listening port is added, no sign-in password is stored, and neither automatic sign-in nor automatic unlock is configured.

The service handles desktop capture and input only. The Web/device connector must still be running; the existing chat service is not converted to SYSTEM, and there is no promise that the device connector comes online automatically when rebooting without sign-in. Physical display output, system power state and sign-in policies requiring Ctrl+Alt+Del can still interfere, and neither a virtual display driver was added nor a sign-in policy changed.

The remote device tab shows 「备注 · 计算机名 · pi-web-ui」 (remark · computer name · pi-web-ui), shows only the computer name when there is no remark, and falls back to the device ID only when an old Hub provides no name. The Hub and local LAN/P2P entries share the naming rules; the icon loads the app's existing favicon over the current authorized channel and opens no extra device resources. Reopen the remote tab after updating for this to take effect.

The remote chat page can also click the desktop's “独立标签页” (Standalone tab). The remote iframe only sends messages carrying a request ID; the trusted outer layer validates the message source, then requests a fresh one-shot ticket for the same device and opens the window. The new window and the original preview each have their own entry point, the iframe's popup/same-origin permissions are not granted, and a URL dictated by the remote page is never accepted. The controlling side, the controlled side and the Hub must all be updated, and old tabs reopened.

Selecting another computer inside a remote page requests a standalone desktop entry through `__desktop_target?device=<id>` under the current capability root. The Hub validates ownership of both the source and the target device and mints a capability for the target device itself; the LAN entry has the local connector request a target ticket from the bound Hub. A normal remote page cannot call the local `devices/:id/open` management API. Nested previews, live desktops and standalone tabs use explicit target IDs, and clipboard messages travel along the corresponding desktop window without reading or writing the intermediate computer's clipboard. Nested cross-device desktops currently go through the Hub relay.

A wrapper holding only a desktop ticket allows opaque ancestors (no `frame-ancestors` is set, because `http: https:` cannot match an opaque origin either); normal device entries still restrict to same-origin ancestors. All remote content stays inside a sandbox without `allow-same-origin`, `frame-src` is limited to that device's capability path, and messages validate the source window and the origin. `tests/device-nested-desktop-test.mjs` uses a real Hub, two connectors and Chrome to verify switching targets, clipboard ownership, preview recovery and standalone tabs; the picture and clipboard use a test backend.

### Windows: keep using the current desktop after closing RDP

Windows boxes with a local console can try handing the active RDP session back to the console. Run `pi-web-ui desktop console --check` on that Windows machine; it only checks the session, permissions and whether other console users exist, without changing sign-in state.

Once you have confirmed the physical screen may stay signed in, run this in an **administrator terminal of the same Windows account**:

```powershell
pi-web-ui desktop console --confirm
```

This invokes the system `tscon`, immediately disconnecting the current RDP session and handing it back to the local console. The small preview retries capture automatically. The command accepts only the active RDP session owned by the current process's user; it refuses to run when another console user is signed in, accepts no explicit session ID, stores no password and configures no automatic sign-in. Sessions that are unconfirmed, not elevated, locked or already disconnected are never switched automatically. A failed switch reports an error, and a successful command is not picture acceptance; keep checking the live picture.

This is a way to keep a signed-in console; it provides no unattended control of the lock screen, the UAC secure desktop, after sign-out, or when rebooting without signing in; cloud hosts without display output may also need a virtual display device. Signing in over RDP again later changes the session state again.

Off by default, enabled by a click on the desktop page; the preference is saved atomically to `<dataDir>/desktop-settings.json`. `PI_DEVICE_DESKTOP=1` forces it on and the page cannot override the env var. Runtime support does not mean system authorization has been granted; a failed capture start shows its reason on the page.

Old `PI_DEVICE_VNC_*` configuration is no longer read. macOS permission requests start on the controlled Mac itself under 「设备中心 → 本机远程桌面」 (Device Center → Local remote desktop): click “授予屏幕录制权限” (Grant screen recording permission) or “授予远程控制权限” (Grant remote control permission), then confirm in the macOS prompt or Settings. View-only needs screen recording; control also needs accessibility. Remote connections only check permissions and never request authorization or open System Settings. A local request tries to open the corresponding settings page when permission is missing; the system may not re-prompt, and the authorization target is whatever host macOS identifies. Do not guess a program in the “＋” file picker. When the system asks for a restart, restart the actual service before reconnecting. Windows is verified on real hardware today; macOS/Linux still need on-device verification.

macOS capture and authorization share `~/Library/Application Support/pi-web-ui/native-desktop/PiWebDesktop`. First use compiles it asynchronously with Apple's `swiftc`, and an unchanged source reuses the same binary across connections, restarts and Node upgrades, avoiding on-the-fly Swift interpretation every time. An upgrade that changes the component may still require re-authorization; the fixed path neither bypasses macOS TCC nor guarantees that permissions survive a signature change. Preview and operation windows report permission errors consistently and reconnect on a timer once permissions or the service recover; real TCC authorization and Swift compilation still need verification on a Mac.

## Host integration and permissions

`server/device-center/desktop.ts` exports `createDeviceDesktop({app,dataDir,authorize})`. Call `desktop.close()` when the service shuts down.

## Transfer and cleanup

Output is binary JPEG of at most 4 MiB, with text frames reporting ready/error/stats. The browser replies `{type:"ack"}` after painting; each connection has exactly one frame awaiting acknowledgement, keeps only the newest candidate frame while waiting, and sends it immediately once the ACK arrives and the previous send has finished, so old frames never queue up. 15 seconds without acknowledgement reports an error and stops capture, and the user can reconnect. The transfer queue is capped at 4 MiB plus up to 4 MiB for the newest candidate frame. Input is JSON of at most 16 KiB, validated for normalized pointer, wheel, physical key code, text and release.

“连接信息” (Connection info) on the live page shows cumulative captured/sent/replaced frame counts, acknowledgement wait, send queue, plus the browser-measured display FPS and decode paint time. The acknowledgement wait includes network, decode and browser scheduling, so it is not pure network RTT; this round keeps the original live capture rate and does not upgrade to 30 FPS video encoding.

At most four desktop connections per device; startup times out at 60 seconds, ping/pong at 30 seconds, and a connection is released after 30 minutes without user input. Disconnect, close, disable or error cleanup tears down capture and releases held mouse/keyboard state. The native process's input queue, frame sizes and error logs are bounded, and cancellation requests exit before terminating the specific child process. The capture side itself listens on no extra TCP port; the device connector provides a shared encrypted LAN port on demand, used by both the desktop and the full device web page. The local service entry holds TLS-PSK in the service; the pure-browser Hub entry holds short-lived device-scoped WebRTC gateway keys, while PSK and device credentials stay server-side. No recordings are stored; received clipboard files are staged within the limits above.

## Verification

### Native GPU encoding path preview

The new Windows x64 path implements the D3D11 / FFmpeg hardware-encoding integration in this project, following a GPU-first architecture and containing no RustDesk `hwcodec` source; see
[`native/desktop-codec/README.md`](../native/desktop-codec/README.md) for details and pinned dependency versions. It sends complete H.264 frames on real desktop updates
and a separate heartbeat when the screen is static; the browser reports frame numbers after painting, and the capture side pauses fetching the next frame according to the unacknowledged window, avoiding continuous backlog.
Automatic mode uses the growth relative to the lowest acknowledgement time plus the decode queue to lower bitrate first and frame rate after; manual quality still honours the user's choice.
Frame rate and bitrate update dynamically through the native interface; AMF in this FFmpeg build needs the encoder rebuilt on parameter changes and keeps the browser connection.
Resolution, monitor or Windows desktop switches likewise rebuild the encoder.
When DXGI has no first frame or cannot establish duplication, a normal signed-in desktop tries WGC GPU capture first, handing textures straight to the native hardware encoder;
the installer compiles this integration on supported Windows using the system's own WinRT metadata, installing no extra programs or drivers.
Some Windows versions cannot activate WGC inside a SYSTEM process (possibly returning `E_OUTOFMEMORY`). In that case the protected service starts
a read-only user capture process of the same executable, validating the signed-in user SID, the pipe peer PID and bounded video packets; input stays with SYSTEM.
Entering a secure desktop such as the lock screen shuts down user capture and restores system capture. The child process exits with the connection and is reclaimed by the Job.
Systems without WGC support, or secure desktops, can still fall back to reusing the GDI pixel buffer and uploading it to the GPU, continuing to use hardware encoding;
identical pixels are never re-sent. This path keeps GPU scaling, color conversion and encoding but cannot remove GDI capture's own cost.

The new binary protocol negotiates through the `video-flow-v1` capability fingerprint and a separate service mode, while old clients keep using the original channel. The `PIV1` browser frame header is sent only after explicit negotiation in the URL, and the device relay still passes the WebSocket through. The preview build's actual runtime identifier is `native-d3d11`. On-device acceptance for Intel, other drivers and 120/240 Hz monitors is not done yet; the low static FPS in browser stats is normal on-demand capture behaviour, and duplicated static frames cannot serve as high-refresh acceptance.

Before a formal package, run `npm run build:desktop-codec` on a Windows x64 build machine, then `npm run pack:p2p`; the CI Windows installer flow performs the same build and validation. Sources, patches, license notes and relinkable libraries ship with the native components, and a release fails with the build command when native components or relink materials are missing instead of silently producing a package without hardware encoding. Releasing the npm package from another OS requires copying the matching native components and compatibility encoder output from a Windows build machine first; maintainers should also check the license requirements of their own distribution channel. See [`native/desktop-codec/README.md`](../native/desktop-codec/README.md).

Related tests live in `tests/unit/device-center-desktop*.test.ts`, `device-desktop-native.test.ts`, `device-desktop-linux.test.ts`, `device-desktop-relay.test.ts` and `device-lan*.test.ts`. The LAN tests use real TLS PSK, HTTP/WS and a Chrome nested sandbox to verify direct chat and picture connections, authorization isolation, path prefixes and reconnection after disconnect. They cover permissions, enable persistence, native process cleanup, input bounds, read-only, frame acknowledgement and real Hub/connector relaying. Where Chrome is available they verify canvas decoding under a proxy prefix, mouse movement in control mode and input length; browser tests with simulated pictures are not on-device verification for each platform.

## Explicit file transfer

Click **Name**, **Modified** or **Size** to sort either pane. Click again to reverse the order. Enter a file path to open its parent folder and select the file. The browser's local pane can navigate within folders or files you have granted it access to.

“文件传输” (File transfer) in the remote desktop toolbar opens a two-pane file manager: the controlling machine's local disk on the left, the current controlled device on the right. Both sides support a path field, home/disk shortcuts, up, refresh, new folder and multi-select; double-click a folder to enter it, pick the destination folder and press “发送 →” (Send →) or “← 接收” (← Receive). The task list below shows name, direction, status, progress, send path and receive path per task, with pause, resume, cancel and clearing completed records. Collapsing does not cancel transfers; closing the desktop or switching devices cancels unfinished tasks.

File transfer is independent of the system clipboard. Chunks are 1 MiB, and a single task is capped at 16 GiB / 10000 entries; the native receiving side first writes into a temporary directory inside the chosen folder, checks the byte count and an incremental CRC32, then publishes the files, appending a number on name collisions and keeping the original files. Old clients without a destination folder still use `~/Downloads/pi-web-ui-Received/<date-taskID>`. CRC32 detects transfer corruption and performs no authentication; requests reuse desktop authorization. Duplicate native chunks are deduplicated by offset and SHA-256, transfers can resume within the same window, and a pause over 30 minutes may expire and require selecting again. A disk failure during publishing can leave some published files behind; a retry reuses published items and never overwrites other files.

Archives transfer byte-for-byte with no recompression; native two-way transfer preserves directory hierarchy and empty folders. Native paths are confined to local disks or the POSIX root and limited by the system permissions of the current service user, rejecting UNC paths, symlinks, device paths and path traversal. A single directory listing shows at most 2000 entries; exporting a directory walks the whole tree and checks the total count and size. Modifying a source file aborts that task, preventing different versions from being mixed into one file.

The file manager runs in the outermost controller document. A remote page can only request that the UI open, or respond to remote file requests initiated by the controller; it cannot initiate local disk operations. `/api/device-desktop/local/files` requires loopback, host authentication, same-origin validation and a custom request header, and is explicitly forbidden by the Hub/LAN forwarders. It does not require enabling the controller's desktop sharing. Nested device pages forward only messages that pass window-identity validation and never treat the intermediate device as “the local machine”.

Remote file operations are bound to the current authenticated desktop WebSocket and lose validity immediately on disconnect. Read-only connections can browse and download files, but the server refuses sending files and creating remote directories; writes resume only after switching back to a controllable mode.

A browser opening the Hub directly cannot access the local disk freely: secure contexts with directory authorization can grant read/write through “选择本机目录” (Choose a local directory); other browsers can send files/folders and receive through the browser's download manager, with folders as `.tar`. The `webkitdirectory` fallback omits empty folders; cancelling a browser directory write can leave partially completed files behind. The browser manages download progress, and the task list only shows what was handed to the browser without claiming verification succeeded. For full two-sided disk browsing, open the remote device from local `pi-web-ui`. The large-file allowance on download responses applies only to `/api/device-desktop/files/download/<taskID>`; other HTTP/WS limits are unchanged. The controlling side, the controlled side and the Hub all need updating.

The image fallback path resizes the canvas and paints within the same animation frame, avoiding the brief black frame from clearing the canvas and waiting for a repaint; cleanup behaviour for disconnects and secure states such as the lock screen is unchanged.

Clipboard file sync shows its state on the desktop page when preparing, transferring, completing or failing. A failure does not clear the user's existing clipboard; folders are explicitly redirected to file transfer. Besides system file events, a file listing check runs while sync is active to avoid missing copy events. Pasting before the large-file completion notice appears may still yield the original file.

The nested remote desktop's device selector fetches its list from the account that owns the current access authorization (`__desktop_devices`), not from the opened device's own pairing account; switching still validates access per device. Both the preview and the enlarged window can select devices, and switching keeps the current mode. A delayed auto-open response for the current desktop must not overwrite a new target the user has already chosen.
