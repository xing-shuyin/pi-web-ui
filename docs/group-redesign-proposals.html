当前群组系统性设计缺陷全景诊断

基于代码实测与深层调用链路审计，当前群组协同存在的 6 大核心瓶颈：

拓扑模型割裂 #FLAW-01

“多头派发 (Fork-and-Forget)” 导致协同孤岛

人类发消息同时 @ 多个 Bot 时，Hub 直接通过 targets.map 并发派生多个独立 Task。每个 Task 执行前被冻结在当前 24 KiB 快照中，并发执行的 Bot 互不可见对方思考与中间产物，缺乏流水线 (Pipeline) 与汇聚 (Join) 编排。

根本后果： 无法处理“Bot A 编写接口，Bot B 同时根据接口编写测试”的依赖协同，各自闭门造车导致产物严重冲突。
概念与存储双轨 #FLAW-02

群公开消息流 vs 点对点私有会话脱节

底层同时维护 RoomMessage（最多 500 条）和 HubConversation。Bot 间调用 send_task / reply 被封装在私有会话中，群聊天流不得不通过拼接伪假消息（group-task:${id}）强塞状态卡片。

根本后果： 群聊主视图被机械的“协同子代理排队中/执行中”卡片严重刷屏，人类对话与多 Bot 业务讨论上下文断层。
记忆断层 #FLAW-03

24 KiB 机械硬上限与“隐形黑板”

任务上下文 groupTaskContext 硬上限仅 24 KiB，稍有长日志即暴力截断旧历史；而服务端虽已设计了 GroupBlackboard（带版本号乐观锁），但前端群组抽屉与聊天主界面完全没有展示与编辑黑板的入口！

根本后果： 长期业务背景与技术约束几轮即丢失；Bot 共识只能盲人摸象，人类完全无法在 UI 上查看或纠偏黑板内容。
分布式一致性 #FLAW-04

资源锁全内存态，重启即失且对人隐形

单机调度器依靠物理路径重叠互斥，但跨设备完全依赖 Hub 的 HubLockManager。该管理器纯内存存储，Hub 重启后锁全丢；且前端聊天框无任何声明资源锁入口，多机 Bot 并发修改同一远程 Git 仓库时处于无保护状态。

根本后果： 极易引发并发 Git push 强制覆盖冲突与文件破坏，断网恢复后无分布式事务补偿机制。
人机交互闭环 #FLAW-05

缺失执行中动态转向 (In-flight Steering)

普通单会话支持实时输入 Steering 纠偏执行；而在群组中，queue: { steering: [], followUp: [] } 被硬编码置空。运行中的 Bot 若理解偏离，人类只能眼睁睁看其执行完或直接粗暴调用 /stop 终止，无法半途介入修正。

根本后果： 长任务容错率极低，单点失误导致整条协作链崩塌，人机协同缺乏灵活性。
硬编码锁死 #FLAW-06

核心配置未解耦，常量写死绕过设置

代码中散落大量如 const HISTORY = 500、GROUP_CONTEXT_BYTES = 24 * 1024、allowBotMentions: false 等写死常量。甚至在 execution-settings.json 调高参数后，Hub 代码多处仍然读取固定常量，配置无法生效。

根本后果： 即使硬件算力与网络条件允许，群组性能与规模仍被底层写死的“小水管”死死锁死。

三大架构级重构方案深度对比

从工程可行性、系统健壮性与前瞻性出发，提供三套阶梯式演进架构方案：

方案 A：渐进增强型 —— “黑板共识中枢 + 全参数动态外置”

保留现有 Hub-Device 主从拓扑与日志模型，聚焦解决关键断层：黑板 UI 原生化、解耦写死常量、放开群内 @ 交互与决策回填。

改造风险
低 (Low)
研发周期
1.5 周

📌 1. 全局与群级配置中枢 (Execution Settings 2.0)

将所有写死常量重构为三级继承模型。支持群级 RoomSettings，在前端群设置中即可随意拖拽调整群历史与上下文大小。

📋 2. 原生黑板常驻面板 (First-Class Blackboard)

在群聊主界面右上侧增加“群组黑板”交互抽屉，支持实时 Markdown 编辑与版本历史展示。任务上下文优先打包全量黑板，彻底根除长期记忆丢失。

💬 3. 受控自发协同 (Safe Bot Mentions)

开启 allowBotMentions: true，并在 Hub 层引入每轮最多派发 3 次的限流熔断计数，Bot 在群里 @ 同伴即可自动触发派发。

🔔 4. 决策自动公报 (Attention Auto-Broadcast)

人类回答 Bot 问卷或审批后，系统自动在公开群消息流广播格式化公报，同时增量回写黑板，消除多 Bot 间的认知信息孤岛。

方案 B：协同总线型 (推荐) —— “全流归一 + 声明式工作流 + 实时转向”

彻底解决消息与会话双轨制；引入拓扑编排（Pipeline / Fan-in / Fan-out）与分布式 Steering 协议，构建工业级多智能体协同流水线。

架构完备度
优秀 (9.5/10)
推荐指数
★★★★★

🌿 1. 统一树状会话模型 (Unified Tree Stream)

废除双轨制，所有消息均为同一树状流中的节点。Bot 间委派成为主消息下的子分支 (Thread)，前端支持折叠与直观下钻，彻底解决卡片刷屏。

🎯 2. 声明式协同工作流 (Pipeline / Fan-in / Fan-out)

人类可在群内直接下发工作流指令（如 @BotA 调研 并转交给 @BotB 实现，最后由 @BotC 汇总），编排器自动按拓扑图推进状态，上一节点的产物自动成为下一节点的精确输入。

🕹️ 3. 飞行中实时转向 (In-flight Steering Protocol)

打通跨设备 Steering 协议。当 Bot 执行长任务时，人类在群内直接打字纠偏，Hub 实时投递到目标设备 Agent 的执行队列中动态影响后续工具选择，无需硬中断。

🔒 4. 分布式锁持久化与意图锁 (Persistent Resource Locks)

HubLockManager 改由追加日志 (WAL) 持久化，支持 Shared Read / Exclusive Write 分级意图锁，群聊输入框支持自动根据 @Bot 涉及的项目根路径推导资源锁。

方案 C：自治智能体网格型 —— “数字研发室 + 分布式知识库 + 沙盒回滚”

前瞻性架构，将群组升级为全自主运行的虚拟团队。引入向量化语义分层记忆、细粒度 Capability 权限衰减与 Git 工作树快照回滚。

前瞻性
极高 (Cutting-edge)
研发周期
4 - 6 周

🧠 1. 分层记忆矩阵 (Hierarchical Memory Matrix)

突破所有纯文本上下文上限：L1 黑板共识 (全局状态) + L2 嵌入式向量知识库 (20,000+ 群历史语义检索按需回填) + L3 任务快照证据链。

🛡️ 2. Git 物理工作树隔离与崩溃快照回滚 (Worktree Sandbox)

每个多机任务派发自动拉取独立 Git 临时分支。发生断网脑裂、崩溃或人类拒绝交付时，自动一键回滚物理目录，零污染主分支代码。

👥 3. 多账号跨设备联邦 (Multi-Tenant Group Collaboration)

重构单一 accountId 架构，支持不同团队成员携带自己的电脑和 Bot 加入同一个分布式项目群组，建立基于公私钥签名的群成员身份链。

📺 4. 多机流式全景看板 (Live Streaming Multiplexing)

前端原生支持多通道实时 Token 流分发，多个 Bot 并发运行时，可像作战指挥室一样分屏实时查看每一个 Agent 的思考与终端执行全貌。
