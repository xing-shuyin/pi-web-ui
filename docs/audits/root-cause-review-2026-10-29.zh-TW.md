# 補丁式實現與根因邊界審查

審查物件：當前工作區程式碼（包含其他對話正在進行的未提交修改）。初次審查只讀原始碼；使用者隨後授權實施，整改與驗證狀態記錄在下節。並行檢查了會話生命週期、目標模式、審批遷移、外掛、任務排程、畫布、配置持久化、多引擎與工作區邊界；避開其他對話正在修復的 MessageList / 流式 Markdown。

## 整改與驗證狀態

使用者授權後，以下 13 項對應修復均已實施，架構約束見 `../root-cause-boundaries.md`。後續複核還修復了外掛 storage 的嚴格讀取、失敗候選快取、非同步排隊鎖釋放，以及舊引擎歷史刪除後再次匯入的問題。

- 統一定向迴歸：29 個非畫布檔案，474 項測試全部通過；覆蓋工作樹、取消/重建/審批、目標代次、外掛配置/secret/storage/cron、MCP/原子寫、多引擎隔離、DNS 繫結與預設網路路徑。
- 本輪定向 Prettier 檢查通過。MCP 未使用 import 的 lint 警告已修復。
- 全專案 `npm run typecheck` 經並行預設對話確認最新一輪五個 tsconfig 全部通過；本對話另行驗證 Web、tests、desktop 和擴充套件四個配置通過。
- 畫布第 3 項完成時，6 個檔案的 58 項迴歸通過。之後使用者在另一對話授權了更廣泛畫布整改，新的執行/隔離語義使本輪 `canvas-deletion-lifecycle.test.ts` 其中 4 項超時，已交給該對話維護，要求保留真實遲到完成覆蓋，不能刪除或跳過。該對話接管畫布後續測試及最終全域性 typecheck/lint；此處不將持續變更的畫布認定為最終驗收完成。
- 當前全域性 lint 的剩餘警告來自並行開發中的 CanvasStudio 未使用匯入/變數，已交接畫布負責人。

未執行 Git 提交、釋出或重啟服務。工作區有其他對話的大量未提交改動，均予保留。MCP 跨檔案遷移恢復由重複同一儲存請求觸發；DSH 初始化失敗測試使用模擬執行時，未啟動真實 DSH 子程序；正文中原始發現保留為審查證據，不代表對應舊實現仍然存在。

這是一次按架構邊界開展的廣泛審查，不等於逐行窮盡。下列發現以實際呼叫鏈為依據；除明確標出的定向復現外，屬於靜態核實，尚需在整改時加入故障注入和競態迴歸。P1 表示優先處理的資料安全、錯誤執行或核心功能失效；P2 表示特定條件下掛起或殘留。

## 1. P1：工作樹狀態讀取失敗被當作無改動，參與強制刪除

位置：`server/worktree-service.ts:130`、`:491`、`:515`。

`getUncommittedCount()` 在 Git status 超時或報錯時返回 `{isDirty:false,count:0}`。`finalizeSubagentWorktree()` 把這個值用於判斷是否自動清理；HEAD 與 base 相同且存在未提交工作時，只要 status 查詢失敗，就可能進入 `removeWorktree(..., true)`，隨後刪除分支。HEAD 查詢異常同樣降級成 ahead=0。

根因：展示用的“最好努力”讀取結果，被複用於破壞性操作的授權依據，未知狀態被壓成安全狀態。

根治：狀態採用 clean / dirty / unknown 三態；僅所有檢查明確成功且無改動時允許自動刪除。失敗應保留工作樹並報告原因，不能將增加超時或重試當作安全邊界。

## 2. P1：外掛 cron 到期後重新查詢未來時間，跳過本次執行

位置：`server/plugins.ts:4997`、`server/plugin-schedule.ts:141`。

`armCron()` 捕獲 next 設定計時器，回撥卻重新呼叫 `nextCronFire(parts, Date.now())`。該函式從下一分鐘開始搜尋，因此正常到期時得到的是下一次，而非本次，`at <= now + 1000` 不成立。分片計時解決了長延遲溢位，卻丟失了本次 dueAt 身份。

定向復現：直接呼叫當前原始碼的 `parseCronSpec` / `nextCronFire`，每分鐘任務計劃 10:01，回撥在 10:01 重新得到 10:02，`willFire=false`。這是到期判斷表示式的確定性復現，未啟動真實外掛或計時器。

根治：儲存本次 dueAt，分片醒來比較 now 與這個 dueAt；到期執行後才計算下一次，補跑與時鐘跳變納入同一狀態轉換。

## 3. P1：刪除執行中的畫布不終止執行，非同步收尾會復活工程

位置：`server/canvas/canvas-dispatch.ts:79`、`canvas-agent-tool.ts:384`、`canvas-store.ts:239`、`canvas-orchestrator.ts:537`。

兩個刪除入口僅刪除圖檔案。節點完成仍呼叫執行態儲存，而儲存函式發現檔案不存在會寫回完整舊圖；之後仍處理下游邊。結果是工程重新出現，刪除後仍可能呼叫模型或啟動下游操作。

根因：刪除持久檔案沒有使執行身份失效；執行態更新兼任建立。

根治：刪除先撤銷圖執行代次並取消執行，再刪除檔案；所有完成回撥、寫盤和下游派發校驗代次。執行態儲存只允許更新現存工程。單獨加 stopAll 不能擋住跨 await 返回的舊回撥。

## 4. P1：外掛設定落盤失敗仍釋出執行態並回報成功

位置：`server/plugins.ts:1757`、`:1783`、`:1985`、`server/dispatch-plugin-handlers.ts:74`。

普通設定寫入失敗只記日誌，仍返回 clean。呼叫方觸發 settingsHandlers 並走成功回執，導致記憶體新配置與磁碟舊配置分裂。secret 還在逐欄位校驗過程中寫入，後續欄位校驗失敗可能留下部分提交。

根治：完整校驗、暫存、持久提交、釋出執行態形成明確邊界；失敗向上返回。secret 與普通配置需要共同提交或可恢復事務，禁止校驗迴圈中產生持久副作用。

## 5. P1：MCP 改名或遷移作用域先刪後寫，失敗丟配置

位置：`server/mcp-manager.ts:85`、`:189`、`:223`。

改名或遷移先刪除舊記錄並寫回，再寫新記錄。第二步失敗或程序退出後，舊配置已經丟失。同文件改名也拆成兩次寫入；直接覆蓋正式檔案及讀取錯誤降級空配置進一步擴大風險。

根治：同文件改名一次記憶體變換後原子提交；跨檔案遷移先持久保證目標存在，再移除源，配可恢復遷移狀態。讀取明確區分不存在、損壞和不可讀，後兩者禁止覆蓋寫回。

## 6. P1：DSH 切專案僅改宿主 cwd，重啟引擎仍在舊目錄

位置：`server/dsh/dsh-agent-service.ts:5807`、`server/dsh/dsh-client.ts:150`、`:314`、`:792`。

切 A 到 B 更新服務 cwd 後對原 runtime 呼叫 restart。restart 只更新模型/provider，初始化仍使用構造時儲存的 A cwd。UI 和檔案樹顯示 B，模型相對路徑操作卻仍可能落在 A。

根治：工作區變更使用目標 cwd 建立並初始化新 runtime，成功後提交切換；不能用只重啟程序代替執行時身份遷移。

## 7. P1：Universal 舊回合找不到歸屬後回退 active，串寫新專案

位置：`server/universal/universal-session.ts:948`、`:1013`、`:1786`。

回合結束通過 turnConvId 找歸屬，失敗則回退 activeConv。切專案直接清空 conversations 且不等待舊回合終止。舊回合完成後找不到原會話，於是將回復、工具結果和統計追加到新專案當前會話，並按當前 cwd 儲存。

根因：補了 ID 錨定，但仍讓可變全域性 active/cwd 充當非同步歸屬的兜底。

根治：每回合捕獲穩定會話物件、cwd、driver 與執行代次，貫穿所有回撥和儲存；歸屬失效禁止回退 active。切專案應取消並等待完成，或讓舊執行時獨立收尾。

## 8. P1：Claude 與 Durable 共用歷史目錄，底層會話 ID 跨引擎恢復

位置：`server/index.ts:1814`、`:1828`、`server/universal/session-store.ts:19`、`universal-session.ts:820`、`drivers/claude-code.ts:280`。

兩個服務使用同一 dataDir，歷史倉庫僅按 cwd 與 conversation ID 區分。切換引擎後可直接載入另一引擎的記錄，將 driverSessionId 傳給當前驅動恢復。Durable ID 可作為 Claude resume 引數；反向恢復可能走目標查詢失敗/root 回退，兩者還可能覆蓋同一歷史檔案。

根治：儲存鍵加入 engine，記錄並校驗 driverKind；跨引擎匯入只能轉換訊息並新建底層會話，不復用 driverSessionId；已有資料需遷移或隔離。

## 9. P1：子代理建立沒有貫穿父工具取消，停止後仍可啟動

位置：`server/subagents.ts:553`、`server/agent-service.ts:1296`、`:1461`。

spawn 工具收到 signal 但未傳入建立鏈。等待 runtime、擴充套件繫結或模型恢復時父對話停止/關閉，建立恢復後仍可註冊並投遞 prompt。關閉時尚未登記的後代不能被後代列舉清理。

根治：取消訊號與穩定父 runtime 身份貫穿建立；註冊和首次投遞前校驗有效性，失敗統一回收未提交資源。

## 10. P1：同一對話可併發強制重建，後完成結果覆蓋前者

位置：`server/agent-service.ts:10822`、`:10879`、`:10930`、`:10941`。

重複停止產生獨立超時器及區域性 forced 標記，兩條強制重建鏈可以同時建立 runtime。提交僅檢查對話仍存在，依次覆蓋 conv.runtime/session，可能遺留被覆蓋 runtime，或替換已經接受新訊息的例項。

根治：每對話單一 interrupt/reset promise；提交繫結原 runtime 代次，失去提交資格的候選例項必須銷燬。

## 11. P2：審批過戶重編號後，原 AbortSignal 回撥失效

位置：`server/agent-service.ts:6302`、`:11682`、`:11817`。

取消回撥捕獲舊審批 id。過戶重新分配 id 並遷移條目後，取消仍刪除舊 id，失敗直接返回，不結算 Promise，不清理目標審批；舊 id 碰撞其他條目時還有誤刪風險。

根治：用穩定請求物件作為結算身份，展示 id 和持有方可遷移；取消、答覆、銷燬共用一次性 settle，刪除當前持有方的當前條目。

## 12. P1：目標設定等待清理後借用新代次，舊請求無法可靠作廢

位置：`server/goal-service.ts:691`、`:696`、`:749`、`:1383`；併發入口 `server/dispatch-domain-handlers.ts:502`。

設定目標 A 遞增代次後等待 stopDelegated；期間清除目標或設定 B 再次遞增代次。A 恢復不校驗原代次，繼續寫狀態，啟動時重新讀取最新 generation，使舊請求借用新代次通過守衛。

根治：入口捕獲操作代次，等待後及每次寫狀態、搶佔或派發前核驗；設定、清除、關閉共用目標轉換邊界，只允許最新有效操作提交。

## 13. P1：DNS 校驗未繫結實際連線，不能保證防住 DNS rebinding

位置：`server/net-guard.ts:216`、`:262`、`:285`；重複路徑 `server/preset-share.ts:686`、`:707`；市場呼叫 `server/market-service.ts:189`。

resolveAndValidateUrl 返回已驗證 IP，但實際 fetch 仍以原域名發起連線，未使用這些 IP。受控域名在預檢查時返回公網 IP，實際連線解析時返回內網 IP，仍可能訪問內網。逐跳 URL/DNS 校驗並沒有關閉檢查與使用之間的視窗。此項基於傳輸呼叫鏈核實，未執行 DNS 攻擊復現。

根治：統一受控 HTTP 傳輸，為每次連線使用已校驗且固定的地址，保留原 Host/TLS servername；重定向逐跳重新驗證並繫結連線，preset 與市場複用同一設施。

## 整改順序與驗收

1. 首先處理誤刪工作樹、錯誤工作區執行與跨專案串寫，以及停止/刪除後繼續執行。
2. 再修復排程到期語義、配置提交與引擎歷史隔離。
3. 收口審批身份、併發重建和 HTTP 連線邊界。

建議圍繞四個可驗證的不變數整改：非同步任務持有穩定歸屬；只有有效代次可提交或派發；持久成功後才釋出成功；未知狀態不得授權破壞性操作。共享機制只在確有共同生命週期時抽取，避免製造一個過大的通用框架。

對應迴歸應覆蓋 Git 查詢失敗、定時器準點與分片、刪除後遲到完成、落盤失敗、遷移第二步失敗、生成中切專案、引擎切換恢復、spawn 過程中取消、重複停止、審批過戶取消、目標設定/清除交錯、DNS 檢查與連線解析不一致。不要只測正常路徑。

審查中還驗證了一個被排除的懷疑：在獨立臨時目錄建立含 65MB 檔案的沙盒，再原樣應用回源，結果 skippedFiles=1、deletedFiles=0，源大檔案仍存在。因此沒有把“匯入跳過大檔案導致直接誤刪”列為發現。臨時目錄已清理。
