# Localization: module dictionaries and language packs

## Sources of truth and module boundaries

UI strings are stored per business module in `web/src/i18n/messages/<module>/<locale>.json`. `core` inherits the Chinese/English dictionaries and existing keys from the former `web/src/i18n.tsx`; Canvas UI strings live in `canvas`, and server run states plus system logs live in `canvas-runtime`. Maintain new features in their module first; generic operations with the same meaning keep using the existing shared keys.

`web/src/i18n/catalog.ts` aggregates the built-in `zh` and `en` dictionaries and keeps exact translation key types. `web/src/i18n.tsx` maintains only the Provider, language selection, language pack loading, parameter substitution and fallback; components still read the current language through the same `useT()` / `useI18n()`, with no module-specific language state.

Both Canvas modules provide all 14 languages: `zh`, `en`, `de`, `es`, `fr`, `it`, `ja`, `ko`, `pt`, `ru`, `tr`, `zh-TW`, `zh-Hant`, `zh-HK`. The additional language module files are the translation sources for these modules; `locales/*.json` remains the flat download pack published externally, keeping the existing server install and download endpoints. Language module sources are not required to bundle every language into the first screen.

## Adding and changing strings

1. Add keys that are semantic and carry module ownership to the module's `zh.json` and `en.json`, e.g. `canvas.deleteConfirm`; legacy keys need no renaming just because files were split.
2. Dynamic values use named placeholders such as `{name}`, `{count}`, passed through `t(key, vars)` instead of assembling whole sentences. Every language must keep the same set of placeholders.
3. Fill in translations in the module's additional language source files. When maintaining a full language module, translation keys must match the module's Chinese, and copying English or Simplified Chinese must never pass for finished translation.
4. Run `npm run i18n:sync` to update the download pack, then run the relevant dictionary, language pack, dead key and Canvas unit tests. The Chinese/English dictionaries and the download pack keep the same merge order.

Translate the UI only: buttons, field labels, states and action hints use explicit keys for the roles and parameters they describe, while roles, states, ports and the like in metadata are resolved through fixed key mappings, never by concatenating translation keys at runtime. Template option names, Pstack names and categories may be localized as UI information.

Concrete content always uses the English source, including Pstack's official descriptions and spec bodies, execution prompts, default instructions, and the actual and example task bodies of templates. This content does not enter the language dictionaries and is not rewritten with the UI language. Names, instructions, AI replies, tool output and imported data saved by users are preserved verbatim.

## Plugin UI language

Plugins keep no language preference of their own; the UI should only ever have one language state. The host exposes `window.__piWebUiHost.locale.current()` / `locale.onChange(fn)` to plugins (`web/src/plugin-host.ts`, v19); a plugin's name and description live in the manifest as `name` / `nameEn` and `description` / `descriptionEn`, and the front end picks the wording for the current locale through `web/src/plugin-name.ts`. See [`architecture-plugins.md`](architecture-plugins.en.md#plugin-ui-language-a-single-host-language-sourceissue-920) for details.

## Server run messages

Server system states and logs carry `CanvasMessage` in the protocol: `{ key, vars? }`. Nodes carry state and error message metadata through `currentActionMessage` and `errorMessage`, logs carry it through `CanvasNodeLogEntry.message`, and `canvas_error` carries it through `messageI18n`.

The existing `currentAction`, `error`, log `text` and error `message` remain as compatibility text. Server-side persistence and front-end import share message shape validation, restricting keys to strings and parameters to strings or finite numbers. The browser translates known message keys into its own current language; unknown keys, corrupted historical metadata or old data fall back to the original text; the same run can be viewed by browsers in different languages at the same time. Interpolation processes the original template exactly once, so content such as `{count}` or `$&` inside user values stays literal. AI replies and user input get no system message metadata attached.

When merging states, new original text must replace the corresponding metadata at the same time; updated original text with message metadata omitted means clearing the old metadata — a system hint from the previous run must not keep showing. Message metadata participates in persistence merging like any other run field and must not be overwritten by a stale topology save.

## Tooling and verification

`scripts/lib/i18n-catalog.mjs` is the single entry point for Node tools reading dictionaries, handling module discovery, merge order, duplicate keys and per-language key / placeholder validation. Translation tooling no longer infers the current dictionaries from React file locations or regex extraction.

- `npm run i18n:sync`: reads the module dictionaries, then fills in, cleans up and reorders `locales/*.json`; extra language translations a module already has override the same key in the download pack. Other strings in the legacy language packs are kept.
- `npm run i18n:diff -- --base <ref>`: compares translation changes against a Git baseline, supporting the old layout where the baseline is still a single `i18n.tsx`.
- `npm run i18n:check`: checks how far the download pack and the current dictionaries have drifted out of sync.
- `node scripts/zh-tw-locale/build-all.mjs`: updates the Traditional Chinese language pack through the unified sync entry point; Traditional translations explicitly provided by a module take priority.

The corresponding guard tests cover module dictionary consistency, download pack keys and placeholders, synchronizer regression, dead keys, the Canvas front-end contract and backend message lifecycle. A new module must also be registered in the browser dictionary entry point, so the modules the tools read match the actual runtime.
