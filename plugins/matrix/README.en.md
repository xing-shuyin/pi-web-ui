# Matrix (Decentralized) Bot and Workbench (Matrix Plugin)

> Matrix bot plugin (experimental feature), built on Matrix Client-Server API (v3) outbound Sync long polling, supporting two-way session conversation (zero public IP / no reverse proxy), structure-aware Markdown smart chunking, allowlist access control and room message push. Zero external third-party package dependencies (Node built-in fetch + node:crypto).

## Features

- 🤖 **Decentralized Matrix outbound Sync duplex long polling**: built on the official Matrix Client-Server spec, the client initiates the outbound long poll itself — **zero public IP, no domain filing, no reverse proxy, no inbound port opened** — and can connect to a self-hosted Synapse or a public Matrix server (such as matrix.org)!
- 📦 **Structure-aware Markdown chunking**: against message length limits, uses a smart chunking algorithm similar to `dsh-im`, guaranteeing that code blocks (\`\`\`) are closed automatically and syntax highlighting is not broken.
- ⚡ **Slash shortcuts**: supports `/help`, `/new`, `/clear` (alias `/reset`; all three reset commands accept an appended prompt and dispatch it verbatim after the reset), `/status`, `/stop` (alias `/abort`), `/model [provider/id|default]`, `/thinking [off|minimal|low|medium|high|xhigh|default]`, `/cwd [绝对目录]` (alias `/workspace`). Commands accept full-width slashes and mixed case; an unknown command shows help and is not delivered to the model. Models are validated against the host's available catalog; the directory must exist and pass the host's file permission check. During a run you must first stop and wait for it to finish before creating a new session or changing directory.
- 🛡️ **Allowlist access control**: set a Matrix User ID allowlist for who may converse (of the form `@user:matrix.org`); unauthorized parties get a friendly rejection, so strangers cannot abuse the bot.
- 💬 **Multi-room and group support**: receive and reply to messages in Matrix rooms, isolating context and command settings per room, thread and sender, with replies staying in the original thread. Runs are claimed by a stable runId, supporting messages that arrive before the acknowledgement as well as end events.
- 🛠️ **AI tool**: registers a `matrix` tool with the AI assistant, so the AI can push messages and notifications to Matrix rooms on its own.

## Configuration guide

1. Have a Matrix account (register at [matrix.org](https://matrix.org/), or use a privately deployed Synapse / Conduit server);
2. Sign in with Element Web or another client, then copy your **Access Token** and **Homeserver URL** from 「个人设置」→「帮助与关于」(Settings → Help & About);
3. Invite that bot account to your target Matrix room;
4. In pi-web-ui's Matrix panel, click 「⚙️ 配置凭证」(Configure credentials), fill in the Homeserver URL and Access Token, and check 「启用 Matrix 机器人双向对话服务」(Enable the Matrix bot two-way conversation service);
5. Click 「🔌 测试连接」(Test connection); once it passes, click 「💾 保存配置」(Save configuration) and the conversation can start.

## Media and limits

- Receiving images, audio (including voice), files and videos: the original bytes are downloaded from the authenticated Matrix media API into `.matrix-media/` in the selected workspace and then passed to `host.chat({text, attachments})`. PNG/JPEG/WebP/GIF images are passed as `{path:"", imageData:base64, mimeType, name}`; other media are referenced as `{path:absolutePath, mode:"reference", name}` with a note telling the model to use read or an available tool. Vision capability depends on the model; the channel does not transcribe voice or decode video automatically and must say so when it cannot parse them.
- Each Matrix message carries one media attachment, so images are at most one per message and no more than 10 MiB (below the host's 8-image/20 MiB total limit), and other attachments are at most 25 MiB; streaming reads are byte-capped the same way. Files stay in the workspace and must be cleaned up by hand. Extra directories must be authorized in the host beforehand; the channel does not bypass file permissions.
- The `matrix` tool's `action=send` supports `path` (a local path inside the workspace), `media_type=image|audio|file|video`, `mimetype`, `text` and `thread_id`: it really reads the file, uploads the raw bytes and sends the corresponding Matrix media event. Path escapes and download/upload/send failures all return errors; an inbound failure attempts a reply in the original thread, and a failed reply itself is logged plus a status error.
- **E2EE is unsupported**: no device keys, no Olm/Megolm decryption, no key backup and no encrypted upload. Messages and attachments in encrypted rooms are explicitly refused, and outbound checks room state first and refuses to send plaintext into an encrypted room. Use an unencrypted room the bot has joined; failing to read room state also refuses the send. Events that cannot be decrypted cannot be read for thread relations.
- The first sync without a persisted cursor only establishes the cursor and does not replay history. Command preferences are in-memory; the stable `sessionId` callback route and the scope epoch persist, so after a plugin reload the final answer of a web continuation can still be delivered to the original room and thread. Legacy hosts support only full `clientId + conversationId` memory routing and do not accept a bare `c1`. Events carrying a `runId` match only that exact run, and an unknown ID never borrows a session; a web continuation without a `runId` must have its record created by `run_start` and is delivered only once at the end, with the assistant message replacing earlier text by the last candidate and excluding tool-call preambles. When a web run has no cancellable run ID, `/stop` explicitly reports that it cannot stop safely and does not guess the session ID. Switching the Homeserver or clearing credentials drops the old routes; `/new`, `/clear` (`/reset`), `/cwd` (`/workspace`) and model or thinking-level switches rotate the peer epoch and accountId so the host creates a brand-new context while keeping the original history; a query with no arguments keeps the context. Changing settings during a run requires stopping and waiting for it to finish. `/stop` cancels the current attachment download immediately, and after a cancel or switch no outdated attachment message is dispatched; a stopped task keeps its session route for later web continuations.
