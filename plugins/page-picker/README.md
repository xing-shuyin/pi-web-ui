# page-picker · 网页元素拾取（浏览器扩展）

在**开发中的网页**上点选元素，把它整理成 AI 能直接动手的上下文，一键注入 pi-web-ui 的对话输入框。

另有**页面桥**（两个**配对过**的页面互相读写）与 **AI 操作页面**（让对话里的模型读写你授权的页面）—— 见下文。

```
在开发网页上按 Alt+Shift+P（或点扩展图标）
   → hover 高亮、点击拾取（Shift+点击多选）
   → 底部浮条写备注
   → 「添加到对话」
   → pi-web-ui 输入框出现已排版好的上下文，你补一句「这三处间距不一致」再发送
```

采集的不是一张截图，而是**能让 AI 一次改对的东西**：

| 采什么                                             | 为什么关键                                                                                                       |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **React 组件源码位置**（`Card.tsx:18:5` + 调用链） | 从 fiber 的 `_debugSource` 挖出来。这是「AI 一次改对」与「AI 满仓库 grep」的分界线                               |
| **Vue SFC 文件**                                   | 从组件实例的 `__file` 拿（只有文件，没有行号 —— 不硬编假行号）                                                   |
| **命中的 CSS：文件 + 源文件行号**                  | Vite dev 的 `<style data-vite-dev-id>` 的 textContent 与源文件逐字对应，行号可精确反推                           |
| **计算样式子集**                                   | **只报与默认值/继承值不同的项**（现场造同 tag 空元素当探针比对）。一个真实卡片通常只剩 3~5 行，而不是 300 个属性 |
| 选择器 / XPath / DOM 路径                          | 首选短且唯一的（`#card` > `section#card` > 兜底全 `:nth-of-type`）                                               |
| HTML 骨架 + 折叠文本                               | 结构而不是整棵 `outerHTML`（超深子节点折成 `…`）                                                                 |
| 元素截图（可选）                                   | 走对话附件，不是塞 base64 进正文                                                                                 |

**发什么由你勾**：页面上下文 / 定位信息 / XPath 与 DOM 路径 / 源码位置 / 文本 /
命中的 CSS / 计算样式 / HTML 骨架，逐项开关 —— 没勾的**根本不采集**（不只是不渲染），
所以「这次只要源码」「这次只要样式」都是最省的那一种。嫌麻烦就用预设：
精简 / **标准（默认）** / 完整 / 只要能改对地方（选择器+源码）/ 只排查样式 / 只看文案结构。

**预设与逐项勾选在拾取浮条上就能改**（点完元素后那条里的一排 chip，`Alt+1~6` 是同一个入口），
不用再去扩展选项页 —— 「这次只要源码位置」这种判断本来就是站在页面上看着元素时才有的。
改完会**立即按新档位重新采集已选元素**，所以浮条上写的就是这次会发出去的；选择会写回扩展设置
（选项页同步、下次拾取沿用）。预设同时决定采集深浅（文本长度、骨架深度），逐项勾选不改深浅。

## 装

扩展**不在 Chrome 应用商店**（上架要走开发者账号 + 审核，且这个扩展的服务地址得你自己填，
商店版没什么额外好处）。三条路，按你是谁选：

### ① 直接下载装（推荐，不需要 Node）

**下载**：[`page-picker-extension.zip`](https://github.com/xing-shuyin/pi-web-ui/releases/latest/download/page-picker-extension.zip)
（永远指向最新版；想钉版本就去 [Releases](https://github.com/xing-shuyin/pi-web-ui/releases) 页
下带版本号的那个）

1. 解压 zip（得到含 `manifest.json` 的目录）
2. Chrome / Edge 打开 `chrome://extensions`（Edge 是 `edge://extensions`）
3. 右上角打开「**开发者模式**」
4. 点「**加载已解压的扩展程序**」，选第 1 步解压出来的目录
5. 定服务地址（二选一）：
   - **最省事**：先打开你的 pi-web-ui 页面，在**那个页面上**点扩展图标 —— 扩展会认出它是
     pi-web-ui，在页面底部弹出「这个页面是 pi-web-ui，要把它设为拾取服务地址吗？」；
     点「设为服务地址」就完事（地址/端口/子路径都按当前页面算，不用手打）
   - 手动：点扩展的「**扩展程序选项**」：填 pi-web-ui 地址（默认 `http://127.0.0.1:8787`）；
     远程/局域网地址要先点「**授权该地址**」，再点「**测试连接**」

> 装完在 `chrome://extensions` 里它会有个「开发者模式扩展」的提示，这是所有未上架扩展的
> 常态（Chrome 更新后偶尔会弹一次「停用开发者模式扩展」，点保留即可）。

### ② 从源码装（改代码的人）

```bash
npm run build:extension        # esbuild 打包到 plugins/page-picker/extension/dist/
```

然后按上面 ① 的第 3~4 步装，只是目录选仓库里的 `plugins/page-picker/extension/`。
改完源码重新 `npm run build:extension`，在 `chrome://extensions` 里点这个扩展的「刷新」图标即可。

### ③ 打包成 zip 分发（自己出包）

```bash
npm run pack:extension         # → release/page-picker-extension-<版本>.zip（含 CRC 自校验）
```

CI 在打 tag 时自动跑同一条命令并把 zip 挂到 GitHub Release（见 `.github/workflows/extension-release.yml`），
所以 ① 的链接永远是最新的。

### 权限观感

只预置了 `localhost` / `127.0.0.1` 的 host 权限 + `activeTab`（**点图标那一次**才临时授权
当前标签页），不做常驻全站注入。换成局域网 IP / 域名 / https 地址时，需要那一个 origin 的
授权 —— 在**那个地址的 pi-web-ui 页面上点一下图标**就会引导你完成（见「服务地址怎么定」）。

### 前置：pi-web-ui 版本要够新

扩展靠 pi-web-ui 页面上的宿主动作桥 `window.__piWebUiHost.compose()` 注入内容
（宿主 API **v2**）。旧版 pi-web-ui 没有这个方法时，扩展会明确提示「版本过旧」并改成
复制 Markdown 兜底，不会静默失败。（**绑定浮条不受版本限制**：没有桥时会退一步探同源的
`/api/health`，一样能认出页面。）

## 远程 / 局域网部署（pi-web-ui 不在本机）

**能用，而且不需要在服务器上装任何东西** —— 扩展是纯浏览器侧的东西，投递走的是
「浏览器里打开的那个 pi-web-ui 页面」，不是服务端 API。所以典型的远端场景是这样：

```
[你的浏览器]
  ├─ 标签页 A：https://pi.example.com/         ← pi-web-ui（远在服务器上）
  └─ 标签页 B：http://localhost:5173/settings  ← 你正在开发/调试的站点
        ↑ 在这里按 Alt+Shift+P 拾取 → 内容注入到标签页 A 的输入框
```

远程/局域网下唯一要做的事就是**把服务地址定对（并授权那一个 origin）** ——
见下一节，其中 ① 就是为这种场景做的。

## 服务地址怎么定（本地 / 局域网 / 远程不限）

地址和端口都不固定（本机可能是 `localhost:8787`，也可能是 `127.0.0.1:9000`；远程是
`http://203.0.113.10:8787` 或反代域名），所以扩展不猜地址 —— **两条路都行**：

### ① 在 pi-web-ui 页面上点一下图标（推荐）

扩展先探测当前页：

- **是 pi-web-ui**（看页面上有没有宿主动作桥，老版本则探一次同源的 `/api/health`）→ 底部弹出
  浮条问「要不要把它设为拾取服务地址」→ 点「**设为服务地址**」。地址、端口、子路径全部
  按当前页面算，不用手打；已经是这个地址时只告诉你「已绑定」，不再多问；
  浮条上还有「**在本页拾取元素**」（开发 pi-web-ui 自己时会用到）。
- **不是 pi-web-ui** → 照旧进入拾取模式（底部同时出现一条**常驻细条**：状态 +
  「**让 AI 操作本页…**」+「与另一页配对…」+「退出」，见下文「AI 操作页面」）。

如果那个远程地址**还没授权**，浮条会提示并给一个「打开设置页授权」按钮 —— 因为
`chrome.permissions.request` 必须在扩展自己的页面里发出（浏览器要求用户手势，网页上的
按钮不算），这不是多余一步，是权限模型的要求。

### ② 选项页手填（等价，出问题时按这个排查）

1. 扩展选项页把地址改成 `https://pi.example.com`（或局域网 `http://192.168.1.10:8787`、
   反代子路径 `https://host/pi`）
2. 点「授权该地址」（这一步是必须的：manifest 只预置了 `localhost` / `127.0.0.1`，
   其余地址要显式授权；没授权时连「找到那个标签页」都做不到）
3. 点「测试连接」——它会同时告诉你**服务端在不在**和**浏览器里有没有打开这个页面**

> 本机部署不管换成 `localhost` 还是别的端口都**不用授权**（预置的 `http://localhost/*`、
> `http://127.0.0.1/*` 端口是通配的），只是要保证选项页里的地址和你地址栏里那个一字不差
> —— 匹配是严格的（宁可报「没找到页面」，也不往前缀相似的调试站点乱注入）。

远程场景下的注意点：

| 情况                                           | 行为                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| pi-web-ui 页面**关着**（服务器在跑但没开页面） | 投递失败 → 复制 Markdown 兜底。**这是设计使然**：注入目标就是那个页面                   |
| 没授权该地址                                   | 明确提示「还没授权 `https://pi.example.com/*`，去选项页点授权」，并复制兜底             |
| 开着多个标签页（含你正在调试的站点）           | 按 URL 复核，只投给 pi-web-ui 那个页面；**绝不往调试站点/前缀相似的站注入**             |
| 子路径反代（`https://host/pi/`）               | 支持（授权按 origin，页面匹配按你填的路径前缀）                                         |
| 开了 `PI_WEB_TOKEN`                            | 与扩展无关：鉴权由页面自己带（cookie/URL），扩展只是往已登录的页面里写草稿              |
| HTTPS + 自签证书                               | 需要浏览器先信任该证书，否则页面打不开就无从注入                                        |
| 服务端与浏览器不在同一台机器                   | 完全没问题，扩展不直接访问服务端（只有选项页的「测试连接」会 fetch 一下 `/api/health`） |

## 交互

| 操作                                             | 效果                                                                                                                                     |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 点扩展图标 / `Alt+Shift+P`                       | **当前页是 pi-web-ui** → 问要不要把它绑成服务地址；否则进入拾取模式（底部同时出现一条常驻细条：“让 AI 操作本页…”就在上面，不用先点元素） |
| （底部细条）让 AI 操作本页 / 与另一页配对 / 退出 | 打开扩展设置页的授权面板（已预填本页）/ 打开配对面板（已预填本端）/ 关掉拾取                                                             |
| （绑定浮条）设为服务地址 / 在本页拾取 / 关闭     | 写入设置 / 像普通页面一样拾取 / 关掉浮条（`Esc` 同）                                                                                     |
| hover                                            | 高亮 + 尺寸/标签浮签                                                                                                                     |
| 点击                                             | 拾取该元素并进入确认条（普通流程）                                                                                                       |
| `Shift`+点击                                     | 追加多选，停留在拾取模式                                                                                                                 |
| `Enter`                                          | 从拾取模式进入确认条                                                                                                                     |
| `Backspace`                                      | 撤销最后一个                                                                                                                             |
| `Alt+1~6`                                        | 一键切预设（精简/标准/完整/改对地方/样式/文案）—— 拾取与确认条都能用                                                                     |
| `Ctrl/⌘+Enter`                                   | 直接发送（键盘能把整套流程走完）                                                                                                         |
| `Esc`                                            | 确认条 → 回拾取模式；拾取模式 → 退出（丢弃）                                                                                             |

确认条里每个元素一行：选择器 + 「这个元素的问题」备注框 + ✕ 移除。元素列表上面是一排**预设 chip**
（精简 / 标准 / 完整 / 改对地方 / 样式 / 文案）+ 右边「调整项 ▾」（展开 8 项逐项勾选，与选项页等价，
默认收起）；预设行下面有一条摘要写着「当前发送什么 + 采集深浅」；再往下还有一条整体说明。

## 失败时的兜底

**绝不会出现「点了添加、什么都没发生」**：

| 情况                                           | 行为                                                                                                                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 没打开 pi-web-ui 页面                          | 提示 + **Markdown 复制到剪贴板**，手动粘进输入框                                                                                                               |
| 在 pi-web-ui 页面上点了图标（不小心）          | 不是报错：改成问「要不要把它绑成服务地址」，也提供「在本页拾取元素」                                                                                           |
| background 认页面失败（CSP / 权限 / 奇怪环境） | 浮条会**自己再认一次**（同源 `/api/health` + DOM 兵形）：是 pi-web-ui 就正常问绑定，不是就自己退场并让 worker 补注入拾取器 —— 不会出现「点了图标什么都没发生」 |
| 点了「设为服务地址」但缺授权                   | 浮条提示差哪次授权，并给「打开设置页授权」（那种页面上的点击给不了浏览器要的手势）                                                                             |
| pi-web-ui 版本过旧（无 compose）               | 明确提示升级后刷新页面，同样复制兜底                                                                                                                           |
| 输入框还没就绪                                 | 提示刷新页面后再试，同样复制兜底                                                                                                                               |
| 截屏失败（无 activeTab 等）                    | 只是没有截图，Markdown 照常投递                                                                                                                                |
| 页面注入不了（`chrome://`、商店页）            | 扩展角标 `!` + 悬浮提示写明原因                                                                                                                                |

## AI 操作页面（给模型一个能读写网页的工具）

这是这个扩展的第二件正事：**让对话里的模型直接操作你在浏览器里打开的页面** ——
读它的内容、点按钮、填表单、滚动、跳转，必要时在它里跑一段脚本。

```
你说：“把后台订单页前 10 条的金额读出来，按金额排序”
   → 模型调 browser_page（op: read / click / …）
   → 服务端把它推给浏览器里那个 pi-web-ui 页面
   → 扩展在**你授权过的目标页面**上执行，结果原路回到模型
```

**另一端固定是 pi-web-ui 页面**（模型的动作要从它那里送进扩展），所以不像页面桥那样要配两端 ——
只需授权**被操作的那个页面**。代价：**那个 pi-web-ui 标签页得开着**（与拾取投递同一个取舍）。

### 怎么开通

**入口在 pi-web-ui 顶栏的「浏览器操作」按钮上**（它同时是状态面板）：

- 打开它就能看到「扩展在不在 / 授权了几个页面 / 两个总开关的状态」；
- 里面有一个 **「打开扩展设置页」** 按钮 —— 网页不能自己跳 `chrome-extension://`，所以这一步由扩展代劳；
- 面板里还写着两句可直接照拄的例子。

授权三步：

1. **在目标页面上点一次扩展图标** —— 它就进了候选；拾取模式下的**底部细条**上直接会显示
   本页的授权状态（未授权 / 已授权 / 总开关关着）；
2. 在细条上点 **「让 AI 操作本页…」**（确认条里的同名按钮、或直接在扩展选项页填地址都行）；
3. 在扩展选项页点 **「授权该页面」**（这一步顺带申请那个地址的 host 权限）。

授权完成后回到那个页面，细条会**自己变成「已授权 · 模型可操作本页」**（扩展监听授权表变化，
不用重新点图标、也不用刷新页面）。

也可以随时在选项页**收回授权**（收回后模型立即再也碰不到那一页）。

### 引用一个页面到对话（不用手打网址）

授权之后，让模型操作某个页面不需要在话里写网址 —— 顶栏那个按钮就是入口：

- **只授权了一个页面**：顶栏按钮**直接变成那个页面的标题**，点一下就把「网页引用」放进输入框；
  右侧的 **▾** 才是原来的状态面板（授权管理 / 开关 / 刷新都在里面）。
- **授权了多个页面**：按钮仍是「浏览器操作 · N」，打开面板，每个页面后面都有 **「引用到对话」**，
  可以连着引用多个。
- 引用进输入框的是一个 `🌐 页面标题` 的附件 chip —— 与「引用文件」同一种东西（可删、可多条、
  可与文件附件混搭），**不会自动发送**：你补一句「把前十条读出来」再发。
- 发送时服务端会给模型附一句说明（`<browser-page url title>`）：**这个页面已授权、用 `browser_page`、
  `target=` 这个 origin** —— 模型不必从你的话里猜网址，也不会跑去抓网页。

**模型在页面里动手时，那个页面右下角会闪一条提示**（「AI 正在操作本页 · click #submit」）——
只报信、不拦截、2 秒后淡出，省得你以为页面自己在动。

### 模型能做什么

| 动作     | 参数                                                  | 说明                                                                                  |
| -------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `pages`  | —                                                     | 列出已授权页面（含标题、是否开着）—— 模型先看这一步再干活                             |
| `read`   | `what`: text / html / title / url / query；`selector` | 读页面或某个元素；`query` 返回元素摘要（文本/尺寸/输入框的值）                        |
| `click`  | `selector`、`index?`                                  | 先滚进视口再派发真点击（页面的监听器会收到）                                          |
| `type`   | `selector`、`text`、`clear?`、`submit?`               | 输入（走原生 setter + 补发 input/change，React 受控组件也认）；`submit` 会发回车      |
| `scroll` | `selector?`、`to?{x,y}`、`by?{x,y}`                   | 滚动或把某个元素滚进视野                                                              |
| `goto`   | `url`                                                 | 跳转（先回结果再跳，不让这次调用变成“没响应”）                                        |
| `wait`   | `selector?`、`text?`、`timeoutMs?`                    | 等元素/文案出现（SPA 异步渲染就靠它）                                                 |
| `eval`   | `code`                                                | 在页面里执行一段 JS（**默认关**，见下）                                               |
| `shot`   | `selector?`、`maxEdge?`                               | **截图**（AI 的眼睛）：给整屏或某个元素，长边默认 1280、上限 1568。需要额外授权，见下 |

### 三层开关

| 开关                        | 位置                     | 默认                         |
| --------------------------- | ------------------------ | ---------------------------- |
| 工具 `browser_page`         | pi-web-ui 设置 → 工具    | 开                           |
| 「允许 AI 操作页面」总开关  | 扩展选项页 → AI 操作页面 | 开                           |
| 「允许执行任意 JS（eval）」 | 扩展选项页 → AI 操作页面 | **关**                       |
| 「允许截图（shot）」        | 扩展选项页 → AI 操作页面 | 开（但要先授一次权限，见下） |

`read` / `click` / `type` / `scroll` / `goto` / `wait` 都是「用页面自己会响应的事件做事」；
`eval` 是「把页面交给一段模型写的脚本」——能改数据、能提交表单，所以它默认关，要用得手动打开。

### 截图（AI 的眼睛）与视觉桥

模型默认只能靠 `read` 读 DOM 文本 —— 「这页看起来对不对」这类问题它答不了。`shot` 补上这一环：
整屏或某个元素截一张图，**主模型能识图就直接看图；纯文本模型自动走视觉桥转写**
（与用户粘贴图片同一套逻辑：设置里开着就生效，不需要额外配置）。

两个必须知道的代价：

| 代价           | 说明                                                                                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **要额外授权** | 浏览器的截图 API 只认 `<all_urls>` 或「你点图标那一刻的临时授权」（普通 host 授权不够）。所以打开「允许截图」时会弹一次**「读取您在所有网站上的数据」** —— 不给就保持关闭，模型仍能用 `read`。 |
| **会切标签页** | 截图只能截**当前活动标签页**：扩展会先把目标页切到前台、截完**立刻切回**（失败也切回）。你的焦点会跳一下。                                                                                     |

截图长边默认 1280、上限 1568（JPEG，体积可控）；`selector` 给了就按元素裁剪（元素几乎不在视口里时**不截**，而不是给一张误导人的碎图）。

### 安全模型

- **授权列表是唯一凭据**：没被授权的页面一个字节都不注入，模型也点不到；
- **只在 pi-web-ui 页面上发起**：扩展只认「浏览器里那个已绑服务地址的 pi-web-ui 页面」作为调用方
  （用 `sender.tab.url` 判定），其它页面和外部程序一律拒绝；
- **动作白名单**：白名单共 12 个（上表 9 个 + 宿主侧自用的 `status` / `openOptions` / `metrics`），之外的动作名直接拒（否则页面里一段脚本就能指使扩展干别的）；
- 授权必须在选项页点一次（host 权限要用户手势），所以“把某个页面交给 AI”总是人工决定。

### 失败时会说什么

| 情况                        | 模型看到的                                            |
| --------------------------- | ----------------------------------------------------- |
| 没授权任何页面              | 「还没有授权任何页面给 AI —— 去选项页授权」           |
| 目标页面没打开              | 「页面（http://…）没打开 —— 先把它开在标签页里」      |
| 页面多个且没指定 target     | 「有多个已授权页面 —— 用 target 指定一个」            |
| 选择器没匹上                | 「选择器没匹上：#xxx」（带下一步建议）                |
| `wait` 超时                 | 返回 `found: null` + 花了多久（不报错，模型自己决策） |
| 打开过 eval 但页面 CSP 禁止 | 一句带「换用 read/click/type」建议的错误              |
| 浏览器里没有 pi-web-ui 页面 | 「请先打开 pi-web-ui 页面」（工具超时前就会说）       |

### 已知限制

- **pi-web-ui 页面得开着**（并在那个浏览器里）：模型的动作只能从它送进扩展。
- **桌面版（Electron 外壳）用不了**：桌面窗口里没有 Chrome 扩展运行时，扩展装不上
  （issue #153）—— 请用系统浏览器打开同一个 pi-web-ui 地址（网页版），面板里有直达按钮。
- **`eval` 受目标页面的 CSP 约束**：页面写了不许 `unsafe-eval`（不少生产站）时，eval 用不了 ——
  这是浏览器的规矩，不是 bug（改数据请用 click/type）。
- 桥装在**顶层帧**；跨源 iframe 里的元素拿不到。
- `chrome://`、扩展页、商店页、`file://`（需手动允许）不能授权。
- 页面里的**第三方脚本**也能看到扩展注入的 `window.__piBridge`（与页面桥同一个边界）——
  所以只对你信任的页面授权。

## 页面桥：让两个页面互相读写

拾取是单向的（网页 → pi-web-ui 输入框）。**页面桥**把扩展的另一半能力也打开：两个
**配对过**的页面可以互相调用 —— 跨源、跨标签页、跨窗口都行。

浏览器里只有扩展能做到这件事：跨源 `postMessage` 需要 `window.open` 的返回句柄且对方配合，
`BroadcastChannel` / `localStorage` 只限同源。

```js
// B 页（被调用方）：注册能力
window.__piBridge.on("orders", () => [...document.querySelectorAll(".order")].map((el) => el.textContent));
window.__piBridge.on("highlight", ({ id }) => document.querySelector(`#${id}`)?.scrollIntoView());

// A 页（调用方）：调它
const orders = await window.__piBridge.call({ op: "orders" }); // 唯一对端时不用写 to
await window.__piBridge.call({ to: "https://other.example", op: "highlight", args: { id: "row-3" } });
window.__piBridge.peers; // 我能跟谁说话（数组，仅参考）
```

| 方法                                   | 说明                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------- |
| `on(op, handler)`                      | 注册操作（`op` 是非空短字符串）；返回注销函数。对端调用时执行 `handler` |
| `off(op)`                              | 注销                                                                    |
| `call({ op, args?, to?, timeoutMs? })` | 调对端，resolve 它的返回值；失败 reject 一个带原因的 `Error`            |
| `peers`                                | 当前对端 origin 列表（**仅供参考**，放行与否由扩展后台按配对表判定）    |
| `version` / `self`                     | 协议版本 / 本页 origin                                                  |

**怎么开通**（**地址不用手打**）：

1. 在要配对的两个页面里**各点一次扩展图标**（拾取那一下就行）—— 它们就进了候选；
2. 开发页上的拾取浮条还有个「与另一页配对…」按钮：点一下会把**本页**预填好并直接打开设置页；
3. 在选项页「页面桥」里点一下另一个端点的输入框、在下拉里选它，再点「授权并添加配对」。

默认**关闭**：只有列出来的配对能通，页面不会因为装了扩展就凭空多出一条通道。

> 候选为什么只看「点过图标的页面」：直接列所有标签页要么得加 host 权限（未授权站点读不到 url），
> 要么得加 `tabs` 权限（安装时会提示「读取您的浏览记录」）—— 为一个下拉框多要一份看着很吓人的权限
> 不划算。点图标那一刻本来就有 `activeTab`，url 与标题都可读。

### 契约与限制

| 项         | 规则                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 数据       | 必须能 JSON 序列化（跨源两个 JS 堆隔离，只能传普通数据）。DOM 节点 / 函数 / 循环引用都过不去 |
| 参数体积   | ≤ 256KB；结果 ≤ 512KB（超了报错，不会把 service worker 拖死）                                |
| `op`       | 非空、≤ 64 字符、不含控制字符                                                                |
| 超时       | 默认 5s，最大 30s；超时由**页面侧**自己兜底（Promise 不会悬着）                              |
| 对端没打开 | 报「对端页面没打开 —— 先把它开在一个标签页里」                                               |
| 对端没注册 | 报错里列出**它注册了什么**（省得对着两个页面对照代码）                                       |
| 注入不了   | `chrome://`、扩展页、商店页、`file://`（需手动允许）都不能配对                               |
| iframe     | 桥装在**顶层帧**；跨源 iframe 里的页面各自算一个页面（另有其 origin）                        |

### 安全模型（重要）

- **默认拒绝**：没配对的 origin 一律拒绝，配对表里被停用的也拒绝。
- **只认 sender**：扩展后台判断「你是谁」只用 `sender.tab.url`，**消息体里的任何字段都不作数**
  —— 否则 A 页面可以自称是 B，把 B 的全部数据拿走。
- **授权要用户手势**：加一对配对要在选项页点一下（`chrome.permissions.request` 不认网页上的
  按钮），所以「开一条桥」天然带一次人工确认。
- **`window.__piBridge` 在页面主世界**：被配对页面里的**任何脚本**（含第三方广告/统计）都摸得到它。
  这是 MAIN world 的物理边界，不是实现缺陷 —— 所以**只对你信任的页面开桥**。

失败时一律是一句能看懂的话（「对端没注册…」「还没配对…」「没授权…」），不会出现「点了没反应」。

## 为什么必须装扩展

「在任意网页上点选元素」这件事只能由浏览器内的代码做（要读你打开的那个页面的 DOM、
要能跨站点运行）。可选的替代方案都更差：

- **书签小工具（bookmarklet）**：不用装东西，但会被页面 CSP 挡（`script-src` 不含
  `unsafe-inline` 的站点直接失效），且无法可靠地把结果送进另一个源的 pi-web-ui 页面。
- **纯 DevTools Snippets**：手贴一段代码，每次都要自己找、自己跑，没有 hover 高亮与多选。

所以扩展是唯一干净的做法；代价就是要在**使用它的那台浏览器**里装一次（开发者模式加载即
可，不必上架商店）。

## 已知限制

- **自动化装扩展：Chrome 不行、Edge 行**。Chrome 137 起移除了 `--load-extension`（本机
  Chrome 153 实测 `chrome://extensions` 装不上），所以主力 E2E 走「注入真实 `dist/picker.js`
  - 真 background 模块 + 真 pi-web-ui 页面」的等价路线（`tests/page-picker-test.mjs`）；
    但**实测 Edge（152，headless）仍然接受 `--load-extension`**，于是另有一条**装真扩展**的
    E2E（`tests/page-picker-edge-ext-test.mjs`，没装 Edge 就 SKIP）—— 它跑的是真 `chrome.*`，
    能发现「假 chrome 不校验 match pattern」那类问题（0.2.0 的投递失败就是这么漏掉的）。
    手动「加载已解压的扩展程序」不受影响。
- 截图只截**当前可见区域**（`captureVisibleTab`）；元素几乎全在视口外时不截，而不是截一张误导人的碎图。
- Vue 只有文件没有行号（SFC 行信息要 sourcemap 才能还原）；生产构建没有 `_debugSource`，
  React/Vue 定位会自然降级到「命中的 CSS 位置」。
- 跨域样式表读不到 `cssRules` → 只跳过那张表，不影响其它来源的规则与拾取本身。
- 投递**依赖 pi-web-ui 页面开着**（这是当前架构的取舍：走页面上的 `compose()` 而不是服务端
  API，好处是零服务端改动、天然复用登录态与草稿合并逻辑；代价是页面关着时只能复制兜底）。
  要做成「页面没开也能收到」，得在服务端插件里加一条 HTTP 收件路由 —— 那是另一条路。
