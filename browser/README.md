# Browser module

This module brings the AI Browser project into pi-web-ui without relocating the existing server, web, or desktop directories. The browser can continue to evolve independently of the Agent.

- `contracts.ts`: public state and host API; page request types derive from the existing wire protocol.
- `runtime/`: tab/session/navigation/download lifecycle and explicit credential filling. `runtime/crx.ts` strips the `.crx` signature header, extracts the payload zip (path/size/entry limits, no links) and validates `manifest.json`, because Electron's extension API only loads unpacked directories. `runtime/extension-state.ts` owns the installed/loaded/enabled merge rules and the popup/options path helpers; `runtime/extension-compat.ts` patches our own crx extraction directory with a `chrome.*` shim (see below).
- `storage/`: bookmarks, history, settings, encrypted credentials and legacy data import.
- `automation/`: native page actions and screenshots, without a dependency on the chat UI. `automation/scripts.ts` implements the `script.*` operations (create / update / remove / enable / disable / run) that back the Agent's `browser_script` tool.
- `runtime/scripts.ts`: page-script records and matching (`PageScript`). `persistent` decides whether a script is written to `userData/browser/scripts.json` or lives only in memory for this run; matching accepts host globs, full-URL globs, `re:<regex>` and `*` (empty list = every http(s) page). Scripts are deliberately unlimited in size, count and capability — they run inside the page, so they never reach the host bridge, and the main process never evaluates their code.
- `renderer/`: browser chrome, new tab, management panels and document/media views.
- `preload.cts`: sandbox-compatible capability handshake.

The desktop composition lives in `desktop/browser-host.ts`. It supplies the Agent view, validates callers, and arranges browser/Agent/split layouts. Browser code must not import the Agent runtime or hardcode an Agent server address.

There is one tab state source, `BrowserManager`. UI and automation consume that source. Changing display modes preserves existing views. Browser settings and session data live under the application's `userData/browser` directory.

`BrowserManager.getActiveTabId()` is the single answer to "which tab does the user currently have open". The automation `pages`/`status` listing marks that tab with `active: true` and returns `activeTabId`, but only when the tab is operable: an internal page or the caller's own view is never reported as the page the user is viewing. Automation still needs an explicit `target` while several tabs are open; the ambiguity error names the tab the user is viewing so the caller can pass it.

Native control is available only to the configured Agent service's origin and base path. Browser shell/storage actions are restricted to exact bundled internal pages. All requests are checked again in the main process, including the current main frame and URL. System Chrome users keep the existing extension integration.

Page scripts are injected from the main process: `executeJavaScript` at `dom-ready`, CDP `Page.addScriptToEvaluateOnNewDocument` for `document-start`, `insertCSS` for styles, and `executeJavaScriptInIsolatedWorld` when a script asks for the isolated world. Operations without an explicit target resolve against the user's current tab (`getActiveTabId()`), the same source the `active` flag on `pages` uses, so a default never lands on a background tab. A script runs once per document (the run state resets on `did-start-navigation`, and the page keeps a per-document token map as a second guard), may `return` a cleanup function that runs before re-injection, disablement or removal, and is reported through `script.status` (`injected` / `skipped` / `errors`). Internal pages are never injected, and `allowScripts` is the single kill switch shown in the settings panel.

Extension installs are remembered in `userData/extensions/installed.json` and reloaded on the next start (Electron's `loadExtension` does not persist by itself). Entries are `{ path, enabled }`; the legacy `string[]` form is still read. Disabling unloads the extension with `removeExtension` and keeps the entry with `enabled: false`, so the folder and the extension's storage survive; removing only unloads and forgets the entry, never deleting the directory; reloading unloads first and then goes through the same `loadExtensionDir`. `.crx` installs land in `userData/extensions/crx-<content hash>`, so reinstalling the same file keeps the extension id and its storage. The merge rules for "loaded now" vs "remembered but disabled" live in `runtime/extension-state.ts`, together with `extensionPopupPath` (manifest `action`/`browser_action`/`page_action` → `default_popup`), `extensionOptionsPath` (`options_ui.page` / `options_page`) and `extensionPageUrl` (rejects `..`, absolute paths and schemes, so only an extension's own declared page can be opened).

Extension APIs come in two layers. **`electron-chrome-extensions`** (wired in `desktop/browser-host.ts`) supplies the semantics Electron lacks: `windows / contextMenus / notifications / cookies / webNavigation / permissions / commands`, and real `tabs.create / remove / update`. It owns no windows or tabs — every write goes back through callbacks into `BrowserManager` (`createTab` / `selectTab` / `removeTab` via `BrowserManagerOptions.extensionHooks`) and into `DesktopBrowserHost` (`chrome.windows.create` opens a real `BrowserWindow`, `remove` destroys it but refuses the app window, `permissions.request` asks the user). Page context menus are built from `getContextMenuItems()` inside the `context-menu` event. The toolbar action buttons are the library's `<browser-action-list>`: `desktop/preload.cts` calls `injectBrowserAction()` for `shell.html` only (bundled with esbuild, since a sandboxed preload cannot resolve modules), `shell.ts` creates the element with `BROWSER_EXTENSION_PARTITION`, the main process maps that partition name back to the browser session via `setSessionPartitionResolver`, and `crx://` icons are served by `ElectronChromeExtensions.handleCRXProtocol(session.defaultSession)`. Clicking an icon opens `action.default_popup` or fires `chrome.action.onClicked`, as in Chrome. The library's `PopupView` sizes and reveals that popup from Electron's `preferred-size-changed` event, which `chrome-extension://` pages never emit here (measured: the window stayed at 25×25 and hidden), so the host listens for `browser-action-popup-created`, measures the popup's content with the same helper the panel popup uses, then delegates positioning and showing back to the library (`updatePosition()` / `show()`).

**`runtime/extension-compat.ts`** is the second layer and only fills what the library also leaves out: `tabs.duplicate / move / highlight / discard`, plus `chrome.storage.sync` routed to `storage.local` as a no-library fallback. `tabs.captureVisibleTab` is real: `runtime/extension-bridge.ts` registers a preload that exposes `__piExtensionBridge` only in `chrome-extension:` contexts, and the main process answers it with `WebContents.capturePage()` for the active tab after re-checking that the sender belongs to the browser session (`format: jpeg` + `quality` supported). The library's preload ends with `Object.freeze(chrome)`, so adding a **new top-level namespace** is no longer possible (`fontSettings` included) — only members of existing namespaces can be filled. Missing members now call back `undefined` and log `[pi] chrome.<api> is not implemented` once instead of faking `[]`/`true`. It patches **our own crx extraction directory** after unpacking: writes `__pi-compat.js`, wraps the MV3 service worker behind `__pi-sw.js` (`importScripts` for classic workers, `import` for `type: "module"`), prepends the shim to MV2 `background.scripts` and to every isolated-world `content_scripts` entry (never `world: "MAIN"`), and injects `<script src="/__pi-compat.js">` into the declared popup/options HTML. It never touches a user-picked unpacked folder, is idempotent, keeps `manifest.original.json`, and stamps `__pi-compat.json` with `COMPAT_VERSION` so a restart re-applies a newer shim. `declarativeNetRequest` needed a third piece: Electron stores and returns DNR rules but never intercepts them (measured on Electron 44). `runtime/dnr.ts` therefore reads the static rulesets listed in each loaded extension's manifest (`declarative_net_request.rule_resources`) and compiles them into a single `session.webRequest.onBeforeRequest` decision, with Chrome's host-permission gate, priority rules (highest wins, `allow` wins ties), resource-type/domain conditions, a literal-token prefilter and regex size/backreference limits. Static rules work; dynamic/session rules live in the extension's LevelDB and stay out of reach, as do `redirect` / `modifyHeaders` actions. The shim also fills `windows.getAll({ populate })` from the real `tabs.query`, which the library leaves out.

Panel action popups: the toolbar now renders real extension buttons through the library, but the extensions panel keeps its own entry point — a click on any row (the row body, not just a small icon) opens `chrome-extension://<id>/<default_popup>` in a frameless window on the same session, anchored under that row, closing on blur; the panel closes first so the page comes back. The window is sized to what the popup page itself asks for (Chrome popup semantics: a fixed 400×560 frame leaves wide empty gutters around a narrow popup). The host measures the page's content box before showing it — containers exactly filling the viewport don't count, content taller than the viewport does, and the real scrollbar width is added — clamps to Chrome's 800×600 limit, measures twice (a width change reflows the text) and falls back to 400×560 when the measurement fails (`runtime/extension-popup.ts`). Extensions without a popup fall back to their options page. Browser navigation policy is untouched: `chrome-extension://` never becomes a valid tab URL.

Two install entry points share one code path: the toolbar extensions panel (`extensions.installCrx` with no `path`) and drag-and-drop (internal pages resolve the file path in preload via `webUtils.getPathForFile` and pass `{ path }`; drops landing on web content are caught by `BrowserManager`'s navigation guard and go through `onFileDrop`).

Build with `npm run build:desktop`; start the full application after `npm run build` with `npm run desktop:dev`. The independent renderer interaction check is `node browser/renderer/verify-ui.mjs`. Native desktop regression is `node tests/browser-desktop-smoke.mjs`; it uses isolated temporary data and does not build implicitly.

See [architecture and security boundaries](../docs/architecture-browser.md) and [renderer behavior](renderer/README.md) before changing module boundaries.
